# HashedTimeWheel 原理总结

HashedTimeWheel，也叫 **哈希时间轮**，是一种高性能延迟任务调度算法，常用于：

```text
延迟任务
超时检测
心跳超时
订单超时取消
连接超时关闭
定时器管理
```

典型应用：

```text
Netty HashedWheelTimer
Kafka 延迟操作
定时任务调度
Redisson 延迟队列底层思想
```

---

## 1. 核心思想

时间轮可以理解为一个 **环形数组**。

```text
slot0 -> slot1 -> slot2 -> slot3 -> ... -> slotN
  ↑                                      ↓
  └──────────────────────────────────────┘
```

每个槽位代表一个时间刻度。

例如：

```text
tickDuration = 1 秒
wheelSize = 60
```

表示：

```text
时间轮一共有 60 个槽
每秒移动一个槽
转一圈是 60 秒
```

---

## 2. 基本结构

时间轮核心组成：

| 组件 | 说明 |
|---|---|
| 时间轮数组 | 环形数组，每个元素是一个槽 |
| Slot 槽位 | 存放到期时间相近的任务 |
| Tick | 时间轮每次前进的时间间隔 |
| Worker 线程 | 推动时间轮转动 |
| Round 轮数 | 任务需要等待时间轮转几圈 |
| Task | 延迟任务 |

---

## 3. 任务如何加入时间轮

假设：

```text
tickDuration = 1 秒
wheelSize = 60
当前槽位 = 10
任务延迟 = 75 秒
```

计算：

```text
ticks = 75 / 1 = 75
slotIndex = (当前槽位 + ticks) % wheelSize
          = (10 + 75) % 60
          = 25

round = ticks / wheelSize
      = 75 / 60
      = 1
```

含义：

```text
任务放入 slot25
时间轮转 1 圈后，再到 slot25 时执行
```

---

## 4. 任务执行流程

```text
时间轮启动
  ↓
Worker 线程每隔 tickDuration 推进一个槽位
  ↓
扫描当前槽位中的任务
  ↓
判断任务 round 是否为 0
  ↓
如果 round > 0，round--
  ↓
如果 round = 0，执行任务
```

示例：

```text
当前指针移动到 slot25
  ↓
遍历 slot25 的任务
  ↓
任务 round = 1，先减为 0，不执行
  ↓
下一圈再次到 slot25
  ↓
round = 0，执行任务
```

---

## 5. 为什么叫 HashedTimeWheel

因为任务根据延迟时间计算出槽位下标：

```text
slotIndex = deadline % wheelSize
```

本质上类似 Hash 映射：

```text
不同到期时间的任务
  ↓
通过取模分散到不同槽位
```

所以叫：

```text
Hashed Time Wheel
```

---

## 6. 时间复杂度

普通定时任务如果用优先队列：

```text
插入任务：O(logN)
删除任务：O(logN)
```

时间轮：

```text
插入任务：O(1)
删除任务：O(1) 或接近 O(1)
执行任务：只扫描当前槽位
```

所以时间轮适合大量延迟任务。

---

## 7. 优势

- 插入任务性能高。
- 适合海量延迟任务。
- 时间复杂度低。
- 不需要每次全量扫描任务。
- 比优先队列更适合高并发定时器场景。
- 实现简单，性能稳定。

---

## 8. 劣势

- 时间精度受 `tickDuration` 影响。
- 不是严格实时执行。
- 延迟任务可能有一定误差。
- 单层时间轮处理超长延迟任务时，需要 round 计数。
- 如果某个槽位任务太多，执行时可能造成抖动。
- 内存任务重启后会丢失，需要配合持久化。

---

## 9. 时间精度问题

如果：

```text
tickDuration = 1 秒
```

那么任务最小调度精度就是 1 秒。

例如：

```text
任务延迟 1500ms
```

可能会在：

```text
1 秒 ~ 2 秒附近执行
```

所以时间轮适合：

```text
允许一定时间误差的延迟任务
```

不适合：

```text
强实时、高精度定时任务
```

---

## 10. 单层时间轮和多层时间轮

### 单层时间轮

```text
一个环形数组 + round 轮数
```

优点：

```text
实现简单
```

缺点：

```text
超长延迟任务依赖 round 计数
槽位任务可能较多
```

---

### 多层时间轮

类似钟表：

```text
毫秒轮
秒轮
分钟轮
小时轮
```

任务先放到高层时间轮，到期后再降级到低层时间轮。

优点：

```text
更适合超长延迟任务
减少单个槽位压力
```

缺点：

```text
实现更复杂
```

---

## 12. 和 DelayQueue 对比

| 对比项 | HashedTimeWheel | DelayQueue |
|---|---|---|
| 数据结构 | 环形数组 | 优先队列 |
| 插入复杂度 | O(1) | O(logN) |
| 时间精度 | 较低，受 tick 影响 | 较高 |
| 海量任务性能 | 更好 | 一般 |
| 实现复杂度 | 中等 | 简单 |
| 适合场景 | 大量延迟任务 | 中小规模延迟任务 |

---

## 13. 和定时任务扫描对比

| 对比项 | 时间轮 | 定时任务扫描 |
|---|---|---|
| 性能 | 高 | 数据量大时差 |
| 实时性 | 较好 | 取决于扫描间隔 |
| 数据库压力 | 小 | 大 |
| 实现复杂度 | 中等 | 简单 |
| 适合场景 | 大量延迟任务 | 简单低频任务 |

---

## 14. 总结

HashedTimeWheel 是一种高性能延迟任务调度算法，底层可以理解为一个环形数组，每个槽位代表一个时间刻度，任务根据延迟时间计算出应该放入哪个槽位。

时间轮每隔固定时间 `tickDuration` 向前移动一格，移动到某个槽位后扫描该槽位上的任务。如果任务的剩余轮数 `round` 大于 0，就先减一；如果等于 0，说明任务到期，可以执行。

时间轮的优点是插入任务复杂度接近 `O(1)`，非常适合大量延迟任务和超时检测场景。缺点是执行时间不是绝对精确，精度受 tick 时间影响，而且内存型时间轮在服务重启后任务会丢失，需要结合持久化机制。

一句话总结：

```text
HashedTimeWheel = 环形数组 + 时间指针 + 槽位任务链表 + round 轮数；
优势是高性能处理大量延迟任务，缺点是时间精度有限。
```
