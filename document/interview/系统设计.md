# 一、如何设计一个秒杀系统

## 1. 秒杀系统的核心特点

秒杀系统的特点是：

```text
瞬时流量高
读多写少
库存有限
并发冲突严重
用户请求集中
业务链路必须短
系统必须防刷、防超卖、防重复下单
```

---

## 2. 秒杀系统的核心目标

设计秒杀系统时，核心目标是：

```text
1. 高并发抗压
2. 防止库存超卖
3. 防止重复下单
4. 快速响应用户
5. 保护数据库
6. 保证最终一致性
7. 支持限流、降级、熔断
8. 支持监控和异常补偿
```

---

## 3. 秒杀整体架构

```text
用户
 |
 v
前端静态页面 / CDN
 |
 v
网关 Gateway
 |
 | 限流、鉴权、防刷
 v
秒杀服务 Seckill Service
 |
 | Redis 预扣库存、幂等校验
 v
MQ 消息队列
 |
 | 异步削峰
 v
订单服务 / 库存服务
 |
 v
MySQL
```

---

## 4. 秒杀核心流程

```text
1. 活动开始前，将秒杀商品和库存预热到 Redis
2. 用户请求进入网关
3. 网关进行限流、防刷、鉴权
4. 秒杀服务校验活动状态、用户资格、购买限制
5. Redis 原子扣减库存
6. 判断用户是否重复下单
7. 秒杀成功请求写入 MQ
8. 订单服务异步消费消息创建订单
9. 用户轮询或查询秒杀结果
10. 失败或超时任务进行补偿
```

---

## 5. 库存预热

活动开始前，把库存加载到 Redis：

```bash
SET seckill:stock:sku:1001 1000
```

这样秒杀时不直接访问数据库库存。

---

## 6. Redis 原子扣减库存

可以使用 Lua 脚本保证库存校验和扣减原子性。

```lua
local stockKey = KEYS[1]
local userKey = KEYS[2]

local stock = tonumber(redis.call('get', stockKey))

if stock == nil or stock <= 0 then
    return -1
end

if redis.call('exists', userKey) == 1 then
    return -2
end

redis.call('decr', stockKey)
redis.call('set', userKey, 1)
redis.call('expire', userKey, 86400)

return 1
```

返回值含义：

```text
1：秒杀资格成功
-1：库存不足
-2：重复秒杀
```

---

## 7. 防止超卖

防止超卖需要多层保障：

```text
1. Redis 原子扣减库存
2. MQ 削峰，异步创建订单
3. 数据库库存扣减时加条件 stock >= num
4. 数据库唯一索引兜底
5. 异常补偿库存
```

数据库扣库存 SQL：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE sku_id = ?
  AND stock >= 1;
```

如果更新行数为 0，说明库存不足。

---

## 8. 防止重复下单

可以从多个层面做：

```text
1. Redis 记录用户秒杀标记
2. 数据库唯一索引
3. MQ 消费幂等
4. 订单状态校验
```

唯一索引示例：

```sql
UNIQUE KEY uk_user_sku_activity(user_id, sku_id, activity_id)
```

---

## 9. MQ 削峰

秒杀接口不要同步创建订单。

应该先快速完成：

```text
资格校验
库存预扣
发送 MQ
返回排队中
```

订单创建异步完成。

这样可以避免数据库被瞬时流量打爆。

---

## 10. 秒杀结果查询

秒杀接口返回：

```json
{
  "code": 0,
  "msg": "排队中",
  "requestId": "xxx"
}
```

用户再通过接口查询结果：

```text
GET /seckill/result?requestId=xxx
```

结果可能是：

```text
排队中
秒杀成功
秒杀失败
库存不足
重复下单
```

---

## 11. 防刷设计

常见防刷措施：

```text
1. 登录校验
2. 验证码
3. 图形验证码
4. 滑块验证
5. IP 限流
6. 用户维度限流
7. 设备指纹
8. 黑名单
9. 接口地址动态化
10. 秒杀 token
```

---

## 12. 页面静态化和 CDN

秒杀商品详情页可以静态化：

```text
商品信息
活动时间
秒杀价格
库存展示
```

静态资源放 CDN，减少应用服务器压力。

---

## 13. 秒杀系统注意事项

```text
1. 秒杀链路要短
2. 数据库不能直接抗秒杀流量
3. 库存必须原子扣减
4. MQ 消息必须可靠
5. 消费端必须幂等
6. 异常必须补偿
7. 热点 key 要防止 Redis 压力过大
8. 限流和降级必须提前设计
```

---

## 14. 面试回答

设计秒杀系统时，我会把核心思路放在削峰、限流、缓存、异步和一致性上。

活动开始前先把商品和库存预热到 Redis，用户请求先进网关做限流、防刷和鉴权。秒杀服务只做活动校验、用户资格校验、Redis 原子扣减库存和重复下单判断，成功后写入 MQ，立即返回排队中。订单服务异步消费 MQ 创建订单，用户通过查询接口获取秒杀结果。

防止超卖方面，Redis 使用 Lua 脚本保证库存判断和扣减原子性，数据库扣减库存时使用 `stock >= num` 条件兜底。防重复下单方面，Redis 记录用户秒杀标记，数据库建立用户、商品、活动维度的唯一索引，消费端也要做幂等。系统还需要配合限流、降级、监控、死信队列和定时补偿。

# 二、如何设计一个短链接系统

## 1. 短链接系统是什么？

短链接系统是把长 URL 转换成短 URL。

例如：

```text
长链接：
https://www.example.com/product/detail?id=1001&utm_source=xxx

短链接：
https://s.xx/aB12Cd
```

访问短链接时，系统根据短码找到原始长链接，并重定向过去。

---

## 2. 核心功能

短链接系统核心功能包括：

```text
1. 长链接生成短链接
2. 短链接访问跳转
3. 短码唯一
4. 访问统计
5. 过期时间控制
6. 防恶意链接
7. 高并发访问
```

---

## 3. 整体架构

```text
用户创建短链接
        |
        v
短链服务
        |
        | 生成短码
        v
MySQL 存储长短链接映射
        |
        v
Redis 缓存热点短链

用户访问短链接
        |
        v
短链跳转服务
        |
        v
Redis 查询短码
        |
        | 未命中
        v
MySQL 查询
        |
        v
302 重定向到长链接
```

---

## 4. 数据库表设计

```sql
CREATE TABLE short_url (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    short_code VARCHAR(32) NOT NULL,
    long_url TEXT NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    expire_time DATETIME DEFAULT NULL,
    create_time DATETIME NOT NULL,
    update_time DATETIME NOT NULL,
    UNIQUE KEY uk_short_code(short_code)
);
```

---

## 5. 短码生成方案

常见短码生成方案：

```text
1. 自增 ID + Base62 编码
2. 长链接 Hash 后取部分字符
3. 雪花算法 ID + Base62
4. 号段模式
5. 随机字符串 + 唯一索引冲突重试
```

---

## 6. Base62 编码

Base62 使用字符：

```text
0-9
a-z
A-Z
```

共 62 个字符。

把数字 ID 转成 Base62，可以生成较短字符串。

例如：

```text
100000 -> q0U
```

---

## 7. 推荐方案：ID + Base62

流程：

```text
1. 插入数据库获得自增 ID
2. 将 ID 转成 Base62
3. 得到 shortCode
4. 更新数据库 shortCode
```

优点：

```text
短码唯一
长度较短
实现简单
冲突概率低
```

缺点：

```text
自增 ID 可能暴露业务增长趋势
```

可以通过：

```text
发号器
雪花算法
ID 混淆
随机盐
```

优化。

---

## 8. 访问跳转流程

```text
1. 用户访问 https://s.xx/aB12Cd
2. 系统解析 shortCode = aB12Cd
3. 先查 Redis
4. Redis 命中，直接获取 longUrl
5. Redis 未命中，查 MySQL
6. 判断是否存在、是否过期、是否禁用
7. 写入 Redis
8. 返回 302 重定向
```

---

## 9. 为什么用 302 重定向？

短链接跳转常用：

```text
302 临时重定向
```

原因：

```text
302 每次访问都会请求短链服务，方便统计访问数据。
```

如果使用 301 永久重定向，浏览器可能缓存跳转结果，后续不再请求短链服务，不利于统计和动态控制。

---

## 10. 缓存设计

Redis 缓存：

```text
key: short:url:{shortCode}
value: longUrl
TTL: 根据过期时间设置
```

示例：

```bash
SET short:url:aB12Cd "https://example.com/xxx" EX 86400
```

---

## 11. 缓存穿透处理

如果用户访问不存在的短码，不能每次都查数据库。

解决方案：

```text
1. 缓存空值
2. 布隆过滤器
3. 参数校验
4. 限流
```

空值缓存：

```bash
SET short:url:notfound:aB12Cd "NULL" EX 60
```

---

## 12. 访问统计

可以统计：

```text
PV
UV
IP
User-Agent
Referer
地区
设备类型
访问时间
```

为了不影响跳转性能，可以异步写 MQ：

```text
访问短链
  |
  v
快速 302 跳转
  |
  v
异步发送访问日志到 MQ
  |
  v
统计服务消费并分析
```

---

## 13. 安全设计

```text
1. 长链接黑名单
2. 域名白名单
3. 反垃圾检测
4. 防钓鱼
5. 创建频率限制
6. 访问频率限制
7. 管理后台审核
```

---

## 14. 面试回答

短链接系统核心是长链接到短码的映射，以及短码访问时的快速跳转。

生成短码可以使用自增 ID 或雪花 ID 做 Base62 编码，保证短码唯一且长度较短。数据库中保存 shortCode 和 longUrl 的映射，并对 shortCode 建唯一索引。访问短链接时，系统先查 Redis，未命中再查 MySQL，找到长链接后返回 302 重定向。

为了提高性能，热点短链要缓存到 Redis；为了防止缓存穿透，可以缓存空值或使用布隆过滤器；访问统计不要同步阻塞跳转流程，可以通过 MQ 异步处理。安全上要做域名黑名单、创建频率限制和访问限流。

# 三、如何设计一个订单超时关闭功能

## 1. 业务场景

用户创建订单后，如果在指定时间内没有支付，需要自动关闭订单并释放相关资源。

例如：

```text
订单 30 分钟未支付自动关闭
释放库存
退回优惠券
关闭支付单
发送通知
```

---

## 2. 核心要求

```text
1. 订单到期自动关闭
2. 不能误关已支付订单
3. 释放库存和优惠券
4. 支持高可靠
5. 支持幂等
6. 支持异常补偿
7. 支持可观测和告警
```

---

## 3. 实现方案

常见实现方式：

```text
1. 延迟队列
2. RocketMQ 延迟消息
3. Redis ZSet
4. 数据库定时扫描
5. 时间轮
```

---

## 4. 推荐方案：延迟消息 + 定时补偿

整体方案：

```text
1. 创建订单
2. 发送一条 30 分钟后的延迟消息
3. 延迟消息到期后消费
4. 查询订单状态
5. 如果未支付，则关闭订单
6. 释放库存、优惠券
7. 如果已支付，则忽略
8. 定时任务扫描异常订单兜底
```

---

## 5. 流程图

```text
用户下单
  |
  v
创建待支付订单
  |
  v
发送订单超时关闭延迟消息
  |
  v
30 分钟后消费消息
  |
  v
查询订单状态
  |
  |-- 已支付：不处理
  |
  |-- 待支付：关闭订单
                  |
                  v
              释放库存
                  |
                  v
              退回优惠券
```

---

## 6. 订单状态设计

订单状态可以设计为：

```text
WAIT_PAY：待支付
PAID：已支付
CLOSED：已关闭
CANCELLED：已取消
REFUNDED：已退款
FINISHED：已完成
```

状态流转：

```text
WAIT_PAY -> PAID
WAIT_PAY -> CLOSED
PAID -> FINISHED
PAID -> REFUNDED
```

---

## 7. 关闭订单 SQL

必须使用状态条件，防止误关已支付订单：

```sql
UPDATE orders
SET status = 'CLOSED',
    close_time = NOW()
WHERE order_id = ?
  AND status = 'WAIT_PAY';
```

如果更新行数为 1，说明关闭成功。

如果更新行数为 0，说明订单可能已经支付或已关闭。

---

## 8. 幂等设计

订单关闭消息可能重复消费，所以关闭逻辑必须幂等。

幂等手段：

```text
1. 状态机控制
2. SQL 加 status = WAIT_PAY 条件
3. 消费记录表
4. 库存释放记录
5. 优惠券回滚记录
```

---

## 9. 库存释放

关闭订单后释放库存：

```sql
UPDATE product_stock
SET stock = stock + #{num}
WHERE sku_id = #{skuId};
```

为了防止重复释放，可以记录库存流水：

```sql
UNIQUE KEY uk_order_sku(order_id, sku_id, type)
```

---

## 10. 优惠券退回

如果订单使用了优惠券，订单关闭后需要恢复优惠券状态：

```sql
UPDATE user_coupon
SET status = 'UNUSED'
WHERE coupon_id = ?
  AND order_id = ?
  AND status = 'LOCKED';
```

---

## 11. 为什么还要定时补偿？

延迟消息可能出现极端异常：

```text
消息发送失败
消息消费失败
消费者宕机
MQ 故障
代码异常
```

因此需要定时任务兜底：

```sql
SELECT *
FROM orders
WHERE status = 'WAIT_PAY'
  AND create_time < NOW() - INTERVAL 30 MINUTE
LIMIT 100;
```

扫描到后执行关闭逻辑。

---

## 12. 方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| 延迟消息 | 实时性较好，适合业务 | 依赖 MQ |
| Redis ZSet | 灵活，实现简单 | 可靠性要自己保证 |
| 数据库扫描 | 简单可靠 | 实时性差，扫描压力大 |
| 时间轮 | 性能高 | 实现复杂 |
| 延迟消息 + 定时补偿 | 可靠性较好 | 系统复杂度略高 |

---

## 13. 面试回答

订单超时关闭可以使用延迟消息实现。用户创建订单后，订单状态为待支付，同时发送一条 30 分钟后的延迟消息。消息到期后，消费者查询订单状态，如果订单仍然是待支付，就执行关闭订单、释放库存、退回优惠券等操作；如果订单已经支付，则直接忽略。

为了防止误关订单，关闭 SQL 必须带状态条件，例如 `WHERE order_id = ? AND status = 'WAIT_PAY'`。为了防止重复释放库存和优惠券，关闭逻辑要做幂等。考虑到延迟消息可能失败，还需要定时任务扫描超时未支付订单做兜底补偿。

---

# 四、如何设计一个接口限流方案

## 1. 为什么需要限流？

限流用于保护系统。

当请求量超过系统承载能力时，如果不做限制，可能导致：

```text
CPU 飙高
线程池打满
数据库连接池耗尽
Redis 压力过大
接口大量超时
系统雪崩
```

---

## 2. 限流维度

常见限流维度：

```text
1. IP
2. 用户 ID
3. 接口 URL
4. AppId
5. 租户 ID
6. 设备 ID
7. API Key
8. 商品 ID / 热点参数
```

---

## 3. 限流位置

限流可以放在：

```text
1. Nginx
2. API Gateway
3. 应用服务
4. Sentinel
5. Redis 分布式限流
6. 服务内部线程池
```

推荐分层限流：

```text
网关层挡大流量
服务层保护核心资源
热点参数层保护特殊业务点
```

---

## 4. 常见限流算法

```text
1. 固定窗口
2. 滑动窗口
3. 漏桶算法
4. 令牌桶算法
```

---

## 5. 固定窗口

例如：

```text
每分钟最多 100 次请求。
```

优点：

```text
实现简单。
```

缺点：

```text
窗口边界可能出现流量突刺。
```

---

## 6. 滑动窗口

统计最近一段时间内的请求数量。

例如：

```text
最近 60 秒最多请求 100 次。
```

比固定窗口更平滑。

---

## 7. 漏桶算法

特点：

```text
请求进入桶
桶按固定速度流出
桶满后拒绝请求
```

适合平滑流量。

---

## 8. 令牌桶算法

特点：

```text
系统按固定速率生成令牌
请求拿到令牌才能通过
桶中可积累令牌
允许一定突发流量
```

适合大多数接口限流场景。

---

## 9. Redis + Lua 分布式限流

以固定窗口为例：

```lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local expire = tonumber(ARGV[2])

local current = tonumber(redis.call('get', key) or "0")

if current + 1 > limit then
    return 0
else
    redis.call('incr', key)
    redis.call('expire', key, expire)
    return 1
end
```

key 示例：

```text
limit:user:1001:/order/create
limit:ip:192.168.1.1:/login
```

---

## 10. Sentinel 限流

使用 Sentinel 可以做：

```text
1. QPS 限流
2. 并发线程数限流
3. 热点参数限流
4. 系统自适应保护
5. 熔断降级
```

示例：

```java
@SentinelResource(value = "createOrder", blockHandler = "blockHandler")
public Result createOrder(CreateOrderRequest request) {
    return orderService.createOrder(request);
}

public Result blockHandler(CreateOrderRequest request, BlockException e) {
    return Result.fail("当前请求过多，请稍后再试");
}
```

---

## 11. 限流后的处理

限流后可以：

```text
1. 返回友好提示
2. 返回默认值
3. 进入排队队列
4. 降级处理
5. 引导用户稍后重试
```

不要直接返回系统异常。

---

## 12. 面试回答

接口限流方案可以分层设计。网关层按照 IP、用户、接口、租户等维度做统一限流，服务层对核心接口做更细粒度限流，例如下单、支付、优惠券领取。对于分布式场景，可以使用 Redis + Lua 实现原子计数，也可以使用 Sentinel 做 QPS、线程数和热点参数限流。

限流算法常见有固定窗口、滑动窗口、漏桶和令牌桶。固定窗口简单但有边界突刺问题；滑动窗口更平滑；漏桶适合平滑流量；令牌桶允许一定突发流量，生产中比较常用。限流后要返回友好提示或降级结果，避免系统被打垮。

---

# 五、如何设计一个日志脱敏系统

## 1. 为什么需要日志脱敏？

日志中可能包含敏感信息：

```text
手机号
身份证号
银行卡号
邮箱
姓名
地址
密码
Token
Cookie
密钥
```

如果不脱敏，可能导致：

```text
隐私泄露
安全风险
合规风险
日志平台泄露风险
```

---

## 2. 脱敏目标

日志脱敏系统需要做到：

```text
1. 对敏感字段统一脱敏
2. 尽量减少业务代码侵入
3. 支持多种脱敏规则
4. 支持配置动态刷新
5. 支持请求日志、响应日志、异常日志
6. 不影响接口性能
7. 规则可维护、可扩展
```

---

## 3. 常见脱敏方式

```text
1. 工具类手动脱敏
2. 注解脱敏
3. AOP 日志切面脱敏
4. Jackson 序列化脱敏
5. Logback 日志输出脱敏
6. 日志采集链路脱敏
7. 配置中心动态规则脱敏
```

---

## 4. 推荐架构

```text
业务请求
  |
  v
Controller
  |
  v
日志 AOP 切面
  |
  | 读取脱敏配置
  | 识别敏感字段
  | 执行脱敏策略
  v
输出安全日志
  |
  v
日志平台
```

---

## 5. 脱敏规则设计

规则可以配置在 Nacos：

```yaml
log:
  desensitize:
    enabled: true
    fields:
      phone: MOBILE
      mobile: MOBILE
      idCard: ID_CARD
      bankCard: BANK_CARD
      email: EMAIL
      address: ADDRESS
      token: TOKEN
```

---

## 6. 脱敏策略

| 类型 | 示例 | 脱敏后 |
|---|---|---|
| 手机号 | `13800138000` | `138****8000` |
| 身份证 | `110101199001011234` | `110101********1234` |
| 银行卡 | `6222020202021234` | `6222 **** **** 1234` |
| 邮箱 | `abc@example.com` | `a***@example.com` |
| 姓名 | `张三` | `张*` |
| Token | `eyJhbGciOi...` | `eyJ***` |

---

## 7. 注解方式

定义注解：

```java
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Desensitize {
    DesensitizeType type();
}
```

使用：

```java
public class UserDTO {

    @Desensitize(type = DesensitizeType.MOBILE)
    private String phone;

    @Desensitize(type = DesensitizeType.ID_CARD)
    private String idCard;
}
```

---

## 8. AOP 统一处理

在日志切面中处理：

```text
1. 拦截请求参数
2. 拦截响应结果
3. 转成 JSON
4. 根据字段名或注解识别敏感字段
5. 执行对应脱敏策略
6. 输出日志
```

---

## 9. Logback 层脱敏

也可以在日志输出层统一替换敏感信息。

适合兜底处理：

```text
手机号正则
身份证正则
银行卡正则
邮箱正则
```

缺点：

```text
正则过多可能影响性能；
复杂对象语义识别不如字段级脱敏准确。
```

---

## 10. 注意事项

```text
1. 密码绝对不能打印
2. Token、Cookie、密钥不能完整打印
3. 请求参数和响应结果都要处理
4. 异常堆栈中也可能有敏感信息
5. 脱敏规则要统一管理
6. 日志平台访问权限也要控制
7. 脱敏逻辑不能明显影响性能
```

---

## 11. 面试回答

日志脱敏系统可以通过 AOP + 注解 + 配置中心实现。我们在统一日志切面中拦截接口请求参数和响应结果，在打印日志前先对敏感字段脱敏。敏感字段可以通过字段名匹配，也可以通过自定义注解标记，例如手机号、身份证、银行卡、邮箱、地址和 Token。

脱敏规则可以放在配置中心，支持动态刷新。对于密码、密钥这类高敏字段，原则上禁止打印。为了兜底，还可以在 Logback 输出层增加正则脱敏，但要注意性能开销。这样可以减少业务代码侵入，同时保证日志安全。

---

# 六、如何设计一个配置中心动态刷新方案

## 1. 配置中心解决什么问题？

配置中心用于统一管理应用配置。

例如：

```text
数据库配置
Redis 配置
线程池参数
限流规则
业务开关
日志级别
脱敏规则
灰度规则
```

---

## 2. 动态刷新目标

配置动态刷新要求：

```text
1. 配置修改后应用无需重启
2. 客户端能及时感知配置变化
3. 本地配置能自动更新
4. 业务 Bean 能读取到新配置
5. 支持回滚
6. 支持灰度发布
7. 支持权限和审计
```

---

## 3. 整体架构

```text
配置管理后台
        |
        v
配置中心 Server
        |
        | 长轮询 / 长连接 / 推送
        v
配置中心 Client
        |
        v
更新本地缓存
        |
        v
刷新 Spring Environment
        |
        v
发布配置变更事件
        |
        v
刷新业务 Bean
```

---

## 4. 配置定位模型

可以使用：

```text
Namespace + Group + DataId
```

例如：

```text
Namespace：prod
Group：ORDER_GROUP
DataId：order-service.yaml
```

---

## 5. 启动加载流程

```text
1. 应用启动
2. 读取配置中心地址
3. 根据 Namespace、Group、DataId 拉取配置
4. 加载到 Spring Environment
5. 绑定到 @ConfigurationProperties
6. 应用启动完成
```

---

## 6. 动态刷新流程

```text
1. 配置中心配置发生变化
2. 服务端通知客户端
3. 客户端拉取最新配置
4. 更新本地快照
5. 更新 Spring Environment
6. 发布 EnvironmentChangeEvent
7. 刷新 @RefreshScope 或 @ConfigurationProperties Bean
8. 业务读取到最新配置
```

---

## 7. 使用 @ConfigurationProperties

推荐把一组配置绑定成对象：

```java
@Component
@ConfigurationProperties(prefix = "limit")
public class LimitProperties {

    private Integer qps;

    private Boolean enabled;

    public Integer getQps() {
        return qps;
    }

    public void setQps(Integer qps) {
        this.qps = qps;
    }

    public Boolean getEnabled() {
        return enabled;
    }

    public void setEnabled(Boolean enabled) {
        this.enabled = enabled;
    }
}
```

---

## 8. 使用 @RefreshScope

对于 `@Value` 注入字段，可以配合：

```java
@RefreshScope
@RestController
public class DemoController {

    @Value("${demo.name}")
    private String name;
}
```

---

## 9. 本地缓存和容灾

客户端应保存本地快照：

```text
1. 配置中心不可用时可以使用本地快照启动
2. 配置拉取失败时使用旧配置
3. 防止配置中心故障影响业务
```

---

## 10. 配置变更安全

配置中心需要支持：

```text
1. 权限控制
2. 配置版本管理
3. 变更审计
4. 配置回滚
5. 灰度发布
6. 配置格式校验
7. 敏感配置加密
```

---

## 11. 哪些配置不适合动态刷新？

```text
数据库连接地址
服务端口
核心中间件连接配置
启动阶段初始化配置
强依赖 Bean 构造参数
```

这类配置变更通常需要重启服务更安全。

---

## 12. 面试回答

配置中心动态刷新可以通过客户端监听机制实现。应用启动时先从配置中心拉取配置，并加载到 Spring Environment 中。运行过程中，客户端通过长轮询、长连接或推送机制监听配置变化。配置变更后，客户端拉取最新配置，更新本地缓存和 Environment，然后发布配置变更事件，让 `@ConfigurationProperties` 或 `@RefreshScope` 管理的 Bean 刷新。

为了保证稳定性，客户端要有本地快照，配置中心不可用时可以使用旧配置。配置中心本身需要支持权限控制、版本管理、审计、回滚和灰度发布。不是所有配置都适合动态刷新，像数据库连接、服务端口这类启动阶段配置通常不建议运行时刷新。

# 七、如何保证分布式系统数据一致性

## 1. 分布式一致性问题来源

分布式系统中，一个业务操作可能涉及多个服务和多个数据库。

例如下单：

```text
订单服务创建订单
库存服务扣库存
优惠券服务核销优惠券
支付服务创建支付单
```

只要中间某一步失败，就可能产生数据不一致。

---

## 2. 一致性分类

```text
1. 强一致性
2. 最终一致性
3. 弱一致性
```

大多数互联网业务采用：

```text
最终一致性
```

---

## 3. 常见解决方案

```text
1. 本地事务
2. 分布式事务 2PC
3. TCC
4. Saga
5. MQ 最终一致性
6. 本地消息表
7. 事务消息
8. 最大努力通知
9. 定时补偿
10. 对账机制
```

---

## 4. 本地事务

单服务单库场景使用本地事务：

```java
@Transactional(rollbackFor = Exception.class)
public void createOrder() {
    // 创建订单
    // 创建订单明细
}
```

---

## 5. MQ 最终一致性

流程：

```text
1. A 服务完成本地事务
2. A 服务发送消息
3. B 服务消费消息执行本地事务
4. 消费失败则重试
5. 多次失败进入死信队列
6. 定时补偿兜底
```

适合：

```text
下单后发积分
订单创建后通知
库存异步扣减
优惠券异步核销
```

---

## 6. 本地消息表

流程：

```text
1. 执行业务操作
2. 插入本地消息表
3. 本地事务提交
4. 后台任务扫描消息表
5. 发送 MQ
6. 发送成功更新状态
7. 发送失败继续重试
```

优点：

```text
业务操作和消息记录在同一个数据库事务中。
```

---

## 7. 事务消息

以 RocketMQ 为例：

```text
1. 发送半消息
2. 执行本地事务
3. 本地事务成功，提交消息
4. 本地事务失败，回滚消息
5. Broker 不确定时回查事务状态
```

---

## 8. TCC

TCC 分为：

```text
Try
Confirm
Cancel
```

示例：

```text
Try：冻结库存
Confirm：真正扣减库存
Cancel：释放冻结库存
```

适合：

```text
对一致性要求高
业务可以拆成 Try/Confirm/Cancel
```

缺点：

```text
业务侵入性强
实现复杂
```

---

## 9. Saga

Saga 把一个长事务拆成多个本地事务。

每个本地事务都有对应补偿操作。

例如：

```text
创建订单 -> 扣库存 -> 扣优惠券
```

如果扣优惠券失败：

```text
补偿扣库存 -> 取消订单
```

---

## 10. 定时补偿和对账

极端异常靠补偿兜底：

```text
订单已支付但状态未更新
库存已扣但订单失败
优惠券已锁定但订单关闭
消息长时间未发送
```

通过定时任务扫描和对账修复。

---

## 11. 面试回答

分布式系统数据一致性要根据业务场景选择方案。单服务单库使用本地事务。跨服务场景如果要求强一致，可以考虑 TCC 或分布式事务，但实现复杂、性能开销高。大多数互联网业务会选择最终一致性。

最终一致性通常通过 MQ、本地消息表、事务消息、消费重试、消费幂等、死信队列、定时补偿和对账机制实现。比如订单服务创建订单后，通过本地消息表或事务消息保证消息可靠发送，库存服务消费消息扣减库存，消费失败自动重试，重复消费通过幂等控制，极端异常通过补偿任务修复。

---

# 八、如何避免重复提交

## 1. 重复提交产生原因

重复提交常见原因：

```text
1. 用户重复点击按钮
2. 浏览器刷新
3. 前端超时重试
4. 网关重试
5. 网络抖动
6. MQ 重复投递
7. 第三方回调多次通知
```

---

## 2. 解决方案

```text
1. 前端按钮置灰
2. 防抖节流
3. 提交 token
4. Redis SET NX
5. 分布式锁
6. 数据库唯一索引
7. 状态机控制
8. 幂等表
```

---

## 3. 前端防重复

用户点击提交后：

```text
按钮置灰
显示 loading
请求完成前禁止再次点击
```

注意：

```text
前端只能提升体验，不能作为最终保障。
```

---

## 4. Token 机制

流程：

```text
1. 用户进入表单页
2. 服务端生成 token
3. token 存 Redis
4. 前端提交时携带 token
5. 服务端用 Lua 脚本校验并删除 token
6. 删除成功才处理请求
7. 删除失败说明重复提交
```

---

## 5. Redis SET NX

```bash
SET submit:order:requestId 1 NX EX 300
```

设置成功：

```text
第一次提交
```

设置失败：

```text
重复提交
```

---

## 6. 数据库唯一索引兜底

例如：

```sql
UNIQUE KEY uk_request_id(request_id)
UNIQUE KEY uk_order_no(order_no)
```

即使应用层漏掉，数据库也能防止重复数据。

---

## 7. 状态机控制

例如支付回调：

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_no = ?
  AND status = 'WAIT_PAY';
```

重复回调时，状态已经不是 `WAIT_PAY`，不会重复处理。

---

## 8. 面试回答

避免重复提交要前后端一起做，但最终以后端为准。前端可以做按钮置灰、防抖节流，减少重复点击。后端可以使用 token 机制，用户提交前先获取 token，提交时携带 token，服务端用 Redis Lua 脚本校验并删除，保证 token 只能使用一次。

对于有业务唯一性的请求，可以使用 Redis `SET NX` 或数据库唯一索引兜底。对于支付回调、订单状态变更这类场景，要使用状态机控制，保证重复请求不会重复执行业务逻辑。

---

# 九、如何设计幂等接口

## 1. 幂等接口是什么？

幂等接口是指：

```text
同一个请求执行一次和执行多次，最终结果一致。
```

例如：

```text
支付回调重复通知
订单取消重复请求
MQ 消息重复消费
接口超时重试
```

都要求接口幂等。

---

## 2. 哪些接口需要幂等？

```text
下单接口
支付接口
退款接口
支付回调
库存扣减
优惠券核销
订单取消
MQ 消费接口
第三方回调接口
```

---

## 3. 幂等设计核心

幂等设计核心是：

```text
识别同一个请求
判断是否已处理
已处理则直接返回结果
未处理才执行业务
```

---

## 4. 幂等 Key 设计

幂等 Key 可以是：

```text
requestId
orderNo
payNo
refundNo
messageId
业务唯一单号
用户ID + 商品ID + 活动ID
```

---

## 5. 幂等方案

```text
1. Token 机制
2. requestId 去重
3. Redis SET NX
4. 数据库唯一索引
5. 幂等记录表
6. 状态机
7. 乐观锁
8. 分布式锁
```

---

## 6. 幂等记录表

```sql
CREATE TABLE idempotent_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    idem_key VARCHAR(128) NOT NULL,
    request_hash VARCHAR(128) DEFAULT NULL,
    status TINYINT NOT NULL,
    response TEXT,
    create_time DATETIME NOT NULL,
    update_time DATETIME NOT NULL,
    UNIQUE KEY uk_idem_key(idem_key)
);
```

---

## 7. 幂等处理流程

```text
1. 请求携带 idemKey
2. 服务端查询幂等记录
3. 如果不存在，插入处理中记录
4. 执行业务逻辑
5. 保存处理结果
6. 返回结果
7. 如果重复请求，直接返回之前结果
```

---

## 8. 状态机幂等

订单取消：

```sql
UPDATE orders
SET status = 'CANCELLED'
WHERE order_no = ?
  AND status = 'WAIT_PAY';
```

重复取消时，更新行数为 0。

---

## 9. MQ 消费幂等

消费记录表：

```sql
CREATE TABLE mq_consume_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    message_id VARCHAR(128) NOT NULL,
    consumer_group VARCHAR(128) NOT NULL,
    create_time DATETIME NOT NULL,
    UNIQUE KEY uk_msg_group(message_id, consumer_group)
);
```

---

## 10. 幂等接口注意事项

```text
1. 幂等 Key 必须唯一
2. 幂等 Key 不能被随意复用
3. 重复请求参数要校验一致性
4. 幂等记录要设置合理过期时间
5. 幂等结果可以缓存
6. 关键业务要用数据库唯一索引兜底
7. 幂等不等于分布式锁
```

## 11. 面试回答

设计幂等接口时，核心是为请求生成唯一幂等 Key，比如 requestId、订单号、支付流水号或 messageId。服务端收到请求后，先根据幂等 Key 判断是否处理过。如果已经处理过，直接返回之前的结果；如果没有处理过，再执行业务逻辑。

具体实现可以使用 Redis `SET NX`、数据库唯一索引、幂等记录表、状态机和消费记录表。比如支付回调可以用支付流水号做唯一键，订单状态更新时通过 `WHERE status = WAIT_PAY` 控制状态流转，MQ 消费时用 messageId 和 consumerGroup 建唯一索引防止重复消费。

# 十三、完整面试回答模板

如果让我设计一个秒杀系统，我会从限流、防刷、缓存、异步和一致性几个方面考虑。活动开始前先把商品信息和库存预热到 Redis，请求进入网关后先做限流、防刷和鉴权。秒杀服务只做活动校验、用户资格校验、Redis 原子扣减库存和重复下单判断，成功后把请求写入 MQ，然后快速返回排队中。订单服务异步消费消息创建订单，用户通过查询接口获取秒杀结果。防超卖通过 Redis Lua 原子扣库存和数据库 `stock >= num` 条件扣减兜底；防重复下单通过 Redis 标记、数据库唯一索引和消费端幂等保证；异常情况通过补偿任务修复。

短链接系统的核心是长链接和短码之间的映射。生成短码可以使用自增 ID 或雪花 ID 做 Base62 编码，保证唯一且较短。数据库保存 shortCode 和 longUrl 的映射，并对 shortCode 建唯一索引。用户访问短链接时，系统先查 Redis，未命中再查 MySQL，找到长链接后返回 302 重定向。热点短链要缓存，访问统计通过 MQ 异步处理，防止影响跳转性能。对于不存在的短码，可以通过空值缓存或布隆过滤器防止缓存穿透。

订单超时关闭可以使用延迟消息实现。创建订单后，订单状态为待支付，同时发送一条 30 分钟后的延迟消息。消息到期后，消费者查询订单状态，如果订单仍然是待支付，就执行关闭订单、释放库存、退回优惠券等逻辑；如果订单已经支付，则直接忽略。关闭订单时 SQL 必须带状态条件，例如 `WHERE order_id = ? AND status = 'WAIT_PAY'`，防止误关已支付订单。考虑到延迟消息可能失败，还需要定时任务扫描超时未支付订单做兜底补偿。

接口限流可以分层设计。网关层按照 IP、用户、接口、租户、AppId 等维度做统一限流，服务层对下单、支付、优惠券领取等核心接口做更细粒度限流。限流算法常见有固定窗口、滑动窗口、漏桶和令牌桶。实现上可以使用 Sentinel 做 QPS、线程数和热点参数限流，也可以使用 Redis + Lua 实现分布式限流。限流后要返回友好提示或降级结果，不能直接返回系统异常。

日志脱敏系统可以通过 AOP、注解和配置中心实现。在统一日志切面中拦截请求参数和响应结果，打印日志前先对手机号、身份证、银行卡、邮箱、地址、Token 等敏感字段脱敏。敏感字段可以通过字段名匹配，也可以通过自定义注解标记。脱敏规则可以放到配置中心，支持动态刷新。对于密码、密钥、完整 Token 等高敏字段，原则上禁止打印。也可以在 Logback 输出层做正则脱敏兜底，但要注意性能开销。

配置中心动态刷新可以通过客户端监听机制实现。应用启动时从配置中心拉取配置，并加载到 Spring Environment 中。运行过程中，客户端通过长轮询、长连接或推送机制监听配置变化。配置发生变化后，客户端拉取最新配置，更新本地快照和 Environment，然后发布配置变更事件，让 `@ConfigurationProperties` 或 `@RefreshScope` 管理的 Bean 刷新。为了保证稳定性，客户端需要本地缓存配置，配置中心不可用时使用旧配置兜底。

分布式系统数据一致性要根据业务场景选择方案。单服务单库使用本地事务。跨服务场景如果要求强一致，可以考虑 TCC 或分布式事务，但复杂度和性能开销较高。大多数互联网业务采用 MQ 最终一致性。比如订单服务创建订单后，通过本地消息表或事务消息保证消息可靠发送，库存服务消费消息扣减库存，消费失败自动重试，重复消费通过幂等控制，极端异常通过定时补偿和对账任务修复。

避免重复提交需要前后端配合，但最终以后端为准。前端可以做按钮置灰、防抖节流，减少重复点击。后端可以使用 token 机制，用户进入页面时先获取 token，提交时携带 token，服务端通过 Redis Lua 脚本校验并删除 token，保证 token 只能使用一次。对于有业务唯一性的请求，可以使用 Redis `SET NX` 或数据库唯一索引兜底。对于支付回调、订单取消等场景，要使用状态机控制，保证重复请求不会重复执行业务逻辑。

设计幂等接口时，核心是为请求生成唯一幂等 Key，比如 requestId、订单号、支付流水号、退款单号或 messageId。服务端收到请求后，先根据幂等 Key 判断是否已经处理过。如果已经处理过，直接返回之前结果；如果没有处理过，再执行业务。具体实现可以使用 Redis `SET NX`、数据库唯一索引、幂等记录表、状态机和消费记录表。MQ 消费场景下，可以基于 messageId 和 consumerGroup 建唯一索引，防止重复消费。

提高系统可用性需要从架构、服务、数据、中间件和运维多个层面设计。首先要避免单点故障，应用服务、网关、Redis、MySQL、MQ、Nacos 等关键组件都要集群化。服务尽量无状态，方便水平扩容。其次要做好限流、熔断、降级、超时和重试控制，防止流量突增或下游故障导致系统雪崩。缓存层要防止穿透、击穿和雪崩，数据库要做好主从、备份、慢 SQL 优化和连接池保护，MQ 要做好持久化、重试、死信和积压监控。最后要建立完善的监控告警、灰度发布、快速回滚和故障预案。
