# 一、TCP 和 UDP 区别

## 1. TCP 是什么？

TCP 全称是：

```text
Transmission Control Protocol
```

中文叫：

```text
传输控制协议
```

TCP 是一种：

```text
面向连接、可靠、基于字节流的传输层协议。
```

使用 TCP 通信前，需要先建立连接。

常见使用 TCP 的协议：

```text
HTTP
HTTPS
FTP
SMTP
SSH
MySQL
Redis
```

---

## 2. UDP 是什么？

UDP 全称是：

```text
User Datagram Protocol
```

中文叫：

```text
用户数据报协议
```

UDP 是一种：

```text
无连接、不可靠、面向报文的传输层协议。
```

UDP 发送数据前不需要建立连接，直接发送数据报。

常见使用 UDP 的场景：

```text
DNS
视频直播
语音通话
在线游戏
物联网数据上报
广播、多播
```

---

## 3. TCP 和 UDP 核心区别

| 对比项 | TCP | UDP |
|---|---|---|
| 是否连接 | 面向连接 | 无连接 |
| 是否可靠 | 可靠传输 | 不保证可靠 |
| 传输形式 | 字节流 | 数据报 |
| 是否保证顺序 | 保证有序 | 不保证有序 |
| 是否有重传 | 有 | 没有内置重传 |
| 是否有流量控制 | 有 | 没有 |
| 是否有拥塞控制 | 有 | 没有 |
| 首部开销 | 较大，至少 20 字节 | 较小，8 字节 |
| 传输速度 | 相对较慢 | 相对较快 |
| 适用场景 | 可靠性要求高 | 实时性要求高 |

---

## 4. TCP 为什么可靠？

TCP 可靠性主要依靠以下机制：

```text
1. 三次握手建立连接
2. 序列号
3. 确认应答 ACK
4. 超时重传
5. 流量控制
6. 拥塞控制
7. 校验和
8. 有序交付
```

---

## 5. UDP 为什么不可靠？

UDP 不保证：

```text
1. 消息一定送达
2. 消息按顺序到达
3. 消息不重复
4. 消息不会丢失
```

UDP 只负责尽力发送，不负责可靠性保障。

如果业务需要可靠性，需要应用层自己实现：

```text
ACK 确认
重试
序列号
去重
超时重传
```

---

## 6. TCP 适合什么场景？

TCP 适合可靠性要求高的场景：

```text
网页访问
文件传输
登录认证
数据库连接
支付交易
消息可靠传输
```

例如：

```text
HTTP / HTTPS 基于 TCP；
MySQL 连接基于 TCP；
Redis 客户端连接基于 TCP。
```

---

## 7. UDP 适合什么场景？

UDP 适合实时性要求高、允许少量丢包的场景：

```text
直播
语音通话
视频会议
在线游戏
DNS 查询
物联网数据采集
```

例如视频直播中，偶尔丢一帧可以接受，但如果为了重传导致卡顿，用户体验反而更差。

---

## 8. 面试回答

TCP 是面向连接、可靠、基于字节流的传输层协议。它通过三次握手建立连接，通过序列号、确认应答、重传、流量控制和拥塞控制保证可靠传输。

UDP 是无连接、不可靠、面向数据报的传输层协议。它发送数据前不需要建立连接，开销小、速度快，但不保证消息送达和顺序。

TCP 适合对可靠性要求高的场景，比如 HTTP、文件传输、数据库连接；UDP 适合对实时性要求高、可以容忍少量丢包的场景，比如直播、语音、游戏和 DNS。

# 二、TCP 三次握手、四次挥手

## 1. TCP 三次握手是什么？

TCP 三次握手用于建立连接。

三次握手的目标是：

```text
确认客户端和服务端双方的发送能力、接收能力都正常。
```

---

## 2. 三次握手流程

三次握手过程：

```text
第一次握手：客户端 -> 服务端：SYN
第二次握手：服务端 -> 客户端：SYN + ACK
第三次握手：客户端 -> 服务端：ACK
```

---

## 3. 三次握手示意图

```text
客户端 Client                              服务端 Server

CLOSED                                     LISTEN
  |                                          |
  | ----------- SYN seq=x ----------------> |
  |                                          |
SYN_SENT                                    |
  | <------ SYN seq=y, ACK=x+1 ------------ |
  |                                          |
  | ----------- ACK=y+1 ------------------> |
  |                                          |
ESTABLISHED                             ESTABLISHED
```

---

## 4. 第一次握手

客户端发送 SYN 包给服务端。

```text
客户端状态：SYN_SENT
服务端状态：LISTEN
```

含义：

```text
客户端告诉服务端：我想建立连接，并发送我的初始序列号 seq=x。
```

---

## 5. 第二次握手

服务端收到 SYN 后，返回 SYN + ACK。

```text
服务端状态：SYN_RECEIVED
```

含义：

```text
服务端告诉客户端：
1. 我收到了你的 SYN；
2. 我也同意建立连接；
3. 我的初始序列号是 seq=y；
4. 我确认你的序列号，下一个期望收到 x+1。
```

---

## 6. 第三次握手

客户端收到服务端的 SYN + ACK 后，再发送 ACK。

```text
客户端状态：ESTABLISHED
服务端收到 ACK 后状态：ESTABLISHED
```

含义：

```text
客户端告诉服务端：我收到了你的 SYN，我确认你的序列号，下一个期望收到 y+1。
```

此时连接建立完成。

---

## 7. TCP 四次挥手是什么？

TCP 四次挥手用于断开连接。

由于 TCP 是全双工通信，客户端和服务端都可以独立发送和接收数据。

所以关闭连接时，需要双方分别关闭自己的发送通道。

---

## 8. 四次挥手流程

四次挥手过程：

```text
第一次挥手：主动关闭方 -> 被动关闭方：FIN
第二次挥手：被动关闭方 -> 主动关闭方：ACK
第三次挥手：被动关闭方 -> 主动关闭方：FIN
第四次挥手：主动关闭方 -> 被动关闭方：ACK
```

---

## 9. 四次挥手示意图

```text
主动关闭方 Client                         被动关闭方 Server

ESTABLISHED                               ESTABLISHED
  |                                           |
  | ------------ FIN seq=u ----------------> |
  |                                           |
FIN_WAIT_1                                  |
  | <----------- ACK=u+1 ------------------- |
  |                                           |
FIN_WAIT_2                              CLOSE_WAIT
  |                                           |
  | <----------- FIN seq=v ----------------- |
  |                                           |
TIME_WAIT                                  LAST_ACK
  | ------------ ACK=v+1 -----------------> |
  |                                           |
TIME_WAIT 持续 2MSL                         CLOSED
  |
CLOSED
```

---

## 10. 第一次挥手

主动关闭方发送 FIN。

含义：

```text
我这边没有数据要发送了，准备关闭发送通道。
```

主动关闭方进入：

```text
FIN_WAIT_1
```

---

## 11. 第二次挥手

被动关闭方收到 FIN 后，返回 ACK。

含义：

```text
我知道你不再发送数据了。
```

被动关闭方进入：

```text
CLOSE_WAIT
```

主动关闭方收到 ACK 后进入：

```text
FIN_WAIT_2
```

---

## 12. 第三次挥手

被动关闭方处理完剩余数据后，也发送 FIN。

含义：

```text
我这边数据也发送完了，也准备关闭发送通道。
```

被动关闭方进入：

```text
LAST_ACK
```

---

## 13. 第四次挥手

主动关闭方收到 FIN 后，返回 ACK。

主动关闭方进入：

```text
TIME_WAIT
```

被动关闭方收到 ACK 后进入：

```text
CLOSED
```

主动关闭方等待 2MSL 后，也进入：

```text
CLOSED
```

---

## 14. 为什么建立连接是三次，关闭连接是四次？

建立连接时，服务端收到客户端 SYN 后，可以把自己的 SYN 和 ACK 合并成一次发送。

所以是三次。

关闭连接时，被动关闭方收到 FIN 后，可能还有数据没有发送完。

所以先回复 ACK，等数据发送完后，再单独发送 FIN。

因此通常是四次。

---

## 15. 面试回答

TCP 三次握手用于建立连接。第一次客户端发送 SYN，第二次服务端返回 SYN + ACK，第三次客户端返回 ACK。三次握手后，双方确认彼此的发送和接收能力正常，连接建立完成。

TCP 四次挥手用于关闭连接。第一次主动关闭方发送 FIN，第二次被动关闭方返回 ACK，第三次被动关闭方发送 FIN，第四次主动关闭方返回 ACK。由于 TCP 是全双工通信，双方的发送通道需要分别关闭，所以通常需要四次挥手。

# 三、为什么需要三次握手

## 1. 三次握手的核心目的

三次握手的核心目的是：

```text
确认双方发送和接收能力都正常；
同步双方初始序列号；
避免历史连接请求造成错误连接。
```

---

## 2. 两次握手可以吗？

如果只有两次握手：

```text
1. 客户端发送 SYN
2. 服务端返回 SYN + ACK
```

服务端返回后就认为连接建立。

但此时服务端并不知道：

```text
客户端是否收到了自己的 SYN + ACK；
客户端的接收能力是否正常；
客户端是否真的还想建立连接。
```

---

## 3. 两次握手的问题：历史 SYN

假设客户端之前发送了一个 SYN 包，因为网络延迟迟迟没有到达服务端。

客户端超时后重新发送 SYN，并建立连接，使用完后关闭。

后来旧的 SYN 包才到达服务端。

如果只需要两次握手：

```text
服务端收到旧 SYN；
返回 SYN + ACK；
服务端认为连接建立；
等待客户端发送数据。
```

但客户端并不想建立这个连接。

结果：

```text
服务端白白分配资源，造成资源浪费。
```

三次握手中，客户端收到旧连接的 SYN + ACK 后，不会再发送第三次 ACK，因此服务端不会真正建立连接。

---

## 4. 三次握手如何确认双方能力？

### 第一次握手

客户端发送 SYN。

服务端可以确认：

```text
客户端发送能力正常；
服务端接收能力正常。
```

---

### 第二次握手

服务端返回 SYN + ACK。

客户端可以确认：

```text
客户端发送能力正常；
客户端接收能力正常；
服务端发送能力正常；
服务端接收能力正常。
```

---

### 第三次握手

客户端发送 ACK。

服务端可以确认：

```text
服务端发送能力正常；
客户端接收能力正常。
```

至此双方都确认彼此收发能力正常。

---

## 5. 为什么不是四次握手？

建立连接时，服务端的 ACK 和 SYN 可以合并发送。

也就是：

```text
ACK 客户端的 SYN
服务端自己的 SYN
```

可以放在同一个报文中。

所以不需要四次。

---

## 6. 面试回答

TCP 需要三次握手，是为了确认客户端和服务端双方的发送能力、接收能力都正常，同时同步双方的初始序列号，并避免历史连接请求导致服务端误建立连接。

如果只有两次握手，服务端发送 SYN + ACK 后就认为连接建立，但它无法确认客户端是否收到了自己的响应，也无法确认客户端是否真的还要建立连接。如果旧的 SYN 报文延迟到达，服务端可能误建立无效连接，浪费资源。

三次握手通过最后一次 ACK，让服务端确认客户端收到了自己的 SYN + ACK，从而保证连接可靠建立。

# 四、TIME_WAIT 是什么

## 1. TIME_WAIT 是什么？

`TIME_WAIT` 是 TCP 主动关闭连接的一方在四次挥手后进入的状态。

主动关闭方发送最后一个 ACK 后，不会立即关闭连接，而是等待一段时间。

这个状态就是：

```text
TIME_WAIT
```

---

## 2. TIME_WAIT 出现在哪里？

四次挥手最后：

```text
主动关闭方收到对方 FIN
主动关闭方发送 ACK
主动关闭方进入 TIME_WAIT
等待 2MSL
连接最终关闭
```

---

## 3. MSL 是什么？

MSL 全称是：

```text
Maximum Segment Lifetime
```

中文叫：

```text
最大报文生存时间
```

表示一个 TCP 报文在网络中最多存活的时间。

TIME_WAIT 通常等待：

```text
2MSL
```

---

## 4. 为什么需要 TIME_WAIT？

TIME_WAIT 主要有两个作用：

```text
1. 确保最后一个 ACK 能被对方收到
2. 防止旧连接的延迟报文影响新连接
```

---

## 5. 作用一：确保最后 ACK 到达

如果主动关闭方发送的最后一个 ACK 丢失，被动关闭方收不到 ACK，会重新发送 FIN。

如果主动关闭方已经关闭连接，就无法处理这个重传的 FIN。

有 TIME_WAIT 后，主动关闭方仍然可以收到重传 FIN，并再次发送 ACK。

---

## 6. 作用二：防止旧报文影响新连接

TCP 连接由四元组唯一标识：

```text
源 IP
源端口
目标 IP
目标端口
```

如果旧连接刚关闭，相同四元组的新连接马上建立，网络中旧连接的延迟报文可能会被新连接误收。

等待 2MSL 可以让旧连接中的报文在网络中自然消失。

---

## 7. TIME_WAIT 过多有什么问题？

大量 TIME_WAIT 可能导致：

```text
端口资源占用
连接数增多
系统资源消耗
短连接高并发场景性能下降
```

常见于：

```text
高并发短连接
服务主动关闭大量连接
HTTP 短连接
频繁请求下游服务
```

---

## 8. 如何减少 TIME_WAIT 影响？

常见优化方式：

```text
1. 使用长连接
2. 使用连接池
3. HTTP Keep-Alive
4. 减少频繁创建和关闭连接
5. 调整系统 TCP 参数，谨慎操作
6. 让客户端主动关闭连接，服务端减少 TIME_WAIT
```

---

## 9. CLOSE_WAIT 和 TIME_WAIT 区别

| 状态 | 含义 | 常见原因 |
|---|---|---|
| TIME_WAIT | 主动关闭方等待 2MSL | 正常 TCP 关闭流程 |
| CLOSE_WAIT | 被动关闭方收到 FIN 后未关闭连接 | 应用程序没有正确关闭 socket |

如果线上出现大量 `CLOSE_WAIT`，通常是程序问题，需要重点排查。

---

## 10. 面试回答

TIME_WAIT 是 TCP 主动关闭连接的一方在发送最后一个 ACK 后进入的状态，通常会等待 2MSL 后才真正关闭连接。

TIME_WAIT 的作用有两个：第一是确保最后一个 ACK 能被对方收到，如果 ACK 丢失，对方重传 FIN 时还能再次回复 ACK；第二是防止旧连接中的延迟报文影响后续使用相同四元组的新连接。

TIME_WAIT 是正常现象，但如果数量过多，可能说明系统存在大量短连接，可以通过连接池、长连接、HTTP Keep-Alive 等方式优化。

---

# 五、HTTP 和 HTTPS 区别

## 1. HTTP 是什么？

HTTP 全称是：

```text
HyperText Transfer Protocol
```

中文叫：

```text
超文本传输协议
```

HTTP 是应用层协议，常用于浏览器和服务器之间传输网页、JSON、图片等资源。

HTTP 默认端口：

```text
80
```

---

## 2. HTTPS 是什么？

HTTPS 全称是：

```text
HyperText Transfer Protocol Secure
```

中文叫：

```text
安全的超文本传输协议
```

HTTPS 可以理解为：

```text
HTTP + TLS/SSL
```

它在 HTTP 和 TCP 之间加入了加密层。

HTTPS 默认端口：

```text
443
```

---

## 3. HTTP 和 HTTPS 核心区别

| 对比项 | HTTP | HTTPS |
|---|---|---|
| 安全性 | 明文传输，不安全 | 加密传输，更安全 |
| 默认端口 | 80 | 443 |
| 是否需要证书 | 不需要 | 需要 CA 证书 |
| 数据加密 | 不加密 | TLS 加密 |
| 防窃听 | 不支持 | 支持 |
| 防篡改 | 不支持 | 支持 |
| 身份认证 | 不支持 | 支持服务器身份认证 |
| 性能 | 开销较低 | 有 TLS 握手和加密开销 |
| URL 前缀 | `http://` | `https://` |

---

## 4. HTTP 存在哪些安全问题？

HTTP 是明文传输，存在以下问题：

```text
1. 窃听风险：数据可能被第三方看到
2. 篡改风险：数据可能被中间人修改
3. 冒充风险：无法确认服务器真实身份
```

---

## 5. HTTPS 解决了什么问题？

HTTPS 通过 TLS 解决：

```text
1. 加密传输，防止窃听
2. 完整性校验，防止篡改
3. 数字证书，验证服务器身份
```

---

## 6. HTTPS 一定绝对安全吗？

HTTPS 提高了传输安全性，但不是绝对安全。

仍然需要注意：

```text
证书是否可信
私钥是否泄露
TLS 版本和加密套件是否安全
服务端是否有漏洞
客户端是否被植入恶意证书
应用层是否有权限漏洞
```

---

## 7. 面试回答

HTTP 是明文传输协议，默认端口是 80，数据在网络中传输时可能被窃听、篡改或冒充。

HTTPS 是 HTTP 加 TLS/SSL，默认端口是 443。它通过证书验证服务器身份，通过非对称加密协商密钥，通过对称加密传输数据，并通过摘要和 MAC 等机制保证数据完整性。

所以 HTTPS 相比 HTTP 更安全，但会多一次 TLS 握手和加解密开销。

---

# 六、HTTPS 加密过程

## 1. HTTPS 为什么既用非对称加密又用对称加密？

原因是：

```text
非对称加密安全，但性能较差；
对称加密性能高，但密钥传输困难。
```

HTTPS 结合两者：

```text
用非对称加密或密钥交换算法安全协商会话密钥；
用对称加密传输业务数据。
```

---

## 2. HTTPS 加密核心目标

HTTPS 需要解决：

```text
1. 服务器身份认证
2. 安全协商会话密钥
3. 加密传输数据
4. 防止数据被篡改
```

---

## 3. HTTPS 大致流程

简化流程：

```text
1. 客户端发起 HTTPS 请求
2. 服务端返回数字证书
3. 客户端验证证书合法性
4. 双方协商生成会话密钥
5. 使用会话密钥进行对称加密通信
```

---

## 4. HTTPS 握手示意图

```text
客户端 Client                              服务端 Server

ClientHello
支持的 TLS 版本、随机数、加密套件
        --------------------------------->

ServerHello
选择的 TLS 版本、随机数、加密套件
证书 Certificate
        <---------------------------------

客户端验证证书
生成或协商会话密钥

密钥交换相关消息
        <-------------------------------->

双方生成相同会话密钥

Finished
        --------------------------------->
Finished
        <---------------------------------

开始使用对称加密传输 HTTP 数据
```

---

## 5. 数字证书有什么作用？

数字证书用于证明：

```text
这个公钥确实属于目标服务器。
```

证书中通常包含：

```text
域名
公钥
证书颁发机构 CA
有效期
签名算法
数字签名
```

---

## 6. 客户端如何验证证书？

客户端会验证：

```text
1. 证书是否过期
2. 域名是否匹配
3. 证书链是否可信
4. 是否由受信任 CA 签发
5. 证书是否被吊销
6. 证书签名是否正确
```

如果证书不可信，浏览器会提示风险。

---

## 7. 对称加密和非对称加密分别做什么？

| 加密方式 | 在 HTTPS 中的作用 |
|---|---|
| 非对称加密 / 密钥交换 | 身份认证、协商会话密钥 |
| 对称加密 | 加密实际业务数据 |
| 摘要 / MAC | 保证数据完整性 |

---

## 8. 为什么不全程使用非对称加密？

因为非对称加密计算开销大，性能较低。

如果所有 HTTP 数据都用非对称加密，会严重影响性能。

所以 HTTPS 只在握手阶段使用非对称加密或密钥交换，后续数据传输使用高效的对称加密。

---

## 9. HTTPS 如何防止中间人攻击？

中间人攻击的核心是：

```text
攻击者伪装成服务端，把自己的公钥发给客户端。
```

HTTPS 通过 CA 证书体系防止这种情况。

客户端不会随便相信一个公钥，而是验证证书是否由可信 CA 签发，证书中的域名是否匹配目标网站。

如果攻击者没有合法证书，就无法通过验证。

---

## 10. 面试回答

HTTPS 的加密过程可以简单理解为：客户端先和服务端进行 TLS 握手，服务端返回数字证书，客户端验证证书是否合法，包括证书是否过期、域名是否匹配、是否由可信 CA 签发等。验证通过后，客户端和服务端通过非对称加密或密钥交换算法协商出一个会话密钥。

之后真正的 HTTP 数据传输使用这个会话密钥进行对称加密。这样既解决了密钥安全传输问题，又保证了传输性能。HTTPS 同时通过证书解决身份认证，通过加密防止窃听，通过完整性校验防止篡改。

---

# 七、HTTP 状态码有哪些

## 1. HTTP 状态码分类

HTTP 状态码由三位数字组成，可以分为五类：

| 状态码范围 | 类型 | 含义 |
|---|---|---|
| 1xx | 信息响应 | 请求已接收，继续处理 |
| 2xx | 成功 | 请求成功处理 |
| 3xx | 重定向 | 需要进一步操作 |
| 4xx | 客户端错误 | 请求有问题 |
| 5xx | 服务端错误 | 服务端处理失败 |

---

## 2. 常见 2xx 状态码

| 状态码 | 含义 |
|---|---|
| 200 | OK，请求成功 |
| 201 | Created，资源创建成功 |
| 202 | Accepted，请求已接受但未处理完成 |
| 204 | No Content，请求成功但无响应体 |

---

## 3. 200 OK

表示请求成功。

例如：

```text
GET 查询成功
POST 处理成功
```

---

## 4. 201 Created

表示资源创建成功。

常用于：

```text
POST 创建资源成功
```

---

## 5. 204 No Content

表示请求成功，但响应体为空。

常用于：

```text
DELETE 删除成功
PUT 更新成功但不返回内容
```

---

## 6. 常见 3xx 状态码

| 状态码 | 含义 |
|---|---|
| 301 | 永久重定向 |
| 302 | 临时重定向 |
| 304 | 资源未修改，可使用缓存 |
| 307 | 临时重定向，保持请求方法 |
| 308 | 永久重定向，保持请求方法 |

---

## 7. 301 和 302 区别

| 状态码 | 含义 | 场景 |
|---|---|---|
| 301 | 永久重定向 | 域名永久迁移 |
| 302 | 临时重定向 | 临时跳转 |

---

## 8. 304 Not Modified

表示资源未修改，客户端可以使用本地缓存。

常用于 HTTP 缓存。

---

## 9. 常见 4xx 状态码

| 状态码 | 含义 |

## 10. 401 和 403 区别

| 状态码 | 含义 |
|---|---|
| 401 | 未登录或认证失败 |
| 403 | 已认证，但没有权限 |

简单理解：

```text
401：你是谁？

```

---

## 11. 常见 5xx 状态码

| 状态码 | 含义 |
|---|---|
| 500 | Internal Server Error，服务端内部错误 |

---

## 12. 502、503、504 区别

| 状态码 | 含义 | 常见原因 |
|---|---|---|
| 502 | 网关收到上游无效响应 | 上游服务挂了、返回异常 |
| 503 | 服务不可用 | 服务过载、维护、限流 |
| 504 | 网关等待上游超时 | 上游响应太慢、网络超时 |

---

## 13. 面试回答

HTTP 状态码分为五类：1xx 表示信息响应，2xx 表示成功，3xx 表示重定向，4xx 表示客户端错误，5xx 表示服务端错误。

常见状态码有：200 表示成功，201 表示创建成功，204 表示成功但无响应体；301 是永久重定向，302 是临时重定向，304 表示资源未修改可用缓存；400 表示请求参数错误，401 表示未认证，403 表示无权限，404 表示资源不存在，405 表示方法不支持，429 表示请求过多；500 表示服务端内部错误，502 表示网关错误，503 表示服务不可用，504 表示网关超时。

# 八、GET 和 POST 区别

## 1. GET 是什么？

GET 通常用于：

```text
获取资源
```

例如：

```http
GET /users/1 HTTP/1.1
```

含义：

```text
获取 ID 为 1 的用户信息。
```

---

## 2. POST 是什么？

POST 通常用于：

```text
提交数据
创建资源
触发服务端处理
```

例如：

```http
POST /users HTTP/1.1

{
  "name": "Tom",
  "age": 18
}
```

含义：

```text
创建一个用户。
```

---

## 3. GET 和 POST 核心区别

| 对比项 | GET | POST |
|---|---|---|
| 语义 | 获取资源 | 提交数据、创建资源 |
| 参数位置 | 通常放 URL 查询参数 | 通常放请求体 |
| 幂等性 | 通常幂等 | 通常不幂等 |
| 安全性语义 | 安全方法，不应修改资源 | 可能修改资源 |
| 是否可缓存 | 更容易被缓存 | 默认一般不缓存 |
| 是否可收藏 | 可以收藏 URL | 不适合收藏 |
| 参数长度 | 受 URL 长度限制 | 理论上受服务端配置限制 |
| 敏感信息 | 不适合放敏感信息 | 相对更适合，但仍需 HTTPS |
| 浏览器回退 | 一般无副作用 | 可能提示重复提交 |

---

## 4. 安全方法是什么意思？

HTTP 中的“安全”不是指加密安全，而是指：

```text
请求不应该修改服务端资源。
```

GET 按语义应该是安全方法。

例如：

```text
GET /users/1
```

只是查询用户，不应该修改数据。

---

## 5. 幂等是什么意思？

幂等是指：

```text
一次请求和多次相同请求，对资源产生的结果相同。
```

GET 通常是幂等的。

例如：

```http
GET /users/1
```

请求一次和多次，理论上不会改变服务端数据。

POST 通常不是幂等的。

例如：

```http
POST /orders
```

请求多次可能创建多个订单。

---

## 6. GET 参数一定在 URL 吗？

通常 GET 参数放在 URL 中：

```http
GET /users?id=1
```

但 HTTP 协议本身没有绝对禁止 GET 带 body。

不过实际开发中不推荐 GET 使用 body，因为很多服务器、代理、框架对 GET body 支持不一致。

---

## 7. POST 一定比 GET 安全吗？

不是。

POST 参数放在请求体中，不会直接显示在 URL 上，但如果使用 HTTP 明文传输，仍然可以被抓包看到。

真正保护数据传输安全，需要使用：

```text
HTTPS
```

---

## 8. 面试回答

GET 和 POST 的主要区别在语义上。GET 用于获取资源，不应该修改服务端数据，通常是幂等的，参数一般放在 URL 查询字符串中，适合查询、分页、筛选等场景。

POST 用于提交数据、创建资源或触发服务端处理，通常不是幂等的，参数一般放在请求体中，适合表单提交、创建订单、上传数据等场景。

需要注意，POST 并不天然比 GET 安全，只是参数不直接显示在 URL 上。如果要保证传输安全，必须使用 HTTPS。

---

# 九、Cookie、Session、Token 区别

## 1. 为什么需要 Cookie、Session、Token？

HTTP 是无状态协议。

无状态是指：

```text
服务器不会天然记住每一次请求来自哪个用户。
```

例如用户登录后，下一次请求服务器需要知道：

```text
这个请求来自已经登录的用户。
```

因此需要身份状态管理机制。

常见方式：

```text
Cookie
Session
Token
```

---

## 2. Cookie 是什么？

Cookie 是服务端发送给浏览器，并保存在浏览器端的一小段数据。

浏览器后续请求同一站点时，会自动携带 Cookie。

---

## 3. Cookie 工作流程

```text
1. 用户登录成功
2. 服务端返回 Set-Cookie 响应头
3. 浏览器保存 Cookie
4. 后续请求自动携带 Cookie
5. 服务端读取 Cookie 识别用户
```

---

## 4. Cookie 示例

响应头：

```http
Set-Cookie: sessionId=abc123; Path=/; HttpOnly
```

后续请求头：

```http
Cookie: sessionId=abc123
```

---

## 5. Cookie 特点

```text
1. 存储在客户端
2. 浏览器自动携带
3. 大小有限制
4. 可以设置过期时间
5. 可以设置作用域
6. 可能存在 CSRF 风险
```

---

## 6. Cookie 常见属性

| 属性 | 说明 |
|---|---|
| `Expires` | 过期时间 |
| `Max-Age` | 最大存活时间 |
| `Domain` | 生效域名 |
| `Path` | 生效路径 |
| `HttpOnly` | 禁止 JavaScript 读取，降低 XSS 风险 |
| `Secure` | 仅 HTTPS 传输 |
| `SameSite` | 限制跨站携带，降低 CSRF 风险 |

---

## 7. Session 是什么？

Session 是服务端保存用户会话状态的一种机制。

浏览器通常只保存一个：

```text
sessionId
```

真正的用户信息保存在服务端。

---

## 8. Session 工作流程

```text
1. 用户登录成功
2. 服务端创建 Session
3. 服务端生成 sessionId
4. sessionId 通过 Cookie 返回给浏览器
5. 浏览器后续请求自动携带 sessionId
6. 服务端根据 sessionId 查询 Session 数据
7. 识别当前用户身份
```

---

## 9. Session 示例

浏览器 Cookie：

```text
JSESSIONID=abc123
```

服务端 Session 存储：

```text
abc123 -> userId=1001, username=Tom
```

---

## 10. Session 的问题

Session 存在一些问题：

```text
1. 服务端需要存储会话，占用内存
2. 多实例部署需要 Session 共享
3. 分布式环境需要 Redis 等集中存储
4. 跨域、移动端场景不够灵活
5. 服务扩容时需要考虑会话一致性
```

---

## 11. Token 是什么？

Token 是一种令牌机制。

用户登录成功后，服务端生成 Token 返回给客户端。

客户端后续请求时主动携带 Token。

常见携带方式：

```http
Authorization: Bearer token值
```

---

## 12. Token 工作流程

```text
1. 用户登录
2. 服务端校验用户名密码
3. 服务端生成 Token
4. 客户端保存 Token
5. 后续请求在 Header 中携带 Token
6. 服务端校验 Token
7. 校验通过后识别用户
```

---

## 13. JWT 是什么？

JWT 全称：

```text
JSON Web Token
```

JWT 是一种常见 Token 格式。

JWT 通常由三部分组成：

```text
Header.Payload.Signature
```

例如：

```text
xxxxx.yyyyy.zzzzz
```

---

## 14. JWT 三部分

| 部分 | 说明 |
|---|---|
| Header | 令牌类型、签名算法 |
| Payload | 用户信息、过期时间等声明 |
| Signature | 签名，防止篡改 |

---

## 15. Token 的优点

```text
1. 服务端可以无状态
2. 适合分布式系统
3. 适合前后端分离
4. 适合移动端和开放 API
5. 跨域更方便
```

---

## 16. Token 的问题

```text
1. Token 泄露后有安全风险
2. 无状态 Token 不容易主动失效
3. JWT 信息默认只是编码，不是加密
4. Token 过长会增加请求体积
5. 需要处理刷新 Token 和过期机制
```

---

## 17. Cookie、Session、Token 对比

| 对比项 | Cookie | Session | Token |
|---|---|---|---|
| 存储位置 | 客户端 | 服务端 | 客户端 |
| 服务端是否存状态 | 不一定 | 是 | 通常否 |
| 客户端是否自动携带 | 浏览器自动携带 | sessionId 通常通过 Cookie 自动携带 | 一般手动放 Header |
| 安全风险 | CSRF、XSS | Session 劫持 | Token 泄露 |
| 分布式支持 | 一般 | 需要共享 Session | 更友好 |
| 适合场景 | 浏览器状态保存 | 传统 Web 登录 | 前后端分离、移动端、API |

---

## 18. Session 和 Token 区别

| 对比项 | Session | Token |
|---|---|---|
| 状态保存 | 服务端保存 | 客户端保存 |
| 扩展性 | 分布式下需要共享 | 更适合分布式 |
| 失效控制 | 服务端容易主动失效 | 无状态 Token 主动失效较难 |
| 安全性 | 依赖 sessionId 安全 | 依赖签名、过期时间和 HTTPS |
| 典型场景 | 传统 Web | 前后端分离、移动端 |

---

## 19. Cookie 和 Token 的关系

Token 可以存储在：

```text
1. Cookie
2. LocalStorage
3. SessionStorage
4. 内存变量
```

如果 Token 存在 Cookie 中，浏览器会自动携带，但要注意 CSRF。

如果 Token 存在 LocalStorage 中，容易受到 XSS 攻击。

实际项目中需要结合安全要求选择。

---

## 20. 面试回答

Cookie 是存储在客户端浏览器中的小段数据，浏览器后续请求会自动携带。Session 是服务端保存用户会话状态的机制，客户端通常只保存 sessionId，服务端通过 sessionId 找到用户信息。Token 是令牌机制，登录成功后服务端生成 Token 返回给客户端，客户端后续请求主动携带 Token，服务端校验 Token 后识别用户。

Session 更适合传统 Web 应用，但分布式部署时需要解决 Session 共享问题。Token 更适合前后端分离、移动端和微服务场景，因为服务端可以无状态。但 Token 泄露后也有风险，需要配合 HTTPS、过期时间、刷新机制和黑名单机制。

---

# 十、面试速记版

## 1. TCP 和 UDP 区别

```text
TCP：面向连接、可靠、字节流、有序、重传、流控、拥塞控制
UDP：无连接、不可靠、数据报、开销小、速度快
```

TCP 适合：

```text
HTTP、HTTPS、文件传输、数据库连接
```

UDP 适合：

```text
直播、语音、游戏、DNS
```

---

## 2. TCP 三次握手

```text
1. Client -> Server：SYN
2. Server -> Client：SYN + ACK
3. Client -> Server：ACK
```

作用：

```text
确认双方收发能力正常；
同步初始序列号；
避免历史连接请求。
```

---

## 3. TCP 四次挥手

```text
1. 主动关闭方 -> 被动关闭方：FIN
2. 被动关闭方 -> 主动关闭方：ACK
3. 被动关闭方 -> 主动关闭方：FIN
4. 主动关闭方 -> 被动关闭方：ACK
```

四次原因：

```text
TCP 是全双工，双方发送通道要分别关闭。
```

---

## 4. 为什么需要三次握手？

```text
两次握手无法确认客户端是否收到服务端 SYN + ACK；
也无法避免历史 SYN 导致服务端误建立连接。
```

三次握手可以确认双方发送和接收能力都正常。

---

## 5. TIME_WAIT 是什么？

```text
主动关闭方发送最后一个 ACK 后进入 TIME_WAIT，等待 2MSL 后关闭。
```

作用：

```text
确保最后 ACK 能被对方收到；
防止旧连接报文影响新连接。
```

---

## 6. HTTP 和 HTTPS 区别

```text
HTTP：明文传输，默认端口 80
HTTPS：HTTP + TLS，加密传输，默认端口 443
```

HTTPS 解决：

```text
防窃听
防篡改
身份认证
```

---

## 7. HTTPS 加密过程

```text
客户端发起请求
服务端返回证书
客户端验证证书
协商会话密钥
后续使用对称加密传输数据
```

---

## 8. HTTP 状态码

```text
1xx：信息
2xx：成功
```

# 十二、完整面试回答模板

TCP 和 UDP 都是传输层协议。TCP 是面向连接、可靠、基于字节流的协议，它通过三次握手建立连接，通过序列号、确认应答、超时重传、流量控制和拥塞控制保证可靠传输。UDP 是无连接、不可靠、面向数据报的协议，发送前不需要建立连接，开销小、速度快，但不保证消息送达和顺序。TCP 适合 HTTP、HTTPS、数据库连接和文件传输等可靠性要求高的场景；UDP 适合直播、语音、游戏和 DNS 等实时性要求高的场景。

TCP 三次握手用于建立连接。第一次客户端发送 SYN，第二次服务端返回 SYN + ACK，第三次客户端返回 ACK。三次握手的目的是确认客户端和服务端双方的发送能力、接收能力都正常，同步双方的初始序列号，并避免历史连接请求导致服务端误建立连接。两次握手无法确认客户端是否收到服务端的响应，也无法有效避免旧 SYN 报文造成资源浪费。

TCP 四次挥手用于关闭连接。第一次主动关闭方发送 FIN，第二次被动关闭方返回 ACK，第三次被动关闭方发送 FIN，第四次主动关闭方返回 ACK。因为 TCP 是全双工通信，双方的发送通道需要分别关闭，所以通常需要四次挥手。

TIME_WAIT 是主动关闭连接的一方在发送最后一个 ACK 后进入的状态，通常会等待 2MSL 后才真正关闭。它的作用有两个：第一是确保最后一个 ACK 能被对方收到，如果 ACK 丢失，对方重传 FIN 时还能再次回复 ACK；第二是防止旧连接中的延迟报文影响后续使用相同四元组的新连接。TIME_WAIT 是正常现象，但如果数量过多，可以考虑使用长连接、连接池和 HTTP Keep-Alive 等方式优化。

HTTP 是明文传输协议，默认端口是 80，数据在网络中传输时可能被窃听、篡改或冒充。HTTPS 是 HTTP 加 TLS/SSL，默认端口是 443。它通过数字证书验证服务器身份，通过非对称加密或密钥交换算法协商会话密钥，然后使用对称加密传输业务数据，并通过完整性校验防止数据被篡改。

HTTPS 加密过程可以简单理解为：客户端发起请求，服务端返回数字证书，客户端验证证书是否合法，包括证书是否过期、域名是否匹配、是否由可信 CA 签发等。验证通过后，双方协商生成会话密钥，后续 HTTP 数据使用会话密钥进行对称加密传输。这样既保证了安全性，也保证了性能。

HTTP 状态码分为五类：1xx 表示信息响应，2xx 表示成功，3xx 表示重定向，4xx 表示客户端错误，5xx 表示服务端错误。常见状态码有 200 成功，201 创建成功，204 成功但无响应体，301 永久重定向，302 临时重定向，304 缓存未修改，400 请求参数错误，401 未认证，403 无权限，404 资源不存在，405 方法不支持，429 请求过多，500 服务端内部错误，502 网关错误，503 服务不可用，504 网关超时。

GET 和 POST 的主要区别在语义上。GET 用于获取资源，不应该修改服务端数据，通常是幂等的，参数一般放在 URL 中，适合查询、分页、筛选等场景。POST 用于提交数据、创建资源或触发服务端处理，通常不是幂等的，参数一般放在请求体中，适合表单提交、创建订单、上传数据等场景。POST 并不天然比 GET 安全，如果要保证传输安全，必须使用 HTTPS。

Cookie、Session 和 Token 都可以用于身份状态管理。Cookie 是存储在客户端浏览器中的小段数据，浏览器后续请求会自动携带。Session 是服务端保存用户会话状态的机制，客户端通常只保存 sessionId，服务端根据 sessionId 找到用户信息。Token 是令牌机制，用户登录成功后服务端生成 Token 返回给客户端，客户端后续请求主动携带 Token，服务端校验 Token 后识别用户。Session 更适合传统 Web 应用，Token 更适合前后端分离、移动端和微服务场景。
