# 线上千万级大表加字段很慢怎么处理

线上大表加字段慢，核心原因是：**DDL 可能触发表结构重建、数据拷贝、元数据锁等待，导致执行时间长，甚至影响线上读写**。

处理思路：

```text
先判断 DDL 类型
  ↓
优先使用 Instant DDL
  ↓
不支持则使用 Online DDL
  ↓
再不行使用 gh-ost / pt-online-schema-change
  ↓
低峰执行 + 灰度验证 + 监控回滚
```

---

## 1. 为什么加字段会慢

大表加字段可能会触发：

- 表重建。
- 全表数据拷贝。
- 索引重建。
- 长时间持有元数据锁。
- 主从延迟增大。
- IO、CPU、磁盘压力上升。
- 影响线上查询和写入。

尤其是老版本 MySQL，或者加字段方式不合适时，可能会非常慢。

---

## 2. 优先判断 MySQL 版本

如果是 **MySQL 8.0.12+**，可以优先考虑：

```sql
ALTER TABLE user_order
ADD COLUMN ext_info VARCHAR(255) NULL,
ALGORITHM=INSTANT;
```

`ALGORITHM=INSTANT` 支持部分加列场景，MySQL 官方说明 Instant ADD COLUMN 可以不随表大小增长而变慢；但它有使用限制，不是所有 DDL 都能走 INSTANT。:contentReference[oaicite:0]{index=0}

推荐加上：

```sql
ALGORITHM=INSTANT
```

好处是：

```text
如果不能使用 INSTANT，SQL 会直接失败，而不是偷偷退化成慢 DDL。
```

MySQL 官方也建议通过指定 `ALGORITHM=INSTANT` 或 `ALGORITHM=INPLACE`，避免 DDL 退化为拷贝整表的方式。:contentReference[oaicite:1]{index=1}

---

## 3. 加字段推荐方式

### 推荐

```sql
ALTER TABLE order_info
ADD COLUMN remark VARCHAR(255) NULL,
ALGORITHM=INSTANT;
```

或者：

```sql
ALTER TABLE order_info
ADD COLUMN remark VARCHAR(255) NULL DEFAULT NULL,
ALGORITHM=INSTANT;
```

### 不推荐

```sql
ALTER TABLE order_info
ADD COLUMN remark VARCHAR(255) NOT NULL DEFAULT '';
```

原因：

```text
NOT NULL + 默认值
可能导致历史数据需要处理
更容易触发表重建或大量数据变更
```

更稳妥做法：

```text
先加 nullable 字段
  ↓
代码兼容空值
  ↓
异步分批回填历史数据
  ↓
必要时再改 NOT NULL
```

---

## 4. 如果不支持 Instant DDL

可以尝试 Online DDL：

```sql
ALTER TABLE order_info
ADD COLUMN remark VARCHAR(255) NULL,
ALGORITHM=INPLACE,
LOCK=NONE;
```

含义：

```text
尽量不拷贝整表
尽量不阻塞读写
```

但注意：

```text
INPLACE 不等于完全无锁
开始和结束阶段仍可能需要短暂 MDL 锁
大表仍可能执行很久
```

---

## 5. 使用 gh-ost 或 pt-online-schema-change

如果线上表特别大，MySQL 版本不支持 Instant，或者 DDL 可能重建表，推荐使用在线变更工具。

---

## 5.1 gh-ost

`gh-ost` 是 GitHub 开源的 MySQL 在线表结构变更工具，特点是 **无触发器、可暂停、可限速、可审计、对主库影响较低**。:contentReference[oaicite:2]{index=2}

基本原理：

```text
创建影子表
  ↓
在影子表上执行新表结构
  ↓
分批拷贝原表数据到影子表
  ↓
通过 binlog 同步增量变更
  ↓
数据追平后切换新旧表
```

适合：

```text
大表在线 DDL
主库压力敏感
需要可暂停、可限速、可控制
```

---

## 5.2 pt-online-schema-change

`pt-online-schema-change` 是 Percona Toolkit 工具，可以在不阻塞读写的情况下修改表结构；它通过创建新表、分块复制数据，并用触发器捕获原表增量变更，最后切换表。:contentReference[oaicite:3]{index=3}

基本原理：

```text
创建新表
  ↓
新表执行目标 DDL
  ↓
分批复制老表数据
  ↓
通过触发器同步增删改
  ↓
rename 切换新旧表
```

适合：

```text
MySQL 5.6 / 5.7
传统在线 DDL
中大型表结构变更
```

注意：

```text
pt-osc 使用触发器，写入压力高的表要谨慎评估。
```

---

## 6. 历史数据回填怎么做

不要一次性：

```sql
UPDATE order_info SET remark = '' WHERE remark IS NULL;
```

千万级大表这样会导致：

```text
大事务
锁等待
binlog 暴增
主从延迟
undo / redo 压力大
```

推荐分批回填：

```sql
UPDATE order_info
SET remark = ''
WHERE id > ?
AND id <= ?
AND remark IS NULL
LIMIT 1000;
```

回填策略：

```text
按主键范围分批
每批 500 ~ 5000 条
每批提交一次
低峰执行
控制 sleep 间隔
监控主从延迟
```

---

## 7. 代码发布要兼容

大表加字段建议分多步发布。

### 第一步：先发兼容代码

```text
代码能兼容字段不存在或字段为空
```

### 第二步：执行 DDL

```text
新增字段，允许 NULL
```

### 第三步：回填历史数据

```text
分批补齐老数据
```

### 第四步：切换业务逻辑

```text
新代码开始读写新字段
```

### 第五步：必要时加约束

```text
确认数据完整后，再考虑 NOT NULL、索引等约束
```

---

## 8. 执行前检查

执行前必须确认：

```text
MySQL 版本
表数据量
字段类型
是否有默认值
是否允许 NULL
是否涉及索引
是否有外键
是否有触发器
是否有大事务
主从延迟
磁盘空间
备份是否可用
```

尤其要看是否会等待元数据锁：

```sql
SHOW PROCESSLIST;
```

如果有长事务或慢查询占着表，DDL 可能一直等待。

---

## 9. 线上执行注意事项

- 低峰期执行。
- 加字段优先允许 `NULL`。
- 优先放到表尾。
- 明确指定 `ALGORITHM=INSTANT` 或 `INPLACE`。
- 避免直接加 `NOT NULL DEFAULT`。
- 避免同时加字段、加索引、改类型。
- 大表 DDL 前先备份。
- 监控主从延迟、CPU、IO、慢 SQL。
- 使用在线 DDL 工具时要限速。
- DDL 前确认没有长事务占用 MDL 锁。
- 先在预发或影子库验证执行计划和耗时。

---

## 10. 推荐方案

| 场景 | 推荐处理 |
|---|---|
| MySQL 8.0.12+，普通加列 | `ALGORITHM=INSTANT` |
| MySQL 支持 Online DDL | `ALGORITHM=INPLACE, LOCK=NONE` |
| 老版本 / 超大表 / 高峰业务 | `gh-ost` / `pt-online-schema-change` |
| 需要历史值 | 先加 nullable 字段，再分批回填 |
| 字段需要 NOT NULL | 回填完成后再加约束 |
| 需要加索引 | 单独评估，最好不要和加字段一起做 |

---

## 11. 面试总结

线上千万级大表加字段不能直接随便执行 `ALTER TABLE`，要先判断 MySQL 版本和 DDL 算法。

如果是 MySQL 8.0 并且满足条件，优先使用 `ALGORITHM=INSTANT`，因为它不需要重建整张表，执行速度很快。如果不支持 Instant，可以尝试 `ALGORITHM=INPLACE, LOCK=NONE`，但仍要注意元数据锁和执行耗时。

如果表非常大，或者 DDL 会触发表重建，建议使用 `gh-ost` 或 `pt-online-schema-change` 做在线变更。它们的核心思路都是创建影子表，分批同步历史数据，再同步增量数据，最后切换新旧表。

加字段时建议先加允许 `NULL` 的字段，不要直接加 `NOT NULL DEFAULT`，历史数据通过后台任务分批回填，避免大事务、锁等待和主从延迟。

一句话总结：

```text
大表加字段 = 优先 Instant DDL；
不支持则 Online DDL；
再不行用 gh-ost / pt-osc；
字段先 nullable，历史数据分批回填，低峰执行并监控。
```
