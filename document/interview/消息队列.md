# 一、为什么使用 MQ

## 1. MQ 是什么？

MQ 全称是：

```text
Message Queue
```

中文叫：

```text
消息队列
```

它是一种用于系统之间异步通信的中间件。

简单来说：

> 生产者把消息发送到 MQ，消费者从 MQ 中拉取或接收消息并处理。

基本模型：

```text
Producer 生产者
        |
        v
Message Queue 消息队列
        |
        v
Consumer 消费者
```

---

## 2. 为什么要使用 MQ？

使用 MQ 的核心原因通常有三个：

```text
1. 解耦
2. 异步
3. 削峰填谷
```

除此之外，还可以用于：

```text
最终一致性
广播通知
日志采集
事件驱动
任务缓冲
系统扩展
```

---

## 3. 解耦

### 3.1 没有 MQ 的问题

例如订单系统下单成功后，需要调用：

```text
库存系统
积分系统
优惠券系统
短信系统
物流系统
推荐系统
```

如果订单系统直接调用所有系统：

```text
订单系统 -> 库存系统
订单系统 -> 积分系统
订单系统 -> 短信系统
订单系统 -> 物流系统
```

问题是：

```text
系统之间强耦合
下游系统异常会影响主流程
新增业务需要修改订单系统代码
接口调用链路变长
系统维护成本高
```

---

### 3.2 使用 MQ 后

订单系统只需要发送一条订单创建成功消息：

```text
订单系统 -> MQ -> 库存系统
             -> 积分系统
             -> 短信系统
             -> 物流系统
```

订单系统不需要关心谁消费了这条消息。

优点：

```text
降低系统耦合
新增消费者不影响生产者
下游异常不会直接阻塞主流程
系统扩展性更好
```

---

## 4. 异步

### 4.1 同步调用问题

假设下单流程：

```text
创建订单：100ms
扣减库存：100ms
增加积分：100ms
发送短信：300ms
```

同步调用总耗时：

```text
100 + 100 + 100 + 300 = 600ms
```

用户需要等待所有流程完成。

---

### 4.2 使用 MQ 异步化

核心流程只做：

```text
创建订单
发送消息
返回成功
```

非核心流程异步处理：

```text
扣减库存
增加积分
发送短信
推送通知
```

这样接口响应可能只需要：

```text
100ms 左右
```

---

## 5. 削峰填谷

在秒杀、抢购、大促场景中，请求流量可能瞬间暴增。

如果请求直接打到数据库，可能导致：

```text
数据库连接被打满
CPU 飙高
锁竞争严重
服务雪崩
```

引入 MQ 后：

```text
高峰请求先进入 MQ
消费者按照自身处理能力慢慢消费
```

这样可以保护后端系统。

---

## 6. 最终一致性

MQ 经常用于实现分布式系统中的最终一致性。

例如下单流程：

```text
订单服务创建订单
发送扣库存消息
库存服务消费消息并扣减库存
```

如果库存服务短暂失败，可以通过：

```text
消息重试
死信队列
人工补偿
定时任务扫描
```

最终让数据达到一致状态。

---

## 7. 使用 MQ 的代价

MQ 不是只有优点，也会带来复杂度。

主要问题：

```text
1. 系统复杂度增加
2. 消息可能丢失
3. 消息可能重复
4. 消息可能乱序
5. 消息可能积压
6. 数据一致性处理更复杂
7. 运维成本增加
```

---

## 8. MQ 适合什么场景？

适合使用 MQ 的场景：

```text
异步处理
系统解耦
流量削峰
事件通知
日志采集
任务队列
最终一致性
```

不适合使用 MQ 的场景：

```text
强实时调用
强一致事务
调用方必须立即拿到结果
链路非常简单且没有扩展需求
```

---

## 9. 面试回答

使用 MQ 主要是为了解耦、异步和削峰填谷。

解耦是指生产者只负责发送消息，不需要直接依赖多个下游系统；异步是指把非核心流程放到消息队列中异步处理，提高接口响应速度；削峰填谷是指在流量高峰时先把请求写入 MQ，由消费者按照自身处理能力慢慢消费，从而保护数据库和下游服务。

不过 MQ 也会带来消息丢失、重复消费、顺序性、积压和最终一致性等问题，所以使用 MQ 时必须设计好可靠投递、幂等消费、重试、死信队列和监控告警机制。

---

# 二、MQ 如何削峰填谷

## 1. 什么是削峰填谷？

削峰填谷是指：

> 在流量高峰时，把瞬时请求先存入 MQ，后端消费者按照稳定速度处理，从而把突发流量削平。

流量示意：

```text
没有 MQ：

请求量
  ^
  |              /\ 
  |             /  \
  |            /    \
  |___________/      \___________
  |
  +--------------------------------> 时间

有 MQ：

消费量
  ^
  |        --------------------
  |       |
  |_______|
  |
  +--------------------------------> 时间
```

---

## 2. 没有 MQ 的问题

秒杀场景：

```text
瞬间 100 万请求进入系统
数据库只能承受每秒 1 万写入
```

如果请求直接打到数据库：

```text
数据库连接池耗尽
大量请求超时
数据库 CPU 飙高
库存行锁竞争严重
系统雪崩
```

---

## 3. 使用 MQ 后的流程

```text
用户请求
   |
   v
业务系统快速校验
   |
   v
写入 MQ
   |
   v
立即返回排队中/受理成功
   |
   v
消费者按固定速度消费
   |
   v
写数据库/调用下游服务
```

---

## 4. 削峰填谷核心思想

核心思想是：

```text
前端流量可以很大；
后端消费速度必须可控。
```

MQ 充当缓冲池。

```text
流量高峰时：消息堆积在 MQ 中
流量低谷时：消费者继续消费积压消息
```

---

## 5. 秒杀场景示例

用户秒杀请求进入后：

```text
1. 校验活动是否开始
2. 校验用户是否重复参与
3. 校验库存预扣或令牌
4. 发送秒杀消息到 MQ
5. 返回排队中
6. 消费者异步创建订单
7. 用户查询秒杀结果
```

---

## 6. 为什么不能无限堆积？

MQ 虽然可以缓冲流量，但不能无限堆积。

如果生产速度长期大于消费速度，会导致：

```text
消息积压
磁盘占满
消费延迟增加
业务结果长时间不可见
MQ 集群压力升高
```

因此削峰填谷必须配合：

```text
限流
降级
消费者扩容
积压监控
超时丢弃或补偿机制
```

---

## 7. 削峰填谷注意事项

```text
1. 入口要限流，不能让无限流量进入 MQ
2. 消息要设置合理的业务超时时间
3. 消费者要支持水平扩容
4. 下游数据库要评估最大处理能力
5. MQ 积压要有监控和告警
6. 核心链路要支持幂等
7. 失败消息要重试或进入死信队列
```

---

## 8. 面试回答

MQ 削峰填谷的原理是把突发流量先写入消息队列，消费者按照自身和下游系统能承受的速度慢慢消费。这样高峰期请求不会直接打爆数据库或下游服务，而是先堆积在 MQ 中，等流量低谷时继续消费。

典型场景是秒杀、大促、批量任务。需要注意的是，MQ 不能代替限流，如果生产速度长期大于消费速度，会产生消息积压，所以还需要配合入口限流、消费者扩容、积压监控、失败重试和降级策略。

# 三、如何保证消息不丢失

## 1. 消息丢失可能发生在哪里？

消息从生产到消费，主要经过三个阶段：

```text
1. 生产者发送消息到 MQ
2. MQ Broker 存储消息
3. 消费者消费消息
```

因此消息丢失可能发生在：

```text
生产者阶段
Broker 阶段
消费者阶段
```

---

## 2. 生产者阶段丢失

### 2.1 可能原因

```text
网络抖动
发送超时
Broker 宕机
生产者发送后没有确认结果
异步发送失败未处理
```

---

### 2.2 解决方案

```text
1. 开启发送确认机制
2. 发送失败进行重试
3. 记录本地消息表
4. 使用事务消息
5. 发送结果必须落日志
6. 异步发送必须处理回调
```

---

### 2.3 本地消息表方案

流程：

```text
1. 业务数据入库
2. 本地消息表记录待发送消息
3. 提交本地事务
4. 后台任务扫描待发送消息
5. 发送到 MQ
6. 发送成功后更新消息状态
7. 失败则重试
```

优点：

```text
业务数据和消息记录在同一个本地事务中
可靠性高
适合强可靠业务
```

---

## 3. Broker 阶段丢失

### 3.1 可能原因

```text
Broker 收到消息但还没刷盘就宕机
Broker 单点故障
副本同步未完成
磁盘故障
配置为异步刷盘导致短时间数据丢失
```

---

### 3.2 解决方案

```text
1. 开启持久化
2. 配置同步刷盘或高可靠刷盘策略
3. 配置主从复制或多副本
4. 等待副本确认
5. 部署高可用集群
6. 监控磁盘和复制状态
```

---

## 4. 消费者阶段丢失

### 4.1 可能原因

```text
消费者拉到消息后还没处理完就提交 offset / ack
业务处理异常但确认了消息
消费者宕机
代码吞掉异常
```

---

### 4.2 解决方案

```text
1. 业务处理成功后再 ack / commit offset
2. 处理失败不要确认消息
3. 开启消费重试
4. 失败多次进入死信队列
5. 消费逻辑保证幂等
6. 关键业务落库记录消费状态
```

---

## 5. Kafka 如何减少消息丢失？

常见配置思路：

```text
生产者：
acks=all
retries > 0
enable.idempotence=true

Broker：
合理配置 replication.factor
min.insync.replicas >= 2

消费者：
关闭自动提交 offset
业务处理成功后手动提交 offset
```

---

## 6. RocketMQ 如何减少消息丢失？

常见做法：

```text
使用同步发送
检查发送结果
发送失败重试
开启 Broker 持久化
重要消息使用事务消息
消费成功后再返回 CONSUME_SUCCESS
消费失败返回 RECONSUME_LATER
失败多次进入死信队列
```

---

## 7. RabbitMQ 如何减少消息丢失？

常见做法：

```text
生产者开启 Publisher Confirm
队列设置 durable
消息设置 persistent
消费者手动 ack
处理成功后再 ack
处理失败 nack/reject 并决定是否 requeue
配置镜像队列或 quorum queue
```

---

## 8. 消息不丢失完整链路

```text
生产者可靠发送
    |
    v
Broker 可靠存储
    |
    v
消费者可靠消费
```

每一段都要保证：

```text
有确认
有重试
有持久化
有补偿
有监控
```

---

## 9. 面试回答

保证消息不丢失要从生产者、Broker 和消费者三个阶段考虑。

生产者阶段要开启发送确认机制，发送失败要重试，关键业务可以使用本地消息表或事务消息。Broker 阶段要开启消息持久化，配置主从复制或多副本，并根据业务可靠性要求选择同步刷盘或副本确认机制。消费者阶段要在业务处理成功后再提交 offset 或 ack，处理失败不能确认消息，要让消息重试或进入死信队列。

同时，消费端必须做好幂等，因为只要开启重试机制，就可能出现重复消费。

# 四、如何保证消息不重复消费

## 1. 为什么会重复消费？

MQ 通常更容易保证：

```text
至少投递一次
```

而不是绝对只投递一次。

也就是说：

```text
消息不丢失和消息不重复，很难同时天然保证。
```

为了保证不丢消息，MQ 往往会在异常场景下重新投递消息。

---

## 2. 重复消费常见原因

```text
1. 消费者处理成功，但 ack 失败
2. 消费者处理成功，但提交 offset 失败
3. 消费者处理超时，被 MQ 认为失败
4. 消费过程中消费者宕机
5. MQ 重试机制导致重复投递
6. 生产者发送重试导致重复消息
7. 网络抖动导致确认丢失
```

---

## 3. 解决核心：幂等性

解决重复消费的核心不是完全避免重复投递，而是：

> 保证同一条消息重复消费多次，业务结果仍然正确。

这就是幂等性。

---

## 4. 什么是幂等？

幂等是指：

```text
同一个操作执行一次和执行多次，最终结果一致。
```

例如：

```text
设置订单状态为已支付：幂等
账户余额扣减 100 元：非幂等
```

---

## 5. 幂等方案一：唯一业务 ID

每条消息必须有唯一业务 ID，例如：

```text
orderId
paymentId
messageId
requestId
eventId
```

消费时先判断是否处理过。

---

## 6. 幂等方案二：数据库唯一约束

建立消费记录表：

```sql
CREATE TABLE mq_consume_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    message_id VARCHAR(128) NOT NULL,
    consumer_group VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL,
    create_time DATETIME NOT NULL,
    UNIQUE KEY uk_msg_group(message_id, consumer_group)
);
```

消费流程：

```text
1. 消费者收到消息
2. 插入消费记录
3. 如果插入成功，说明第一次消费
4. 执行业务逻辑
5. 更新消费状态
6. 如果唯一键冲突，说明已经消费过，直接返回成功
```

---

## 7. 幂等方案三：业务状态机

利用业务状态判断是否允许重复执行。

例如订单状态：

```text
待支付 -> 已支付 -> 已发货 -> 已完成
```

支付消息消费：

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_id = ?
  AND status = 'WAIT_PAY';
```

如果重复消费，订单已经是 `PAID`，更新行数为 0，不会重复处理。

---

## 8. 幂等方案四：Redis 去重

使用 Redis 记录消息是否处理过。

```bash
SET mq:consume:messageId 1 NX EX 86400
```

如果设置成功，说明第一次消费。

如果设置失败，说明已经处理过。

适合：

```text
高并发
允许一定过期时间
去重窗口有限
```

注意：

```text
Redis 去重需要考虑 Redis 数据丢失和过期时间。
```

---

## 9. 幂等方案五：分布式锁

对于同一个业务 key，可以加分布式锁。

例如：

```text
lock:order:1001
```

防止同一订单被并发重复处理。

但分布式锁通常不是最终幂等方案，最好仍然配合业务状态或唯一约束。

---

## 10. 消费确认时机

正确方式：

```text
业务处理成功后，再 ack / commit offset。
```

错误方式：

```text
先 ack，再执行业务。
```

如果先 ack 后业务失败，消息就丢了。

---

## 11. 面试回答

消息重复消费很常见，因为 MQ 为了保证消息不丢，通常会采用至少投递一次机制。消费者处理成功但 ack 失败、提交 offset 失败、消费超时、消费者宕机或生产者重试，都可能导致消息重复。

解决重复消费的核心是业务幂等。常见方案包括：使用消息唯一 ID 建消费记录表并加唯一索引；利用业务状态机控制状态流转；使用 Redis 的 `SET NX` 做去重；必要时加分布式锁。消费端应该在业务处理成功后再 ack 或提交 offset。

# 五、如何保证消息顺序

## 1. 什么是消息顺序？

消息顺序通常分为：

```text
1. 全局顺序
2. 局部顺序
```

---

## 2. 全局顺序

全局顺序是指：

```text
整个 Topic / Queue 中所有消息都严格按照发送顺序消费。
```

这种要求非常高。

通常意味着：

```text
只能使用一个队列或一个分区；
只能有一个消费者串行消费；
吞吐量会明显下降。
```

---

## 3. 局部顺序

局部顺序是指：

```text
同一个业务 key 的消息保持顺序。
```

例如：

```text
同一个订单的创建、支付、发货、完成消息必须顺序消费；
不同订单之间可以并行消费。
```

实际业务中更常见的是局部顺序。

---

## 4. 顺序消息核心原则

保证顺序的核心是：

```text
同一个业务 key 的消息进入同一个队列或分区；
同一个队列或分区由同一个消费者按顺序消费。
```

---

## 5. Kafka 如何保证顺序？

Kafka 的顺序性是：

```text
同一个 Partition 内有序；
不同 Partition 之间不保证顺序。
```

因此要保证同一个订单消息有序，需要：

```text
使用 orderId 作为消息 key；
让同一个 orderId 的消息进入同一个 Partition；
同一个 Partition 内按 offset 顺序消费。
```

示例：

```text
key = orderId
```

---

## 6. RocketMQ 如何保证顺序？

RocketMQ 顺序消息通常做法：

```text
同一个业务 key 选择同一个 MessageQueue；
消费者顺序消费该队列。
```

例如：

```text
同一个 orderId 的消息发送到同一个队列。
```

---

## 7. RabbitMQ 如何保证顺序？

RabbitMQ 中可以通过：

```text
同一个业务 key 路由到同一个 Queue；
单个消费者串行消费；
合理设置 prefetch；
处理失败时注意重试顺序。
```

如果多个消费者同时消费同一个队列，严格顺序会更难保证。

---

## 8. 消费失败对顺序的影响

顺序消息中，如果某条消息消费失败：

```text
不能直接跳过继续消费后面的消息；
否则会破坏顺序。
```

常见处理方式：

```text
暂停当前队列消费
等待重试
达到最大次数后进入死信或人工处理
```

---

## 9. 顺序消息的代价

保证顺序会带来代价：

```text
并发度下降
吞吐量下降
某个 key 的慢消息会阻塞后续消息
失败重试会影响后续消费
热点 key 可能导致单分区压力过大
```

---

## 10. 面试回答

保证消息顺序的核心是让同一个业务 key 的消息进入同一个队列或分区，并由同一个消费者按顺序消费。

Kafka 中同一个 Partition 内有序，不同 Partition 不保证顺序，所以可以使用业务 key，例如 orderId 作为消息 key，让同一个订单的消息进入同一个 Partition。RocketMQ 可以通过 MessageQueueSelector 将同一个业务 key 的消息发送到同一个队列。RabbitMQ 可以让同一个业务 key 路由到同一个 Queue，并使用单消费者串行消费。

实际业务中通常保证局部顺序，而不是全局顺序，因为全局顺序会严重影响吞吐量。

---

# 六、如何处理消息积压

## 1. 什么是消息积压？

消息积压是指：

```text
生产者发送消息的速度 > 消费者消费消息的速度
```

导致 MQ 中未消费消息越来越多。

---

## 2. 消息积压的表现

常见表现：

```text
消费延迟升高
队列堆积数量持续增加
消费者 CPU 或线程池打满
数据库压力升高
业务处理结果延迟
监控告警触发
```

---

## 3. 消息积压常见原因

```text
1. 消费者处理能力不足
2. 消费者数量太少
3. 消费逻辑慢
4. 下游数据库或接口慢
5. 消费者频繁异常重试
6. 单条消息处理耗时过长
7. 消息体过大
8. 消费线程池配置不合理
9. MQ 分区或队列数量不足
10. 热点 key 导致单分区积压
```

---

## 4. 处理步骤一：先判断积压原因

排查方向：

```text
1. 看消费者是否存活
2. 看消费者是否报错
3. 看消费耗时是否变长
4. 看下游数据库是否慢
5. 看是否大量重试
6. 看是否某个分区或队列热点
7. 看队列数量和消费者数量是否匹配
```

---

## 5. 处理步骤二：临时扩容消费者

如果消费逻辑正常，只是消费能力不足，可以扩容消费者实例。

```text
增加消费者机器
增加消费者线程数
增加消费并发度
```

注意：

```text
消费者数量不能无限增加；
Kafka 中同一个消费组内消费者数量超过 Partition 数没有意义；
RocketMQ/RabbitMQ 也受队列数量和业务并发限制。
```

---

## 6. 处理步骤三：优化消费逻辑

常见优化：

```text
减少单条消息处理耗时
批量消费
批量写数据库
减少远程调用
增加本地缓存
优化慢 SQL
异步化非核心逻辑
```

---

## 7. 处理步骤四：排查下游瓶颈

如果消费者慢是因为下游慢，比如数据库慢：

```text
盲目扩容消费者可能会打爆数据库。
```

此时应该：

```text
优化数据库
增加限流
批量处理
降级非核心逻辑
控制消费速率
```

---

## 8. 处理步骤五：跳过或隔离异常消息

如果某些消息一直消费失败，会反复重试，拖慢整体消费。

解决方式：

```text
达到最大重试次数后进入死信队列
异常消息落库
人工处理
跳过毒丸消息
```

这种反复失败的消息也叫：

```text
毒丸消息
```

---

## 9. 处理步骤六：增加队列或分区

如果单个队列或分区成为瓶颈，可以增加队列或分区数量。

例如 Kafka：

```text
增加 Topic Partition 数
增加消费者实例
提升并行消费能力
```

注意：

```text
增加分区可能影响消息顺序和 key 分布；
需要评估业务影响。
```

---

## 10. 处理步骤七：临时转储积压消息

如果积压非常严重，可以考虑：

```text
临时启动专门消费者快速拉取消息
将消息转储到临时 Topic / 队列 / 文件 / 数据库
再慢慢回放处理
```

这种方案适合紧急止血，但实现复杂，需要谨慎。

---

## 11. 消息积压预防措施

```text
1. 监控消费延迟
2. 监控队列积压量
3. 监控消费者异常率
4. 监控消费耗时
5. 设置死信队列
6. 做容量评估和压测
7. 消费端支持水平扩容
8. 下游服务设置限流保护
```

---

## 12. 面试回答

处理消息积压首先要定位原因，看是消费者宕机、消费异常、消费逻辑变慢、下游数据库变慢，还是队列分区数量不足。

如果只是消费能力不足，可以临时扩容消费者，增加消费线程或消费者实例。如果消费逻辑慢，要优化 SQL、减少远程调用、批量处理或异步化。如果是异常消息反复重试，要让其进入死信队列或落库人工处理。如果是单分区或单队列瓶颈，可以增加分区或队列数量。

同时要做好积压量、消费延迟、异常率和消费耗时监控，提前告警。

---

# 七、死信队列是什么

## 1. 什么是死信？

死信是指：

> 无法被正常消费或无法被正常投递的消息。

这些消息如果一直留在正常队列中，会影响正常消费。

因此通常会被转移到专门的队列中，这个队列就叫死信队列。

---

## 2. 死信队列是什么？

死信队列英文是：

```text
Dead Letter Queue，DLQ
```

它用于保存处理失败、过期、被拒绝或达到最大重试次数的消息。

---

## 3. 什么情况下消息会进入死信队列？

常见场景：

```text
1. 消费失败超过最大重试次数
2. 消息被消费者拒绝且不重新入队
3. 消息过期
4. 队列达到最大长度
5. 消息无法路由
6. 业务主动投递到死信队列
```

不同 MQ 的死信机制略有差异。

---

## 4. 死信队列的作用

死信队列主要用于：

```text
1. 防止异常消息阻塞正常队列
2. 保存失败消息，便于排查
3. 支持人工补偿
4. 支持后续重放
5. 提高系统可观测性
```

---

## 5. 死信队列处理流程

```text
消费者消费消息失败
        |
        v
MQ 自动重试或业务重试
        |
        v
超过最大重试次数
        |
        v
消息进入死信队列
        |
        v
告警通知
        |
        v
人工排查或自动补偿
```

---

## 6. 死信消息如何处理？

常见处理方式：

```text
1. 记录告警
2. 人工查看失败原因
3. 修复业务数据
4. 手动重新投递
5. 定时任务补偿
6. 丢弃无效消息
7. 单独建立后台管理页面
```

---

## 7. RabbitMQ 死信队列

RabbitMQ 通常通过：

```text
Dead Letter Exchange，DLX
```

实现死信队列。

消息成为死信后，会被重新发布到指定的死信交换机，再路由到死信队列。

---

## 8. RocketMQ 死信队列

RocketMQ 中，消息消费失败会进行重试。

超过最大重试次数后，消息会进入死信队列。

通常可以根据 ConsumerGroup 找到对应死信 Topic。

---

## 9. Kafka 死信队列

Kafka 本身没有强制统一的死信队列模型，通常由业务实现。

常见做法：

```text
消费失败达到阈值后，将消息发送到 DLT Topic
```

例如：

```text
order-topic
order-topic-dlt
```

---

## 10. 面试回答

死信队列是用于保存无法被正常消费或无法正常投递消息的特殊队列。消息消费失败超过最大重试次数、被拒绝且不重新入队、消息过期或队列满等情况，都可能进入死信队列。

死信队列的作用是隔离异常消息，避免影响正常消息消费，同时方便后续排查、告警、人工补偿或重新投递。实际项目中死信队列必须配合监控告警，否则消息进入死信队列后没人处理，问题仍然存在。

---

# 八、延迟队列怎么实现

## 1. 什么是延迟队列？

延迟队列是指：

> 消息发送后，不会立即被消费，而是在指定时间之后才能被消费。

例如：

```text
订单 30 分钟未支付自动取消
优惠券到期提醒
延迟重试
定时任务触发
超时关单
物流超时检查
```

---

## 2. 延迟队列常见实现方式

常见实现方式：

```text
1. MQ 原生延迟消息
2. RabbitMQ TTL + 死信队列
3. RabbitMQ 延迟消息插件
4. Redis ZSet
5. Kafka 延迟 Topic / 时间轮
6. 数据库定时扫描
7. 时间轮
```

---

## 3. RocketMQ 延迟消息

RocketMQ 支持延迟消息。

发送消息时可以设置延迟时间或延迟级别。

适合场景：

```text
订单超时取消
延迟重试
定时触发
```

流程：

```text
1. 生产者发送延迟消息
2. Broker 暂存消息
3. 到达指定时间后消息变为可投递
4. 消费者消费消息
```

---

## 4. RabbitMQ TTL + DLX 实现延迟队列

RabbitMQ 可以通过：

```text
TTL + Dead Letter Exchange
```

实现延迟队列。

流程：

```text
1. 消息先发送到延迟队列
2. 延迟队列不绑定消费者
3. 消息在延迟队列中等待 TTL 到期
4. 消息过期后成为死信
5. 死信被投递到死信交换机
6. 死信交换机路由到真正消费队列
7. 消费者消费消息
```

---

## 5. RabbitMQ TTL + DLX 图

```text
Producer
   |
   v
Delay Exchange
   |
   v
Delay Queue，设置 TTL，不消费
   |
   | TTL 到期，变成死信
   v
Dead Letter Exchange
   |
   v
Real Queue
   |
   v
Consumer
```

---

## 6. RabbitMQ 延迟插件

RabbitMQ 也可以使用延迟消息插件。

特点：

```text
使用 x-delayed-message 交换机
通过消息头设置延迟时间
到期后再路由到目标队列
```

优点：

```text
使用方便
不同消息可设置不同延迟时间
```

---

## 7. Redis ZSet 实现延迟队列

使用 ZSet：

```text
member：消息内容或消息 ID
score：执行时间戳
```

写入：

```bash
ZADD delay:queue 1714380000000 order:1
```

消费者轮询：

```bash
ZRANGEBYSCORE delay:queue 0 当前时间戳 LIMIT 0 10
```

取到后删除：

```bash
ZREM delay:queue order:1
```

为了避免并发重复消费，删除需要保证原子性，可以使用 Lua 脚本。

---

## 8. Kafka 延迟队列实现

Kafka 本身更偏日志流模型，通常不直接作为精确延迟队列。

常见方案：

```text
1. 延迟 Topic
2. 重试 Topic
3. 时间轮调度
4. 消费端判断时间，未到期则暂停或转发
```

例如：

```text
order-delay-5m
order-delay-30m
order-delay-1h
```

消息先进入不同延迟 Topic，到期后再转发到真实业务 Topic。

---

## 9. 数据库定时扫描

数据库方案：

```text
将任务保存到任务表
记录执行时间
定时任务扫描到期任务
执行任务
更新任务状态
```

示例：

```sql
SELECT *
FROM delay_task
WHERE execute_time <= NOW()
  AND status = 'INIT'
LIMIT 100;
```

优点：

```text
简单可靠
方便查询和补偿
```

缺点：

```text
扫描压力大
实时性一般
高并发能力弱
```

---

## 10. 时间轮

时间轮是一种高效的定时任务调度结构。

适合：

```text
大量定时任务
延迟任务
超时检测
```

Netty、Kafka、RocketMQ 等系统中都能看到类似思想。

---

## 11. 延迟队列方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| RocketMQ 延迟消息 | 原生支持，使用简单 | 依赖 RocketMQ 能力 |
| RabbitMQ TTL + DLX | 不依赖插件 | 不同延迟时间管理复杂 |
| RabbitMQ 延迟插件 | 使用方便 | 需要安装插件 |
| Redis ZSet | 灵活，简单 | 需要自己保证可靠性 |
| Kafka 延迟 Topic | 适合 Kafka 体系 | 实现复杂，延迟精度一般 |
| 数据库扫描 | 简单可靠，可补偿 | 性能和实时性一般 |
| 时间轮 | 性能高 | 实现复杂 |

---

## 12. 面试回答

延迟队列是指消息发送后不会立即消费，而是在指定时间后才能被消费，常用于订单超时取消、延迟重试和定时任务。

实现方式有很多。RocketMQ 支持原生延迟消息；RabbitMQ 可以通过 TTL 加死信交换机实现，也可以使用延迟消息插件；Redis 可以用 ZSet 实现，score 存执行时间戳，消费者扫描到期消息；Kafka 通常通过延迟 Topic、重试 Topic 或时间轮实现；简单场景也可以用数据库定时扫描。

不同方案要根据可靠性、延迟精度、吞吐量和系统复杂度选择。

---

# 九、RocketMQ / Kafka / RabbitMQ 区别

## 1. 三者定位

| MQ | 定位 |
|---|---|
| RocketMQ | 分布式消息中间件，偏业务消息、事务消息、顺序消息、延迟消息 |
| Kafka | 分布式日志流平台，偏高吞吐、流式处理、日志采集、大数据 |
| RabbitMQ | AMQP 消息队列，偏传统消息路由、灵活路由、企业集成 |

---

## 2. RocketMQ 特点

RocketMQ 特点：

```text
1. 支持普通消息
2. 支持顺序消息
3. 支持延迟消息
4. 支持事务消息
5. 支持消息重试
6. 支持死信队列
7. 适合业务系统解耦和最终一致性
8. Java 生态使用较多
```

适合场景：

```text
订单
交易
支付
库存
事务消息
延迟消息
业务事件驱动
```

---

## 3. Kafka 特点

Kafka 特点：

```text
1. 高吞吐
2. 分区存储
3. 顺序追加写
4. 消费者通过 offset 管理消费进度
5. 天然适合日志流和数据管道
6. 适合大数据和实时流处理
7. 分区内有序
```

适合场景：

```text
日志采集
用户行为埋点
实时数据流
大数据管道
监控数据
流式计算
```

---

## 4. RabbitMQ 特点

RabbitMQ 特点：

```text
1. 基于 AMQP
2. Exchange 路由能力强
3. 支持 direct、fanout、topic、headers 等交换机
4. 支持 ack、confirm、TTL、DLX
5. 功能成熟
6. 路由模型灵活
```

适合场景：

```text
企业应用集成
异步任务
复杂路由
中小规模业务消息
延迟重试
```

## 13. 面试回答

RocketMQ、Kafka 和 RabbitMQ 都是常见 MQ，但定位不同。

RocketMQ 更偏业务消息，支持顺序消息、延迟消息、事务消息、重试和死信队列，适合订单、交易、支付、库存等业务场景。

Kafka 更像分布式日志流平台，基于 Topic 和 Partition，吞吐量很高，适合日志采集、埋点、大数据管道和流式计算。Kafka 保证 Partition 内有序。

RabbitMQ 基于 AMQP，核心模型是 Exchange、Queue 和 Binding，路由能力很强，适合企业应用集成、复杂路由、异步任务和中小规模业务消息。

选型时，如果追求高吞吐日志流，优先 Kafka；如果是复杂业务消息和事务消息，优先 RocketMQ；如果需要灵活路由和传统消息队列模型，可以选择 RabbitMQ。

# 十二、完整面试回答模板

使用 MQ 主要是为了解耦、异步和削峰填谷。解耦是指生产者只需要发送消息，不需要直接依赖多个下游系统；异步是指把非核心流程放到消息队列中处理，提高主流程响应速度；削峰填谷是指在流量高峰时先把请求写入 MQ，由消费者按照稳定速度消费，从而保护数据库和下游服务。MQ 也常用于最终一致性、事件驱动和任务缓冲。

MQ 削峰填谷的原理是把突发流量先写入消息队列，消费者按照自身和下游系统能承受的速度慢慢消费。高峰期消息堆积在 MQ 中，低谷期继续消费积压消息。不过 MQ 不能代替限流，如果生产速度长期大于消费速度，会导致消息积压，所以还需要配合入口限流、消费者扩容、积压监控和降级策略。

保证消息不丢失要从生产者、Broker 和消费者三个阶段考虑。生产者阶段要开启发送确认机制，失败要重试，关键业务可以使用本地消息表或事务消息。Broker 阶段要开启持久化，配置主从复制或多副本，并根据业务可靠性要求选择同步刷盘或副本确认机制。消费者阶段要在业务处理成功后再提交 offset 或 ack，处理失败不能确认消息，要让消息重试或进入死信队列。

消息重复消费很常见，因为 MQ 为了保证消息不丢，通常会采用至少投递一次机制。消费者处理成功但 ack 失败、提交 offset 失败、消费超时、消费者宕机或生产者重试，都可能导致消息重复。解决重复消费的核心是业务幂等，常见方案包括消费记录表唯一索引、业务状态机、Redis 去重和分布式锁。

保证消息顺序的核心是让同一个业务 key 的消息进入同一个队列或分区，并由同一个消费者按顺序消费。Kafka 中同一个 Partition 内有序，不同 Partition 不保证顺序，所以可以使用 orderId 作为消息 key。RocketMQ 可以把同一个业务 key 的消息发送到同一个 MessageQueue。RabbitMQ 可以让同一个业务 key 路由到同一个 Queue，并使用单消费者串行消费。实际业务中通常保证局部顺序，而不是全局顺序。

处理消息积压时，首先要定位原因，看是消费者宕机、消费异常、消费逻辑慢、下游数据库慢，还是分区或队列数量不足。如果只是消费能力不足，可以扩容消费者或增加消费线程；如果消费逻辑慢，要优化 SQL、减少远程调用、批量处理或异步化；如果是异常消息反复重试，要让其进入死信队列或落库人工处理；如果是单分区瓶颈，可以增加分区或队列数量。

死信队列是用于保存无法被正常消费或无法正常投递消息的特殊队列。消息消费失败超过最大重试次数、被拒绝且不重新入队、消息过期或队列满等情况，都可能进入死信队列。死信队列的作用是隔离异常消息，避免影响正常消费，同时方便后续排查、告警、人工补偿或重新投递。

延迟队列是指消息发送后不会立即被消费，而是在指定时间后才能被消费，常用于订单超时取消、延迟重试和定时任务。RocketMQ 支持原生延迟消息；RabbitMQ 可以通过 TTL 加死信交换机实现，也可以使用延迟消息插件；Redis 可以用 ZSet 实现，score 存执行时间戳；Kafka 通常通过延迟 Topic、重试 Topic 或时间轮实现；简单场景也可以用数据库定时扫描。

RocketMQ、Kafka 和 RabbitMQ 的定位不同。RocketMQ 更偏业务消息，支持顺序消息、延迟消息、事务消息、重试和死信队列，适合订单、交易、支付、库存等业务场景。Kafka 更像分布式日志流平台，基于 Topic 和 Partition，吞吐量高，适合日志采集、埋点、大数据管道和流式计算。RabbitMQ 基于 AMQP，核心模型是 Exchange、Queue 和 Binding，路由能力强，适合企业应用集成、复杂路由和中小规模业务消息。
