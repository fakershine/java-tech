## 4. 面试回答

项目中最大的难点是下单链路的高并发和分布式一致性问题。

因为一个下单请求不仅要创建订单，还要校验库存、扣减库存、核销优惠券、发送消息通知，并且后续还涉及支付和订单状态流转。这个过程中任何一个环节失败，都可能导致订单、库存、优惠券状态不一致。

另外，用户可能重复点击，前端可能重试，网关或调用方也可能重试，这些都会导致接口重复调用。所以我们需要同时解决接口幂等、库存防超卖、消息可靠投递、重复消费和异常补偿问题。

# 六、你是怎么解决的

## 1. 解决方案总览

针对下单链路问题，我们主要用了以下方案：

```text
1. 接口幂等防重复提交
2. Redis 分布式锁控制并发
3. 数据库唯一索引兜底
4. 乐观锁防止库存超卖
5. 订单状态机控制状态流转
6. RocketMQ 异步解耦
7. 本地消息表保证消息可靠投递
8. 消费端幂等防止重复消费
9. 定时任务补偿异常数据
10. Sentinel 限流降级保护系统
```

---

## 2. 接口幂等

下单前，前端先获取一个下单 token。

服务端生成 token 后存入 Redis：

```bash
SET order:token:userId:token 1 EX 300
```

提交订单时，服务端通过 Lua 脚本校验并删除 token：

```lua
if redis.call('get', KEYS[1]) then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

这样可以保证：

```text
同一个 token 只能使用一次。
```

---

## 3. 分布式锁

对于同一个用户、同一个商品的并发下单，我们使用 Redis 分布式锁：

```text
lock:order:userId:skuId
```

加锁成功后才进入下单逻辑。

这样可以避免同一用户短时间重复下单。

---

## 4. 数据库唯一索引兜底

对于业务上必须唯一的数据，数据库加唯一索引。

例如：

```sql
UNIQUE KEY uk_order_no(order_no)
UNIQUE KEY uk_user_coupon(user_id, coupon_id)
```

这样即使 Redis 或代码层出现问题，数据库也能做最后兜底。

---

## 5. 防止库存超卖

库存扣减使用乐观锁：

```sql
UPDATE product_stock
SET stock = stock - #{num}
WHERE sku_id = #{skuId}
  AND stock >= #{num};
```

如果更新行数为 0，说明库存不足。

这样可以保证库存不会扣成负数。

---

## 6. 消息可靠投递

下单成功后，需要发送订单创建消息。

为了防止消息丢失，我们使用本地消息表：

```text
1. 创建订单
2. 插入本地消息表
3. 提交本地事务
4. 后台任务扫描待发送消息
5. 发送 RocketMQ
6. 发送成功后更新消息状态
7. 失败则重试
```

---

## 7. 消费端幂等

消费者消费消息时，根据 `messageId` 或业务唯一键做幂等。

例如建立消费记录表：

```sql
CREATE TABLE mq_consume_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    message_id VARCHAR(128) NOT NULL,
    consumer_group VARCHAR(128) NOT NULL,
    create_time DATETIME NOT NULL,
    UNIQUE KEY uk_msg_group(message_id, consumer_group)
);
```

如果插入消费记录失败，说明消息已经消费过，直接返回成功。

---

## 8. 定时补偿

对于极端异常情况，例如：

```text
订单创建成功但消息发送失败
库存扣减成功但订单取消失败
优惠券核销成功但订单创建失败
```

我们通过定时任务扫描异常状态数据，并进行补偿处理。

---

## 9. 面试回答

我们主要从幂等、并发控制、消息可靠性和补偿机制几个方面解决。

首先，下单接口使用 Redis token 防止重复提交，同时对关键业务字段加数据库唯一索引兜底。其次，库存扣减使用带条件的 update，例如 `stock >= num`，避免并发下库存扣成负数。对于同一用户短时间重复下单，使用 Redis 分布式锁控制并发。

在跨服务数据一致性方面，我们没有使用强依赖的分布式事务，而是使用 RocketMQ 异步解耦，并结合本地消息表保证消息可靠投递。消费端通过消费记录表和唯一索引保证幂等。最后通过定时补偿任务扫描异常状态数据，保证最终一致性。

## 2. 示例一：慢 SQL 优化

### 问题

订单列表查询接口响应较慢，线上高峰期偶尔超过 2 秒。

原 SQL 类似：

```sql
SELECT *
FROM orders
WHERE user_id = ?
ORDER BY create_time DESC
LIMIT ?, ?;
```

问题：

```text
1. 使用 SELECT *
2. create_time 排序没有充分利用索引
3. 深分页时扫描数据量大
4. 回表次数较多
```

---

### 优化

建立联合索引：

```sql
CREATE INDEX idx_user_time ON orders(user_id, create_time DESC);
```

把查询字段改为必要字段：

```sql
SELECT id, order_no, status, amount, create_time
FROM orders
WHERE user_id = ?
ORDER BY create_time DESC
LIMIT ?, ?;
```

对深分页使用游标分页：

```sql
SELECT id, order_no, status, amount, create_time
FROM orders
WHERE user_id = ?
  AND create_time < ?
ORDER BY create_time DESC
LIMIT 20;
```

---

### 效果

```text
接口平均响应时间从 1.5s 降到 200ms 左右。
```

## 3. 示例二：缓存优化

### 问题

商品详情接口访问量很高，直接查询数据库压力较大。

---

### 优化

使用 Redis 缓存商品详情：

```text
1. 先查 Redis
2. Redis 命中直接返回
3. 未命中查 MySQL
4. 写入 Redis
5. 设置随机 TTL
```

防止缓存穿透：

```text
对不存在商品缓存空值；
对非法 ID 做参数校验；
热点商品提前预热。
```

防止缓存击穿：

```text
热点 key 使用互斥锁或逻辑过期。
```

## 5. 面试回答

我做过几类性能优化。

第一类是 SQL 和索引优化。比如订单列表接口原来按照用户和时间查询，但是索引设计不合理，导致排序和扫描成本较高。我通过 `EXPLAIN` 分析执行计划，建立了 `(user_id, create_time)` 联合索引，同时减少 `SELECT *`，只查询必要字段，并对深分页改成游标分页，接口响应时间从秒级降到几百毫秒。

第二类是缓存优化。对于商品详情、用户信息这类读多写少的数据，我们接入 Redis 缓存，并通过随机 TTL、空值缓存、互斥锁和热点预热来避免缓存穿透、击穿和雪崩。

第三类是异步优化。下单后的短信通知、积分增加、消息推送等非核心逻辑通过 RocketMQ 异步处理，减少主链路耗时。

# 十、项目中如何保证接口幂等

## 1. 什么是接口幂等？

接口幂等是指：

> 同一个请求执行一次和执行多次，最终结果一致。

例如：

```text
用户重复点击下单按钮；
网络超时后前端重试；
网关重试；
MQ 重复消费；
```

这些都可能导致同一个操作被执行多次。

---

## 2. 哪些接口需要幂等？

常见需要幂等的接口：

```text
下单接口
支付回调接口
退款接口
优惠券核销接口
库存扣减接口
提交表单接口
MQ 消费接口
```

---

## 3. 幂等实现方案

常见方案：

```text
1. 前端防重复提交
2. Token 机制
3. Redis SET NX
4. 数据库唯一索引
5. 乐观锁
6. 状态机
7. 分布式锁
8. 消费记录表
```

---

## 4. Token 机制

下单前先获取 token：

```text
GET /order/token
```

服务端生成 token 并存 Redis：

```bash
SET order:token:userId:token 1 EX 300
```

提交订单时携带 token：

```text
POST /order/create
```

服务端使用 Lua 脚本校验并删除 token。

如果删除成功，说明第一次提交。

如果删除失败，说明重复提交。

---

## 5. Redis SET NX

对于业务唯一请求，可以使用：

```bash
SET idem:order:requestId 1 NX EX 300
```

如果设置成功，继续执行业务。

如果设置失败，说明请求已经处理过。

---

## 6. 数据库唯一索引

例如订单号唯一：

```sql
UNIQUE KEY uk_order_no(order_no)
```

支付流水唯一：

```sql
UNIQUE KEY uk_pay_no(pay_no)
```

即使应用层重复处理，数据库也能兜底防止重复数据。

---

## 7. 状态机控制

例如订单状态：

```text
待支付 -> 已支付 -> 已发货 -> 已完成
```

支付回调时：

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_no = ?
  AND status = 'WAIT_PAY';
```

如果重复回调，订单已经是 `PAID`，更新行数为 0，不会重复处理。

---

## 8. MQ 消费幂等

消费消息时，使用消息 ID 或业务 ID 做唯一约束：

```sql
UNIQUE KEY uk_msg_group(message_id, consumer_group)
```

如果消息已经消费过，直接返回成功。

---

## 9. 面试回答

项目中接口幂等主要根据场景处理。

对于下单这种用户主动提交接口，我们使用 token 机制。用户进入下单页时先获取 token，服务端把 token 存到 Redis。提交订单时通过 Lua 脚本校验并删除 token，保证同一个 token 只能使用一次。

对于支付回调、退款回调这类接口，我们主要使用业务状态机和数据库唯一索引。例如支付回调只允许订单从待支付更新为已支付，如果订单已经是已支付状态，重复回调不会再次处理。

对于 MQ 消费，我们使用消费记录表，基于 messageId 和 consumerGroup 建唯一索引，保证同一条消息不会被重复处理。

# 十一、项目中如何保证数据一致性

## 1. 数据一致性场景

项目中常见数据一致性问题：

```text
1. 订单创建成功，库存扣减失败
2. 库存扣减成功，订单创建失败
3. 订单支付成功，订单状态更新失败
4. 优惠券核销成功，订单创建失败
5. MQ 消息发送失败
6. MQ 消费失败或重复消费
```

---

## 2. 一致性方案选择

项目中一般根据业务选择不同一致性方案：

| 场景 | 方案 |
|---|---|
| 单服务单库 | 本地事务 |
| 跨服务非强实时 | MQ 最终一致性 |
| 关键链路消息可靠 | 本地消息表 / 事务消息 |
| 强一致要求 | 分布式事务 / TCC |
| 异常情况 | 定时补偿 / 对账 |

---

## 3. 本地事务

单个服务内部可以使用数据库事务：

```java
@Transactional(rollbackFor = Exception.class)
public void createOrder() {
    // 创建订单
    // 写订单明细
    // 写本地消息表
}
```

保证同一个数据库内的数据一致。

---

## 4. MQ 最终一致性

跨服务场景下，采用 MQ 异步最终一致性。

例如：

```text
1. 订单服务创建订单
2. 发送订单创建消息
3. 库存服务消费消息扣减库存
4. 优惠券服务消费消息核销优惠券
5. 消费失败自动重试
6. 多次失败进入死信队列
7. 定时任务补偿
```

---

## 5. 本地消息表

为了保证业务操作和消息发送一致，使用本地消息表：

```text
1. 订单数据入库
2. 本地消息表插入待发送消息
3. 本地事务提交
4. 后台任务发送消息
5. 发送成功更新状态
6. 发送失败继续重试
```

---

## 6. 事务消息

如果使用 RocketMQ，可以使用事务消息：

```text
1. 发送半消息
2. 执行业务本地事务
3. 本地事务成功，提交消息
4. 本地事务失败，回滚消息
5. Broker 不确定时回查本地事务状态
```

---

## 7. 消费端一致性

消费端要保证：

```text
1. 消费成功后再 ack
2. 消费失败要重试
3. 消费逻辑要幂等
4. 多次失败进入死信队列
5. 必要时人工补偿
```

---

## 8. 定时补偿

通过定时任务扫描异常数据：

```text
超时未支付订单
支付成功但订单未更新
订单已取消但库存未释放
优惠券已锁定但订单失败
消息表长时间未发送消息
```

发现异常后自动补偿或报警人工处理。

---

## 9. 对账机制

对于支付、资金、库存等关键业务，需要对账。

例如：

```text
订单系统支付状态
支付渠道流水
账户余额变动
库存流水
```

通过每日对账发现不一致数据并修复。

---

## 10. 面试回答

项目中数据一致性主要分场景处理。

单服务单库内的数据一致性使用本地事务，比如创建订单和订单明细入库放在同一个事务中。

跨服务场景下，我们更多采用 MQ 最终一致性。例如订单创建成功后发送消息，库存服务和优惠券服务消费消息完成扣减和核销。为了防止消息丢失，我们使用本地消息表或 RocketMQ 事务消息，保证业务操作和消息发送一致。

消费端处理时保证幂等，业务处理成功后再 ack，失败则重试，多次失败进入死信队列。对于极端异常场景，我们通过定时补偿和对账任务修复不一致数据。

示例：

```java
public class DesensitizeUtil {

    public static String mobile(String mobile) {
        if (mobile == null || mobile.length() != 11) {
            return mobile;
        }
        return mobile.substring(0, 3) + "****" + mobile.substring(7);
    }
}
```

使用：

```java
log.info("用户手机号：{}", DesensitizeUtil.mobile(phone));
```

缺点：

```text
容易遗漏；
代码侵入性强。
```

---

## 5. 注解脱敏

定义注解：

```java
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Desensitize {
    DesensitizeType type();
}
```

使用：

```java
public class UserDTO {

    @Desensitize(type = DesensitizeType.MOBILE)
    private String phone;

    @Desensitize(type = DesensitizeType.ID_CARD)
    private String idCard;
}
```

通过序列化或 AOP 统一处理。

---

## 6. AOP 日志脱敏

在接口日志切面中：

```text
1. 拦截请求参数
2. 判断字段名或注解
3. 对敏感字段脱敏
4. 再打印日志
```

适合：

```text
请求日志
响应日志
操作日志
```

---

## 7. 配置中心动态脱敏

脱敏规则放在 Nacos 配置中心：

```yaml
log:
  desensitize:
    fields:
      - phone
      - mobile
      - idCard
      - bankCard
      - address
      - token
```

服务启动后加载规则，配置变更后动态刷新。

优点：

```text
新增脱敏字段不需要发版；
规则统一管理；
适合多服务复用。
```

---

## 8. 日志脱敏注意事项

```text
1. 密码绝对不能打印
2. Token、Cookie、密钥不能完整打印
3. 请求和响应日志都要脱敏
4. 异常日志也要注意敏感信息
5. 脱敏规则要统一维护
6. 不能只依赖前端脱敏
7. 生产日志权限要控制
```

---

## 9. 面试回答

项目中日志脱敏主要针对手机号、身份证、银行卡、邮箱、地址、Token 等敏感字段。

我们做法是在统一日志切面中拦截请求参数和响应结果，对敏感字段进行脱敏后再打印。字段识别有两种方式：一种是通过字段名匹配，比如 phone、mobile、idCard；另一种是通过自定义注解标记敏感字段。

为了方便后续维护，我们把部分脱敏字段规则放在 Nacos 配置中心，支持动态刷新。这样新增脱敏字段时不需要重新发版。同时我们规定密码、密钥、完整 Token 这类字段禁止打印。

# 十四、项目中如何做限流

## 1. 为什么要限流？

限流的目的是保护系统。

当流量超过系统承载能力时，如果不限制请求，可能导致：

```text
CPU 飙高
线程池打满
数据库连接池耗尽
Redis 被打爆
接口大量超时
系统雪崩
```

---

## 2. 限流位置

项目中限流通常可以放在：

```text
1. 网关层
2. 服务接口层
3. 用户维度
4. IP 维度
5. 接口维度
6. 租户维度
7. 资源维度
```

---

## 3. 常见限流算法

```text
1. 固定窗口
2. 滑动窗口
3. 漏桶算法
4. 令牌桶算法
```

---

## 4. 固定窗口

例如：

```text
每分钟最多 100 次请求。
```

优点：

```text
实现简单。
```

缺点：

```text
窗口边界可能产生突刺流量。
```

---

## 5. 滑动窗口

滑动窗口将时间划分为多个小窗口，统计最近一段时间内的请求数。

优点：

```text
比固定窗口更平滑。
```

---

## 6. 漏桶算法

漏桶算法特点：

```text
请求先进桶；
桶以固定速率流出；
超过桶容量的请求被拒绝。
```

适合：

```text
平滑流量。
```

---

## 7. 令牌桶算法

令牌桶算法特点：

```text
系统按固定速率生成令牌；
请求需要拿到令牌才能通过；
桶中可以积累令牌；
允许一定突发流量。
```

适合：

```text
允许短时间突发流量的场景。
```

---

## 8. 使用 Sentinel 限流

项目中可以使用 Sentinel。

常见规则：

```text
1. QPS 限流
2. 线程数限流
3. 热点参数限流
4. 系统自适应限流
```

示例：

```java
@SentinelResource(value = "createOrder", blockHandler = "createOrderBlockHandler")
public Result createOrder(CreateOrderRequest request) {
    return orderService.createOrder(request);
}
```

限流后降级处理：

```java
public Result createOrderBlockHandler(CreateOrderRequest request, BlockException e) {
    return Result.fail("当前下单人数较多，请稍后再试");
}
```

---

## 9. 网关限流

在 Gateway 层可以做统一限流：

```text
按 IP 限流
按用户限流
按接口限流
按租户限流
```

优点：

```text
请求还没进入后端服务就被拦截；
可以保护整体系统。
```

---

## 10. Redis + Lua 限流

也可以用 Redis 实现分布式限流。

例如按用户限流：

```text
limit:user:1001:/order/create
```

使用 Redis 计数器或 ZSet 滑动窗口。

Lua 脚本保证判断和计数原子性。

---

## 11. 限流后的处理

限流后不能直接返回系统错误。

可以返回：

```text
请求过于频繁，请稍后再试
当前排队人数较多，请稍后重试
系统繁忙，请稍后再试
```

也可以：

```text
进入排队队列
返回默认结果
降级处理
```

---

## 12. 面试回答

项目中限流主要分为网关层限流和服务层限流。

网关层主要按 IP、用户、接口和租户维度限流，防止流量直接打到后端服务。服务层对核心接口，比如下单、支付、优惠券领取等接口使用 Sentinel 做 QPS 限流、线程数限流和热点参数限流。

限流算法上常见有固定窗口、滑动窗口、漏桶和令牌桶。我们一般使用 Sentinel 或 Redis + Lua 实现分布式限流。限流后会返回友好提示，或者走降级逻辑，避免把后端服务打垮。

# 十五、项目中如何做熔断降级

## 1. 为什么需要熔断降级？

微服务之间存在远程调用。

如果某个下游服务异常，例如：

```text
库存服务响应慢
优惠券服务超时
支付服务异常
第三方短信服务不可用
```

上游如果一直等待或不断重试，可能导致：

```text
线程池耗尽
请求堆积
级联故障
系统雪崩
```

熔断降级就是为了防止故障扩散。

---

## 2. 熔断是什么？

熔断是指：

> 当下游服务异常比例或慢调用比例达到阈值时，暂时停止调用该服务，直接返回降级结果。

类似电路保险丝。

---

## 3. 降级是什么？

降级是指：

> 当系统压力大或依赖服务异常时，关闭非核心功能，返回兜底结果，保证核心链路可用。

---

## 4. 熔断和降级区别

| 对比项 | 熔断 | 降级 |
|---|---|
| 触发原因 | 下游异常、超时、慢调用 | 系统压力大、非核心功能关闭 |
| 目标 | 防止故障扩散 | 保核心功能 |
| 表现 | 暂时不调用下游 | 返回默认值或简化逻辑 |
| 典型场景 | 库存服务超时 | 关闭推荐、短信通知 |

---

## 5. Sentinel 熔断规则

Sentinel 常见熔断指标：

```text
1. 慢调用比例
2. 异常比例
3. 异常数
```

---

## 6. 熔断状态

熔断一般有三种状态：

```text
1. Closed：关闭，正常调用
2. Open：打开，直接降级
3. Half-Open：半开，允许少量请求探测
```

---

## 7. OpenFeign 降级

Feign 调用可以配置 fallback。

示例：

```java
@FeignClient(
    name = "coupon-service",
    fallback = CouponFeignFallback.class
)
public interface CouponFeignClient {

    @PostMapping("/coupon/use")
    Result useCoupon(@RequestBody UseCouponRequest request);
}
```

降级类：

```java
@Component
public class CouponFeignFallback implements CouponFeignClient {

    @Override
    public Result useCoupon(UseCouponRequest request) {
        return Result.fail("优惠券服务暂时不可用");
    }
}
```

---

## 8. 项目中的降级策略

不同业务采用不同降级策略：

| 场景 | 降级策略 |
|---|---|
| 商品推荐失败 | 返回默认推荐 |
| 短信服务失败 | 记录日志，异步重试 |
| 优惠券服务失败 | 提示稍后重试 |
| 库存服务失败 | 下单失败，保护库存一致性 |
| 用户画像失败 | 不影响主流程 |
| 日志上报失败 | 本地落盘或忽略 |

---

## 9. 核心链路和非核心链路

核心链路：

```text
下单
支付
库存扣减
订单状态更新
```

非核心链路：

```text
短信通知
积分发放
推荐更新
日志上报
用户画像
```

原则：

```text
核心链路尽量保证正确性；
非核心链路可以异步、降级或补偿。
```

---

## 10. 面试回答

项目中熔断降级主要使用 Sentinel 和 OpenFeign fallback。

对于服务间调用，如果下游服务出现大量异常、超时或慢调用，Sentinel 会根据慢调用比例、异常比例或异常数触发熔断。熔断后请求不会继续打到异常服务，而是直接走降级逻辑，避免线程被拖死，防止故障扩散。

对于非核心功能，比如短信通知、推荐、积分等，可以降级为异步重试、返回默认值或暂时关闭。对于核心链路，比如下单、支付、库存扣减，不能随便返回成功，失败时要明确返回失败或进入补偿流程，保证数据正确性。

# 十七、完整面试回答模板

我最近做的是一个电商订单与营销平台，主要支持用户下单、优惠券核销、库存扣减、订单支付、订单取消和后台订单管理。项目采用 Spring Boot + Spring Cloud Alibaba 微服务架构，注册配置中心使用 Nacos，服务调用使用 OpenFeign，网关使用 Spring Cloud Gateway，限流熔断使用 Sentinel，缓存和分布式锁使用 Redis，异步消息使用 RocketMQ，核心业务数据存储在 MySQL 中。

项目整体架构上，前端请求先进入 Gateway 网关，网关负责统一鉴权、路由、限流和日志记录。后端按照业务拆分为用户服务、商品服务、订单服务、库存服务、优惠券服务、支付服务和通知服务。服务之间通过 OpenFeign 调用，通过 Nacos 做服务注册发现和配置管理。Redis 用于缓存、分布式锁和接口幂等，RocketMQ 用于异步解耦和最终一致性，Sentinel 用于限流、熔断和降级。

我主要负责订单服务和部分营销模块，包括下单接口、订单状态流转、库存扣减、优惠券核销、订单超时取消、MQ 消息发送和消费、接口幂等、日志脱敏以及部分性能优化。下单接口是项目核心链路，我重点解决了重复提交、库存超卖、消息丢失、重复消费和跨服务数据一致性问题。

项目中最大的难点是高并发下单场景下，如何保证接口幂等、库存不超卖、消息不丢失以及跨服务数据最终一致性。因为下单流程涉及订单服务、库存服务、优惠券服务、支付服务和通知服务，任何一个环节异常，都可能导致订单、库存、优惠券状态不一致。

为了解决这些问题，我们首先在接口层做幂等控制。下单前服务端生成 token 并存入 Redis，提交订单时通过 Lua 脚本校验并删除 token，保证同一个 token 只能使用一次。对于同一用户短时间重复下单，我们使用 Redis 分布式锁控制并发。同时，数据库层通过唯一索引做兜底，例如订单号唯一、支付流水唯一、用户优惠券唯一。

库存扣减方面，我们使用带条件的 update 防止超卖，例如 `UPDATE stock SET stock = stock - num WHERE sku_id = ? AND stock >= num`。如果更新行数为 0，说明库存不足。订单状态流转使用状态机控制，例如只能从待支付变为已支付，不能随意跨状态修改。

跨服务数据一致性方面，我们主要使用 RocketMQ 做最终一致性。订单创建成功后发送订单创建消息，由库存服务、优惠券服务、通知服务等异步消费。为了防止消息丢失，我们使用本地消息表或事务消息，保证业务操作和消息发送一致。消费端通过消费记录表和唯一索引保证幂等，处理成功后再 ack，失败则重试，多次失败进入死信队列。对于极端异常情况，通过定时补偿任务和对账任务修复异常数据。

我也做过性能优化。比如订单列表接口一开始响应较慢，通过 `EXPLAIN` 分析发现没有使用合适索引，并且存在排序开销。后来根据查询条件和排序字段建立了 `(user_id, create_time)` 联合索引，同时减少 `SELECT *`，只查询必要字段，并对深分页改成游标分页。优化后接口响应时间从秒级降到几百毫秒。对于商品详情、用户信息等读多写少的数据，我们使用 Redis 缓存，并通过随机 TTL、空值缓存、互斥锁和热点预热来解决缓存穿透、击穿和雪崩问题。下单后的短信通知、积分增加、消息推送等非核心逻辑通过 RocketMQ 异步处理，减少主链路耗时。

线上问题方面，我遇到过接口响应慢、慢 SQL、消息积压和 CPU 飙高。排查线上问题时，我一般先确认影响范围和服务是否存活，再查看日志、监控和 traceId。如果是接口报错，就看异常堆栈和请求参数；如果是接口超时，就看慢 SQL、远程调用、Redis、MQ、线程池和连接池；如果是 CPU 飙高，就用 `top -Hp pid` 找到高 CPU 线程，把线程 ID 转成十六进制，再用 `jstack` 定位代码；如果是内存问题，就通过 `jstat`、GC 日志和 dump 文件分析。线上处理原则是先止血恢复服务，比如回滚、扩容、限流、降级或摘除异常节点，然后再定位根因并复盘。

项目中的权限控制主要基于 RBAC 模型，也就是用户、角色、权限三层关系。用户登录后，服务端校验账号密码，查询用户角色和权限，生成 Token 返回给前端。前端后续请求在 Header 中携带 Token。网关层统一校验 Token，解析用户信息，并把用户 ID、角色、租户等信息透传给下游服务。接口权限通过权限标识控制，例如 `order:query`、`order:cancel`。数据权限则根据用户角色、部门、租户等信息，在查询时追加数据范围条件。前端按钮权限只做展示控制，真正权限校验必须在后端完成。

日志脱敏方面，我们在统一日志切面中拦截请求参数和响应结果，对手机号、身份证、银行卡、邮箱、地址、Token 等敏感字段进行脱敏后再打印。字段识别支持字段名匹配和自定义注解两种方式。为了方便维护，我们将脱敏字段规则放在 Nacos 配置中心，支持动态刷新。对于密码、密钥、完整 Token 这类字段，原则上禁止打印。

限流方面，我们分为网关层限流和服务层限流。网关层主要按 IP、用户、接口和租户维度限流，防止流量直接打到后端服务。服务层对下单、支付、优惠券领取等核心接口使用 Sentinel 做 QPS 限流、线程数限流和热点参数限流。限流后会返回友好提示，或者走降级逻辑，避免把后端服务打垮。

熔断降级方面，我们使用 Sentinel 和 OpenFeign fallback。对于服务间调用，如果下游服务出现大量异常、超时或慢调用，Sentinel 会根据慢调用比例、异常比例或异常数触发熔断。熔断后请求不会继续打到异常服务，而是直接走降级逻辑，避免线程被拖死，防止故障扩散。对于短信通知、推荐、积分等非核心功能，可以降级为异步重试、返回默认值或暂时关闭；对于下单、支付、库存扣减等核心链路，不能随便返回成功，失败时要明确返回失败或进入补偿流程，保证数据正确性。
