# 一、事务 ACID 是什么

## 1. 什么是事务？

事务是数据库中一组操作的集合。

这组操作要么全部成功，要么全部失败。

例如转账场景：

```sql
UPDATE account SET balance = balance - 100 WHERE user_id = 1;

UPDATE account SET balance = balance + 100 WHERE user_id = 2;
```

这两个操作必须作为一个整体执行：

```text
扣款成功，收款也必须成功；
如果收款失败，扣款也必须回滚。
```

---

## 2. ACID 是什么？

事务有四大特性，简称 ACID：

```text
A：Atomicity，原子性
C：Consistency，一致性
I：Isolation，隔离性
D：Durability，持久性
```

---

## 3. 原子性 Atomicity

原子性指的是：

> 一个事务中的所有操作，要么全部成功，要么全部失败。

事务不能只执行一部分。

---

### 示例

转账操作：

```text
账户 A 扣 100 元
账户 B 加 100 元
```

如果账户 A 扣款成功后，系统宕机，账户 B 没有加钱，那么必须回滚账户 A 的扣款。

---

### MySQL 如何保证原子性？

InnoDB 主要通过：

```text
undo log
```

保证原子性。

当事务执行失败或回滚时，InnoDB 可以根据 undo log 将数据恢复到修改前的状态。

---

## 4. 一致性 Consistency

一致性指的是：

> 事务执行前后，数据库都必须从一个一致性状态变成另一个一致性状态。

简单来说：

```text
数据必须满足业务规则和完整性约束。
```

---

### 示例

转账前：

```text
A 账户：1000 元
B 账户：1000 元
总金额：2000 元
```

转账 100 元后：

```text
A 账户：900 元
B 账户：1100 元
总金额：2000 元
```

总金额不变，这就是一致性。

---

### MySQL 如何保证一致性？

一致性是事务最终目标，依赖多个机制共同保证：

```text
原子性
隔离性
持久性
约束
触发器
应用层业务逻辑
```

---

## 5. 隔离性 Isolation

隔离性指的是：

> 多个事务并发执行时，一个事务的执行不应该被其他事务随意干扰。

例如事务 A 正在修改一条数据，事务 B 不应该随便读取到事务 A 尚未提交的数据。

---

### MySQL 如何保证隔离性？

InnoDB 主要通过以下机制保证隔离性：

```text
锁机制
MVCC
事务隔离级别
```

---

## 6. 持久性 Durability

持久性指的是：

> 事务一旦提交，它对数据库的修改就是永久性的，即使系统宕机也不应该丢失。

---

### MySQL 如何保证持久性？

InnoDB 主要通过：

```text
redo log
```

保证持久性。

事务提交后，redo log 会记录数据页的物理修改。即使数据库宕机，重启后也可以通过 redo log 恢复已提交事务的数据。

---

## 7. ACID 和 MySQL 日志的关系

| ACID 特性 | 主要保障机制 |
|---|---|
| 原子性 | undo log |
| 一致性 | 原子性、隔离性、持久性、约束共同保证 |
| 隔离性 | 锁 + MVCC |
| 持久性 | redo log |

---

## 8. 面试回答

事务 ACID 指的是原子性、一致性、隔离性和持久性。

原子性表示事务中的操作要么全部成功，要么全部失败，InnoDB 主要通过 undo log 保证。

一致性表示事务执行前后数据库都必须满足完整性约束和业务规则，它是事务追求的最终目标。

隔离性表示多个事务并发执行时相互隔离，InnoDB 主要通过锁和 MVCC 保证。

持久性表示事务提交后数据不会丢失，InnoDB 主要通过 redo log 保证。

---

# 二、MySQL 默认隔离级别是什么

## 1. MySQL 默认隔离级别

MySQL InnoDB 默认事务隔离级别是：

```text
REPEATABLE READ
```

中文叫：

```text
可重复读
```

---

## 2. 查看当前隔离级别

MySQL 8.x 可以使用：

```sql
SELECT @@transaction_isolation;
```

返回结果可能是：

```text
REPEATABLE-READ
```

---

## 3. 查看全局隔离级别

```sql
SELECT @@global.transaction_isolation;
```

---

## 4. 查看当前会话隔离级别

```sql
SELECT @@session.transaction_isolation;
```

---

## 5. 修改当前会话隔离级别

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

---

## 6. 修改全局隔离级别

```sql
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

注意：

```text
修改全局隔离级别通常只影响后续新建连接。
```

---

## 7. 单个事务设置隔离级别

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

START TRANSACTION;

-- SQL 操作

COMMIT;
```

注意：

```text
SET TRANSACTION 通常要在 START TRANSACTION 之前执行。
```

---

## 8. 为什么 MySQL 默认使用可重复读？

InnoDB 默认使用可重复读，主要是为了在并发性能和一致性之间取得平衡。

可重复读可以解决：

```text
脏读
不可重复读
```

在 InnoDB 中，配合 MVCC 和 next-key lock，还能在很多场景下避免幻读问题。

---

## 9. 面试回答

MySQL InnoDB 默认隔离级别是 `REPEATABLE READ`，也就是可重复读。

可以通过 `SELECT @@transaction_isolation;` 查看当前隔离级别。

可重复读可以避免脏读和不可重复读。在 InnoDB 中，可重复读还会配合 MVCC 和 next-key lock，在很多场景下解决幻读问题。

---

# 三、读未提交、读已提交、可重复读、串行化区别

## 1. 四种隔离级别

MySQL InnoDB 支持四种事务隔离级别：

```text
1. READ UNCOMMITTED，读未提交
2. READ COMMITTED，读已提交
3. REPEATABLE READ，可重复读
4. SERIALIZABLE，串行化
```

隔离级别越高：

```text
数据一致性越强
并发性能通常越低
```

---

## 2. READ UNCOMMITTED：读未提交

读未提交是最低的隔离级别。

含义：

```text
一个事务可以读取到其他事务尚未提交的数据。
```

可能出现：

```text
脏读
不可重复读
幻读
```

---

### 示例

事务 A：

```sql
START TRANSACTION;

UPDATE user SET age = 20 WHERE id = 1;

-- 暂不提交
```

事务 B：

```sql
START TRANSACTION;

SELECT age FROM user WHERE id = 1;
```

事务 B 可能读到事务 A 尚未提交的 `age = 20`。

如果事务 A 最后回滚，那么事务 B 读到的就是脏数据。

---

## 3. READ COMMITTED：读已提交

读已提交表示：

```text
一个事务只能读取到其他事务已经提交的数据。
```

可以避免：

```text
脏读
```

但可能出现：

```text
不可重复读
幻读
```

---

### 示例

事务 A 第一次读取：

```sql
START TRANSACTION;

SELECT age FROM user WHERE id = 1;
```

结果：

```text
18
```

事务 B 修改并提交：

```sql
UPDATE user SET age = 20 WHERE id = 1;
COMMIT;
```

事务 A 第二次读取：

```sql
SELECT age FROM user WHERE id = 1;
```

结果可能变成：

```text
20
```

同一个事务中两次读取同一行数据结果不同，这就是不可重复读。

---

## 4. REPEATABLE READ：可重复读

可重复读表示：

```text
同一个事务中多次读取同一行数据，结果保持一致。
```

可以避免：

```text
脏读
不可重复读
```

在 InnoDB 中，普通快照读通过 MVCC 实现可重复读。

---

### 示例

事务 A：

```sql
START TRANSACTION;

SELECT age FROM user WHERE id = 1;
```

结果：

```text
18
```

事务 B：

```sql
UPDATE user SET age = 20 WHERE id = 1;
COMMIT;
```

事务 A 再次查询：

```sql
SELECT age FROM user WHERE id = 1;
```

结果仍然是：

```text
18
```

这就是可重复读。

---

## 5. SERIALIZABLE：串行化

串行化是最高隔离级别。

含义：

```text
事务之间像串行执行一样，一个一个执行。
```

它可以避免：

```text
脏读
不可重复读
幻读
```

但是并发性能最低。

---

## 6. 四种隔离级别对比表

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 并发性能 |
|---|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 最高 |
| READ COMMITTED | 不会 | 可能 | 可能 | 较高 |
| REPEATABLE READ | 不会 | 不会 | 标准定义下可能，InnoDB 很多场景可避免 | 较好 |
| SERIALIZABLE | 不会 | 不会 | 不会 | 最低 |

---

## 7. 四种隔离级别适用场景

| 隔离级别 | 适用场景 |
|---|---|
| READ UNCOMMITTED | 很少使用，对一致性要求极低 |
| READ COMMITTED | Oracle、PostgreSQL 常用，适合一般业务 |
| REPEATABLE READ | MySQL InnoDB 默认，适合大多数 MySQL 业务 |
| SERIALIZABLE | 强一致要求高、并发要求低的场景 |

---

## 8. 面试回答

MySQL InnoDB 支持四种隔离级别：读未提交、读已提交、可重复读和串行化。

读未提交可以读到其他事务未提交的数据，可能出现脏读、不可重复读和幻读。

读已提交只能读到其他事务已提交的数据，可以避免脏读，但可能出现不可重复读和幻读。

可重复读保证同一个事务中多次读取同一行数据结果一致，可以避免脏读和不可重复读，是 MySQL InnoDB 默认隔离级别。

串行化隔离级别最高，可以避免脏读、不可重复读和幻读，但并发性能最低。

---

# 四、脏读、不可重复读、幻读是什么

## 1. 脏读是什么？

脏读是指：

> 一个事务读取到了另一个事务尚未提交的数据。

如果另一个事务最后回滚，那么当前事务读到的数据就是无效数据。

---

### 脏读示例

事务 A：

```sql
START TRANSACTION;

UPDATE user SET age = 20 WHERE id = 1;

-- 尚未提交
```

事务 B：

```sql
START TRANSACTION;

SELECT age FROM user WHERE id = 1;
```

事务 B 读到了 `age = 20`。

事务 A 回滚：

```sql
ROLLBACK;
```

此时事务 B 之前读到的 `age = 20` 就是脏数据。

---

## 2. 不可重复读是什么？

不可重复读是指：

> 同一个事务中，多次读取同一行数据，结果不一致。

通常是因为其他事务修改或删除了这行数据并提交。

---

### 不可重复读示例

事务 A 第一次查询：

```sql
START TRANSACTION;

SELECT age FROM user WHERE id = 1;
```

结果：

```text
18
```

事务 B 修改并提交：

```sql
UPDATE user SET age = 20 WHERE id = 1;
COMMIT;
```

事务 A 第二次查询：

```sql
SELECT age FROM user WHERE id = 1;
```

结果：

```text
20
```

同一事务内两次读取同一行结果不同，这就是不可重复读。

---

## 3. 幻读是什么？

幻读是指：

> 同一个事务中，按照相同条件多次查询，第二次查询出现了第一次没有看到的新行，或者少了某些行。

通常是因为其他事务插入或删除了满足条件的数据并提交。

---

### 幻读示例

事务 A 第一次查询：

```sql
START TRANSACTION;

SELECT * FROM user WHERE age = 18;
```

结果：

```text
查到 3 条数据
```

事务 B 插入一条满足条件的数据并提交：

```sql
INSERT INTO user(id, name, age) VALUES(100, 'Tom', 18);
COMMIT;
```

事务 A 第二次查询：

```sql
SELECT * FROM user WHERE age = 18;
```

结果可能变成：

```text
查到 4 条数据
```

这多出来的一行就像“幻影”一样，所以叫幻读。

---

## 4. 不可重复读和幻读区别

| 对比项 | 不可重复读 | 幻读 |
|---|---|---|
| 关注点 | 同一行数据内容变化 | 符合条件的记录数量变化 |
| 典型原因 | UPDATE / DELETE | INSERT / DELETE |
| 查询类型 | 点查或单行查询 | 范围查询 |
| 示例 | 同一行 age 从 18 变 20 | 同一范围多出一行数据 |

---

## 5. 三类问题对比表

| 问题 | 含义 | 典型隔离级别 |
|---|---|---|
| 脏读 | 读到其他事务未提交的数据 | READ UNCOMMITTED 可能出现 |
| 不可重复读 | 同一事务中两次读同一行结果不同 | READ COMMITTED 可能出现 |
| 幻读 | 同一事务中两次范围查询结果集不同 | REPEATABLE READ 标准定义下可能出现 |

---

## 6. InnoDB 如何避免这些问题？

| 问题 | InnoDB 处理方式 |
|---|---|
| 脏读 | READ COMMITTED 及以上避免 |
| 不可重复读 | REPEATABLE READ 通过 MVCC 快照读避免 |
| 幻读 | 快照读通过 MVCC 避免；当前读通过 next-key lock 避免 |

---

## 7. 快照读和当前读

### 快照读

普通 `SELECT` 通常是快照读。

例如：

```sql
SELECT * FROM user WHERE age = 18;
```

快照读通过 MVCC 读取事务可见版本，不加锁。

---

### 当前读

当前读读取的是最新版本，并且通常会加锁。

例如：

```sql
SELECT * FROM user WHERE age = 18 FOR UPDATE;

SELECT * FROM user WHERE age = 18 LOCK IN SHARE MODE;

UPDATE user SET name = 'Tom' WHERE id = 1;

DELETE FROM user WHERE id = 1;
```

当前读会通过锁机制保证并发安全。

---

## 8. 面试回答

脏读是指一个事务读到了另一个事务尚未提交的数据，如果对方回滚，读到的数据就是脏数据。

不可重复读是指同一个事务中多次读取同一行数据，结果不一致，通常是其他事务修改或删除了这行数据并提交。

幻读是指同一个事务中按照相同条件多次范围查询，结果集数量发生变化，通常是其他事务插入或删除了满足条件的数据。

不可重复读关注的是同一行数据内容变化，幻读关注的是范围查询结果集数量变化。

# 五、MVCC 原理

## 1. MVCC 是什么？

MVCC 全称是：

```text
Multi-Version Concurrency Control
```

中文叫：

```text
多版本并发控制
```

它是一种并发控制机制。

核心思想是：

> 为数据保存多个版本，让读操作可以读取某个历史版本，从而实现读写并发。

---

## 2. MVCC 解决什么问题？

如果没有 MVCC，读写之间可能会频繁加锁。

例如：

```text
事务 A 正在修改一行数据；
事务 B 想读取这行数据；
如果没有 MVCC，事务 B 可能需要等待事务 A 释放锁。
```

有了 MVCC 后：

```text
写操作修改最新版本；
读操作读取符合自己事务可见性的历史版本；
读写可以并发执行。
```

---

## 3. MVCC 的核心组成

InnoDB MVCC 主要依赖：

```text
1. 隐藏字段
2. undo log 版本链
3. ReadView
```

---

## 4. 隐藏字段

InnoDB 每行记录中有一些隐藏字段。

常见重要字段：

| 隐藏字段 | 说明 |
|---|---|
| `trx_id` | 最近一次修改该记录的事务 ID |
| `roll_pointer` | 指向 undo log 中上一个版本的指针 |
| `row_id` | 如果没有主键，InnoDB 生成的隐藏行 ID |

---

## 5. trx_id

`trx_id` 表示最后一次修改这行记录的事务 ID。

每次事务修改记录时，都会把自己的事务 ID 写入记录的 `trx_id`。

---

## 6. roll_pointer

`roll_pointer` 指向 undo log 中的历史版本。

当记录被更新时，旧版本会被写入 undo log，新版本中的 `roll_pointer` 指向旧版本。

---

## 7. undo log 版本链

假设一行数据多次被修改：

```text
原始数据：name = A
事务 10 修改为：name = B
事务 20 修改为：name = C
事务 30 修改为：name = D
```

版本链类似：

```text
当前记录 name = D, trx_id = 30
        |
        v
undo log name = C, trx_id = 20
        |
        v
undo log name = B, trx_id = 10
        |
        v
undo log name = A
```

不同事务读取时，会根据自己的 ReadView 判断哪个版本可见。

---

## 8. ReadView 是什么？

ReadView 是事务执行快照读时生成的一致性视图。

它用于判断某个数据版本对当前事务是否可见。

ReadView 中通常包含：

| 字段 | 说明 |
|---|---|
| `m_ids` | 创建 ReadView 时活跃事务 ID 列表 |
| `min_trx_id` | 活跃事务中最小事务 ID |
| `max_trx_id` | 下一个即将分配的事务 ID |
| `creator_trx_id` | 创建该 ReadView 的事务 ID |

---

## 9. ReadView 可见性判断规则

对于某条记录版本的 `trx_id`，判断规则大致如下：

### 9.1 如果 trx_id 等于 creator_trx_id

说明这个版本是当前事务自己修改的。

```text
可见
```

---

### 9.2 如果 trx_id 小于 min_trx_id

说明这个版本在创建 ReadView 前已经提交。

```text
可见
```

---

### 9.3 如果 trx_id 大于等于 max_trx_id

说明这个版本是在创建 ReadView 之后才产生的。

```text
不可见
```

---

### 9.4 如果 trx_id 在 min_trx_id 和 max_trx_id 之间

需要判断它是否在活跃事务列表 `m_ids` 中：

```text
如果在 m_ids 中，说明该事务当时还没提交，不可见；
如果不在 m_ids 中，说明该事务已经提交，可见。
```

---

## 10. 如果当前版本不可见怎么办？

如果当前记录版本不可见，InnoDB 会通过 `roll_pointer` 找到 undo log 中的上一个版本，继续判断可见性。

直到找到一个可见版本，或者版本链结束。

---

## 11. READ COMMITTED 下的 MVCC

在读已提交隔离级别下：

```text
每次 SELECT 都会生成新的 ReadView。
```

因此，同一个事务中两次查询可能看到不同结果。

这就是为什么 READ COMMITTED 可能出现不可重复读。

---

## 12. REPEATABLE READ 下的 MVCC

在可重复读隔离级别下：

```text
事务中第一次快照读时生成 ReadView；
后续快照读复用同一个 ReadView。
```

因此，同一个事务中多次查询看到的结果一致。

这就是可重复读的实现基础。

---

## 13. MVCC 能解决幻读吗？

需要分情况：

### 13.1 快照读场景

普通 `SELECT` 是快照读。

在 InnoDB 的 REPEATABLE READ 下，快照读复用同一个 ReadView，因此通常可以避免幻读。

---

### 13.2 当前读场景

当前读读取最新数据，并会加锁。

例如：

```sql
SELECT * FROM user WHERE age > 18 FOR UPDATE;
```

InnoDB 会通过：

```text
next-key lock
```

锁住记录和间隙，防止其他事务插入满足条件的新记录，从而避免幻读。

---

## 14. MVCC 和锁的关系

MVCC 主要优化的是：

```text
读写并发
```

它让普通快照读不需要加锁，也能读到一致性数据。

但是对于当前读、更新、删除等操作，仍然需要锁机制保证并发安全。

---

## 15. MVCC 原理图

```text
当前记录
name = D, trx_id = 30, roll_pointer
        |
        v
undo log 版本 1
name = C, trx_id = 20, roll_pointer
        |
        v
undo log 版本 2
name = B, trx_id = 10, roll_pointer
        |
        v
undo log 版本 3
name = A

事务读取时：
根据 ReadView 判断每个版本是否可见
```

---

## 16. 面试回答

MVCC 是多版本并发控制，用于提高数据库读写并发能力。它的核心思想是为数据保存多个版本，让读操作读取符合自己事务可见性的历史版本，而写操作修改最新版本，从而实现读写不阻塞。

InnoDB 的 MVCC 主要依赖隐藏字段、undo log 版本链和 ReadView。每行记录中有 `trx_id` 和 `roll_pointer`，`trx_id` 表示最后修改该行的事务 ID，`roll_pointer` 指向 undo log 中的历史版本。事务执行快照读时会生成 ReadView，用于判断某个版本是否对当前事务可见。

在 READ COMMITTED 下，每次查询都会生成新的 ReadView；在 REPEATABLE READ 下，事务第一次快照读生成 ReadView，后续查询复用同一个 ReadView，因此可以实现可重复读。

# 六、undo log、redo log、binlog 区别

## 1. 三种日志分别是什么？

MySQL 中常见三种重要日志：

```text
undo log
redo log
binlog
```

它们作用不同：

| 日志 | 主要作用 |
|---|---|
| undo log | 回滚和 MVCC |
| redo log | 崩溃恢复，保证持久性 |
| binlog | 主从复制和数据恢复 |

---

## 2. undo log 是什么？

undo log 是回滚日志。

它记录的是：

```text
数据修改前的旧值
```

用于事务回滚和 MVCC。

---

## 3. undo log 示例

原数据：

```text
id = 1, age = 18
```

执行：

```sql
UPDATE user SET age = 20 WHERE id = 1;
```

undo log 中会记录类似：

```text
把 age 从 20 回滚到 18 所需的信息
```

如果事务回滚，就可以根据 undo log 恢复旧值。

---

## 4. undo log 的作用

undo log 主要有两个作用：

```text
1. 保证事务原子性
2. 支持 MVCC 一致性读
```

---

## 5. undo log 如何支持回滚？

事务执行更新时，InnoDB 会先记录 undo log。

如果事务回滚，InnoDB 根据 undo log 执行反向操作。

例如：

| 操作 | undo log 反向操作 |
|---|---|
| INSERT | DELETE |
| DELETE | INSERT |
| UPDATE | 恢复旧值 |

---

## 6. undo log 如何支持 MVCC？

当一行数据被多次修改时，旧版本会保存在 undo log 中。

当前记录通过 `roll_pointer` 指向旧版本，形成版本链。

快照读时，InnoDB 根据 ReadView 判断当前版本是否可见。

如果不可见，就沿着 undo log 版本链查找可见版本。

---

## 7. redo log 是什么？

redo log 是重做日志。

它记录的是：

```text
数据页做了什么物理修改
```

用于数据库崩溃后的恢复。

---

## 8. redo log 解决什么问题？

如果每次事务提交都把数据页直接刷盘，性能会很差。

InnoDB 使用 redo log：

```text
事务提交时先写 redo log；
数据页可以稍后再刷盘；
宕机后通过 redo log 恢复已提交数据。
```

这就是 WAL 思想。

WAL 全称：

```text
Write-Ahead Logging
```

即：

```text
先写日志，再写数据页。
```

---

## 9. redo log 的作用

redo log 主要作用：

```text
保证事务持久性
支持崩溃恢复
提升写入性能
```

---

## 10. redo log 示例

执行：

```sql
UPDATE user SET age = 20 WHERE id = 1;
```

redo log 记录类似：

```text
某个表空间的某个数据页，在某个偏移位置做了某种修改
```

如果数据库提交后宕机，但数据页还没刷盘，重启后可以通过 redo log 恢复。

---

## 11. binlog 是什么？

binlog 是二进制日志。

它是 MySQL Server 层日志。

它记录的是：

```text
数据库变更事件
```

例如：

```text
表结构变更
数据增删改
事务提交事件
```

---

## 12. binlog 的作用

binlog 主要用于：

```text
1. 主从复制
2. 数据恢复
3. 数据同步
4. 审计
```

---

## 13. binlog 常见格式

binlog 有三种常见格式：

| 格式 | 说明 |
|---|---|
| STATEMENT | 记录 SQL 语句 |
| ROW | 记录每行数据变更 |
| MIXED | STATEMENT 和 ROW 混合 |

---

### 13.1 STATEMENT

记录原始 SQL。

例如：

```sql
UPDATE user SET age = age + 1 WHERE id = 1;
```

优点：

```text
日志量小
```

缺点：

```text
某些函数或非确定性 SQL 可能导致主从不一致
```

---

### 13.2 ROW

记录每一行数据的变化。

优点：

```text
更准确，主从一致性更好
```

缺点：

```text
日志量可能较大
```

---

### 13.3 MIXED

由 MySQL 根据情况选择 STATEMENT 或 ROW。

---

## 14. redo log 和 binlog 区别

| 对比项 | redo log | binlog |
|---|---|---|
| 所属层级 | InnoDB 存储引擎层 | MySQL Server 层 |
| 日志类型 | 物理日志 | 逻辑日志 |
| 记录内容 | 数据页的物理修改 | SQL 或行级数据变更事件 |
| 主要作用 | 崩溃恢复 | 主从复制、数据恢复 |
| 写入方式 | 循环写 | 追加写 |
| 是否 InnoDB 特有 | 是 | 不是 |
| 是否用于复制 | 通常不用 | 是 |
| 是否保证持久性 | 是 | 不是 InnoDB 持久性的核心机制 |

---

## 15. undo log 和 redo log 区别

| 对比项 | undo log | redo log |
|---|---|---|
| 中文名 | 回滚日志 | 重做日志 |
| 记录内容 | 修改前的旧值 | 数据页的物理修改 |
| 主要作用 | 回滚、MVCC | 崩溃恢复 |
| 保证特性 | 原子性 | 持久性 |
| 用于事务回滚 | 是 | 否 |
| 用于崩溃恢复 | 间接参与 | 是 |
| 是否形成版本链 | 是 | 否 |

---

## 16. 三种日志完整对比

| 对比项 | undo log | redo log | binlog |
|---|---|---|---|
| 所属层级 | InnoDB | InnoDB | Server 层 |
| 日志类型 | 逻辑日志 | 物理日志 | 逻辑日志 |
| 记录内容 | 数据修改前的旧值 | 数据页物理修改 | 数据库变更事件 |
| 主要作用 | 回滚、MVCC | 崩溃恢复 | 主从复制、数据恢复 |
| 保障能力 | 原子性、隔离性部分能力 | 持久性 | 复制、恢复 |
| 写入方式 | 追加写 | 循环写 | 追加写 |
| 是否存储引擎特有 | InnoDB 特有 | InnoDB 特有 | Server 层通用 |
| 是否用于主从复制 | 否 | 否 | 是 |
| 是否用于事务回滚 | 是 | 否 | 否 |
| 是否用于崩溃恢复 | 间接 | 是 | 可用于恢复，但不是崩溃恢复核心 |

---

## 17. 两阶段提交是什么？

MySQL 更新数据时，通常既要写 redo log，又要写 binlog。

为了保证 redo log 和 binlog 一致，MySQL 使用两阶段提交。

大致流程：

```text
1. 执行 SQL，修改内存数据页
2. 写 undo log
3. 写 redo log prepare
4. 写 binlog
5. 提交事务
6. 写 redo log commit
```

---

## 18. 为什么需要两阶段提交？

如果没有两阶段提交，可能出现 redo log 和 binlog 不一致。

例如：

### 情况一：redo log 写了，binlog 没写

数据库崩溃恢复后，主库有这次修改。

但 binlog 没记录，从库无法同步这次修改。

结果：

```text
主从数据不一致
```

---

### 情况二：binlog 写了，redo log 没写

从库根据 binlog 执行了这次修改。

但主库崩溃恢复后没有这次修改。

结果：

```text
主从数据不一致
```

---

## 19. 两阶段提交的作用

两阶段提交用于保证：

```text
redo log 和 binlog 的一致性
```

从而保证：

```text
主库崩溃恢复数据
和
从库通过 binlog 同步数据
保持一致
```

---

## 20. 面试回答

undo log、redo log 和 binlog 作用不同。

undo log 是 InnoDB 的回滚日志，记录数据修改前的旧值，主要用于事务回滚和 MVCC，保证事务原子性。

redo log 是 InnoDB 的重做日志，记录数据页的物理修改，主要用于崩溃恢复，保证事务持久性。

binlog 是 MySQL Server 层的二进制日志，记录数据库变更事件，主要用于主从复制和数据恢复。

redo log 是物理日志、循环写；binlog 是逻辑日志、追加写。为了保证 redo log 和 binlog 一致，MySQL 使用两阶段提交机制。

# 七、面试速记版

## 1. 事务 ACID 是什么？

ACID 是事务四大特性：

```text
A：原子性，要么全成功，要么全失败
C：一致性，事务前后数据满足约束
I：隔离性，并发事务之间互不干扰
D：持久性，事务提交后数据不丢失
```

InnoDB 中：

```text
undo log 保证原子性
锁 + MVCC 保证隔离性
redo log 保证持久性
一致性由多个机制共同保证
```

---

## 2. MySQL 默认隔离级别是什么？

MySQL InnoDB 默认隔离级别是：

```text
REPEATABLE READ
```

也就是：

```text
可重复读
```

查看命令：

```sql
SELECT @@transaction_isolation;
```

---

## 3. 四种隔离级别区别

```text
READ UNCOMMITTED：读未提交，可能脏读
READ COMMITTED：读已提交，避免脏读
REPEATABLE READ：可重复读，避免脏读和不可重复读，MySQL 默认
SERIALIZABLE：串行化，隔离最强，并发最低
```

---

## 4. 脏读、不可重复读、幻读是什么？

```text
脏读：读到其他事务未提交的数据
不可重复读：同一事务两次读取同一行结果不同
幻读：同一事务两次范围查询结果集数量不同
```

区别：

```text
不可重复读关注同一行内容变化；
幻读关注范围查询结果集变化。
```

---

## 5. MVCC 原理

MVCC 是多版本并发控制。

核心组成：

```text
隐藏字段 trx_id
隐藏字段 roll_pointer
undo log 版本链
ReadView
```

快照读时，根据 ReadView 判断记录版本是否可见。

READ COMMITTED 每次查询生成新的 ReadView。

REPEATABLE READ 第一次快照读生成 ReadView，后续复用。

---

## 6. undo log、redo log、binlog 区别

```text
undo log：回滚日志，记录旧值，用于回滚和 MVCC
redo log：重做日志，记录物理修改，用于崩溃恢复
binlog：二进制日志，记录数据库变更事件，用于主从复制和数据恢复
```

# 九、完整面试回答模板

事务 ACID 指的是原子性、一致性、隔离性和持久性。原子性表示事务中的操作要么全部成功，要么全部失败，InnoDB 主要通过 undo log 保证；一致性表示事务执行前后数据库都必须满足完整性约束和业务规则；隔离性表示多个事务并发执行时互不干扰，InnoDB 主要通过锁和 MVCC 保证；持久性表示事务提交后数据不会丢失，InnoDB 主要通过 redo log 保证。

MySQL InnoDB 默认事务隔离级别是 `REPEATABLE READ`，也就是可重复读。可以通过 `SELECT @@transaction_isolation;` 查看当前隔离级别。

MySQL 支持四种隔离级别：读未提交、读已提交、可重复读和串行化。读未提交可以读到其他事务未提交的数据，可能出现脏读、不可重复读和幻读。读已提交只能读到其他事务已经提交的数据，可以避免脏读，但可能出现不可重复读和幻读。可重复读可以保证同一个事务中多次读取同一行数据结果一致，可以避免脏读和不可重复读，是 MySQL InnoDB 默认隔离级别。串行化隔离级别最高，可以避免脏读、不可重复读和幻读，但并发性能最低。

脏读是指一个事务读到了另一个事务尚未提交的数据，如果对方回滚，读到的数据就是脏数据。不可重复读是指同一个事务中多次读取同一行数据结果不一致，通常是因为其他事务修改或删除了这行数据并提交。幻读是指同一个事务中按照相同条件多次范围查询，结果集数量发生变化，通常是因为其他事务插入或删除了满足条件的数据。不可重复读关注的是同一行数据内容变化，幻读关注的是范围查询结果集变化。

MVCC 是多版本并发控制，用于提高数据库读写并发能力。它的核心思想是为数据保存多个版本，让读操作读取符合自己事务可见性的历史版本，而写操作修改最新版本。InnoDB 的 MVCC 主要依赖隐藏字段、undo log 版本链和 ReadView。每行记录中有 `trx_id` 和 `roll_pointer`，`trx_id` 表示最后修改该行的事务 ID，`roll_pointer` 指向 undo log 中的历史版本。事务进行快照读时会生成 ReadView，用于判断某个版本是否对当前事务可见。

在 READ COMMITTED 隔离级别下，每次查询都会生成新的 ReadView，因此同一个事务中两次查询可能看到不同结果。在 REPEATABLE READ 隔离级别下，事务第一次快照读生成 ReadView，后续快照读复用同一个 ReadView，因此可以实现可重复读。

undo log、redo log 和 binlog 作用不同。undo log 是 InnoDB 的回滚日志，记录数据修改前的旧值，主要用于事务回滚和 MVCC，保证事务原子性。redo log 是 InnoDB 的重做日志，记录数据页的物理修改，主要用于崩溃恢复，保证事务持久性。binlog 是 MySQL Server 层的二进制日志，记录数据库变更事件，主要用于主从复制和数据恢复。redo log 是物理日志、循环写；binlog 是逻辑日志、追加写。为了保证 redo log 和 binlog 一致，MySQL 使用两阶段提交机制。
