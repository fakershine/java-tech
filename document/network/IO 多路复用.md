# IO 多路复用总结

IO 多路复用是指：**一个线程可以同时监听多个 IO 连接，当某个连接就绪时，再进行读写处理**。

核心作用：

```text
用少量线程处理大量连接
```

---

## 1. 为什么需要 IO 多路复用

传统阻塞 IO 模型中，一个连接通常需要一个线程处理。

```text
1 个连接 -> 1 个线程
10000 个连接 -> 10000 个线程
```

问题：

- 线程数量多。
- 内存开销大。
- 上下文切换成本高。
- 高并发连接下性能差。

IO 多路复用可以做到：

```text
1 个线程监听多个 Socket
哪个 Socket 就绪，就处理哪个 Socket
```

---

## 2. IO 多路复用核心思想

```text
多个连接注册到一个多路复用器
  ↓
线程阻塞等待事件
  ↓
某些连接就绪
  ↓
返回就绪连接列表
  ↓
应用程序处理读写事件
```

简单理解：

```text
不是一个线程等一个连接
而是一个线程等一批连接
```

---

## 3. 常见 IO 模型

| IO 模型 | 说明 |
|---|---|
| 阻塞 IO | 一个线程阻塞等待一个连接 |
| 非阻塞 IO | 不阻塞，但需要不断轮询 |
| IO 多路复用 | 一个线程监听多个连接 |
| 信号驱动 IO | 内核通知应用程序处理 IO |
| 异步 IO | 内核完成 IO 后通知应用程序 |

---

## 4. select

### 实现原理

`select` 可以监听多个文件描述符。

```text
应用程序把 fd 集合传给内核
  ↓
内核遍历 fd 集合
  ↓
找到就绪 fd
  ↓
返回给应用程序
```

### 优势

- 跨平台支持较好。
- 实现简单。

### 劣势

- 监听 fd 数量有限。
- 每次调用都要拷贝 fd 集合。
- 内核需要遍历所有 fd。
- 性能较差。

---

## 5. poll

### 实现原理

`poll` 和 `select` 类似，也需要遍历所有 fd。

区别是：

```text
poll 使用链表结构，没有固定 fd 数量限制
```

### 优势

- 没有 select 的 fd 数量限制。
- 使用方式相对简单。

### 劣势

- 仍然需要遍历所有 fd。
- fd 集合仍然需要在用户态和内核态之间拷贝。
- 高并发下性能仍然一般。

---

## 6. epoll

### 实现原理

`epoll` 是 Linux 下高性能 IO 多路复用机制。

核心方法：

```text
epoll_create：创建 epoll 实例
epoll_ctl：注册、修改、删除 fd
epoll_wait：等待就绪事件
```

流程：

```text
连接注册到 epoll
  ↓
内核维护监听集合
  ↓
连接就绪时加入就绪队列
  ↓
epoll_wait 返回就绪事件
  ↓
应用程序处理
```

### 优势

- 不需要每次重复传递所有 fd。
- 不需要遍历所有连接。
- 只返回就绪事件。
- 支持大量连接。
- 高并发性能好。

### 劣势

- Linux 特有。
- 编程模型比 select / poll 复杂。
- 需要注意水平触发和边缘触发。

---

## 7. select、poll、epoll 对比

| 对比项 | select | poll | epoll |
|---|---|---|---|
| fd 数量限制 | 有限制 | 理论上无限制 | 理论上无限制 |
| 数据结构 | 位图 | 链表 / 数组 | 红黑树 + 就绪队列 |
| 是否重复拷贝 fd | 是 | 是 | 否 |
| 是否遍历所有 fd | 是 | 是 | 否 |
| 返回结果 | 需要遍历找就绪 | 需要遍历找就绪 | 直接返回就绪事件 |
| 性能 | 较差 | 一般 | 高 |
| 适用场景 | 少量连接 | 中等连接 | 高并发连接 |

---

## 8. epoll 两种触发模式

## 8.1 LT 水平触发

LT 是默认模式。

特点：

```text
只要 fd 还有数据没读完
epoll_wait 就会一直通知
```

优势：

- 编程简单。
- 不容易漏事件。

劣势：

- 可能重复通知。
- 性能略低。

---

## 8.2 ET 边缘触发

ET 只在状态变化时通知一次。

特点：

```text
数据从无到有时通知一次
如果没读完，不会重复通知
```

使用 ET 时通常要求：

```text
非阻塞 IO
一次性把数据读到 EAGAIN
```

优势：

- 通知次数少。
- 性能更高。

劣势：

- 编程复杂。
- 如果没有一次读完，可能丢事件。

---

## 9. Java 中的 IO 多路复用

Java NIO 中的核心组件：

| 组件 | 说明 |
|---|---|
| Channel | 通道，类似 Socket |
| Buffer | 缓冲区 |
| Selector | 多路复用器 |
| SelectionKey | 注册事件 |

Java NIO 流程：

```text
SocketChannel 设置为非阻塞
  ↓
注册到 Selector
  ↓
Selector 监听多个 Channel
  ↓
select() 返回就绪事件
  ↓
根据事件处理 accept / read / write
```

常见事件：

```text
OP_ACCEPT
OP_CONNECT
OP_READ
OP_WRITE
```

---

## 10. Netty 和 IO 多路复用

Netty 底层就是基于 Java NIO 的多路复用模型。

核心组件：

```text
EventLoop
Selector
Channel
Pipeline
Handler
```

简化流程：

```text
一个 EventLoop 绑定一个线程
  ↓
一个 EventLoop 维护一个 Selector
  ↓
一个 Selector 监听多个 Channel
  ↓
事件就绪后交给 Pipeline 处理
```

这也是 Netty 能高并发处理大量连接的重要原因。

---

## 11. IO 多路复用适用场景

适合：

```text
高并发连接
长连接服务
网关
RPC 框架
消息队列
Redis
Nginx
Netty 服务端
WebSocket 服务
```

不适合：

```text
CPU 密集型任务
每个请求处理耗时很长的业务
大量阻塞数据库或远程调用
```

原因：

```text
IO 多路复用解决的是连接和 IO 等待问题，不解决业务处理慢的问题。
```

---

## 12. 总结

IO 多路复用是指一个线程可以同时监听多个 IO 连接，当某个连接就绪时，再处理对应的读写事件。它可以用少量线程处理大量连接，避免传统阻塞 IO 中一个连接一个线程带来的巨大线程开销。

常见实现有 `select`、`poll` 和 `epoll`。`select` 和 `poll` 每次都需要把 fd 集合传给内核，并遍历所有 fd，性能较差；`epoll` 会在内核中维护监听集合，并通过就绪队列返回已经就绪的事件，因此更适合高并发场景。

Java NIO 中的 `Selector` 就是 IO 多路复用的体现，Netty 底层也是基于 NIO 和 Selector 实现高并发网络通信。

一句话总结：

```text
IO 多路复用 = 一个线程监听多个连接；
select/poll 需要遍历所有连接，epoll 只返回就绪连接，更适合高并发。
```
