# 双亲委派机制总结

双亲委派机制是 Java 类加载器加载类时的一种规则。  
它的核心思想是：**一个类加载器收到类加载请求后，先不自己加载，而是先委托父类加载器加载，父类加载不了时，自己才尝试加载。**

---

## 1. 什么是双亲委派机制

类加载器加载类时，并不是直接自己加载，而是按照如下流程：

```text
当前类加载器收到类加载请求
  ↓
先委托父类加载器加载
  ↓
父类加载器继续向上委托
  ↓
一直委托到顶层 Bootstrap ClassLoader
  ↓
父类加载器加载不了
  ↓
再由子类加载器尝试加载
```

简单理解：

```text
先问父亲能不能加载，父亲不行，自己再加载。
```

---

## 2. 类加载器层级

Java 中常见类加载器如下：

```text
Bootstrap ClassLoader
        ↓
Extension ClassLoader / Platform ClassLoader
        ↓
Application ClassLoader
        ↓
Custom ClassLoader
```

### JDK 8

| 类加载器 | 说明 |
|---|---|
| Bootstrap ClassLoader | 启动类加载器，加载 `rt.jar` 等核心类库 |
| Extension ClassLoader | 扩展类加载器，加载 `jre/lib/ext` 下的类 |
| Application ClassLoader | 应用类加载器，加载 classpath 下的类 |
| Custom ClassLoader | 自定义类加载器 |

### JDK 9+

JDK 9 引入模块化后，类加载器有所调整：

| 类加载器 | 说明 |
|---|---|
| Bootstrap ClassLoader | 加载核心 Java 模块 |
| Platform ClassLoader | 替代 Extension ClassLoader |
| Application ClassLoader | 加载应用 classpath / modulepath 下的类 |

---

## 3. 双亲委派加载流程

以加载 `java.lang.String` 为例：

```text
Application ClassLoader 收到加载 java.lang.String 的请求
  ↓
委托给 Platform / Extension ClassLoader
  ↓
继续委托给 Bootstrap ClassLoader
  ↓
Bootstrap ClassLoader 发现自己可以加载
  ↓
加载 java.lang.String
  ↓
返回 Class 对象
```

因此，即使用户自己定义了一个：

```java
package java.lang;

public class String {
}
```

也不会替代 JDK 自带的 `java.lang.String`。

---

## 4. 双亲委派机制的源码入口

类加载主要入口在 `ClassLoader#loadClass()`。

核心逻辑可以简化为：

```java
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {

    synchronized (getClassLoadingLock(name)) {

        // 1. 先检查是否已经加载过
        Class<?> c = findLoadedClass(name);

        if (c == null) {
            try {
                if (parent != null) {
                    // 2. 委托父类加载器加载
                    c = parent.loadClass(name, false);
                } else {
                    // 3. 父加载器为空，则委托 Bootstrap 加载
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器加载失败
            }

            if (c == null) {
                // 4. 父加载器加载不了，自己再加载
                c = findClass(name);
            }
        }

        if (resolve) {
            resolveClass(c);
        }

        return c;
    }
}
```

核心流程：

```text
findLoadedClass
  ↓
parent.loadClass
  ↓
findClass
```

---

## 5. 双亲委派机制的好处

### 1. 保证核心类库安全

比如 `java.lang.String`、`java.lang.Object`、`java.util.List` 这些核心类，都会优先由 Bootstrap ClassLoader 加载。

这样可以防止用户自己写同名类替换 JDK 核心类。

---

### 2. 避免类重复加载

如果没有双亲委派，不同类加载器可能重复加载同一个类。

双亲委派可以保证：

```text
父类加载器能加载的类，子类加载器就不重复加载。
```

---

### 3. 保证类的一致性

在 JVM 中，判断两个类是否相同，不仅看类的全限定名，还要看加载它们的类加载器。

```text
类唯一性 = 类全限定名 + 类加载器
```

例如：

```text
同一个 com.example.User
被不同 ClassLoader 加载
在 JVM 看来是两个不同的类
```

双亲委派可以减少这种混乱。

---

## 6. 类加载器和类唯一性

JVM 判断两个类是否相同，需要同时满足：

```text
类全限定名相同
加载它们的 ClassLoader 相同
```

否则即使类名完全一样，也不是同一个类。

示例：

```text
ClassLoaderA 加载 com.demo.User
ClassLoaderB 加载 com.demo.User
```

这两个 `User` 类在 JVM 中不是同一个类。

可能导致：

```text
ClassCastException
```

---

## 7. 为什么要打破双亲委派

虽然双亲委派有安全性和一致性优势，但有些场景需要打破它。

常见场景：

- SPI 机制。
- JDBC 驱动加载。
- Tomcat 多 Web 应用隔离。
- OSGi 模块化。
- 热部署。
- 插件化系统。
- 自定义类加载隔离。

---

## 8. SPI 为什么需要打破双亲委派

### 问题

Java SPI 的接口通常由核心类库提供，例如：

```java
java.sql.Driver
```

这个接口由 Bootstrap ClassLoader 加载。

但是具体实现类，比如 MySQL 驱动：

```text
com.mysql.cj.jdbc.Driver
```

通常在应用 classpath 下，由 Application ClassLoader 加载。

问题来了：

```text
Bootstrap ClassLoader 能加载 java.sql.Driver
但它无法加载 classpath 下的 MySQL Driver 实现类
```

这就出现了：

```text
父类加载器需要加载子类加载器路径下的类
```

这违反了双亲委派的方向。

---

## 9. SPI 如何解决

Java 使用 **线程上下文类加载器** 解决 SPI 加载问题。

```java
Thread.currentThread().getContextClassLoader();
```

核心思想：

```text
父类加载器加载接口
但通过线程上下文类加载器加载具体实现类
```

例如：

```text
DriverManager 由 Bootstrap 加载
MySQL Driver 由 Application ClassLoader 加载
```

这样就实现了父加载器反向使用子加载器加载实现类。

---

## 10. Tomcat 如何打破双亲委派

Tomcat 中每个 Web 应用都有自己的 WebAppClassLoader。

原因：

```text
不同 Web 应用可能依赖不同版本的 jar
```

例如：

```text
应用 A 使用 spring-5.0
应用 B 使用 spring-6.0
```

如果完全遵守双亲委派，公共父加载器可能会先加载某个版本，导致应用之间依赖冲突。

Tomcat 的类加载策略大致是：

```text
先加载 Web 应用自己的 WEB-INF/classes 和 WEB-INF/lib
加载不到时，再委托父加载器
```

这样可以实现：

```text
Web 应用之间类隔离
不同应用可以使用不同版本依赖
```

---

## 11. 如何打破双亲委派

默认情况下，`loadClass()` 实现了双亲委派。

如果要打破双亲委派，一般有两种方式：

### 方式一：重写 `loadClass()`

可以改变委派顺序。

```java
@Override
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    // 自定义加载逻辑
}
```

### 方式二：重写 `findClass()`

如果仍然想遵守双亲委派，只需要重写 `findClass()`。

```java
@Override
protected Class<?> findClass(String name)
        throws ClassNotFoundException {
    byte[] bytes = loadClassBytes(name);
    return defineClass(name, bytes, 0, bytes.length);
}
```

一般推荐：

```text
遵守双亲委派：重写 findClass()
打破双亲委派：重写 loadClass()
```

## 12. 双亲委派和类加载过程

类加载完整过程包括：

```text
加载 -> 验证 -> 准备 -> 解析 -> 初始化
```

### 加载

通过类加载器读取 `.class` 文件，生成 Class 对象。

### 验证

验证字节码是否合法。

### 准备

为静态变量分配内存并设置默认值。

```java
static int count = 10;
```

准备阶段：

```text
count = 0
```

初始化阶段：

```text
count = 10
```

### 解析

将符号引用转换为直接引用。

### 初始化

执行静态变量赋值和静态代码块。

## 13. 双亲委派常见问题

### 1. 能不能自己写一个 `java.lang.String`

不能正常替换 JDK 的 `String`。

原因：

```text
java.lang.String 会优先由 Bootstrap ClassLoader 加载。
```

而且新版本 JDK 对 `java.*` 包也有安全限制。

---

### 2. 为什么同名类会 ClassCastException

因为 JVM 判断类相同，需要：

```text
类名相同 + 类加载器相同
```

如果两个不同 ClassLoader 加载了同名类，它们在 JVM 中是两个不同类型。

---

### 3. ClassNotFoundException 和 NoClassDefFoundError 区别

| 异常 | 说明 |
|---|---|
| ClassNotFoundException | 运行时主动加载类失败，例如 `Class.forName()` |
| NoClassDefFoundError | 编译时存在，运行时找不到或初始化失败 |

---

## 14. 总结

双亲委派机制是 Java 类加载器的加载规则。一个类加载器收到类加载请求后，会先委托父类加载器加载，父类加载器加载不了时，自己才尝试加载。

它的好处是可以保证 Java 核心类库安全，避免核心类被篡改，同时避免类重复加载，保证类加载的一致性。

类加载器主要包括 Bootstrap ClassLoader、Extension/Platform ClassLoader、Application ClassLoader 和自定义 ClassLoader。

双亲委派不是绝对不能打破。像 SPI、JDBC、Tomcat、插件化、热部署等场景都会打破或绕开双亲委派。SPI 通过线程上下文类加载器，让父加载器可以加载子加载器路径下的实现类；Tomcat 通过自定义 WebAppClassLoader 实现不同 Web 应用之间的类隔离。

一句话总结：

```text
双亲委派 = 类加载先委托父加载器，父加载不了才自己加载；
核心价值 = 保护核心类库安全，避免重复加载，保证类的一致性。
```
