# 垃圾收集器选型总结

垃圾收集器选型主要看四个指标：

```text
吞吐量
低延迟
堆大小
CPU 资源
```

简单原则：

```text
普通后端服务：G1
低延迟大内存：ZGC / Shenandoah
吞吐优先：Parallel
小应用 / 单核环境：Serial
老项目低停顿：CMS，但新项目不推荐
```

---

## 1. 常见垃圾收集器

| 收集器 | 特点 | 适合场景 |
|---|---|---|
| Serial | 单线程，简单 | 小内存、单核、客户端应用 |
| Parallel | 多线程，吞吐优先 | 批处理、后台任务、计算任务 |
| CMS | 低停顿，老年代并发回收 | 老项目，JDK 8 常见 |
| G1 | 平衡吞吐和停顿 | 大多数服务端应用 |
| ZGC | 超低延迟，大堆友好 | 延迟敏感、大内存服务 |
| Shenandoah | 超低停顿，并发整理 | 延迟敏感服务 |

JVM 提供多个 GC，是因为不同应用对吞吐、延迟、内存占用和启动时间的要求不同；例如 ZGC 更偏低延迟，Parallel 更偏吞吐，G1 更偏平衡。:contentReference[oaicite:0]{index=0}

## 2. Serial GC

### 特点

```text
单线程收集
Stop The World
实现简单
资源占用少
```

开启方式：

```bash
-XX:+UseSerialGC
```

### 适合场景

```text
小内存应用
单核机器
客户端工具
测试环境
```

### 不适合

```text
高并发服务端应用
大堆内存应用
延迟敏感系统
```

---

## 3. Parallel GC

### 特点

```text
多线程垃圾回收
吞吐量优先
停顿时间可能较长
```

开启方式：

```bash
-XX:+UseParallelGC
```

### 适合场景

```text
批处理任务
离线计算
报表任务
后台作业
对响应时间不敏感但要求吞吐高
```

### 面试理解

```text
Parallel GC 追求单位时间内完成更多业务任务。
```

---

## 4. CMS GC

### 特点

CMS 是老年代并发收集器，目标是降低停顿。

```text
初始标记：STW
并发标记：和用户线程并发
重新标记：STW
并发清理：和用户线程并发
```

开启方式：

```bash
-XX:+UseConcMarkSweepGC
```

### 优势

```text
停顿时间比传统老年代收集器短
JDK 8 老项目常见
```

### 劣势

```text
会产生内存碎片
并发阶段占用 CPU
可能出现 Concurrent Mode Failure
已经不推荐新项目使用
```

### 适合场景

```text
JDK 8 老项目
历史系统仍在使用 CMS
```

---

## 5. G1 GC

### 特点

G1 是面向服务端应用的垃圾收集器，目标是在吞吐和停顿之间取得平衡。它把堆划分为多个 Region，并优先回收垃圾最多的 Region。Oracle 文档中也说明 G1 是服务器风格收集器，适合多处理器和大内存机器，并尝试在高吞吐和短暂停顿之间取得平衡。:contentReference[oaicite:1]{index=1}

开启方式：

```bash
-XX:+UseG1GC
```

常用参数：

```bash
-XX:MaxGCPauseMillis=200
```

### 优势

```text
适合大多数后端服务
支持可预测停顿目标
不会像 CMS 一样容易产生碎片
整体调优成本较低
```

### 劣势

```text
极致低延迟不如 ZGC / Shenandoah
对小堆应用优势不明显
```

### 适合场景

```text
普通 Java 后端服务
Spring Boot 微服务
中大堆内存服务
对吞吐和延迟都要兼顾
```

---

## 6. ZGC

### 特点

ZGC 是低延迟垃圾收集器，大部分耗时工作和应用线程并发执行。Oracle 文档说明 ZGC 的最大停顿时间通常只有几毫秒，并且停顿时间不随堆大小明显增长；OpenJDK 项目也说明 ZGC 可处理从 8MB 到 16TB 的堆。:contentReference[oaicite:2]{index=2}

开启方式：

```bash
-XX:+UseZGC
```

### 优势

```text
超低停顿
适合大堆内存
停顿时间和堆大小关系较弱
调优相对简单
```

### 劣势

```text
吞吐可能略低于 G1 / Parallel
需要更多 CPU 资源支持并发回收
老版本 JDK 支持不如 G1 普遍
```

### 适合场景

```text
低延迟接口
大内存服务
交易系统
风控系统
实时推荐
对 P99 / P999 延迟敏感
```

---

## 7. Shenandoah

### 特点

Shenandoah 也是低停顿收集器，通过和应用线程并发执行更多 GC 工作来降低停顿。OpenJDK 文档说明，Shenandoah 会并发执行包括并发整理在内的大部分 GC 工作，使暂停时间不再直接随堆大小增长。:contentReference[oaicite:3]{index=3}

开启方式：

```bash
-XX:+UseShenandoahGC
```

### 优势

```text
低停顿
支持并发整理
适合大堆和低延迟场景
```

### 劣势

```text
不同 JDK 发行版支持情况不同
吞吐会有一定损耗
使用前要确认运行时是否支持
```

### 适合场景

```text
低延迟服务
大堆应用
对停顿敏感的系统
```

---

## 8. 选型建议

| 场景 | 推荐 |
|---|---|
| 普通 Spring Boot 服务 | G1 |
| 微服务后端接口 | G1 |
| 低延迟交易系统 | ZGC / Shenandoah |
| 大堆内存应用 | ZGC / Shenandoah / G1 |
| 批处理、报表任务 | Parallel |
| 小内存工具应用 | Serial |
| JDK 8 老项目 | G1 / CMS |
| 新项目 | G1 / ZGC |
| 对吞吐极致敏感 | Parallel |
| 对 P99 延迟敏感 | ZGC / Shenandoah |

---

## 9. 常见版本建议

```text
JDK 8：常见选择 G1 / Parallel / CMS
JDK 11：常见选择 G1，也可评估 ZGC
JDK 17+：普通服务选 G1，低延迟服务可选 ZGC
```

说明：

```text
新项目不建议再优先选择 CMS。
```

CMS 属于老一代低停顿收集器，后续更推荐 G1、ZGC 或 Shenandoah。

---

## 10. 怎么判断选型是否合适

重点看这些指标：

```text
平均 RT
P95 / P99 / P999 延迟
Young GC 频率和耗时
Full GC 次数
老年代使用率
GC 后内存是否下降
CPU 使用率
吞吐量
```

查看 GC 日志：

```bash
-Xlog:gc*:file=gc.log:time,level,tags
```

JDK 8：

```bash
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-Xloggc:gc.log
```

---

## 11. 总结

垃圾收集器选型主要看系统更关注吞吐量还是低延迟。

如果是普通 Java 后端服务，优先选择 G1，因为它在吞吐和停顿之间比较均衡，适合大多数微服务场景。

如果是批处理、离线计算、报表任务，更关注吞吐量，可以选择 Parallel GC。

如果是交易、风控、实时推荐等低延迟系统，尤其关注 P99、P999 延迟，可以考虑 ZGC 或 Shenandoah。

如果是小内存、单核应用，可以使用 Serial GC。

一句话总结：

```text
普通服务选 G1；
吞吐优先选 Parallel；
低延迟大内存选 ZGC / Shenandoah；
小应用选 Serial；
CMS 老项目可见，新项目不推荐。
```
