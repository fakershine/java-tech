# 高并发系统为何建议选择 G1 垃圾收集器

高并发系统选择 G1，核心原因是：

```text
G1 在吞吐量和低停顿之间比较均衡，
能减少 Full GC 风险，
并且可以通过目标停顿时间控制 GC 行为。
```

---

## 1. 高并发系统最怕什么

高并发系统最怕：

```text
长时间 Stop The World
```

因为 GC 停顿期间，业务线程会暂停。

可能导致：

- 接口 RT 突增。
- P99 / P999 延迟变高。
- 请求堆积。
- 线程池打满。
- 网关或调用方超时。
- 熔断、重试放大流量。

所以高并发系统更关注：

```text
GC 停顿时间是否可控
```

---

## 2. G1 的核心优势

| 优势 | 说明 |
|---|---|
| 停顿时间可控 | 可以设置期望最大停顿时间 |
| 分区回收 | 按 Region 回收，不必每次整堆回收 |
| 优先回收垃圾多的区域 | Garbage First，回收收益高 |
| 支持并发标记 | 大部分标记工作和业务线程并发执行 |
| 减少 Full GC 风险 | 相比 CMS 更不容易因碎片触发 Full GC |
| 适合大堆 | 比传统新生代/老年代收集器更适合中大堆 |

---

## 3. G1 的 Region 机制

G1 不再简单把堆固定分为：

```text
新生代
老年代
```

而是把堆切成很多个大小相等的 Region。

```text
Heap
├── Region
├── Region
├── Region
├── Region
└── Region
```

每个 Region 可以作为：

```text
Eden
Survivor
Old
Humongous
```

好处：

```text
GC 可以选择部分 Region 回收
不必每次扫描或整理整个堆
```

---

## 4. Garbage First 是什么意思

G1 全称：

```text
Garbage First
```

意思是：

```text
优先回收垃圾最多、收益最高的 Region
```

例如：

```text
Region A 垃圾 90%
Region B 垃圾 20%
```

G1 会优先回收 A。

这样可以在有限停顿时间内：

```text
回收更多内存
提升 GC 效率
```

---

## 5. 可预测停顿时间

G1 可以设置目标停顿时间：

```bash
-XX:MaxGCPauseMillis=200
```

含义：

```text
希望单次 GC 停顿尽量控制在 200ms 左右
```

注意：

```text
这不是绝对保证，而是 JVM 的调优目标。
```

G1 会根据目标停顿时间，选择合适数量的 Region 进行回收。

---

## 6. 对高并发的好处

高并发系统中，请求非常密集。

如果一次 GC 停顿 2 秒：

```text
2 秒内所有请求都被暂停
```

可能导致：

```text
调用方超时
请求重试
线程池堆积
系统雪崩
```

G1 通过分区回收和停顿预测，可以降低长暂停概率。

所以它更适合：

```text
高并发 Web 服务
微服务接口
网关服务
订单服务
支付服务
用户服务
```

---

## 7. 相比 Parallel GC

Parallel GC 主要追求：

```text
吞吐量
```

它适合：

```text
批处理
离线任务
报表计算
```

但缺点是：

```text
单次停顿可能较长
```

对高并发在线服务不友好。

对比：

| 对比项 | Parallel GC | G1 |
|---|---|---|
| 目标 | 吞吐优先 | 吞吐 + 停顿平衡 |
| 停顿控制 | 较弱 | 较强 |
| 适合场景 | 批处理 | 在线服务 |
| 高并发接口 | 不优先 | 推荐 |

---

## 8. 相比 CMS

CMS 也是低停顿收集器，但有明显问题：

```text
内存碎片
Concurrent Mode Failure
对 CPU 敏感
老年代整理能力弱
```

如果 CMS 并发回收失败，会退化成 Full GC。

高并发系统一旦 Full GC：

```text
停顿时间可能很长
```

G1 会做 Region 复制整理，能减少碎片问题。

对比：

| 对比项 | CMS | G1 |
|---|---|---|
| 是否整理内存 | 不充分，容易碎片 | Region 复制整理 |
| Full GC 风险 | 碎片导致风险较高 | 相对较低 |
| 停顿预测 | 较弱 | 较强 |
| 新项目推荐 | 不推荐 | 推荐 |

---

## 9. 相比 ZGC

ZGC 更适合：

```text
超低延迟
大堆内存
P99/P999 极敏感
```

但 G1 的优势是：

```text
成熟稳定
吞吐表现好
生态使用广
调优经验多
适合大多数普通高并发服务
```

选择建议：

```text
普通高并发服务：G1
极低延迟大内存服务：ZGC
```

---

## 10. G1 常用参数

常见配置：

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-Xms4g
-Xmx4g
```

如果是 JDK 11+，GC 日志：

```bash
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags
```

如果是 JDK 8：

```bash
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-Xloggc:/data/logs/gc.log
```

---

## 11. 使用 G1 的注意点

G1 不是万能的。

如果代码中存在：

```text
大对象频繁创建
一次查询大量数据
缓存无限增长
对象生命周期混乱
日志打印大对象
内存泄漏
```

即使用 G1，GC 也会变差。

所以还要配合：

```text
减少对象创建
控制大对象
分页查询
限制本地缓存
优化线程池
分析 GC 日志
```

---

## 12. 总结

高并发系统建议使用 G1，主要是因为 G1 在吞吐量和低停顿之间比较均衡。

高并发在线服务最怕长时间 STW，因为 GC 停顿会导致请求堆积、接口超时、线程池打满，甚至触发重试风暴。G1 把堆划分成多个 Region，优先回收垃圾最多的 Region，并且可以通过 `MaxGCPauseMillis` 设置期望停顿时间，从而降低长时间停顿风险。

相比 Parallel GC，G1 的停顿时间更可控；相比 CMS，G1 可以减少内存碎片和 Full GC 风险；相比 ZGC，G1 更成熟通用，适合大多数普通高并发 Java 服务。

一句话总结：

```text
高并发系统选 G1，是因为它能在较高吞吐下控制 GC 停顿，减少 Full GC 风险，让接口 RT 更稳定。
```
