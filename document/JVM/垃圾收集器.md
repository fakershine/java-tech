# JVM 垃圾收集器总结

JVM 垃圾收集器用于自动回收不再被引用的对象，核心目标是在 **吞吐量、停顿时间、内存占用** 之间做平衡。

常见垃圾收集器包括：

- Serial GC
- Parallel GC
- CMS GC
- G1 GC
- ZGC
- Shenandoah GC

其中，JDK 21 文档列出的 HotSpot 可用收集器包括 Serial、Parallel、G1 和 ZGC；G1 在多数硬件和操作系统配置下是默认收集器。:contentReference[oaicite:0]{index=0}

---

## 1. Serial GC

### 实现原理

Serial GC 是单线程垃圾收集器。

```text
应用线程全部暂停
  ↓
单个 GC 线程执行垃圾回收
  ↓
回收完成后应用线程继续执行
```

启用参数：

```bash
-XX:+UseSerialGC
```

### 优势

- 实现简单。
- 单线程场景开销小。
- 小内存应用表现较好。

### 劣势

- GC 时会 Stop The World。
- 只能单线程回收。
- 不适合多核、大内存、高并发服务。

### 适用场景

- 小型应用。
- 单核或低配置机器。
- 客户端程序。
- 堆内存较小的服务。

---

## 2. Parallel GC

### 实现原理

Parallel GC 又叫吞吐量优先收集器，使用多个 GC 线程并行回收。

```text
应用线程暂停
  ↓
多个 GC 线程并行回收
  ↓
回收完成后应用线程继续执行
```

启用参数：

```bash
-XX:+UseParallelGC
```

### 优势

- 吞吐量高。
- 多线程 GC，回收速度快。
- 适合 CPU 资源充足的机器。
- 适合后台计算任务。

### 劣势

- GC 期间仍然会 STW。
- 停顿时间可能较长。
- 不适合低延迟接口服务。

### 适用场景

- 批处理系统。
- 后台任务。
- 大数据计算。
- 对吞吐量要求高、对延迟不敏感的系统。

---

## 3. CMS GC

### 实现原理

CMS，全称 Concurrent Mark Sweep，是以低停顿为目标的老年代垃圾收集器。

主要流程：

```text
初始标记 STW
  ↓
并发标记
  ↓
重新标记 STW
  ↓
并发清理
```

启用参数：

```bash
-XX:+UseConcMarkSweepGC
```

### 优势

- 大部分阶段可以和应用线程并发执行。
- 停顿时间比传统收集器短。
- 曾经常用于低延迟服务。

### 劣势

- 会产生内存碎片。
- 对 CPU 资源敏感。
- 并发清理期间会占用业务线程资源。
- 可能发生 Concurrent Mode Failure，退化为 Full GC。
- 新版本 JDK 中已不推荐使用，CMS 已被移除。OpenJDK 的 JEP 363 明确说明移除 CMS，并建议用户迁移到 G1 或其他收集器。:contentReference[oaicite:1]{index=1}

### 适用场景

- 老版本 JDK 中的低延迟服务。
- 现在新项目一般不推荐使用。

---

## 4. G1 GC

### 实现原理

G1，全称 Garbage First，是面向服务端应用的垃圾收集器。

G1 不再简单地把堆划分为连续的新生代和老年代，而是将堆划分成多个大小相等的 Region。

```text
Heap
 ├── Region
 ├── Region
 ├── Region
 └── Region
```

G1 会优先回收垃圾最多、收益最高的 Region。

主要特点：

```text
分 Region 管理堆内存
支持并发标记
支持压缩整理
可以设置停顿时间目标
```

启用参数：

```bash
-XX:+UseG1GC
```

常见参数：

```bash
-XX:MaxGCPauseMillis=200
```

G1 是分代、增量、并行、mostly concurrent、STW 与 evacuation 结合的收集器，会根据暂停时间目标来决定每次回收工作量。:contentReference[oaicite:2]{index=2}

### 优势

- 适合大堆内存。
- 可以设置期望停顿时间。
- 能整理内存，减少碎片。
- 吞吐量和延迟比较均衡。
- JDK 8 以后服务端应用使用较多。

### 劣势

- 参数和行为比 Parallel GC 更复杂。
- 低延迟能力不如 ZGC、Shenandoah。
- 停顿时间目标不是绝对保证。
- 对小堆应用不一定比 Parallel GC 更好。

### 适用场景

- 大多数 Java 服务端应用。
- Spring Boot 微服务。
- 中大堆内存服务。
- 既关注吞吐量，也关注停顿时间的系统。

---

## 5. ZGC

### 实现原理

ZGC 是低延迟垃圾收集器，目标是尽量减少 GC 停顿时间。

ZGC 的核心特点：

```text
并发标记
并发转移
并发重定位
低停顿
支持大堆
```

启用参数：

```bash
-XX:+UseZGC
```

JDK 21 中，Generational ZGC 可以通过以下方式开启：

```bash
-XX:+UseZGC -XX:+ZGenerational
```

ZGC 的设计目标是低停顿，STW 阶段主要限制在 Root 扫描，因此暂停时间不会随着堆大小或存活对象集合增大而明显增长。:contentReference[oaicite:3]{index=3}

### 优势

- 停顿时间极短。
- 适合大内存应用。
- GC 停顿对堆大小不敏感。
- 适合低延迟服务。

### 劣势

- 对 CPU 和内存资源要求较高。
- 吞吐量可能低于吞吐量优先收集器。
- 需要较新 JDK 支持。
- 调优和排查门槛较高。

### 适用场景

- 大堆内存服务。
- 低延迟接口。
- 实时系统。
- 对 GC 停顿非常敏感的业务。

---

## 6. Shenandoah GC

### 实现原理

Shenandoah 是低停顿垃圾收集器，核心目标也是减少 GC 停顿时间。

它通过并发方式完成大部分 GC 工作：

```text
并发标记
并发清理
并发整理
```

启用参数：

```bash
-XX:+UseShenandoahGC
```

OpenJDK JEP 521 说明，Generational Shenandoah 在 JDK 25 中从实验特性变为产品特性，但默认模式仍保持单代模式。:contentReference[oaicite:4]{index=4}

### 优势

- 低停顿。
- 大部分回收工作和应用线程并发执行。
- 适合响应时间敏感的服务。
- 支持并发整理，减少内存碎片。

### 劣势

- 吞吐量可能受到一定影响。
- 对 CPU 资源敏感。
- 不同 JDK 发行版支持情况可能不同。
- 使用复杂度高于 G1。

### 适用场景

- 低延迟服务。
- 大堆内存服务。
- 对停顿时间敏感的系统。

---

## 7. 垃圾收集器对比

| 收集器 | 核心目标 | 是否低延迟 | 是否高吞吐 | 适用场景 |
|---|---|---|---|---|
| Serial GC | 简单、低资源 | 否 | 否 | 小内存、单核、小应用 |
| Parallel GC | 吞吐量优先 | 否 | 是 | 批处理、后台任务 |
| CMS GC | 降低老年代停顿 | 是 | 中 | 老版本 JDK 低延迟服务 |
| G1 GC | 吞吐和延迟平衡 | 中高 | 中高 | 大多数服务端应用 |
| ZGC | 极低停顿 | 是 | 中 | 大内存、低延迟服务 |
| Shenandoah | 极低停顿 | 是 | 中 | 低延迟、大堆服务 |

---

## 8. 如何选择垃圾收集器

### 小内存、小应用

推荐：

```bash
-XX:+UseSerialGC
```

适合：

```text
小工具
客户端程序
低配置机器
```

---

### 吞吐量优先

推荐：

```bash
-XX:+UseParallelGC
```

适合：

```text
批处理
离线计算
后台任务
对停顿不敏感的服务
```

---

### 通用服务端应用

推荐：

```bash
-XX:+UseG1GC
```

适合：

```text
Spring Boot 服务
微服务系统
中大型业务服务
```

---

### 低延迟、大内存

推荐：

```bash
-XX:+UseZGC
```

或：

```bash
-XX:+UseShenandoahGC
```

适合：

```text
低延迟接口
大堆内存服务
实时业务系统
对 GC 停顿敏感的应用
```

---

## 9. GC 相关核心概念

### Stop The World

STW 指 GC 时暂停所有业务线程。

```text
应用线程暂停
  ↓
GC 执行
  ↓
应用线程恢复
```

调优时通常希望：

```text
减少 STW 次数
降低 STW 时间
```

---

### 吞吐量

吞吐量指应用线程运行时间占总时间的比例。

```text
吞吐量 = 应用运行时间 / 总运行时间
```

Parallel GC 更偏吞吐量优先。

---

### 停顿时间

停顿时间指 GC 导致应用线程暂停的时间。

```text
停顿时间越短，接口响应越稳定
```

G1、ZGC、Shenandoah 更关注停顿时间。

---

## 10. 总结

JVM 常见垃圾收集器包括 Serial、Parallel、CMS、G1、ZGC 和 Shenandoah。

Serial GC 是单线程收集器，适合小内存、小应用；Parallel GC 是吞吐量优先收集器，适合后台任务和批处理系统；CMS 是老年代低停顿收集器，但会产生内存碎片，并且新版本 JDK 已经不推荐使用；G1 是目前服务端应用中常用的垃圾收集器，通过 Region 管理堆内存，能够在吞吐量和停顿时间之间取得平衡；ZGC 和 Shenandoah 是低延迟收集器，适合大内存、低停顿要求高的系统。

实际选择时，如果是普通 Spring Boot 微服务，通常使用 G1；如果是批处理任务，可以考虑 Parallel GC；如果业务对停顿非常敏感，可以考虑 ZGC 或 Shenandoah。

一句话总结：

```text
吞吐量优先选 Parallel，通用服务端选 G1，低延迟大内存选 ZGC 或 Shenandoah，小内存小应用选 Serial。
```
