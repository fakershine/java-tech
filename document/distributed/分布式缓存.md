# 分布式缓存总结

分布式缓存是将热点数据存放在独立缓存系统中，多个应用实例共享访问，用于减少数据库压力、提升系统性能和响应速度。常见实现组件有 **Redis、Memcached**，实际项目中 Redis 使用最多。

---

## 1. 分布式缓存的作用

### 核心目的

- 降低数据库访问压力。
- 提升接口响应速度。
- 缓存热点数据。
- 承担部分高并发读流量。
- 提高系统整体吞吐量。

### 常见使用场景

- 用户信息缓存。
- 商品详情缓存。
- 首页配置缓存。
- 字典数据缓存。
- 登录 Token / Session 缓存。
- 排行榜、计数器、限流、分布式锁等场景。

---

## 2. 常见缓存方案

| 缓存类型 | 说明 | 适用场景 |
|---|---|---|
| 本地缓存 | 缓存在应用进程内，如 Caffeine、Guava Cache | 单机热点数据、极低延迟读取 |
| 分布式缓存 | 多个服务实例共享缓存，如 Redis、Memcached | 多实例共享数据、高并发读 |
| 多级缓存 | 本地缓存 + 分布式缓存 | 超高并发、热点数据读取 |

---

## 3. Redis 分布式缓存实现原理

### 基本流程

读取数据时：

```text
请求接口
  ↓
先查 Redis
  ↓
Redis 命中，直接返回
  ↓
Redis 未命中，查询数据库
  ↓
将数据库结果写入 Redis
  ↓
返回结果
```

伪代码：

```java
public User getUser(Long userId) {
    User user = redis.get("user:" + userId);
    if (user != null) {
        return user;
    }

    user = db.queryUser(userId);
    if (user != null) {
        redis.set("user:" + userId, user, 30, TimeUnit.MINUTES);
    }

    return user;
}
```

## 4. 缓存更新策略

### 1. Cache Aside Pattern

最常用的缓存模式，也叫旁路缓存模式。

#### 查询流程

```text
先查缓存
缓存有，直接返回
缓存没有，查数据库
查到后写入缓存
```

#### 更新流程

```text
先更新数据库
再删除缓存
```

推荐做法：

```text
更新数据库成功后，删除缓存，而不是直接更新缓存。
```

### 优势

- 实现简单。
- 业务可控。
- 实际项目中最常用。

### 劣势

- 可能存在短暂数据不一致。
- 需要处理缓存删除失败问题。

---

## 5. 为什么是删除缓存，而不是更新缓存？

更新数据库后，通常推荐 **删除缓存**，而不是直接更新缓存。

原因：

- 缓存中的数据可能是复杂计算结果，直接更新成本高。
- 并发更新时，容易出现旧数据覆盖新数据。
- 删除缓存后，下次查询会重新从数据库加载最新数据。

推荐流程：

```text
更新数据库
  ↓
删除缓存
  ↓
下次查询缓存未命中
  ↓
查询数据库
  ↓
重新写入缓存
```

## 6. 缓存一致性问题

### 常见问题

分布式缓存和数据库是两个不同系统，无法天然保证强一致。

可能出现：

```text
数据库更新成功
缓存删除失败
导致缓存中仍然是旧数据
```

### 常见解决方案

| 方案 | 说明 |
|---|---|
| 先更新数据库，再删除缓存 | 最常用方案 |
| 延迟双删 | 更新数据库后删除缓存，延迟一段时间再删一次 |
| 消息队列重试 | 缓存删除失败后发送 MQ 异步重试 |
| 监听 binlog | 通过 Canal 监听数据库变更后删除缓存 |
| 设置过期时间 | 即使删除失败，缓存最终也会过期 |

### 面试推荐回答

一般业务场景下，使用：

```text
先更新数据库，再删除缓存 + 缓存过期时间 + 删除失败重试
```

如果一致性要求更高，可以使用：

```text
binlog 监听 + MQ 重试删除缓存
```

## 7. 缓存穿透

### 问题描述

缓存穿透指查询一个数据库中也不存在的数据，导致每次请求都会打到数据库。

例如恶意请求：

```text
userId = -1
userId = 999999999
```

缓存中没有，数据库中也没有，每次都访问数据库。

### 解决方案

| 方案 | 说明 |
|---|---|
| 缓存空值 | 数据库查不到时，将空结果缓存一段时间 |
| 布隆过滤器 | 请求先经过布隆过滤器，不存在的数据直接拦截 |
| 参数校验 | 非法参数直接拒绝 |
| 接口限流 | 防止恶意高频访问 |

### 常用做法

```text
缓存空值 + 短过期时间
```

例如：

```text
user:999 = null，过期时间 1 分钟
```

## 8. 缓存击穿

### 问题描述

缓存击穿指某个热点 Key 过期瞬间，大量请求同时访问，全部打到数据库。

例如：

```text
商品详情 product:1001 是热点 Key
该 Key 过期
瞬间大量请求访问
数据库压力暴增
```

### 解决方案

| 方案 | 说明 |
|---|---|
| 互斥锁 | 只允许一个线程查数据库并重建缓存 |
| 逻辑过期 | 缓存不真正过期，由后台异步刷新 |
| 热点 Key 永不过期 | 对极热点数据不设置物理过期 |
| 提前预热 | 提前加载热点数据到缓存 |

### 常用做法

```text
互斥锁 + 双重检查
```

流程：

```text
查询缓存
  ↓
缓存未命中
  ↓
尝试获取锁
  ↓
获取锁成功，查询数据库并写缓存
  ↓
其他线程等待或稍后重试
```

## 9. 缓存雪崩

### 问题描述

缓存雪崩指大量缓存 Key 在同一时间失效，导致请求集中打到数据库。

例如：

```text
大量缓存统一设置 30 分钟过期
30 分钟后同时失效
数据库瞬间压力暴增
```

### 解决方案

| 方案 | 说明 |
|---|---|
| 过期时间加随机值 | 避免大量 Key 同时失效 |
| 热点数据预热 | 系统启动前提前加载热点缓存 |
| 多级缓存 | 本地缓存 + Redis 缓存 |
| 限流降级 | 数据库压力过大时保护系统 |
| Redis 高可用 | 使用主从、哨兵、集群保证缓存服务可用 |

### 常用做法

```text
缓存过期时间 = 固定时间 + 随机时间
```

例如：

```text
30 分钟 + 0~5 分钟随机值
```

## 10. 缓存淘汰策略

Redis 内存不足时，会根据配置的淘汰策略删除部分 Key。

常见策略：

| 策略 | 说明 |
|---|---|
| noeviction | 不淘汰，写入时报错 |
| allkeys-lru | 从所有 Key 中淘汰最近最少使用的 |
| volatile-lru | 从设置了过期时间的 Key 中淘汰最近最少使用的 |
| allkeys-random | 从所有 Key 中随机淘汰 |
| volatile-random | 从设置了过期时间的 Key 中随机淘汰 |
| volatile-ttl | 优先淘汰快过期的 Key |
| allkeys-lfu | 从所有 Key 中淘汰访问频率最低的 |
| volatile-lfu | 从设置过期时间的 Key 中淘汰访问频率最低的 |

实际项目常用：

```text
allkeys-lru 或 allkeys-lfu
```

## 11. 多级缓存

### 实现原理

多级缓存一般由 **本地缓存 + Redis 缓存 + 数据库** 组成。

查询流程：

```text
先查本地缓存
  ↓
本地缓存没有，查 Redis
  ↓
Redis 没有，查数据库
  ↓
回写 Redis
  ↓
回写本地缓存
```

### 优势

- 访问速度更快。
- 减少 Redis 压力。
- 适合热点数据读取。

### 劣势

- 一致性更复杂。
- 本地缓存更新不及时。
- 多实例之间缓存数据可能不一致。

### 适用场景

- 商品详情页。
- 首页配置。
- 字典数据。
- 热点活动数据。

---

## 12. 分布式缓存注意点

- 缓存 Key 要规范命名，例如：`业务名:模块名:id`。
- 热点 Key 要重点监控。
- 大 Key 要避免，防止 Redis 阻塞。
- 缓存数据要设置合理过期时间。
- 更新数据库后优先删除缓存。
- 删除缓存失败要有重试机制。
- 高并发热点 Key 要防止击穿。
- 不存在的数据要防止穿透。
- 大量 Key 过期要防止雪崩。
- Redis 要配置主从、哨兵或集群保证高可用。

---

## 13. 总结

分布式缓存主要用于提升系统性能、降低数据库压力，常见实现是 Redis。

查询时一般采用旁路缓存模式：先查缓存，缓存命中直接返回；缓存未命中再查数据库，并将结果写入缓存。

更新时通常采用“先更新数据库，再删除缓存”的方式，而不是直接更新缓存，这样可以降低并发场景下缓存脏数据风险。

分布式缓存需要重点解决缓存一致性、缓存穿透、缓存击穿和缓存雪崩问题。缓存穿透可以用缓存空值或布隆过滤器解决；缓存击穿可以用互斥锁或逻辑过期解决；缓存雪崩可以通过过期时间加随机值、缓存预热、多级缓存、限流降级等方式解决。

实际项目中，一般使用 Redis 作为分布式缓存，并结合本地缓存、过期时间、删除失败重试、监控告警等手段保证系统稳定性。
