# 分布式锁实现方式总结

分布式锁用于在分布式环境下，保证同一时刻只有一个节点能操作共享资源。常见实现方式主要有：**数据库、Redis、Redisson、ZooKeeper**。

---

## 1. 数据库实现分布式锁

### 实现原理

数据库分布式锁通常基于 **唯一索引** 或 **行锁** 实现。

- **唯一索引方式**：创建锁表，对 `lock_key` 建唯一索引。加锁时插入记录，插入成功表示获取锁成功；插入失败表示锁已被占用。释放锁时删除对应记录。
- **行锁方式**：通过 `select ... for update` 对某一行加锁，事务提交或回滚后自动释放锁。

### 优势

- 实现简单，不需要额外引入中间件。
- 依赖数据库事务和唯一约束，一致性较好。
- 适合低并发、简单业务场景。

### 劣势

- 性能一般，高并发下容易给数据库带来压力。
- 需要处理锁超时、死锁、服务宕机后锁未释放等问题。
- 不适合高频加锁场景。

---

## 2. Redis 实现分布式锁

### 实现原理

Redis 分布式锁通常使用 `SET NX PX` 命令实现：

```bash
SET lock_key unique_value NX PX expire_time
```

参数说明：

- `NX`：只有 key 不存在时才设置成功，保证互斥。
- `PX`：设置锁过期时间，防止死锁。
- `unique_value`：标识锁持有者，防止误删其他线程的锁。

释放锁时不能直接 `DEL`，需要使用 Lua 脚本保证“判断锁归属”和“删除锁”两个操作的原子性：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### 优势

- 性能高，适合高并发场景。
- 实现简单，使用方便。
- 支持过期时间，可以避免死锁。
- 适合大多数业务分布式锁场景。

### 劣势

- 锁过期时间不好控制，业务执行时间过长可能导致锁提前失效。
- 需要自己处理锁续期问题。
- Redis 主从切换时可能存在锁丢失风险。
- 实现不当可能误删其他线程的锁。

---

## 3. Redisson 实现分布式锁

### 实现原理

Redisson 是基于 Redis 实现的 Java 分布式锁组件，底层并不是简单使用 `SET NX PX`，而是主要基于 **Redis Hash + Lua 脚本 + WatchDog 自动续期 + Pub/Sub 通知机制** 实现。

---

### 1. 使用的数据结构

Redisson 使用 Redis 的 **Hash** 结构保存锁信息。

结构大致如下：

```text
lock_key = {
    "clientId:threadId": reentrant_count
}
```

说明：

- `lock_key`：锁名称。
- `clientId:threadId`：锁持有者标识，由 Redisson 客户端 ID 和线程 ID 组成。
- `reentrant_count`：重入次数。

例如：

```text
order_lock = {
    "uuid-001:thread-10": 2
}
```

表示 `uuid-001` 这个 Redisson 客户端中的 `thread-10` 线程持有锁，并且已经重入了 2 次。

---

### 2. 加锁流程

Redisson 加锁时会执行 Lua 脚本，保证加锁逻辑的原子性。

加锁逻辑可以简化理解为：

```lua
if lock_key 不存在 then
    创建 Hash
    将当前线程标识的重入次数加 1
    设置锁过期时间
    返回加锁成功
elseif lock_key 中存在当前线程标识 then
    说明是当前线程重复加锁
    重入次数加 1
    重新设置锁过期时间
    返回加锁成功
else
    说明锁被其他线程持有
    返回锁剩余过期时间
end
```

核心逻辑：

```text
1. 如果锁不存在，直接加锁成功。
2. 如果锁已经存在，但持有者是当前线程，说明是重入，加锁成功。
3. 如果锁已经存在，并且持有者不是当前线程，则加锁失败。
```

---

### 3. 如何实现可重入

Redisson 通过 Redis Hash 中的 **重入次数** 实现可重入。

第一次加锁：

```text
order_lock = {
    "uuid-001:thread-10": 1
}
```

同一个线程再次加锁：

```text
order_lock = {
    "uuid-001:thread-10": 2
}
```

也就是说，同一个线程重复获取同一把锁时，不会被阻塞，而是将 Hash 中对应线程的计数加一。

释放锁时，计数会减一：

```text
2 -> 1
```

只有当重入次数减到 `0` 时，才会真正删除锁。

---

### 4. 如何实现自动续期

Redisson 提供 **WatchDog 看门狗机制**。

如果加锁时没有手动指定 `leaseTime`，Redisson 会默认给锁设置一个过期时间，默认是 `30` 秒。

在业务还没有执行完成时，WatchDog 会定期检查当前线程是否仍然持有锁：

```text
如果当前线程仍然持有锁
    则自动延长锁的过期时间
```

默认情况下，Redisson 会周期性地将锁的过期时间重新续到 `30` 秒。

这样可以避免业务执行时间过长时，锁提前过期，导致其他线程获取到锁。

---

### 5. 如果指定了 leaseTime 会怎样

如果手动指定了锁过期时间，例如：

```java
lock.lock(10, TimeUnit.SECONDS);
```

表示锁最多持有 `10` 秒，时间到了会自动释放。

这种情况下，Redisson 不会无限续期，锁会按照指定的 `leaseTime` 自动过期。

所以：

```text
不指定 leaseTime：启用 WatchDog 自动续期
指定 leaseTime：到期自动释放，不走无限续期
```

---

### 6. 释放锁流程

释放锁时，Redisson 同样通过 Lua 脚本保证原子性。

释放逻辑可以简化理解为：

```lua
if lock_key 中不存在当前线程标识 then
    说明当前线程不是锁持有者
    不能释放锁
else
    将当前线程的重入次数减 1

    if 重入次数 > 0 then
        说明还有重入未释放
        重新设置过期时间
    else
        删除锁
        发布锁释放消息
    end
end
```

释放过程：

```text
1. 判断当前线程是否持有锁。
2. 如果不是当前线程持有锁，不能释放。
3. 如果是当前线程持有锁，重入次数减一。
4. 如果重入次数大于 0，说明还没有完全释放。
5. 如果重入次数等于 0，删除锁。
6. 删除锁后通过 Pub/Sub 通知其他等待线程重新竞争锁。
```

---

### 7. Pub/Sub 通知机制

当线程获取锁失败时，不会一直死循环抢锁。

Redisson 会让等待线程订阅一个释放锁的频道。

当持有锁的线程释放锁后，会发布一条释放锁消息，通知其他等待线程重新尝试获取锁。

这样可以减少无效自旋，降低 Redis 压力。

---

### 优势

- 支持可重入锁。
- 支持 WatchDog 自动续期，避免业务未执行完锁就过期。
- 使用 Lua 脚本保证加锁和释放锁的原子性。
- 使用 Hash 结构记录线程标识和重入次数。
- 释放锁时校验线程标识，避免误删其他线程的锁。
- 通过 Pub/Sub 通知等待线程，减少无效轮询。
- 使用简单，适合 Java 项目。

---

### 劣势

- 底层仍然依赖 Redis，Redis 故障会影响锁的可用性。
- WatchDog 续期依赖 Redisson 客户端正常运行，如果 JVM 长时间停顿、网络抖动，可能导致续期失败。
- 如果指定了固定 `leaseTime`，业务执行时间超过该时间后，锁仍可能提前释放。
- Redis 主从切换时，仍可能存在锁丢失风险。
- 相比普通 Redis 锁，实现更复杂，引入了额外框架依赖。

---

### 总结

Redisson 分布式锁底层主要使用 Redis Hash 结构存储锁信息，Hash 的 field 是客户端 ID 加线程 ID，value 是重入次数。加锁和释放锁都通过 Lua 脚本保证原子性。

加锁时，如果锁不存在，则创建 Hash 并设置过期时间；如果锁已经存在但持有者是当前线程，则将重入次数加一，实现可重入；如果锁被其他线程持有，则获取锁失败。

释放锁时，会先判断当前线程是否持有锁，如果持有则将重入次数减一，只有重入次数减到零时才会真正删除锁。删除锁后，会通过 Pub/Sub 通知其他等待线程重新竞争锁。

如果加锁时没有指定 `leaseTime`，Redisson 会启用 WatchDog 机制，默认每隔一段时间自动为锁续期，避免业务还没执行完锁就过期。如果指定了 `leaseTime`，则锁会在指定时间后自动释放，不会无限续期。

---

## 4. ZooKeeper 实现分布式锁

### 实现原理

ZooKeeper 分布式锁通常基于 **临时顺序节点 + Watch 机制** 实现。

加锁流程：

1. 多个客户端在同一目录下创建临时顺序节点。
2. 判断自己创建的节点是否是序号最小的节点。
3. 如果是最小节点，则获取锁成功。
4. 如果不是，则监听自己前一个节点。
5. 前一个节点删除后，再次判断是否获取锁。
6. 业务执行完成后，删除自己的节点释放锁。

临时节点可以保证客户端宕机后自动释放锁，顺序节点可以保证加锁的公平性。

### 优势

- 一致性强，可靠性高。
- 临时节点机制可以自动释放锁。
- 顺序节点天然支持公平锁。
- Watch 机制可以避免无效轮询。
- 适合分布式协调、Leader 选举等场景。

### 劣势

- 性能不如 Redis。
- 部署和维护成本较高。
- 对网络抖动较敏感，Session 过期可能导致锁被释放。
- 不适合高频短时间加锁场景。

---

## 5. 方案对比

| 实现方式 | 核心原理 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|---|
| 数据库 | 唯一索引 / 行锁 | 简单、一致性较好 | 性能一般、需处理超时和死锁 | 低并发、简单业务锁 |
| Redis | `SET NX PX` + Lua | 性能高、实现简单 | 需处理续期、误删、主从切换问题 | 高并发业务锁 |
| Redisson | Redis + Lua + WatchDog | 支持可重入、自动续期、使用方便 | 依赖 Redis，极端情况下仍可能失效 | Java 项目常用分布式锁 |
| ZooKeeper | 临时顺序节点 + Watch | 一致性强、支持公平锁 | 性能较低、维护成本高 | 强一致协调、Leader 选举 |

---

## 6. 总结

数据库分布式锁实现简单，通常基于唯一索引或行锁实现，适合低并发场景，但性能一般。

Redis 分布式锁通常基于 `SET NX PX` 实现，通过过期时间防止死锁，通过唯一 value 和 Lua 脚本防止误删锁，性能高，适合高并发场景。

Redisson 是 Redis 分布式锁的成熟封装，支持可重入锁、自动续期、公平锁等能力，Java 项目中使用较多。

ZooKeeper 分布式锁基于临时顺序节点和 Watch 机制实现，一致性强，可靠性高，适合 Leader 选举和分布式协调场景，但性能不如 Redis。

实际选择时：

- 简单低频场景可以使用数据库锁。
- 高并发业务场景优先使用 Redis 或 Redisson。
- Java 项目中推荐使用 Redisson。
- 强一致协调或 Leader 选举场景可以使用 ZooKeeper。
