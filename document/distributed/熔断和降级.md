# 熔断和降级总结

熔断和降级都是微服务高可用设计中的常见手段，主要用于防止系统在异常流量、依赖故障或资源不足时被拖垮。

---

## 1. 熔断

### 实现原理

熔断主要用于保护调用方，防止下游服务异常时，调用方持续请求导致线程、连接等资源被耗尽。

当某个服务调用失败率、超时率达到阈值后，熔断器会打开，后续请求不再真正调用下游服务，而是直接失败或走降级逻辑。

熔断器通常有三种状态：

| 状态 | 说明 |
|---|---|
| 关闭 | 正常调用下游服务 |
| 打开 | 不再调用下游服务，直接返回失败或降级结果 |
| 半开 | 放少量请求试探下游是否恢复 |

状态流转：

```text
正常调用
  ↓
失败率或超时率达到阈值
  ↓
熔断打开，快速失败
  ↓
等待一段时间后进入半开状态
  ↓
少量请求成功，熔断关闭
  ↓
少量请求失败，继续熔断
```

### 优势

- 防止故障扩散。
- 避免调用方线程被大量阻塞。
- 可以快速失败，提升系统恢复能力。
- 保护核心服务和系统资源。

### 劣势

- 阈值配置不合理可能导致误熔断。
- 熔断期间部分请求无法正常处理。
- 需要配合监控、告警和降级策略使用。

### 适用场景

- 调用第三方接口超时。
- 下游服务异常或响应变慢。
- 数据库、缓存、RPC 服务不可用。
- 防止某个服务故障拖垮整个链路。

---

## 2. 降级

### 实现原理

降级是在系统压力过大或依赖服务异常时，主动放弃部分非核心功能，优先保证核心功能可用。

降级可以返回默认值、缓存数据、兜底文案，也可以关闭部分功能。

常见降级方式：

| 降级方式 | 说明 |
|---|---|
| 返回默认值 | 例如返回空列表、默认配置 |
| 返回缓存数据 | 例如返回上一次成功查询的结果 |
| 关闭非核心功能 | 例如关闭推荐、评论、排行榜 |
| 异步处理 | 例如请求先入队，后续异步处理 |
| 兜底页面 | 例如返回“系统繁忙，请稍后再试” |

示例：

```java
public UserInfo getUserInfo(Long userId) {
    try {
        return userService.queryUserInfo(userId);
    } catch (Exception e) {
        return UserInfo.defaultUser();
    }
}
```

### 优势

- 保证核心链路可用。
- 提升系统容错能力。
- 用户体验比直接报错更好。
- 可以降低下游服务压力。

### 劣势

- 返回结果可能不完整或不实时。
- 需要提前设计兜底逻辑。
- 降级过多可能影响业务体验。
- 需要区分核心功能和非核心功能。

### 适用场景

- 首页推荐失败时返回默认推荐。
- 查询用户标签失败时返回空标签。
- 商品详情中评论服务异常时隐藏评论模块。
- 秒杀高峰期关闭非核心功能。
- 第三方接口异常时返回兜底结果。

---

## 3. 熔断和降级的区别

| 对比项 | 熔断 | 降级 |
|---|---|---|
| 目的 | 防止故障扩散 | 保证核心功能可用 |
| 触发方式 | 通常根据失败率、超时率自动触发 | 可以自动触发，也可以人工开关 |
| 关注点 | 是否继续调用下游服务 | 返回什么兜底结果 |
| 作用对象 | 主要保护调用方 | 主要保护整体业务体验 |
| 常见结果 | 快速失败或走降级逻辑 | 返回默认值、缓存、兜底数据 |
| 典型场景 | 下游服务异常、超时 | 非核心功能关闭、返回兜底结果 |

---

## 4. 熔断和降级的关系

熔断和降级通常会配合使用。

```text
下游服务异常
    ↓
调用失败率升高
    ↓
触发熔断
    ↓
不再调用下游
    ↓
执行降级逻辑
    ↓
返回兜底结果
```

简单理解：

```text
熔断：决定还要不要继续调用下游。
降级：决定不调用下游后返回什么。
```

---

## 5. 常见实现方式

### Sentinel

Sentinel 是阿里开源的流量治理组件，支持：

- 限流
- 熔断降级
- 系统保护
- 热点参数限流
- 实时监控

适合 Java 微服务项目，尤其是 Spring Cloud Alibaba 体系。

### Resilience4j

Resilience4j 是轻量级容错组件，常见能力包括：

- CircuitBreaker：熔断
- RateLimiter：限流
- Bulkhead：隔离
- Retry：重试
- TimeLimiter：超时控制

适合 Spring Boot / Spring Cloud 项目。

### Hystrix

Hystrix 是 Netflix 早期的熔断降级组件，但目前已经进入维护状态，新项目一般更推荐使用 Sentinel 或 Resilience4j。

---

## 6. 实现注意点

- 熔断要配置合理的失败率、慢调用比例、最小请求数和恢复时间。
- 降级逻辑要轻量，不能再依赖容易失败的服务。
- 核心链路和非核心链路要提前区分。
- 熔断、降级、限流、超时、重试通常要配合使用。
- 重试要谨慎，避免在下游故障时放大流量。
- 降级结果要可接受，不能破坏核心业务一致性。
- 必须配合监控和告警，及时发现服务异常。

---

## 7. 总结

熔断和降级都是微服务容错的重要手段。

熔断主要是为了防止下游服务故障影响调用方，当失败率、超时率达到阈值时，熔断器会打开，后续请求不再调用下游服务，而是快速失败或走降级逻辑。熔断器一般有关闭、打开、半开三种状态。

降级主要是为了保证核心功能可用，当系统压力过大或依赖服务异常时，可以主动关闭非核心功能，或者返回默认值、缓存数据、兜底结果。

两者通常配合使用：熔断负责判断是否继续调用下游，降级负责在调用失败或熔断后返回什么结果。实际项目中可以使用 Sentinel、Resilience4j 等组件实现。
