# 接口幂等实现方式总结

接口幂等指的是：**同一个请求执行一次和执行多次，最终产生的结果一致**。  
主要用于解决接口重复提交、网络重试、MQ 重复消费、支付回调重复通知等问题。

---

## 1. 唯一索引实现幂等

### 实现原理

通过数据库唯一索引保证同一业务请求只能成功插入一次。

例如创建订单时，使用 `order_no`、`request_id` 或 `biz_no` 建唯一索引：

```sql
CREATE UNIQUE INDEX uk_order_no ON t_order(order_no);
```

请求重复提交时，第一次插入成功，后续插入会因为唯一索引冲突失败。

### 优势

- 实现简单。
- 一致性强。
- 依赖数据库唯一约束，可靠性高。

### 劣势

- 只适合新增类接口。
- 高并发下数据库压力较大。
- 需要设计好业务唯一键。

### 适用场景

- 创建订单
- 创建支付单
- 防止重复开户
- 防止重复提交表单

## 2. Token 机制实现幂等

### 实现原理

客户端提交请求前，先向服务端申请一个唯一 Token。

流程：

1. 客户端先请求服务端生成 Token。
2. 服务端将 Token 保存到 Redis，并返回给客户端。
3. 客户端提交业务请求时携带 Token。
4. 服务端校验 Token 是否存在。
5. 校验成功后删除 Token，并执行业务。
6. 如果重复提交，Token 已被删除，请求直接拒绝。

Redis 示例：

```text
SET idempotent:token:xxx 1 EX 300
```

业务请求时：

```text
校验 Token 存在 -> 删除 Token -> 执行业务
```

校验和删除需要使用 Lua 脚本保证原子性。

### 优势

- 可以防止表单重复提交。
- 对业务侵入较小。
- 适合前端主动提交类接口。

### 劣势

- 需要客户端配合。
- 多一次获取 Token 的请求。
- Token 过期时间需要合理设置。

### 适用场景

- 表单提交
- 创建订单
- 用户注册
- 防止按钮重复点击

---

## 3. Redis `SETNX` 实现幂等

### 实现原理

使用 Redis 的 `SETNX` 或 `SET key value NX EX` 判断请求是否已经处理过。

例如使用 `request_id` 作为幂等 Key：

```bash
SET idempotent:request:123 1 NX EX 300
```

如果设置成功，说明第一次请求，可以继续执行业务。  
如果设置失败，说明请求已经处理过，直接返回重复请求结果。

### 优势

- 性能高。
- 实现简单。
- 适合高并发场景。
- 可以设置过期时间，避免 Key 无限增长。

### 劣势

- Redis 异常会影响幂等判断。
- 需要考虑业务执行失败后的 Key 处理。
- 如果先写 Redis 后业务失败，可能导致请求无法重试。

### 适用场景

- 接口防重复提交
- MQ 消息去重
- 支付回调去重
- 高并发请求幂等控制

## 4. 状态机实现幂等

### 实现原理

通过业务状态流转控制接口幂等。

例如订单状态：

```text
待支付 -> 已支付 -> 已发货 -> 已完成
```

支付接口只能将订单从 `待支付` 更新为 `已支付`：

```sql
UPDATE t_order
SET status = 'PAID'
WHERE order_no = 'xxx'
AND status = 'WAIT_PAY';
```

如果重复支付回调再次执行，由于订单状态已经是 `PAID`，更新失败，不会重复处理。

### 优势

- 符合业务语义。
- 不依赖额外组件。
- 适合有明确状态流转的业务。
- 可以防止非法状态变更。

### 劣势

- 需要设计清晰的状态机。
- 不适合无状态流转的接口。
- 状态判断逻辑容易分散。

### 适用场景

- 订单支付
- 订单取消
- 退款审核
- 发货确认
- 审批流程

## 5. 乐观锁实现幂等

### 实现原理

通过版本号控制并发更新。

表中增加 `version` 字段：

```sql
UPDATE t_order
SET status = 'PAID',
    version = version + 1
WHERE order_no = 'xxx'
AND version = 1;
```

只有版本号匹配时才能更新成功。  
重复请求或并发请求因为版本号不一致，更新失败。

### 优势

- 不阻塞线程。
- 适合并发更新场景。
- 可以避免重复修改数据。

### 劣势

- 需要增加版本字段。
- 高并发下可能频繁失败重试。
- 更适合更新类接口。

### 适用场景

- 库存扣减
- 账户余额更新
- 订单状态更新
- 并发修改数据

## 6. 去重表实现幂等

### 实现原理

创建一张请求去重表，记录已经处理过的请求。

```sql
CREATE TABLE idempotent_request (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    request_id VARCHAR(128) NOT NULL,
    biz_type VARCHAR(64),
    status VARCHAR(32),
    create_time DATETIME,
    UNIQUE KEY uk_request_id(request_id)
);
```

处理流程：

1. 请求进来后，先插入 `request_id`。
2. 插入成功，说明第一次处理。
3. 插入失败，说明请求已经处理过。
4. 业务处理完成后，更新处理状态。

### 优势

- 可靠性高。
- 可记录请求处理状态。
- 方便排查问题。
- 适合重要业务链路。

### 劣势

- 多一次数据库操作。
- 表数据会持续增长，需要定期清理。
- 实现比 Redis 稍复杂。

### 适用场景

- 支付回调
- 退款回调
- MQ 消息消费
- 第三方通知处理

## 7. MQ 消息幂等

### 实现原理

MQ 可能会因为重试、网络异常、消费者异常导致消息重复投递，所以消费者必须保证幂等。

常见做法：

- 使用消息唯一 ID 做去重。
- 消费前查询是否处理过。
- 使用 Redis `SETNX` 或数据库唯一索引记录消费状态。
- 业务更新时结合状态机或乐观锁。

示例：

```text
message_id = 123
SET mq:consume:123 1 NX EX 86400
```

设置成功则消费，设置失败则说明已经消费过。

### 优势

- 可以防止消息重复消费。
- 适合异步系统。
- 可以结合 Redis 或数据库实现。

### 劣势

- 需要额外维护消费记录。
- 消费失败时要处理状态回滚或重试。
- 需要结合业务保证最终一致性。

### 适用场景

- Kafka 消费
- RabbitMQ 消费
- RocketMQ 消费
- 异步订单处理

## 8. 各方案对比

| 方案 | 核心思想 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|---|
| 唯一索引 | 业务唯一键防重复 | 简单、可靠 | 依赖数据库 | 创建类接口 |
| Token 机制 | 一次性令牌 | 防重复提交效果好 | 需要客户端配合 | 表单提交 |
| Redis SETNX | 请求 Key 去重 | 性能高 | 依赖 Redis | 高并发接口 |
| 状态机 | 控制状态流转 | 符合业务语义 | 依赖状态设计 | 订单、支付 |
| 乐观锁 | version 控制更新 | 无阻塞 | 可能重试 | 更新类接口 |
| 去重表 | 记录请求处理状态 | 可靠、可追踪 | 多一次 DB 操作 | 支付、回调、MQ |
| MQ 幂等 | 消息 ID 去重 | 防重复消费 | 需维护消费状态 | 异步消费 |

---

## 9. 实现幂等的注意点

- 幂等 Key 要全局唯一，例如 `request_id`、`order_no`、`message_id`。
- 判断幂等和业务处理之间要保证原子性。
- 重要业务建议使用数据库唯一索引或去重表。
- 高并发场景可以使用 Redis，但要考虑业务失败后的 Key 处理。
- 支付、订单、退款等场景建议结合状态机实现。
- MQ 消费必须做幂等，不能只依赖 MQ 不重复投递。
- 重复请求应该返回相同结果，而不是直接报错。

---

## 10. 总结

接口幂等常见实现方式有唯一索引、Token、Redis `SETNX`、状态机、乐观锁、去重表和 MQ 消息去重。

创建类接口可以使用唯一索引或 Token 防重复提交；高并发接口可以使用 Redis `SETNX` 做请求去重；订单、支付、退款这类有状态流转的业务，推荐使用状态机控制幂等；更新类接口可以使用乐观锁；支付回调和 MQ 消费这种重要链路，通常使用去重表或唯一索引记录处理状态。

实际项目中不会只依赖一种方式，通常会结合 **业务唯一键 + 状态机 + Redis/数据库去重** 来保证接口幂等。
