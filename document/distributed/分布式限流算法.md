# 分布式限流算法总结

分布式限流用于在多实例环境下控制请求速率，防止流量过大导致系统不可用。常见算法有：**固定窗口、滑动窗口、滑动日志、漏桶、令牌桶、并发数限流**。

---

## 1. 固定窗口计数器

### 实现原理

将时间划分为固定窗口，例如每分钟最多允许 100 次请求。

Redis 中通常使用 `String` 计数：

```bash
INCR rate_limit:api:202604251200
EXPIRE rate_limit:api:202604251200 60
```

每次请求计数加一，超过阈值则拒绝。

### 优势

- 实现简单。
- 性能高。
- Redis 计数器即可实现。

### 劣势

- 存在窗口边界问题。
- 限流不够平滑。

---

## 2. 滑动窗口计数器

### 实现原理

将一个大窗口拆成多个小窗口，例如将 1 分钟拆成 6 个 10 秒窗口。

每次请求统计最近 1 分钟内所有小窗口的总请求数，超过阈值则拒绝。

Redis 中可使用 `Hash` 或多个 `String` 保存每个小窗口的计数。

### 优势

- 比固定窗口更平滑。
- 能缓解窗口边界问题。
- 性能较好。

### 劣势

- 实现比固定窗口复杂。
- 小窗口越多，统计成本越高。
- 属于近似限流，不是完全精确。

---

## 3. 滑动日志算法

### 实现原理

记录每一次请求的时间戳，只统计当前时间窗口内的请求数量。

Redis 中通常使用 `ZSet`：

```text
score  = 请求时间戳
member = 请求唯一标识
```

请求流程：

1. 删除窗口外的旧请求。
2. 统计当前窗口内请求数。
3. 未超过阈值则写入当前请求并放行。
4. 超过阈值则拒绝。

### 优势

- 限流精确。
- 不存在窗口边界问题。

### 劣势

- 每个请求都要存储记录。
- 内存占用较高。
- 高并发下性能压力较大。

---

## 4. 漏桶算法

### 实现原理

请求先进入桶中，系统按照固定速率从桶中处理请求。

```text
请求进入桶 -> 按固定速率流出
```

如果桶满了，新请求直接拒绝。

Redis 中可用 `Hash` 保存桶状态：

```text
water：当前桶中请求数
last_leak_time：上次漏水时间
```

### 优势

- 流量输出平滑。
- 可以保护下游系统。
- 适合固定速率处理场景。

### 劣势

- 不适合突发流量。
- 即使系统空闲，也只能按固定速率处理。
- 实现相对复杂。

---

## 5. 令牌桶算法

### 实现原理

系统按照固定速率生成令牌，请求必须获取令牌后才能执行。

```text
生成令牌 -> 放入桶中 -> 请求获取令牌
```

如果桶中有令牌，请求放行；如果没有令牌，请求拒绝或等待。

Redis 中可用 `Hash` 保存状态：

```text
tokens：当前令牌数
last_refill_time：上次生成令牌时间
```

### 优势

- 支持一定突发流量。
- 可以控制平均访问速率。
- 实际项目中使用较多。

### 劣势

- 实现比计数器复杂。
- 需要维护令牌数和生成时间。
- 分布式场景下需要保证原子性。

---

## 6. 并发数限流

### 实现原理

限制同一时刻正在执行的请求数量，而不是限制单位时间请求次数。

例如接口最多同时处理 100 个请求：

```text
请求开始：计数 +1
请求结束：计数 -1
```

Redis 中可以使用 `String` 计数器，或用 `ZSet` 记录正在执行的请求并设置超时兜底。

### 优势

- 能直接保护线程池、连接池、下游服务。
- 适合慢接口和资源型接口。

### 劣势

- 请求结束时必须释放计数。
- 服务异常可能导致计数不准确。
- 需要超时兜底机制。

---

## 7. 算法对比

| 算法 | 核心思想 | 常用数据结构 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|---|---|
| 固定窗口 | 固定时间内计数 | Redis String | 简单、高性能 | 窗口边界问题 | 简单接口限流 |
| 滑动窗口 | 多个小窗口统计 | Redis Hash/String | 更平滑 | 近似统计 | 通用接口限流 |
| 滑动日志 | 记录每次请求时间 | Redis ZSet | 精确 | 内存成本高 | 精确限流 |
| 漏桶 | 固定速率处理请求 | Redis Hash | 流量平滑 | 不支持突发 | 保护下游系统 |
| 令牌桶 | 固定速率生成令牌 | Redis Hash | 支持突发 | 实现较复杂 | 网关、接口限流 |
| 并发数限流 | 限制同时执行数量 | Redis String/ZSet | 保护资源 | 需释放计数 | 慢接口、资源保护 |

---

## 8. 分布式限流注意点

- Redis 多命令操作需要使用 **Lua 脚本** 保证原子性。
- 限流 Key 要按业务维度设计，例如用户、接口、IP、租户等。
- 高并发热点接口要注意 Redis 热 Key 问题。
- 超过限流阈值后，需要明确拒绝、降级、排队或异步处理策略。
- 常见返回状态码为 `429 Too Many Requests`。

---

## 9. 总结

分布式限流常见算法包括固定窗口、滑动窗口、滑动日志、漏桶和令牌桶。

固定窗口实现最简单，但存在窗口边界问题；滑动窗口通过拆分小窗口缓解边界问题；滑动日志最精确，但存储和性能成本较高；漏桶可以让流量平滑输出，适合保护下游系统；令牌桶既能控制平均速率，又能支持一定突发流量，因此实际项目中使用较多。

在分布式场景下，通常使用 **Redis + Lua 脚本** 实现限流，保证计数、判断、过期、扣减等操作的原子性。
