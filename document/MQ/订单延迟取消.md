# 延迟取消订单总结

延迟取消订单是指：**用户创建订单后，如果在规定时间内未支付，系统自动取消订单并释放库存**。

常见场景：

```text
用户下单
  ↓
锁定库存
  ↓
30 分钟内未支付
  ↓
自动取消订单
  ↓
释放库存
```

---

## 1. 为什么需要延迟取消订单

如果用户下单后一直不支付，订单会长期占用库存。

可能导致：

- 库存被无效订单占用。
- 其他用户无法购买。
- 数据状态长期不一致。
- 人工清理成本高。

所以需要定时或延迟机制自动关闭超时未支付订单。

---

## 2. 常见实现方案

| 方案 | 核心原理 | 推荐程度 |
|---|---|---|
| 定时任务扫描 | 定时查询超时订单并取消 | 简单场景可用 |
| MQ 延迟消息 | 下单后发送延迟消息，到期后检查并取消 | 推荐 |
| Redis 过期监听 | 利用 Redis Key 过期事件触发取消 | 不太推荐 |
| 时间轮 | 将订单放入时间轮，到期触发任务 | 高性能场景可用 |
| DelayQueue | JVM 内存延迟队列 | 单机场景可用 |

---

## 3. 定时任务扫描

### 实现原理

通过定时任务周期性扫描数据库中超时未支付的订单。

例如每分钟执行一次：

```sql
SELECT *
FROM t_order
WHERE status = 'WAIT_PAY'
AND create_time < NOW() - INTERVAL 30 MINUTE;
```

查到超时订单后执行取消：

```text
更新订单状态为已取消
释放库存
记录操作日志
```

### 优势

- 实现简单。
- 不依赖 MQ。
- 容易理解和维护。

### 劣势

- 实时性较差。
- 扫描数据库有压力。
- 数据量大时效率低。
- 任务执行间隔不好控制。

### 适用场景

- 订单量不大。
- 对取消实时性要求不高。
- 系统早期简单实现。

---

## 4. MQ 延迟消息

### 实现原理

用户下单成功后，发送一条延迟消息。

```text
创建订单
  ↓
锁定库存
  ↓
发送 30 分钟延迟消息
  ↓
30 分钟后消费者收到消息
  ↓
查询订单状态
  ↓
如果仍是待支付，则取消订单并释放库存
```

注意：

```text
收到延迟消息后，不能直接取消订单，必须先查订单当前状态。
```

因为用户可能已经支付成功。

### 伪代码

```java
public void createOrder(Order order) {
    // 1. 创建订单，状态为待支付
    orderMapper.insert(order);

    // 2. 锁定库存
    stockService.lockStock(order.getSkuId(), order.getCount());

    // 3. 发送延迟消息
    delayMessageProducer.send(order.getOrderNo(), 30, TimeUnit.MINUTES);
}
```

消费延迟消息：

```java
public void consumeDelayMessage(String orderNo) {
    Order order = orderMapper.selectByOrderNo(orderNo);

    if (order == null) {
        return;
    }

    if ("WAIT_PAY".equals(order.getStatus())) {
        cancelOrder(orderNo);
    }
}
```

取消订单：

```java
public void cancelOrder(String orderNo) {
    // 只有待支付订单才能取消，保证幂等
    int rows = orderMapper.updateStatus(
        orderNo,
        "WAIT_PAY",
        "CANCELLED"
    );

    if (rows > 0) {
        stockService.releaseStock(orderNo);
    }
}
```

### 优势

- 实时性较好。
- 不需要频繁扫描数据库。
- 适合高并发订单场景。
- 可以削峰解耦。
- RocketMQ 原生支持延迟消息。

### 劣势

- 依赖 MQ 可用性。
- 消息可能重复消费，需要保证幂等。
- 消息可能丢失，需要可靠投递。
- 需要处理支付和取消并发问题。

### 适用场景

- 电商订单。
- 支付超时取消。
- 库存锁定释放。
- 优惠券超时回滚。

## 5. Redis 过期监听

### 实现原理

下单后写入一个 Redis Key，并设置过期时间。

```bash
SET order:timeout:1001 1001 EX 1800
```

当 Key 过期后，通过 Redis Key 过期事件监听到期订单，再执行取消逻辑。

### 优势

- 实现相对简单。
- 不需要 MQ。
- 到期触发比较直观。

### 劣势

- Redis 过期事件不保证强实时。
- Redis 过期监听可能丢事件。
- Redis 重启或配置不当会影响可靠性。
- 不适合核心订单取消链路。

### 适用场景

- 非核心业务。
- 临时过期提醒。
- 对可靠性要求不高的场景。

---

## 6. 时间轮

### 实现原理

时间轮是一种高性能延迟任务调度结构。

可以理解为一个环形数组，每个槽位代表一个时间刻度。

```text
slot0 -> slot1 -> slot2 -> ... -> slotN
```

下单后，将订单取消任务放入未来某个槽位，到时间后执行取消逻辑。

### 优势

- 性能高。
- 适合大量延迟任务。
- 时间复杂度低。
- Netty、Kafka 等系统中都有类似思想。

### 劣势

- 实现复杂。
- 需要处理服务重启后的任务恢复。
- 单纯内存时间轮不可靠，需要持久化配合。

### 适用场景

- 大量延迟任务。
- 高性能调度系统。
- 自研任务调度平台。

---

## 7. DelayQueue

### 实现原理

JDK 提供的 `DelayQueue` 可以实现 JVM 内存级延迟任务。

订单对象实现 `Delayed` 接口，到期后才能从队列中取出。

### 优势

- 实现简单。
- 不依赖外部组件。
- 适合单机延迟任务。

### 劣势

- 数据在内存中，服务重启会丢失。
- 不适合分布式环境。
- 不适合核心订单业务。

### 适用场景

- 单机应用。
- 临时延迟任务。
- 非核心业务。

## 8. 支付和取消并发问题

延迟取消订单必须处理支付和取消并发。

可能出现：

```text
延迟消息准备取消订单
同时用户支付成功
```

解决方式：

```text
使用状态机 + 条件更新
```

取消订单时：

```sql
UPDATE t_order
SET status = 'CANCELLED'
WHERE order_no = ?
AND status = 'WAIT_PAY';
```

支付成功时：

```sql
UPDATE t_order
SET status = 'PAID'
WHERE order_no = ?
AND status = 'WAIT_PAY';
```

谁先更新成功，谁就改变订单状态。  
后执行的一方因为状态已变化，更新失败。

这样可以保证：

```text
订单只能从 WAIT_PAY 变成 PAID 或 CANCELLED 中的一种状态
```

---

## 9. 幂等处理

延迟消息可能重复消费，所以取消订单必须幂等。

核心做法：

```text
只有 WAIT_PAY 状态的订单才能取消
```

SQL：

```sql
UPDATE t_order
SET status = 'CANCELLED'
WHERE order_no = ?
AND status = 'WAIT_PAY';
```

如果影响行数为 `1`：

```text
取消成功，释放库存
```

如果影响行数为 `0`：

```text
订单已支付或已取消，直接忽略
```

---

## 10. 库存释放问题

如果下单时锁定库存，取消订单时需要释放库存。

常见流程：

```text
创建订单
  ↓
冻结库存
  ↓
支付成功
  ↓
扣减冻结库存

创建订单
  ↓
冻结库存
  ↓
超时未支付
  ↓
释放冻结库存
```

库存表可以设计：

```text
total_stock：总库存
available_stock：可用库存
locked_stock：锁定库存
```

下单锁库存：

```sql
UPDATE stock
SET available_stock = available_stock - ?,
    locked_stock = locked_stock + ?
WHERE sku_id = ?
AND available_stock >= ?;
```

取消释放库存：

```sql
UPDATE stock
SET available_stock = available_stock + ?,
    locked_stock = locked_stock - ?
WHERE sku_id = ?
AND locked_stock >= ?;
```

---

## 11. 推荐方案

实际项目中推荐：

```text
MQ 延迟消息 + 订单状态机 + 幂等处理 + 库存冻结/释放
```

流程：

```text
1. 用户下单，创建 WAIT_PAY 订单。
2. 冻结库存。
3. 发送延迟取消订单消息。
4. 用户支付成功，将订单改为 PAID。
5. 延迟消息到期后查询订单状态。
6. 如果仍是 WAIT_PAY，则取消订单并释放库存。
7. 如果已经 PAID，则忽略消息。
```

---

## 12. 总结

延迟取消订单常见实现方式有定时任务扫描、MQ 延迟消息、Redis 过期监听、时间轮和 DelayQueue。

定时任务实现简单，但实时性差，数据量大时数据库压力较高；Redis 过期监听不保证可靠性，不适合核心业务；DelayQueue 只适合单机场景；时间轮性能高，但实现复杂。

实际项目中更推荐使用 MQ 延迟消息。下单成功后发送一条延迟消息，消息到期后消费者查询订单状态，如果订单仍是待支付，则取消订单并释放库存；如果订单已经支付，则直接忽略。

实现时要重点处理支付和取消并发问题，通常通过订单状态机和条件更新保证幂等，例如只允许 `WAIT_PAY` 状态更新为 `CANCELLED` 或 `PAID`。

一句话总结：

```text
延迟取消订单 = 延迟消息触发 + 查询订单状态 + 条件更新取消 + 幂等释放库存。
```
