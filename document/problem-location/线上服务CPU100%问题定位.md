# 线上服务 CPU 负载 100% 怎么定位

线上服务 CPU 100%，核心思路是：

```text
先定位进程
再定位线程
再定位代码
最后判断原因并处理
```

---

## 1. 定位高 CPU 进程

先看哪一个进程占用 CPU 高。

```bash
top
```

关注：

```text
PID
CPU%
MEM%
load average
```

如果是 Java 服务，找到对应进程：

```bash
ps -ef | grep java
```

---

## 2. 定位高 CPU 线程

假设 Java 进程 PID 是：

```text
12345
```

查看该进程下线程 CPU 使用情况：

```bash
top -Hp 12345
```

找到 CPU 占用最高的线程 ID，例如：

```text
线程 ID = 12367
```

---

## 3. 线程 ID 转十六进制

`jstack` 中线程 ID 是十六进制，需要转换。

```bash
printf "%x\n" 12367
```

得到：

```text
304f
```

---

## 4. 导出线程栈

```bash
jstack 12345 > jstack.log
```

然后搜索线程 ID：

```bash
grep -n "304f" jstack.log
```

或者：

```bash
less jstack.log
```

搜索：

```text
nid=0x304f
```

---

## 5. 分析线程栈

重点看该线程正在执行什么代码。

常见情况：

### 1. 死循环

线程栈一直停在某个业务方法中。

```text
while(true)
递归调用
循环条件错误
```

处理：

```text
修复循环逻辑
增加退出条件
限制循环次数
```

---

### 2. 大量计算

例如：

```text
复杂规则计算
大集合遍历
JSON 序列化
正则匹配
加解密
报表统计
```

处理：

```text
优化算法
减少数据量
异步处理
缓存结果
```

---

### 3. 频繁 GC

如果 CPU 高同时接口变慢，需要看 GC。

```bash
jstat -gcutil 12345 1000
```

重点看：

```text
YGC 是否频繁
FGC 是否频繁
Old 区是否持续上涨
```

如果 Full GC 频繁，继续导出堆：

```bash
jmap -dump:format=b,file=heap.hprof 12345
```

用 MAT / VisualVM 分析大对象和内存泄漏。

---

### 4. 锁竞争严重

线程栈中大量线程处于：

```text
BLOCKED
WAITING
TIMED_WAITING
```

常见原因：

```text
synchronized 锁粒度太大
ReentrantLock 等待
分布式锁等待
线程池资源竞争
```

处理：

```text
缩小锁粒度
减少锁内逻辑
避免锁内调用慢接口
使用无锁或分段锁优化
```

---

### 5. 线程池打满

查看是否大量线程卡在：

```text
业务线程池
Tomcat 线程池
Dubbo 线程池
异步线程池
```

常见原因：

```text
下游接口慢
数据库慢
Redis 慢
线程池队列堆积
超时时间过长
```

处理：

```text
增加超时控制
隔离线程池
熔断降级
优化下游接口
调整线程池参数
```

---

## 6. 使用 Arthas 快速定位

线上推荐用 Arthas。

查看高 CPU 线程：

```bash
thread -n 10
```

查看指定线程栈：

```bash
thread 线程ID
```

查看方法耗时：

```bash
trace com.demo.UserService queryUser
```

查看方法调用参数和返回值：

```bash
watch com.demo.UserService queryUser "{params, returnObj}" -x 3
```

查看热点方法：

```bash
profiler start
profiler stop --format html
```

---

## 7. 常见原因总结

| 原因 | 表现 |
|---|---|
| 死循环 | 单个线程 CPU 长时间很高 |
| 频繁 Full GC | CPU 高，接口卡顿，内存回收频繁 |
| 大量计算 | 某些业务方法 CPU 高 |
| 正则回溯 | CPU 飙高，线程卡在正则方法 |
| JSON 序列化大对象 | CPU 高，接口响应慢 |
| 日志打印过多 | CPU 和 IO 都高 |
| 锁竞争 | 大量线程 BLOCKED |
| 线程池打满 | 请求排队，RT 升高 |
| 流量突增 | QPS 上升，整体 CPU 高 |
| 下游超时重试 | 重试放大流量，CPU 升高 |

---

## 8. 临时止血方案

如果已经影响线上服务，可以先止血：

```text
扩容实例
限流
降级非核心接口
关闭异常任务
回滚最近版本
重启异常节点
切走流量
```

注意：

```text
重启前尽量先保留现场：
jstack
jmap
GC 日志
应用日志
监控截图
```

---

## 9. 排查流程总结

```text
1. top 找到高 CPU 进程。
2. top -Hp 找到高 CPU 线程。
3. printf 转换线程 ID 为十六进制。
4. jstack 找到线程执行栈。
5. 判断是死循环、GC、锁竞争、线程池、慢调用还是大计算。
6. 用 Arthas 进一步 trace / watch / profiler。
7. 先止血，再修复根因。
```

---

## 10. 总结

线上服务 CPU 100%，我会先用 `top` 找到高 CPU 的 Java 进程，再用 `top -Hp pid` 找到具体高 CPU 线程，然后把线程 ID 转成十六进制，通过 `jstack` 定位线程栈，查看线程正在执行哪段代码。

如果线程一直停在某个业务方法，可能是死循环、大量计算、正则回溯或大对象序列化；如果伴随频繁 Full GC，需要用 `jstat`、`jmap` 分析内存；如果大量线程 BLOCKED，要排查锁竞争；如果线程池打满，要排查下游慢调用、超时和重试。

一句话总结：

```text
CPU 100% 排查 = top 找进程 + top -Hp 找线程 + jstack 找代码 + jstat 看 GC + Arthas 深入定位。
```
