# 接口慢怎么排查

## 一、先明确：接口慢是“真慢”还是“偶发慢”

先看现象，明确接口慢的范围、时间和影响面。

| 维度 | 要确认的问题 |
|---|---|
| 慢的范围 | 单个接口慢，还是多个接口都慢？ |
| 慢的时间 | 一直慢，还是某个时间段慢？ |
| 慢的比例 | 所有请求慢，还是少量请求慢？ |
| 慢的环境 | 线上慢，本地/测试环境是否慢？ |
| 慢的指标 | 平均耗时、P95、P99、超时率是多少？ |

面试可以这样说：

> 我会先通过监控和日志确认接口慢的范围，是单接口问题还是系统整体问题，是持续慢还是偶发慢，然后再沿着调用链逐层排查。

---

## 二、看接口调用链耗时

接口一般会经过这些环节：

```text
客户端
  ↓
网关 / Nginx
  ↓
应用服务
  ↓
数据库 / Redis / MQ / 第三方接口
```

排查时不要一上来就看代码，而是先确认慢在哪一段。

---

## 三、排查方向一：网关 / Nginx 是否慢

如果请求在应用服务之前就慢，可能是网关问题。

重点看：

| 排查点 | 可能原因 |
|---|---|
| Nginx access log | 请求耗时是否已经很高 |
| 网关限流 | 是否被限流、排队 |
| 网关线程池 | 是否线程耗尽 |
| 网络连接 | 是否存在连接超时、重试 |
| SSL / DNS | 是否有解析或握手耗时 |

如果 Nginx 日志里 `upstream_response_time` 很长，一般说明后端应用慢。

---

## 四、排查方向二：应用服务是否慢

这是 Java 后端最常见的排查重点。

### 1. 看应用日志

可以在关键节点打耗时日志：

```java
long start = System.currentTimeMillis();

queryUser();

log.info("queryUser cost: {} ms", System.currentTimeMillis() - start);
```

更规范一点，可以用 AOP 统一记录接口耗时：

```java
@Around("@annotation(org.springframework.web.bind.annotation.RequestMapping)")
public Object logCost(ProceedingJoinPoint joinPoint) throws Throwable {
    long start = System.currentTimeMillis();
    try {
        return joinPoint.proceed();
    } finally {
        log.info("{} cost {} ms",
                joinPoint.getSignature(),
                System.currentTimeMillis() - start);
    }
}
```

排查重点：

```text
Controller 耗时
Service 耗时
DAO 耗时
RPC 调用耗时
Redis 调用耗时
第三方接口耗时
```

### 2. 看线程状态

接口慢时，先看线程是不是被阻塞了。

常用命令：

```bash
jstack <pid> > jstack.log
```

重点看线程状态：

| 状态 | 含义 |
|---|---|
| RUNNABLE | 正在运行，可能 CPU 高 |
| BLOCKED | 等锁 |
| WAITING | 等待通知 |
| TIMED_WAITING | sleep、join、网络等待等 |

如果大量线程卡在：

```text
java.net.SocketInputStream.socketRead0
```

说明可能在等远程接口或数据库响应。

如果大量线程卡在：

```text
BLOCKED
```

说明可能存在锁竞争。

### 3. 看 CPU 是否打满

如果 CPU 很高，可能是：

| 原因 | 举例 |
|---|---|
| 死循环 | while 条件异常 |
| 大量计算 | 加密、压缩、复杂规则计算 |
| 频繁 GC | 对象创建过多 |
| 线程上下文切换 | 线程过多 |

排查命令：

```bash
top
top -Hp <pid>
printf "%x\n" <线程id>
jstack <pid> | grep <16进制线程id>
```

这样可以定位哪个 Java 线程占 CPU 高。

### 4. 看 GC 是否频繁

接口慢可能不是代码逻辑慢，而是频繁 GC 导致 Stop The World。

常用命令：

```bash
jstat -gcutil <pid> 1000
```

或者查看 GC 日志。

重点关注：

| 指标 | 问题 |
|---|---|
| YGC 很频繁 | Young GC 频繁 |
| FGC 次数增加 | Full GC 频繁 |
| Old 区持续升高 | 可能内存泄漏 |
| GC 耗时长 | 会导致接口响应慢 |

常见原因：

```text
一次性查询大量数据
大对象频繁创建
缓存无限增长
集合没有及时释放
JSON 序列化对象过大
```

## 五、排查方向三：数据库是否慢

数据库是接口慢的高频原因。

### 1. 看慢 SQL

MySQL 可以开启慢查询日志：

```sql
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'long_query_time';
```

查看是否有慢 SQL。

### 2. 使用 EXPLAIN 分析 SQL

例如：

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1001;
```

重点看：

| 字段 | 说明 |
|---|---|
| type | 访问类型，ALL 表示全表扫描 |
| key | 是否命中索引 |
| rows | 扫描行数 |
| Extra | 是否 Using filesort / Using temporary |

如果出现：

```text
type = ALL
key = null
Using filesort
Using temporary
```

通常说明 SQL 有优化空间。

### 3. 常见 SQL 慢原因

| 原因 | 示例 |
|---|---|
| 没有索引 | where 字段没建索引 |
| 索引失效 | 对索引列使用函数 |
| 查询数据量大 | 一次查几十万条 |
| 深分页 | limit 100000, 20 |
| join 过多 | 多表关联复杂 |
| 排序慢 | order by 字段无索引 |
| 锁等待 | 行锁、表锁竞争 |
| 事务太长 | 长事务占用锁 |

### 4. 看数据库连接池

接口慢也可能是拿不到数据库连接。

比如 HikariCP 连接池耗尽：

```text
Connection is not available, request timed out
```

排查点：

| 参数 | 含义 |
|---|---|
| maximumPoolSize | 最大连接数 |
| connectionTimeout | 获取连接超时时间 |
| active connections | 活跃连接数 |
| idle connections | 空闲连接数 |

如果连接池满了，要看是不是：

```text
SQL 太慢
事务没提交
连接泄漏
并发量突然升高
连接池配置过小
```

## 六、排查方向四：Redis 是否慢

如果接口依赖 Redis，也要看 Redis 耗时。

常见问题：

| 问题 | 说明 |
|---|---|
| 大 key | value 很大，网络传输慢 |
| 热 key | 某个 key 访问量过高 |
| 慢命令 | keys、hgetall、大范围 zrange |
| 网络抖动 | 应用到 Redis 延迟高 |
| 连接池不足 | Jedis/Lettuce 连接不够 |
| 缓存穿透 | 大量请求打到数据库 |
| 缓存击穿 | 热点 key 失效 |
| 缓存雪崩 | 大量 key 同时失效 |

可以使用：

```bash
SLOWLOG GET
```

查看 Redis 慢命令。

---

## 七、排查方向五：第三方接口 / RPC 是否慢

很多接口慢是因为调用外部系统慢。

比如：

```text
支付接口
风控接口
短信接口
用户中心
订单中心
库存服务
```

排查点：

| 排查点 | 说明 |
|---|---|
| RPC 耗时 | 单次调用是否变慢 |
| 超时时间 | 是否设置过长 |
| 重试机制 | 是否失败后多次重试 |
| 熔断降级 | 是否没有降级 |
| 线程池隔离 | 是否被慢调用拖垮 |
| 下游服务监控 | 下游是否异常 |

一个典型问题：

```text
接口本身只需要 100ms，
但调用第三方设置了 5 秒超时，
第三方偶发慢时，接口就被拖到 5 秒。
```

优化方式：

```text
设置合理超时
失败快速返回
增加熔断降级
异步化非核心流程
使用本地缓存
```

## 八、排查方向六：锁竞争 / 并发问题

如果接口里用了 `synchronized`、`ReentrantLock`、分布式锁，要重点排查锁等待。

常见问题：

```java
synchronized (this) {
    // 查询数据库
    // 调用远程接口
}
```

这种写法很危险，因为锁里面做了慢操作，会导致大量请求排队。

正确思路：

```text
缩小锁范围
锁内只做内存操作
不要在锁内调用数据库或远程服务
分布式锁设置过期时间
避免锁粒度过粗
```

## 九、排查方向七：代码逻辑问题

代码层面常见导致接口慢的问题：

| 问题 | 示例 |
|---|---|
| 循环查库 | for 循环里调用 mapper |
| N+1 查询 | 查列表后逐条查详情 |
| 大对象序列化 | 返回 JSON 太大 |
| 复杂嵌套循环 | O(n²)、O(n³) |
| 同步处理太多逻辑 | 发短信、写日志、发 MQ 全同步 |
| 重复计算 | 没有缓存中间结果 |
| 日志过多 | 大量 info 日志影响性能 |

典型问题：

```java
for (User user : users) {
    Order order = orderMapper.selectByUserId(user.getId());
}
```

这就是 N+1 查询。

优化成批量查询：

```java
List<Long> userIds = users.stream()
        .map(User::getId)
        .collect(Collectors.toList());

List<Order> orders = orderMapper.selectByUserIds(userIds);
```

## 十、常见优化方案

### 1. SQL 优化

```text
加合适索引
避免全表扫描
避免 select *
优化 order by / group by
分页优化
拆分复杂 SQL
控制返回数据量
```

### 2. 缓存优化

```text
热点数据放 Redis
本地缓存 Caffeine
设置合理过期时间
防止缓存穿透、击穿、雪崩
```

### 3. 异步化

非核心流程可以异步：

```text
发送短信
发送邮件
记录操作日志
写埋点数据
发送 MQ
生成报表
```

比如接口返回前只完成核心链路，其他逻辑交给 MQ 或线程池处理。

### 4. 并行化

多个互不依赖的查询可以并行执行。

```java
CompletableFuture<User> userFuture =
        CompletableFuture.supplyAsync(() -> queryUser(userId), executor);

CompletableFuture<List<Order>> orderFuture =
        CompletableFuture.supplyAsync(() -> queryOrders(userId), executor);

CompletableFuture.allOf(userFuture, orderFuture).join();
```

不过要注意：

```text
线程池隔离
超时时间
异常处理
不要共用业务主线程池
```

### 5. 限流 / 降级 / 熔断

当接口压力过大时，需要保护系统：

```text
限流：控制请求量
熔断：下游异常时快速失败
降级：返回默认值或兜底数据
隔离：不同业务使用不同线程池
```

## 十二、总结

可以这样回答：

> 接口慢我一般不会直接看代码，而是先通过监控、日志和链路追踪确认慢的范围和慢的阶段。
>
> 首先看是单接口慢还是整体服务慢，是持续慢还是偶发慢。然后通过网关日志、应用日志、APM 链路追踪定位耗时主要发生在哪一层，比如应用逻辑、数据库、Redis、RPC 调用还是第三方接口。
>
> 如果是应用层慢，我会看线程堆栈、CPU、GC、线程池、锁竞争等问题；如果是数据库慢，我会看慢 SQL、执行计划、索引、锁等待和连接池；如果是缓存慢，会排查大 key、热 key、慢命令和连接池；如果是下游服务慢，会看超时、重试、熔断降级是否合理。
>
> 定位到具体原因后，再针对性优化，比如 SQL 加索引、批量查询代替循环查库、增加缓存、异步化非核心流程、并行化独立调用、调整线程池和连接池参数，或者增加限流、熔断、降级来保护系统。

---

## 十三、案例补充

面试时最好加一个实际案例，会更有说服力：

> 比如之前遇到过一个订单列表接口慢的问题，通过链路追踪发现主要耗时在数据库。继续看慢 SQL，发现订单表按 `user_id` 查询没有合适索引，并且接口里还存在循环查询订单明细的 N+1 问题。
>
> 后来给 `user_id`、`create_time` 建了联合索引，同时把循环查询改成批量查询，接口耗时从 2 秒左右降到了 200ms 以内。

---

## 十四、一句话总结

> 接口慢排查核心就是：先看链路定位耗时点，再从应用、数据库、缓存、RPC、系统资源几个方向逐层深入，最后针对瓶颈做优化。
