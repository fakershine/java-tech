# 分库分表总结

分库分表用于解决单库、单表在数据量和并发量过大时带来的性能瓶颈，核心目标是提升数据库的 **存储能力、写入能力和查询性能**。

---

## 1. 为什么要分库分表

### 常见问题

- 单表数据量过大，查询和写入变慢。
- 单库连接数、CPU、IO 压力过高。
- 索引膨胀，维护成本变高。
- 大表 DDL 变更困难。
- 单库容量达到瓶颈。
- 高并发写入时数据库成为系统瓶颈。

### 常见场景

- 订单表。
- 用户表。
- 支付流水表。
- 日志表。
- 消息记录表。
- 交易明细表。

---

## 2. 垂直拆分

### 实现原理

按照业务模块或字段维度进行拆分。

### 垂直分库

将不同业务的表拆到不同数据库中。

```text
用户库：user、user_address
订单库：order、order_item
支付库：payment、refund
```

### 垂直分表

将一张大表中的冷热字段、宽字段拆开。

```text
user_base：id、name、phone
user_extend：user_id、avatar、profile、remark
```

### 优势

- 业务边界清晰。
- 降低单库压力。
- 减少单表字段数量。
- 便于按业务独立扩展。

### 劣势

- 无法解决单表数据量持续增长问题。
- 跨库 Join 变复杂。
- 跨库事务处理复杂。

---

## 3. 水平拆分

### 实现原理

将同一张表的数据按照某种规则拆分到多个库或多张表中。

### 水平分表

同一个库中拆成多张表。

```text
order_0
order_1
order_2
order_3
```

### 水平分库

同一业务数据拆到多个数据库中。

```text
order_db_0.order
order_db_1.order
order_db_2.order
order_db_3.order
```

### 水平分库分表

同时拆库和拆表。

```text
order_db_0.order_0
order_db_0.order_1
order_db_1.order_0
order_db_1.order_1
```

### 优势

- 解决单表数据量过大问题。
- 解决单库写入压力问题。
- 支持数据和流量水平扩展。
- 适合高并发、大数据量业务。

### 劣势

- 路由规则复杂。
- 跨库查询、分页、排序复杂。
- 跨库事务处理困难。
- 扩容迁移成本较高。

---

## 4. 常见分片策略

### 1. Hash 取模

根据分片键取模决定数据落在哪个库表。

```text
user_id % 4 = 表编号
```

示例：

```text
user_id = 1001
1001 % 4 = 1
数据落到 order_1
```

### 优势

- 数据分布相对均匀。
- 实现简单。
- 适合按用户 ID、订单 ID 查询。

### 劣势

- 扩容困难。
- 扩容后取模规则变化，数据迁移成本高。
- 不适合范围查询。

---

### 2. Range 范围分片

按照时间、ID 范围拆分。

```text
order_202401
order_202402
order_202403
```

或者：

```text
id 1 ~ 1000      -> order_0
id 1001 ~ 2000   -> order_1
id 2001 ~ 3000   -> order_2
```

### 优势

- 适合范围查询。
- 便于归档历史数据。
- 按时间拆分时查询逻辑直观。

### 劣势

- 容易产生热点。
- 最新数据所在分片压力可能过大。
- 数据分布可能不均匀。

---

### 3. 一致性 Hash

通过一致性 Hash 环决定数据分布。

### 优势

- 扩容时数据迁移量相对较少。
- 适合节点动态扩缩容。
- 比普通取模更灵活。

### 劣势

- 实现复杂。
- 数据分布可能不均，需要虚拟节点。
- 业务系统中使用成本较高。

---

### 4. 按业务字段分片

根据业务维度分片，例如：

```text
tenant_id
user_id
merchant_id
region_id
```

### 优势

- 符合业务查询习惯。
- 可以减少跨库查询。
- 适合多租户、商户系统。

### 劣势

- 分片键选择不合理会导致热点。
- 后续查询必须尽量带上分片键。
- 跨分片统计会变复杂。

---

## 5. 分片键如何选择

分片键非常关键，通常选择查询频率高、区分度高、数据分布均匀的字段。

### 常见分片键

| 业务 | 常见分片键 |
|---|---|
| 用户表 | user_id |
| 订单表 | user_id / order_id |
| 支付流水 | user_id / order_id / trade_no |
| 商户数据 | merchant_id |
| 多租户系统 | tenant_id |

### 选择原则

- 查询时经常携带该字段。
- 数据分布尽量均匀。
- 避免热点数据集中到一个分片。
- 尽量减少跨库查询。
- 分片规则要长期稳定。

---

## 6. 分库分表带来的问题

### 1. 跨库 Join 问题

分库后，不同表可能在不同数据库中，无法直接 Join。

### 解决方案

- 在业务层组装数据。
- 适当冗余字段。
- 使用宽表。
- 使用 Elasticsearch 做复杂查询。
- 避免强依赖跨库 Join。

---

### 2. 跨库事务问题

一次业务操作可能涉及多个库，普通本地事务无法保证一致性。

### 解决方案

- 尽量避免跨库事务。
- 使用最终一致性。
- 使用 MQ 事务消息。
- 使用 TCC / Saga。
- 使用 Seata 等分布式事务框架。

---

### 3. 分布式 ID 问题

分库分表后，不能依赖单表自增 ID 作为全局主键。

### 解决方案

- Snowflake。
- 数据库号段模式。
- Redis 自增。
- Leaf / UidGenerator。

---

### 4. 跨库分页问题

分库后分页需要从多个分片查询数据，再在内存中排序和截取。

例如：

```sql
LIMIT 10000, 20
```

在分库场景下性能会很差。

### 解决方案

- 避免深分页。
- 使用游标分页。
- 使用 last_id 分页。
- 将查询条件带上分片键。
- 使用 Elasticsearch 承接复杂分页查询。

---

### 5. 跨库排序和聚合问题

例如：

```sql
ORDER BY create_time DESC
COUNT(*)
SUM(amount)
```

多个分片都要查询，再进行结果合并。

### 解决方案

- 业务层聚合。
- 离线数仓统计。
- 建立汇总表。
- 使用 Elasticsearch / ClickHouse 等查询系统。

---

### 6. 扩容迁移问题

如果使用简单取模：

```text
user_id % 4
```

扩容成：

```text
user_id % 8
```

大量数据需要重新迁移。

### 解决方案

- 初期预留足够分片数。
- 使用一致性 Hash。
- 使用逻辑分片 + 物理库映射。
- 通过双写、数据迁移、灰度切流完成扩容。

---

## 7. 常见中间件

| 中间件 | 说明 |
|---|---|
| ShardingSphere | Java 生态常用，支持分库分表、读写分离、分布式事务 |
| MyCat | 数据库代理层中间件 |
| TDDL | 阿里内部早期分库分表方案 |
| Vitess | 适合大规模 MySQL 分片场景 |
| PolarDB-X | 阿里云分布式数据库方案 |

---

## 8. 分库分表和读写分离的区别

| 对比项 | 分库分表 | 读写分离 |
|---|---|---|
| 解决问题 | 数据量大、写入压力大 | 读请求压力大 |
| 核心方式 | 数据拆分到多个库表 | 主库写，从库读 |
| 是否拆数据 | 是 | 否 |
| 主要提升 | 存储能力、写入能力 | 读取能力 |
| 常见问题 | 跨库查询、事务、扩容 | 主从延迟、读一致性 |

---

## 9. 实现注意点

- 不要过早分库分表，优先优化索引、SQL、缓存、读写分离。
- 分片键选择非常关键。
- 分库分表后尽量让查询带上分片键。
- 避免跨库 Join、跨库事务、深分页。
- 主键要使用全局唯一 ID。
- 需要提前设计扩容和数据迁移方案。
- 核心数据要做好对账和补偿。
- 复杂查询可以交给 Elasticsearch、ClickHouse 或数仓系统。

---

## 10. 总结

分库分表主要用于解决单库、单表数据量过大和并发压力过高的问题。

分库分表分为垂直拆分和水平拆分。垂直拆分是按照业务或字段拆分，适合业务解耦；水平拆分是按照分片键将同一张表的数据拆到多个库表中，适合解决大表和高并发写入问题。

常见分片策略有 Hash 取模、Range 范围分片、一致性 Hash 和按业务字段分片。分片键一般选择查询频率高、数据分布均匀、业务稳定的字段，例如 user_id、order_id、merchant_id。

分库分表会带来跨库 Join、跨库事务、分布式 ID、跨库分页、排序聚合和扩容迁移等问题。实际项目中，要尽量避免跨库操作，使用全局 ID、冗余字段、业务层聚合、MQ 最终一致性和数据迁移方案来解决。

一般建议：数据量和并发量没有达到瓶颈前，不要过早分库分表；真正需要时，优先选择合适的分片键和成熟中间件，例如 ShardingSphere。
