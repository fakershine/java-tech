# ShardingSphere 总结

Apache ShardingSphere 是一个分布式数据库中间件，核心作用是：**在不大幅改造业务代码的前提下，提供分库分表、读写分离、分布式事务、数据加密、弹性伸缩等能力**。官方定位是面向数据分片、扩缩容、加密等场景的分布式 SQL 事务与查询引擎。:contentReference[oaicite:0]{index=0}

---

## 1. ShardingSphere 核心能力

| 能力 | 说明 |
|---|---|
| 分库分表 | 按分片规则将数据路由到不同库表 |
| 读写分离 | 写请求走主库，读请求走从库 |
| 分布式事务 | 支持跨库事务处理 |
| 分布式治理 | 配置、元数据、规则统一管理 |
| 数据加密 | 对敏感字段透明加解密 |
| 影子库压测 | 线上流量压测隔离 |
| 弹性伸缩 | 支持数据迁移和扩容 |

---

## 2. 两种接入方式

ShardingSphere 主要有两个接入端：**ShardingSphere-JDBC** 和 **ShardingSphere-Proxy**，二者可以单独部署，也可以混合部署。:contentReference[oaicite:1]{index=1}

| 接入方式 | 说明 | 适用场景 |
|---|---|---|
| ShardingSphere-JDBC | Java JDBC 增强驱动，嵌入应用内部 | Java 项目，性能要求高 |
| ShardingSphere-Proxy | 独立代理服务，对外表现像数据库 | 多语言项目，统一数据库代理 |

---

## 3. ShardingSphere-JDBC

### 实现原理

ShardingSphere-JDBC 本质是增强版 JDBC Driver。

```text
应用程序
  ↓
ShardingSphere-JDBC
  ↓
SQL 解析、路由、改写、执行、归并
  ↓
真实数据库
```

### 优势

- 性能较好。
- 不需要单独部署代理服务。
- 适合 Java 项目。
- 和 Spring Boot、MyBatis 集成方便。

### 劣势

- 只适合 Java 生态。
- 每个应用都需要引入依赖和配置规则。
- 多语言系统无法统一接入。

---

## 4. ShardingSphere-Proxy

### 实现原理

ShardingSphere-Proxy 是独立部署的数据库代理服务。

```text
应用程序
  ↓
ShardingSphere-Proxy
  ↓
SQL 解析、路由、改写、执行、归并
  ↓
真实数据库
```

应用连接 Proxy 就像连接 MySQL 一样。

### 优势

- 对业务语言无侵入。
- 支持多语言系统。
- 配置集中管理。
- 适合统一数据库访问入口。

### 劣势

- 多一层网络转发。
- Proxy 本身需要高可用部署。
- 性能比 JDBC 嵌入式方式略有损耗。

## 5. 分库分表原理

### 核心思想

根据分片键，把数据分散到不同数据库或数据表。

例如按 `user_id` 分库分表：

```text
user_id % 2 = 0 -> ds0
user_id % 2 = 1 -> ds1

user_id % 4 = 0 -> user_0
user_id % 4 = 1 -> user_1
user_id % 4 = 2 -> user_2
user_id % 4 = 3 -> user_3
```

### 执行流程

```text
SQL 进入 ShardingSphere
  ↓
解析 SQL
  ↓
根据分片键计算目标库表
  ↓
改写 SQL
  ↓
发送到真实数据库执行
  ↓
结果归并
  ↓
返回应用
```

---

## 6. SQL 执行流程

ShardingSphere 执行 SQL 的核心流程：

```text
SQL 解析
  ↓
SQL 路由
  ↓
SQL 改写
  ↓
SQL 执行
  ↓
结果归并
```

| 阶段 | 说明 |
|---|---|
| SQL 解析 | 解析表名、字段、条件、排序等 |
| SQL 路由 | 判断 SQL 应该发到哪些库表 |
| SQL 改写 | 将逻辑表名改成真实表名 |
| SQL 执行 | 并发执行真实 SQL |
| 结果归并 | 对多库多表结果做合并、排序、分页 |

---

## 7. 分片策略

| 策略 | 说明 |
|---|---|
| 标准分片 | 单分片键，支持精确和范围分片 |
| 复合分片 | 多个分片键组合路由 |
| Hint 分片 | 不从 SQL 解析分片键，由代码指定路由 |
| 广播表 | 每个库都有一份相同数据 |
| 绑定表 | 分片规则一致的表，避免笛卡尔路由 |

---

## 8. 广播表

### 实现原理

广播表会在每个数据库中保存一份完整数据。

适合：

```text
字典表
配置表
地区表
状态表
```

示例：

```text
ds0.t_dict
ds1.t_dict
ds2.t_dict
```

### 优势

- 查询时本地库即可关联。
- 避免跨库 Join。
- 适合小表。

### 劣势

- 写入时需要同步到所有库。
- 不适合大表或频繁更新表。

---

## 9. 绑定表

### 实现原理

绑定表指分片规则一致的一组表。

例如：

```text
order 表按 user_id 分片
order_item 表也按 user_id 分片
```

这样查询订单和订单明细时，可以路由到同一个库表。

### 优势

- 避免跨库笛卡尔积查询。
- 提高 Join 查询效率。

### 适用场景

```text
订单表 + 订单明细表
用户表 + 用户扩展表
```

---

## 10. 读写分离

### 实现原理

```text
INSERT / UPDATE / DELETE -> 主库
SELECT -> 从库
```

整体流程：

```text
应用 SQL
  ↓
ShardingSphere 判断 SQL 类型
  ↓
写请求路由到主库
  ↓
读请求路由到从库
```

### 注意

读写分离要关注：

```text
主从延迟
强一致读
事务内读写一致
从库故障摘除
```

---

## 11. 分布式事务

ShardingSphere 支持分布式事务能力，常见包括：

```text
XA 事务
BASE 柔性事务
```

### XA 事务

特点：

```text
强一致
性能相对较低
适合一致性要求高的场景
```

### BASE 事务

特点：

```text
最终一致
性能较好
适合互联网业务
```

---

## 12. 数据加密

### 实现原理

对敏感字段透明加解密。

例如：

```text
phone -> 加密后存储到数据库
查询时自动解密返回业务
```

业务代码看到的是明文，数据库中存储的是密文。

适合：

```text
手机号
身份证号
银行卡号
邮箱
地址
```

## 13. 使用场景

适合使用 ShardingSphere 的场景：

```text
单表数据量过大
单库写入压力过高
需要水平分库分表
需要读写分离
需要透明数据加密
需要兼容 MySQL 生态
Java 项目希望低侵入分片
```

不适合：

```text
数据量不大
SQL 极其复杂
强依赖跨库 Join
频繁跨库事务
团队缺少分库分表经验
```

## 14. 常见问题

### 1. 分片键怎么选？

优先选择：

```text
查询频率高
区分度高
大多数 SQL 都会带上的字段
```

常见分片键：

```text
user_id
order_id
tenant_id
shop_id
```

---

### 2. 没有分片键会怎样？

如果 SQL 不带分片键，可能会出现：

```text
全库全表路由
```

问题：

```text
性能差
数据库压力大
结果归并成本高
```

---

### 3. 分页查询有什么问题？

跨库分页可能需要：

```text
每个分片查询大量数据
再统一排序归并
```

例如：

```sql
LIMIT 100000, 10
```

在分库分表下性能会更差。

优化方式：

```text
避免深分页
使用游标分页
按分片键查询
冷热数据分离
```

---

### 4. 跨库 Join 怎么办？

尽量避免跨库 Join。

常见方案：

```text
绑定表
广播表
业务层组装
数据冗余
宽表设计
ES 查询
```

---

## 15. 总结

ShardingSphere 是一个分布式数据库中间件，主要用于解决单库单表数据量过大、数据库读写压力高的问题。

它有两种常见接入方式：ShardingSphere-JDBC 和 ShardingSphere-Proxy。JDBC 方式嵌入 Java 应用内部，性能较好，适合 Java 项目；Proxy 方式独立部署，应用像连接数据库一样连接 Proxy，适合多语言系统和统一数据库代理场景。

ShardingSphere 执行 SQL 时，会经过 SQL 解析、路由、改写、执行和结果归并几个阶段。分库分表时，根据分片键和分片算法计算目标库表；读写分离时，根据 SQL 类型将写请求路由到主库，读请求路由到从库。

实际使用时，要重点设计好分片键，避免无分片键查询、跨库 Join、深分页和大量分布式事务。

一句话总结：

```text
ShardingSphere = 分库分表 + 读写分离 + 分布式事务 + 数据加密；
核心流程 = SQL 解析 -> 路由 -> 改写 -> 执行 -> 归并。
```
