# MySQL 索引总结

MySQL 索引是一种用于提高查询效率的数据结构。它类似于书的目录，可以帮助数据库快速定位数据，减少全表扫描。

---

## 1. 索引的作用

### 核心作用

- 提高查询效率。
- 减少扫描行数。
- 提高排序、分组效率。
- 提高 Join 查询效率。
- 通过唯一索引保证数据唯一性。

### 缺点

- 索引会占用额外磁盘空间。
- 插入、更新、删除时需要维护索引。
- 索引过多会降低写入性能。
- 不合理的索引可能不会被使用。

---

## 2. MySQL 常见索引类型

| 索引类型 | 说明 |
|---|---|
| 主键索引 | 主键字段自动创建，唯一且不能为空 |
| 唯一索引 | 保证字段值唯一，可以有 NULL |
| 普通索引 | 最常见索引，只提升查询效率 |
| 联合索引 | 多个字段组成一个索引 |
| 全文索引 | 用于全文搜索 |
| 前缀索引 | 对字符串字段前几个字符建索引 |

---

## 3. 索引底层数据结构

MySQL InnoDB 默认使用 **B+Tree** 作为索引结构。

### 为什么使用 B+Tree

- B+Tree 层级低，查询磁盘 IO 少。
- 非叶子节点只存索引值，能存更多索引项。
- 叶子节点之间有双向链表，适合范围查询。
- 查询性能稳定，适合数据库场景。

### B+Tree 特点

```text
根节点
  ↓
中间节点
  ↓
叶子节点：存储索引值和数据指针
```

所有数据最终都在叶子节点中，叶子节点之间按顺序连接。

---

## 4. 聚簇索引和非聚簇索引

### 聚簇索引

InnoDB 中，主键索引就是聚簇索引。

特点：

```text
数据和主键索引存放在一起
叶子节点存储完整行数据
```

例如：

```sql
PRIMARY KEY(id)
```

根据主键查询非常快：

```sql
SELECT * FROM user WHERE id = 1;
```

### 非聚簇索引

普通索引、唯一索引、联合索引都属于二级索引，也叫非聚簇索引。

特点：

```text
叶子节点存储索引值 + 主键 ID
```

通过普通索引查询时，如果需要查询完整数据，需要先找到主键 ID，再根据主键回表查询完整记录。

---

## 5. 什么是回表

如果通过二级索引查询，但查询字段不在索引中，就需要回到主键索引中查询完整数据，这个过程叫 **回表**。

示例：

```sql
CREATE INDEX idx_name ON user(name);
```

SQL：

```sql
SELECT * FROM user WHERE name = 'Tom';
```

执行过程：

```text
1. 先通过 idx_name 找到主键 id。
2. 再通过主键 id 查询完整行数据。
```

这就是回表。

### 如何减少回表

使用覆盖索引。

---

## 6. 覆盖索引

### 实现原理

如果查询字段都在索引中，不需要回表，就叫覆盖索引。

示例：

```sql
CREATE INDEX idx_name_age ON user(name, age);
```

SQL：

```sql
SELECT name, age FROM user WHERE name = 'Tom';
```

因为 `name` 和 `age` 都在索引中，所以不需要回表。

### 优势

- 减少回表次数。
- 提高查询性能。
- 适合高频查询接口。

---

## 7. 联合索引

### 实现原理

联合索引是多个字段组成一个索引。

```sql
CREATE INDEX idx_user_status_time
ON order_info(user_id, status, create_time);
```

联合索引的顺序非常重要。

### 最左前缀原则

联合索引必须从最左边的字段开始匹配。

可以使用索引：

```sql
WHERE user_id = 1001;

WHERE user_id = 1001
AND status = 1;

WHERE user_id = 1001
AND status = 1
AND create_time > '2026-01-01';
```

不容易使用完整索引：

```sql
WHERE status = 1;

WHERE create_time > '2026-01-01';

WHERE status = 1
AND create_time > '2026-01-01';
```

### 总结

联合索引要遵守：

```text
最左前缀原则
```

---

## 8. 索引下推

### 实现原理

索引下推，也叫 ICP，Index Condition Pushdown。

在没有索引下推之前，MySQL 通过索引找到数据后，需要先回表，再判断其他条件。

有索引下推后，可以在索引遍历阶段先过滤一部分数据，减少回表次数。

示例：

```sql
CREATE INDEX idx_name_age ON user(name, age);
```

SQL：

```sql
SELECT * FROM user
WHERE name LIKE 'Tom%'
AND age = 18;
```

如果使用索引下推，可以在索引层先判断 `age = 18`，减少无效回表。

### 优势

- 减少回表次数。
- 提高查询效率。
- 对联合索引查询有帮助。

---

## 9. 索引设计原则

### 适合建索引的字段

- 经常作为查询条件的字段。
- 经常用于排序的字段。
- 经常用于分组的字段。
- 经常用于 Join 关联的字段。
- 区分度高的字段。
- 数据量大的表中高频查询字段。

### 不适合建索引的字段

- 区分度低的字段，例如性别、状态。
- 很少查询的字段。
- 经常频繁更新的字段。
- 数据量很小的表。
- 大字段，例如 `TEXT`、`BLOB`。

---

## 10. 联合索引设计原则

联合索引字段顺序一般可以按照以下规则设计：

```text
等值查询字段 -> 范围查询字段 -> 排序字段
```

示例：

```sql
SELECT *
FROM order_info
WHERE user_id = 1001
AND status = 1
AND create_time > '2026-01-01'
ORDER BY create_time DESC;
```

可以考虑：

```sql
CREATE INDEX idx_user_status_time
ON order_info(user_id, status, create_time);
```

### 注意

- 区分度高的字段优先。
- 高频查询字段优先。
- 排序字段尽量放到联合索引中。
- 避免创建重复索引。

---

## 11. 索引失效常见场景

| 场景 | 说明 |
|---|---|
| 不满足最左前缀 | 联合索引没有从最左字段开始使用 |
| 跳过中间字段 | 后面的字段无法继续使用索引 |
| 范围查询后字段 | 范围条件后面的字段可能无法继续利用索引 |
| 索引字段使用函数 | 例如 `DATE(create_time)` |
| 索引字段参与计算 | 例如 `age + 1 = 18` |
| 隐式类型转换 | 字符串字段用数字查询 |
| LIKE 左模糊 | 例如 `LIKE '%abc'` |
| OR 条件不合理 | OR 一边没有索引可能导致全表扫描 |
| 字段区分度低 | 命中数据太多，优化器可能不走索引 |
| 返回数据太多 | 回表成本过高，优化器可能全表扫描 |

---

## 12. 如何查看索引是否生效

使用 `EXPLAIN` 查看执行计划：

```sql
EXPLAIN SELECT * FROM user WHERE phone = '13800138000';
```

重点关注：

| 字段 | 说明 |
|---|---|
| type | 访问类型，ALL 表示全表扫描 |
| possible_keys | 可能使用的索引 |
| key | 实际使用的索引 |
| rows | 预估扫描行数 |
| Extra | 是否使用覆盖索引、排序、临时表等 |

### type 性能从好到差

```text
system > const > eq_ref > ref > range > index > ALL
```

如果出现：

```text
type = ALL
```

通常说明发生了全表扫描，需要重点优化。

---

## 13. 索引优化建议

- 不要盲目建索引，要结合查询场景。
- 优先为高频查询 SQL 设计索引。
- 联合索引优先于多个单列索引。
- 尽量使用覆盖索引减少回表。
- 避免 `SELECT *`。
- 避免索引字段参与函数和计算。
- 字符串查询时注意类型一致，避免隐式转换。
- 排序、分组字段可以结合查询条件建立联合索引。
- 定期使用 `EXPLAIN` 检查索引使用情况。
- 删除重复索引和长期不用的索引。

---

## 14. 总结

MySQL 索引主要用于提高查询效率，InnoDB 默认使用 B+Tree 作为索引结构。B+Tree 层级低，叶子节点有序并通过链表连接，适合等值查询和范围查询。

InnoDB 中主键索引是聚簇索引，叶子节点存储完整行数据；普通索引是二级索引，叶子节点存储索引值和主键 ID。如果通过二级索引查询完整数据，需要再根据主键回到聚簇索引查询，这个过程叫回表。

联合索引需要遵守最左前缀原则，字段顺序非常重要。实际设计索引时，要根据查询条件、排序字段、字段区分度和覆盖索引来综合考虑。

常见索引失效场景包括函数计算、隐式类型转换、LIKE 左模糊、不满足最左前缀、范围查询后字段失效、OR 条件不合理等。

一句话总结：

```text
MySQL 索引优化的核心是：让查询尽量命中高效索引，减少扫描、减少回表、减少排序。
```
