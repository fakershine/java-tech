# 读写分离详解

## 1. 什么是读写分离？

读写分离是数据库架构中常见的一种性能优化方案。

核心思想是：

> 写操作走主库，读操作走从库。

也就是说，根据 SQL 操作类型，把请求路由到不同的数据库实例上。

| 操作类型 | 数据库 |
|---|---|
| INSERT | 主库 |
| UPDATE | 主库 |
| DELETE | 主库 |
| SELECT | 从库 |

典型架构如下：

```text
                ┌──────────────┐
                │    应用服务    │
                └───────┬──────┘
                        │
              ┌─────────┴─────────┐
              │                   │
            写请求               读请求
              │                   │
              ▼                   ▼
        ┌──────────┐        ┌──────────┐
        │  主库     │───────▶│  从库1    │
        │ Master   │ 数据同步 │ Slave1   │
        └──────────┘        └──────────┘
              │             ┌──────────┐
              └────────────▶│  从库2    │
                            │ Slave2   │
                            └──────────┘
```

---

## 2. 为什么需要读写分离？

在大多数业务系统中，读请求通常远多于写请求。

例如电商系统：

| 业务操作 | 类型 |
|---|---|
| 浏览商品 | 读 |
| 搜索商品 | 读 |
| 查看商品详情 | 读 |
| 查看订单 | 读 |
| 加购物车 | 写 |
| 下单 | 写 |
| 支付 | 写 |

如果所有请求都访问同一个数据库，会导致：

- 主库连接数过高
- 查询压力过大
- 慢 SQL 增多
- CPU、IO、内存压力上升
- 写操作被大量读操作影响
- 数据库成为系统性能瓶颈

读写分离可以把大量查询请求分摊到多个从库上，从而降低主库压力，提高系统吞吐量。

---

## 3. 读写分离解决了什么问题？

### 3.1 分摊数据库读压力

不做读写分离时：

```text
所有请求 → 主库
```

做读写分离后：

```text
写请求 → 主库
读请求 → 从库
```

这样可以明显降低主库压力。

---

### 3.2 提升系统并发能力

如果有多个从库，读请求可以分散到不同从库上。

```text
读请求 → 从库1
读请求 → 从库2
读请求 → 从库3
```

从库越多，理论上能够承载的读并发能力越强。

---

### 3.3 提升系统可用性

如果某个从库宕机，可以将读流量切换到其他从库。

```text
从库1 宕机
读请求 → 从库2 / 从库3
```

但是要注意：

> 读写分离本身不等于高可用。  
> 主库高可用还需要主从切换、故障转移、VIP 漂移、MGR、MHA、Orchestrator 等机制支持。

---

## 4. 读写分离的核心依赖：主从复制

读写分离依赖数据库的主从复制。

以 MySQL 为例，主从复制大致流程如下：

```text
1. 主库执行写操作
2. 主库将数据变更记录到 binlog
3. 从库 IO 线程读取主库 binlog
4. 从库将 binlog 写入 relay log
5. 从库 SQL 线程重放 relay log
6. 从库数据最终与主库保持一致
```

架构图：

```text
┌──────────────┐
│    主库       │
│   Master     │
└──────┬───────┘
       │
       │ 1. 写入数据
       ▼
┌──────────────┐
│    binlog    │
└──────┬───────┘
       │
       │ 2. 传输 binlog
       ▼
┌──────────────┐
│  从库 IO线程  │
└──────┬───────┘
       │
       │ 3. 写入 relay log
       ▼
┌──────────────┐
│  relay log   │
└──────┬───────┘
       │
       │ 4. SQL线程重放日志
       ▼
┌──────────────┐
│    从库       │
│   Slave      │
└──────────────┘
```

---

## 5. MySQL 主从复制类型

### 5.1 异步复制

MySQL 默认是异步复制。

流程：

```text
主库提交事务成功后直接返回
从库异步拉取 binlog 并执行
```

优点：

- 写入性能高
- 主库不需要等待从库

缺点：

- 主从可能存在延迟
- 主库宕机时，可能有数据还没有同步到从库

---

### 5.2 半同步复制

半同步复制是指主库提交事务后，需要至少等待一个从库确认收到 binlog，主库才返回成功。

流程：

```text
主库写入 binlog
至少一个从库确认收到 binlog
主库返回提交成功
```

优点：

- 降低数据丢失风险
- 比异步复制更安全

缺点：

- 写入性能下降
- 只能保证从库收到日志，不一定保证从库已经执行完成

---

### 5.3 全同步复制

全同步复制要求所有从库都完成数据同步后，主库才返回成功。

优点：

- 数据一致性最好

缺点：

- 性能较差
- 延迟高
- 实际使用较少

---

## 6. 读写分离的实现方式

### 6.1 代码层面手动控制

最简单的方式是在代码中手动指定访问主库还是从库。

示例：

```java
public User queryUser(Long id) {
    return slaveUserMapper.selectById(id);
}

public void updateUser(User user) {
    masterUserMapper.updateById(user);
}
```

优点：

- 实现简单
- 控制明确
- 不依赖中间件

缺点：

- 代码侵入性强
- 容易写错
- 不利于维护
- 不适合复杂系统

---

### 6.2 Spring AOP + 动态数据源

Java 项目中比较常见的方式是使用：

```text
Spring AOP + AbstractRoutingDataSource + ThreadLocal
```

核心流程：

```text
1. 配置多个数据源：master、slave
2. 使用 AbstractRoutingDataSource 动态选择数据源
3. 使用 ThreadLocal 保存当前数据源标识
4. 通过 AOP 拦截方法，根据注解切换数据源
5. SQL 执行完成后清理 ThreadLocal
```

#### 6.2.1 定义数据源枚举

```java
public enum DataSourceType {
    MASTER,
    SLAVE
}
```

#### 6.2.2 定义 ThreadLocal 上下文

```java
public class DataSourceContextHolder {

    private static final ThreadLocal<DataSourceType> CONTEXT = new ThreadLocal<>();

    public static void useMaster() {
        CONTEXT.set(DataSourceType.MASTER);
    }

    public static void useSlave() {
        CONTEXT.set(DataSourceType.SLAVE);
    }

    public static DataSourceType getDataSourceType() {
        return CONTEXT.get();
    }

    public static void clear() {
        CONTEXT.remove();
    }
}
```

#### 6.2.3 定义动态数据源

```java
public class DynamicDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        return DataSourceContextHolder.getDataSourceType();
    }
}
```

#### 6.2.4 定义读库注解

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface ReadOnly {
}
```

#### 6.2.5 使用 AOP 切换数据源

```java
@Aspect
@Component
public class DataSourceAspect {

    @Before("@annotation(ReadOnly)")
    public void useSlave() {
        DataSourceContextHolder.useSlave();
    }

    @After("@annotation(ReadOnly)")
    public void clear() {
        DataSourceContextHolder.clear();
    }
}
```

#### 6.2.6 使用示例

```java
@ReadOnly
public User getUserById(Long id) {
    return userMapper.selectById(id);
}

@Transactional
public void updateUser(User user) {
    userMapper.updateById(user);
}
```

优点：

- 对业务代码侵入较小
- 可以通过注解灵活控制
- 适合中小型项目
- 不需要额外引入数据库代理

缺点：

- 需要自己处理事务问题
- 需要自己处理主从延迟问题
- 需要防止 ThreadLocal 泄漏
- 多数据源配置和维护复杂度上升

### 6.3 使用 ShardingSphere-JDBC

ShardingSphere-JDBC 是常用的数据库增强框架，支持：

- 读写分离
- 分库分表
- 数据加密
- 分布式事务
- 数据脱敏

架构：

```text
应用服务
   │
   ▼
ShardingSphere-JDBC
   │
   ├── 写请求 → 主库
   ├── 读请求 → 从库1
   └── 读请求 → 从库2
```

优点：

- 对业务侵入较小
- 功能完善
- 支持读写分离和分库分表
- 适合 Java 技术栈

缺点：

- 有一定学习成本
- 配置相对复杂
- 需要理解其 SQL 路由规则

---

### 6.4 使用数据库代理中间件

常见数据库代理包括：

| 中间件 | 说明 |
|---|---|
| ProxySQL | 常用于 MySQL 代理，功能强大 |
| MyCat | 国内常见数据库中间件 |
| ShardingSphere-Proxy | ShardingSphere 的代理模式 |
| Atlas | 360 开源的 MySQL 代理，较老 |
| Amoeba | 较早期数据库代理中间件 |

架构：

```text
应用服务
   │
   ▼
数据库代理
   │
   ├── 写请求 → 主库
   ├── 读请求 → 从库1
   └── 读请求 → 从库2
```

优点：

- 应用层基本无感知
- 支持多语言系统
- 可统一管理数据库访问
- 可以集中做路由、负载均衡、限流、故障转移

缺点：

- 增加额外组件
- 代理层本身需要高可用
- 问题排查链路变长
- 代理层可能成为新的性能瓶颈

## 7. 读写分离中的核心问题

### 7.1 主从延迟

读写分离最大的问题是主从延迟。

场景示例：

```text
1. 用户修改昵称
2. 数据写入主库成功
3. 用户立刻查询个人信息
4. 查询请求被路由到从库
5. 从库还没有同步到最新数据
6. 用户看到的还是旧昵称
```

这就是典型的主从延迟问题。

---

### 7.2 主从延迟产生原因

常见原因如下：

| 原因 | 说明 |
|---|---|
| 主库写压力大 | binlog 产生速度过快 |
| 从库性能不足 | 从库执行 relay log 跟不上 |
| 大事务 | 一个大事务回放时间长 |
| 慢 SQL | 从库执行 SQL 慢 |
| 网络延迟 | 主从之间网络传输慢 |
| 从库并行复制能力不足 | SQL 线程执行效率低 |
| 硬件差异 | 从库配置比主库低 |
| 锁冲突 | 从库执行日志时出现锁等待 |

---

## 8. 如何解决主从延迟？

### 8.1 写后读主库

对于刚写完的数据，短时间内强制读主库。

示例：

```text
修改用户信息 → 写主库
立即查询用户信息 → 读主库
```

适用场景：

- 修改个人资料后立即查看
- 下单后立即查看订单
- 支付后立即查看支付状态
- 修改密码后立即校验
- 创建数据后立即查询详情

示例代码：

```java
public User updateAndQuery(User user) {
    userMapper.updateById(user);

    DataSourceContextHolder.useMaster();
    return userMapper.selectById(user.getId());
}
```

优点：

- 实现简单
- 一致性较好

缺点：

- 增加主库读压力
- 需要识别哪些场景必须读主库

---

### 8.2 强一致性场景读主库

不同业务对一致性的要求不同。

| 业务场景 | 建议 |
|---|---|
| 账户余额 | 读主库 |
| 支付状态 | 读主库 |
| 库存扣减 | 读主库 |
| 订单提交结果 | 读主库 |
| 用户登录校验 | 读主库 |
| 普通商品列表 | 读从库 |
| 首页推荐 | 读从库 |
| 资讯文章浏览 | 读从库 |

原则：

```text
强一致性场景 → 读主库
最终一致性场景 → 读从库
```

---

### 8.3 延迟后读从库

写入成功后，等待一小段时间再读取从库。

```text
写主库
等待 100ms ~ 500ms
读从库
```

优点：

- 实现简单

缺点：

- 不可靠
- 延迟时间不好设置
- 用户体验可能变差

这种方式不建议作为核心方案，只能作为辅助方案。

---

### 8.4 基于缓存减少读库压力

对于热点数据，可以引入缓存。

读流程：

```text
读请求 → Redis → 未命中 → 从库
```

写流程：

```text
写主库 → 删除缓存 → 查询时重新加载
```

优点：

- 降低数据库读压力
- 提升查询性能

缺点：

- 增加缓存一致性问题
- 不能从根本上解决主从延迟
- 缓存击穿、穿透、雪崩需要额外处理

---

### 8.5 监控主从延迟

可以通过 MySQL 命令查看复制状态。

旧版本命令：

```sql
SHOW SLAVE STATUS\G;
```

新版本命令：

```sql
SHOW REPLICA STATUS\G;
```

重点关注字段：

```text
Seconds_Behind_Master
Seconds_Behind_Source
```

如果发现从库延迟过高，可以：

```text
1. 暂时摘除延迟从库
2. 将读流量切换到其他从库
3. 必要时让部分读请求回主库
4. 排查慢 SQL、大事务、复制线程状态
```

---

### 8.6 从库延迟过高自动摘除

如果某个从库异常，应该自动将其从读库列表中移除。

常见摘除条件：

- 连接失败
- 主从延迟超过阈值
- 复制线程中断
- 查询超时
- 从库 CPU 或 IO 过高
- SQL 执行异常

示例：

```text
从库1 延迟 10s，超过阈值
系统将从库1 从读库列表中摘除

读请求 → 从库2 / 从库3
```

## 9. 读写分离与事务

事务是读写分离中非常关键的问题。

### 9.1 事务内通常应该走主库

示例：

```java
@Transactional
public void createOrder() {
    orderMapper.insert(order);
    Order dbOrder = orderMapper.selectById(order.getId());
}
```

虽然 `selectById` 是查询操作，但是它应该走主库。

原因：

```text
同一个事务中，前面刚写入的数据，后面必须能读到。
```

因此，一般规则是：

> 只要方法开启事务，整个事务内的 SQL 都走主库。

---

### 9.2 事务内读从库的问题

如果事务中写主库后又读从库，可能出现异常。

```text
1. 开启事务
2. 插入订单到主库
3. 查询订单走从库
4. 从库还没有同步
5. 查询不到订单
6. 业务逻辑异常
```

所以事务方法中默认走主库更安全。

---

### 9.3 Spring 中判断是否存在事务

可以通过以下方式判断当前线程是否存在事务：

```java
TransactionSynchronizationManager.isActualTransactionActive()
```

示例：

```java
if (TransactionSynchronizationManager.isActualTransactionActive()) {
    DataSourceContextHolder.useMaster();
} else {
    DataSourceContextHolder.useSlave();
}
```

## 10. 读写分离的路由策略

### 10.1 按 SQL 类型路由

最常见规则：

```text
SELECT → 从库
INSERT / UPDATE / DELETE → 主库
```

但是这种方式有一些特殊情况。

例如：

```sql
SELECT LAST_INSERT_ID();
SELECT ... FOR UPDATE;
SELECT ... LOCK IN SHARE MODE;
```

这些虽然是 SELECT，但是应该走主库。

---

### 10.2 按方法注解路由

通过注解显式指定访问主库还是从库。

```java
@ReadOnly
public List<Product> listProducts() {
    return productMapper.selectList(null);
}

@Master
public Order getOrderDetail(Long orderId) {
    return orderMapper.selectById(orderId);
}
```

优点：

- 控制准确
- 业务语义清晰

缺点：

- 需要开发人员规范使用
- 容易漏加注解

---

### 10.3 按业务场景路由

根据业务一致性要求决定走主库还是从库。

| 业务场景 | 数据源 |
|---|---|
| 普通列表查询 | 从库 |
| 商品详情 | 从库 |
| 首页推荐 | 从库 |
| 报表统计 | 从库或独立分析库 |
| 支付结果 | 主库 |
| 库存查询 | 主库 |
| 用户登录校验 | 主库 |
| 写后立即查询 | 主库 |
| 事务内查询 | 主库 |

这是实际项目中比较推荐的方式。

---

## 11. 从库负载均衡策略

当存在多个从库时，需要对读请求做负载均衡。

常见策略如下：

| 策略 | 说明 |
|---|---|
| 轮询 | 请求依次分配到不同从库 |
| 随机 | 随机选择一个从库 |
| 权重 | 配置高的从库承担更多请求 |
| 最小连接数 | 优先选择连接数少的从库 |
| 延迟优先 | 优先选择主从延迟低的从库 |
| 可用性优先 | 自动避开异常从库 |

例如：

```text
从库1：权重 5
从库2：权重 3
从库3：权重 2
```

请求分配比例大致为：

```text
从库1：50%
从库2：30%
从库3：20%
```

## 12. 读写分离适合哪些场景？

### 12.1 适合场景

读写分离适合读多写少的业务系统。

例如：

| 场景 | 说明 |
|---|---|
| 电商商品浏览 | 读多写少 |
| 内容资讯系统 | 阅读量大，写入少 |
| 社交动态浏览 | 查询多 |
| 后台管理系统 | 查询和报表多 |
| 订单查询系统 | 查询频繁 |
| 用户信息展示 | 读多写少 |
| CMS 内容系统 | 内容发布少，访问多 |

---

### 12.2 不适合场景

以下场景不一定适合读写分离：

| 场景 | 原因 |
|---|---|
| 写多读少 | 从库分摊效果不明显 |
| 强一致性要求极高 | 主从延迟难以接受 |
| 数据量很小 | 没必要增加架构复杂度 |
| 单库压力不大 | 属于过早优化 |
| 事务链路复杂 | 容易引入一致性问题 |
| 写入瓶颈明显 | 读写分离不能解决写瓶颈 |

---

## 13. 读写分离的优缺点

### 13.1 优点

- 提升数据库读性能
- 降低主库压力
- 提升系统并发能力
- 支持读请求横向扩展
- 可以利用从库做报表查询
- 可以利用从库做备份
- 提升一定程度的可用性
- 有利于隔离读写负载

---

### 13.2 缺点

- 架构复杂度增加
- 存在主从延迟问题
- 事务处理复杂
- 数据源路由容易出错
- 从库故障需要自动摘除
- 运维和监控成本增加
- 不能解决写压力
- 不能解决单表数据量过大问题

---

## 14. 读写分离不能解决什么问题？

### 14.1 不能解决写压力

读写分离主要解决的是读压力。

如果系统写入压力很大，例如：

```text
秒杀扣库存
订单高并发创建
日志高频写入
用户行为打点
交易流水写入
```

读写分离帮助有限。

这时可能需要：

- 分库分表
- 消息队列削峰
- 批量写入
- 异步化处理
- 缓存预扣
- 数据库水平拆分
- 引入 NoSQL 或日志型存储

---

### 14.2 不能解决单表数据量过大

如果单表数据量过大，例如：

```text
订单表 1 亿数据
日志表 10 亿数据
流水表 5 亿数据
```

读写分离不能从根本上解决单表查询慢的问题。

这种情况需要考虑：

- 分表
- 分区表
- 冷热数据分离
- 历史数据归档
- 合理设计索引
- 引入 Elasticsearch
- 引入 ClickHouse、Doris 等 OLAP 系统

---

### 14.3 不能完全保证强一致性

由于主从复制通常存在延迟，从库数据可能不是最新的。

所以：

```text
读写分离适合最终一致性场景
不适合所有强一致性场景
```

对于强一致性业务，应优先读主库。

---

## 15. 实际项目中如何设计读写分离？

### 15.1 推荐整体架构

```text
应用服务
   │
   ▼
动态数据源 / 数据库中间件
   │
   ├── 主库 Master
   ├── 从库 Slave1
   ├── 从库 Slave2
   └── 从库 Slave3
```

推荐规则：

```text
写请求 → 主库
事务请求 → 主库
强一致性读 → 主库
写后立即读 → 主库
普通查询 → 从库
报表统计 → 从库或独立报表库
```

---

### 15.2 Java 项目常见方案选择

#### 方案一：Spring AOP + AbstractRoutingDataSource

适合：

- 中小型项目
- 业务复杂度不高
- 团队希望自己控制路由规则
- 不想引入额外中间件

---

#### 方案二：ShardingSphere-JDBC

适合：

- Java 技术栈
- 需要读写分离
- 未来可能做分库分表
- 希望减少自研成本

---

#### 方案三：ProxySQL / MyCat / ShardingSphere-Proxy

适合：

- 多语言系统
- 希望应用层无感知
- 需要统一管理数据库访问
- 数据库集群规模较大

## 16. 读写分离设计注意事项

### 16.1 默认写主库

以下操作必须走主库：

```sql
INSERT
UPDATE
DELETE
REPLACE
DDL
```

---

### 16.2 事务内强制主库

只要方法上有事务：

```java
@Transactional
```

建议整个方法内所有 SQL 都走主库。

---

### 16.3 写后读强制主库

以下场景建议强制读主库：

- 下单成功后查订单
- 支付成功后查支付状态
- 修改资料后查用户信息
- 创建数据后查详情
- 修改密码后校验登录

---

### 16.4 特殊 SELECT 走主库

以下 SQL 虽然是查询，但建议走主库：

```sql
SELECT LAST_INSERT_ID();
SELECT ... FOR UPDATE;
SELECT ... LOCK IN SHARE MODE;
```

---

### 16.5 从库设置只读

从库应该设置只读，避免误写。

```sql
read_only = 1;
super_read_only = 1;
```

---

### 16.6 做好监控

需要重点监控：

- 主库 QPS
- 从库 QPS
- 主从延迟
- 慢 SQL
- 数据库连接数
- CPU 使用率
- IO 使用率
- 内存使用率
- 复制线程状态
- 从库可用性
- 锁等待情况

---

### 16.7 从库故障自动摘除

如果某个从库异常：

```text
连接失败
延迟过高
查询超时
复制中断
CPU 过高
IO 过高
```

应该自动从读库列表中摘除。

## 17. 读写分离常见面试问题

### 17.1 什么是读写分离？

读写分离是指将数据库的读操作和写操作分开处理，写请求访问主库，读请求访问从库，通过主从复制保证主库和从库的数据同步。

---

### 17.2 为什么要做读写分离？

因为大多数业务系统都是读多写少，如果所有请求都访问主库，会导致主库压力过大。读写分离可以把读请求分摊到多个从库上，从而降低主库压力，提高查询性能和系统并发能力。

---

### 17.3 读写分离有什么问题？

主要问题是主从延迟。写入主库后，从库可能还没有同步到最新数据，如果马上读取从库，可能读到旧数据。

此外还有：

- 事务内数据一致性问题
- 数据源路由问题
- 从库故障处理问题
- 主从复制异常问题
- 运维复杂度增加

---

### 17.4 如何解决主从延迟？

常见方式有：

- 写后读主库
- 强一致性场景读主库
- 事务内强制读主库
- 监控主从延迟
- 从库延迟过高时自动摘除
- 使用半同步复制降低数据丢失风险
- 优化慢 SQL 和大事务
- 提升从库硬件配置
- 开启并行复制

---

### 17.5 事务内为什么建议走主库？

因为事务内可能先写后读。

如果写入主库后，后续查询走从库，而从库还没有同步到最新数据，就可能查询不到刚写入的数据，导致业务逻辑异常。

所以事务内一般强制走主库。

---

### 17.6 SELECT 一定走从库吗？

不一定。

以下 SELECT 建议走主库：

```sql
SELECT LAST_INSERT_ID();
SELECT ... FOR UPDATE;
SELECT ... LOCK IN SHARE MODE;
```

此外，强一致性场景下的查询也应该走主库。

---

### 17.7 读写分离能解决写压力吗？

不能。

读写分离主要解决读压力，不能解决写压力。如果写压力很大，需要考虑分库分表、消息队列削峰、异步化、批量写入、缓存预扣等方案。

---

### 17.8 读写分离和分库分表有什么区别？

| 对比项 | 读写分离 | 分库分表 |
|---|---|---|
| 解决问题 | 读压力大 | 数据量大、写压力大 |
| 核心方式 | 主库写，从库读 | 数据水平拆分 |
| 是否拆数据 | 不拆数据 | 拆分数据 |
| 一致性问题 | 主从延迟 | 分布式事务、跨库查询 |
| 常见场景 | 读多写少 | 单表过大、写入瓶颈 |

---

## 18. 总结

可以这样回答：

> 读写分离是数据库性能优化的一种常见方案，核心思想是写请求走主库，读请求走从库，通过主从复制保证主库和从库之间的数据同步。
>
> 因为大多数业务系统都是读多写少，所以把查询请求分摊到多个从库，可以降低主库压力，提高系统吞吐量和并发能力。
>
> 读写分离一般有几种实现方式：一种是在代码层手动控制数据源，一种是通过 Spring AOP 加 AbstractRoutingDataSource 动态切换数据源，还有一种是使用 ShardingSphere、MyCat、ProxySQL 这类中间件统一做路由。
>
> 但是读写分离最大的问题是主从延迟。比如写入主库之后，从库还没有同步完成，马上查询从库可能读不到最新数据。所以对于强一致性场景，比如订单支付、账户余额、库存扣减、写后立即查询，一般要强制读主库。而普通列表页、商品详情、资讯内容这类可以接受短暂延迟的查询，可以走从库。
>
> 另外，在事务中一般也要强制走主库，避免事务内写完之后再读从库导致读不到数据。实际项目中还要做好从库负载均衡、主从延迟监控、故障摘除和主库高可用。

## 19. 简化总结

```text
读写分离 = 写主库，读从库。

解决的问题：
1. 读压力大
2. 主库负载高
3. 查询并发高

核心依赖：
1. 主从复制
2. 数据源路由
3. 从库负载均衡

最大问题：
1. 主从延迟
2. 事务一致性
3. 路由准确性

常见解决方案：
1. 写后读主库
2. 事务内读主库
3. 强一致性场景读主库

```

## 20. 一句话总结

读写分离适合读多写少的系统，通过主从复制把读请求分摊到从库，提高数据库读性能和系统并发能力，但需要重点处理主从延迟、事务一致性、数据源路由、从库负载均衡和故障摘除问题。
