# MySQL 锁总结

MySQL 锁用于解决并发事务下的数据一致性问题。  
锁的核心作用是：**控制多个事务对同一数据的并发访问，避免数据冲突。**

---

## 1. MySQL 锁分类

MySQL 中常见锁可以从不同维度分类：

| 分类维度 | 锁类型 |
|---|---|
| 按粒度 | 全局锁、表级锁、行级锁 |
| 按模式 | 共享锁、排他锁 |
| 按算法 | 记录锁、间隙锁、临键锁 |
| 按思想 | 悲观锁、乐观锁 |
| 按意向 | 意向共享锁、意向排他锁 |

---

## 2. 全局锁

### 实现原理

全局锁会锁住整个数据库实例，使整个库处于只读状态。

常用命令：

```sql
FLUSH TABLES WITH READ LOCK;
```

释放锁：

```sql
UNLOCK TABLES;
```

加全局锁后：

- 数据不能写入。
- 表结构不能修改。
- 主要用于全库备份。

### 优势

- 可以保证备份期间数据一致。
- 实现简单。

### 劣势

- 影响整个数据库写入。
- 锁粒度太大。
- 不适合业务高峰期使用。

### 适用场景

- 全库逻辑备份。
- 数据迁移前的一致性快照。

---

## 3. 表级锁

### 实现原理

表级锁是对整张表加锁。

加读锁：

```sql
LOCK TABLES user READ;
```

加写锁：

```sql
LOCK TABLES user WRITE;
```

释放锁：

```sql
UNLOCK TABLES;
```

### 读锁

加读锁后：

- 当前会话可以读。
- 其他会话可以读。
- 所有会话不能写。

### 写锁

加写锁后：

- 当前会话可以读写。
- 其他会话不能读写。

### 优势

- 实现简单。
- 加锁开销小。
- 适合读多写少或表级操作。

### 劣势

- 锁粒度大。
- 并发能力差。
- 容易阻塞大量请求。

### 适用场景

- MyISAM 存储引擎。
- 表维护操作。
- 低并发批量处理。

---

## 4. 行级锁

### 实现原理

行级锁是 InnoDB 中最常用的锁，只锁定满足条件的行。

例如：

```sql
SELECT * FROM user WHERE id = 1 FOR UPDATE;
```

或者：

```sql
UPDATE user SET name = 'Tom' WHERE id = 1;
```

InnoDB 会对 `id = 1` 这行数据加锁。

### 优势

- 锁粒度小。
- 并发能力强。
- 适合高并发事务场景。

### 劣势

- 加锁开销比表锁大。
- 容易产生死锁。
- 如果条件没有命中索引，可能锁住更多数据。

### 适用场景

- InnoDB 事务。
- 订单更新。
- 库存扣减。
- 账户余额更新。

---

## 5. 共享锁和排他锁

## 5.1 共享锁

共享锁也叫读锁，多个事务可以同时持有共享锁。

加锁方式：

```sql
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;
```

MySQL 8.0 推荐：

```sql
SELECT * FROM user WHERE id = 1 FOR SHARE;
```

特点：

- 可以多个事务同时读。
- 不允许其他事务修改。
- 适合读取时防止数据被修改。

---

## 5.2 排他锁

排他锁也叫写锁，同一时间只能有一个事务持有。

加锁方式：

```sql
SELECT * FROM user WHERE id = 1 FOR UPDATE;
```

或者执行：

```sql
UPDATE user SET name = 'Tom' WHERE id = 1;
```

特点：

- 当前事务可以读写。
- 其他事务不能修改。
- 其他事务也不能加排他锁。
- 适合更新、删除场景。

---

## 6. 意向锁

### 实现原理

意向锁是表级锁，用于表示事务接下来要对表中的某些行加锁。

常见类型：

| 锁类型 | 说明 |
|---|---|
| 意向共享锁 IS | 表示事务准备给某些行加共享锁 |
| 意向排他锁 IX | 表示事务准备给某些行加排他锁 |

例如执行：

```sql
SELECT * FROM user WHERE id = 1 FOR UPDATE;
```

InnoDB 会先给表加 **意向排他锁 IX**，再给具体行加排他锁。

### 作用

意向锁主要用于提高表锁和行锁之间的冲突判断效率。

如果没有意向锁，数据库想给整张表加锁时，需要逐行判断是否有行锁，成本很高。

### 面试总结

意向锁不是业务主动加的，而是 InnoDB 自动加的，用于协调表锁和行锁之间的关系。

---

## 7. 记录锁

### 实现原理

记录锁锁定的是索引中的一条具体记录。

例如表中有主键索引：

```sql
SELECT * FROM user WHERE id = 10 FOR UPDATE;
```

如果 `id = 10` 存在，InnoDB 会锁住这条索引记录。

### 特点

- 只锁具体存在的记录。
- 需要基于索引加锁。
- 常用于等值查询命中唯一索引。

### 适用场景

- 根据主键更新数据。
- 根据唯一索引更新数据。

---

## 8. 间隙锁

### 实现原理

间隙锁锁定的是索引记录之间的范围，不锁具体记录。

例如表中有数据：

```text
id = 10
id = 20
```

执行：

```sql
SELECT * FROM user WHERE id > 10 AND id < 20 FOR UPDATE;
```

InnoDB 可能会锁住 `(10, 20)` 这个区间，防止其他事务插入新数据。

### 作用

间隙锁主要用于防止幻读。

### 特点

- 锁的是范围，不是具体行。
- 会阻止其他事务在范围内插入数据。
- 主要出现在可重复读隔离级别下。

### 劣势

- 容易扩大锁范围。
- 可能导致插入阻塞。
- 并发性能会下降。

---

## 9. 临键锁

### 实现原理

临键锁也叫 Next-Key Lock，是 **记录锁 + 间隙锁** 的组合。

它锁定：

```text
左开右闭区间
```

例如索引中有：

```text
10, 20, 30
```

可能形成区间：

```text
(-∞, 10]
(10, 20]
(20, 30]
(30, +∞)
```

执行范围查询时，InnoDB 会通过临键锁锁定相关区间。

### 作用

- 锁住已有记录。
- 锁住记录之间的间隙。
- 防止其他事务插入新数据。
- 解决当前读下的幻读问题。

### 适用场景

- 范围查询加锁。
- `FOR UPDATE`
- `UPDATE`
- `DELETE`

---

## 10. 悲观锁

### 实现原理

悲观锁认为数据随时可能被别人修改，所以操作前先加锁。

常见写法：

```sql
SELECT * FROM user WHERE id = 1 FOR UPDATE;
```

流程：

```text
开启事务
  ↓
查询并加锁
  ↓
执行业务修改
  ↓
提交事务释放锁
```

### 优势

- 实现简单。
- 数据一致性强。
- 适合写多冲突多的场景。

### 劣势

- 并发性能较差。
- 容易阻塞。
- 可能产生死锁。

### 适用场景

- 库存扣减。
- 账户余额修改。
- 强一致更新场景。

---

## 11. 乐观锁

### 实现原理

乐观锁认为冲突不多，不提前加锁，而是在更新时判断数据是否被修改过。

通常使用 `version` 字段实现：

```sql
UPDATE product
SET stock = stock - 1,
    version = version + 1
WHERE id = 1
AND version = 10;
```

如果影响行数为 `1`，说明更新成功。  
如果影响行数为 `0`，说明数据已经被其他事务修改，需要重试或失败。

### 优势

- 不阻塞线程。
- 并发性能较好。
- 适合读多写少场景。

### 劣势

- 高并发写冲突时重试成本高。
- 需要业务表增加版本字段。
- 需要业务层处理失败重试。

### 适用场景

- 库存扣减。
- 状态更新。
- 读多写少的并发更新。

---

## 12. 当前读和快照读

### 快照读

普通查询属于快照读：

```sql
SELECT * FROM user WHERE id = 1;
```

特点：

- 不加锁。
- 基于 MVCC 读取历史版本。
- 读写不阻塞。

---

### 当前读

当前读读取的是最新数据，并且会加锁。

常见当前读：

```sql
SELECT * FROM user WHERE id = 1 FOR UPDATE;

SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;

UPDATE user SET name = 'Tom' WHERE id = 1;

DELETE FROM user WHERE id = 1;
```

特点：

- 读取最新版本。
- 会加锁。
- 可能触发行锁、间隙锁、临键锁。

---

## 13. 死锁

### 产生原因

死锁是指多个事务互相等待对方释放锁，导致都无法继续执行。

示例：

```text
事务 A 锁住 id = 1，等待 id = 2
事务 B 锁住 id = 2，等待 id = 1
```

结果：

```text
A 等 B
B 等 A
形成死锁
```

### 解决方式

InnoDB 会自动检测死锁，并回滚其中一个事务。

查看死锁信息：

```sql
SHOW ENGINE INNODB STATUS;
```

### 避免死锁

- 保持固定的加锁顺序。
- 控制事务尽快提交。
- 避免大事务。
- 更新条件尽量命中索引。
- 减少范围更新。
- 降低热点数据竞争。
- 必要时使用乐观锁。

---

## 14. 锁优化建议

- 查询和更新条件必须尽量命中索引。
- 避免无索引更新导致锁范围扩大。
- 控制事务大小，避免长事务。
- 不要在事务中调用远程接口。
- 避免大范围 `UPDATE` / `DELETE`。
- 批量更新建议分批执行。
- 热点行更新可以用 Redis、MQ 或分片降低竞争。
- 使用 `EXPLAIN` 确认 SQL 是否走索引。
- 通过 `SHOW ENGINE INNODB STATUS` 分析锁等待和死锁。

---

## 15. 常见锁对比

| 锁类型 | 粒度 | 作用 | 特点 |
|---|---|---|---|
| 全局锁 | 整个实例 | 全库只读 | 影响最大 |
| 表锁 | 整张表 | 控制表级并发 | 开销小，并发差 |
| 行锁 | 单行数据 | 控制行级并发 | 并发好，开销较大 |
| 共享锁 | 行/表 | 允许多个事务读 | 读读共享 |
| 排他锁 | 行/表 | 独占写入 | 写写互斥 |
| 意向锁 | 表级 | 协调表锁和行锁 | InnoDB 自动加 |
| 记录锁 | 索引记录 | 锁具体行 | 精确锁定 |
| 间隙锁 | 索引区间 | 防止插入 | 防幻读 |
| 临键锁 | 记录 + 间隙 | 防幻读 | 范围锁定 |
| 乐观锁 | 业务层 | 更新时校验版本 | 不阻塞 |
| 悲观锁 | 数据库层 | 操作前先加锁 | 强一致 |

---

## 16. 总结

MySQL 锁可以按照粒度分为全局锁、表锁和行锁。全局锁会让整个库只读，主要用于备份；表锁锁住整张表，开销小但并发差；行锁是 InnoDB 最常用的锁，粒度小，并发能力强。

从锁模式看，主要有共享锁和排他锁。共享锁允许多个事务同时读，排他锁用于写操作，同一时间只能一个事务持有。

InnoDB 的行锁是基于索引实现的，常见有记录锁、间隙锁和临键锁。记录锁锁具体索引记录，间隙锁锁索引范围，临键锁是记录锁和间隙锁的组合，主要用于解决可重复读隔离级别下当前读的幻读问题。

实际优化锁问题时，要重点保证 SQL 命中索引，避免大事务、长事务和大范围更新，减少锁等待和死锁。

一句话总结：

```text
MySQL 锁的核心是：通过不同粒度和不同模式的锁，在数据一致性和并发性能之间做平衡。
```
