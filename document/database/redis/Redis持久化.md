# Redis 持久化总结

Redis 是内存数据库，持久化用于把内存数据保存到磁盘，防止 Redis 重启后数据全部丢失。

Redis 常见持久化方式：

```text
RDB
AOF
混合持久化
```

---

## 1. RDB 持久化

### 实现原理

RDB 是快照持久化，会在某个时间点把 Redis 内存数据生成一份快照文件。

```text
内存数据
  ↓
生成 RDB 快照
  ↓
保存到 dump.rdb
```

触发方式：

```text
save
bgsave
自动触发
```

---

### save

```bash
save
```

特点：

```text
主线程执行持久化
会阻塞 Redis
生产环境不推荐
```

---

### bgsave

```bash
bgsave
```

特点：

```text
fork 子进程生成 RDB
主进程继续处理请求
生产环境常用
```

流程：

```text
主进程 fork 子进程
  ↓
子进程写 RDB 文件
  ↓
写临时文件
  ↓
替换旧 RDB 文件
```

---

### 优势

- 文件紧凑，体积小。
- 恢复速度快。
- 适合全量备份。
- 对性能影响相对较小。

### 劣势

- 可能丢失最近一次快照后的数据。
- fork 子进程会消耗内存。
- 数据量大时生成快照有一定开销。

---

## 2. AOF 持久化

### 实现原理

AOF 会记录 Redis 执行过的写命令。

```text
客户端写命令
  ↓
Redis 执行命令
  ↓
追加到 AOF 文件
```

重启恢复时：

```text
读取 AOF 文件
  ↓
重新执行写命令
  ↓
恢复数据
```

---

### AOF 刷盘策略

| 策略 | 说明 | 数据安全性 | 性能 |
|---|---|---|---|
| `always` | 每次写命令都刷盘 | 最高 | 最差 |
| `everysec` | 每秒刷盘一次 | 较高，最多丢 1 秒数据 | 较好 |
| `no` | 由操作系统决定刷盘 | 较低 | 最好 |

常用配置：

```bash
appendonly yes
appendfsync everysec
```

生产环境一般使用：

```text
everysec
```

---

### AOF 重写

AOF 文件会越来越大，所以 Redis 会进行 AOF 重写。

### 实现原理

把多条历史命令压缩成当前数据状态的最少命令。

例如：

```text
INCR count
INCR count
INCR count
```

可以重写成：

```text
SET count 3
```

触发方式：

```bash
bgrewriteaof
```

流程：

```text
fork 子进程
  ↓
子进程生成新的 AOF 文件
  ↓
主进程继续处理写请求
  ↓
重写期间的新写命令写入缓冲区
  ↓
追加到新 AOF
  ↓
替换旧 AOF
```

---

### 优势

- 数据安全性比 RDB 更高。
- `everysec` 最多丢失 1 秒数据。
- AOF 文件可读性相对较好。
- 适合对数据安全要求更高的场景。

### 劣势

- 文件通常比 RDB 大。
- 恢复速度通常比 RDB 慢。
- AOF 重写有额外开销。
- 极端情况下 AOF 文件可能损坏，需要修复。

---

## 3. 混合持久化

### 实现原理

混合持久化结合 RDB 和 AOF。

AOF 文件前半部分是 RDB 快照，后半部分是增量 AOF 命令。

```text
AOF 文件
├── RDB 快照部分
└── AOF 增量命令部分
```

配置：

```bash
aof-use-rdb-preamble yes
```

---

### 优势

- 恢复速度比纯 AOF 快。
- 数据安全性比纯 RDB 好。
- 兼顾恢复性能和数据完整性。

### 劣势

- 文件可读性比纯 AOF 差。
- 需要较新 Redis 版本支持。
- 理解和排查成本略高。

---

## 4. RDB 和 AOF 对比

| 对比项 | RDB | AOF |
|---|---|---|
| 持久化方式 | 快照 | 追加写命令 |
| 文件大小 | 小 | 通常较大 |
| 恢复速度 | 快 | 相对慢 |
| 数据安全性 | 较低 | 较高 |
| 性能影响 | 较小 | 略高 |
| 是否适合备份 | 适合 | 一般 |
| 数据丢失风险 | 丢最近一次快照后的数据 | everysec 最多丢 1 秒 |

---

## 5. Redis 启动恢复顺序

如果同时开启 RDB 和 AOF：

```text
Redis 优先使用 AOF 恢复数据
```

原因：

```text
AOF 通常比 RDB 数据更完整
```

---

## 6. 持久化配置建议

### 缓存场景

如果 Redis 只是缓存，数据可从数据库恢复：

```text
可以只开 RDB
甚至不开持久化
```

---

### 重要数据场景

如果 Redis 保存重要数据：

```text
开启 AOF
appendfsync everysec
开启混合持久化
```

推荐：

```bash
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
```

---

## 7. 常见问题

### 1. RDB 会不会阻塞 Redis？

`save` 会阻塞。

`bgsave` 不会长时间阻塞主线程，但 `fork` 子进程时可能短暂阻塞。

---

### 2. AOF 为什么要重写？

因为 AOF 记录每条写命令，文件会越来越大。

重写后可以：

```text
减少文件体积
提升恢复速度
```

---

### 3. AOF everysec 会丢数据吗？

会。

最多可能丢失最近 1 秒的数据。

---

### 4. RDB 和 AOF 可以同时开启吗？

可以。

同时开启时，Redis 重启恢复会优先加载 AOF。

---

## 8. 总结

Redis 持久化主要有 RDB 和 AOF 两种方式。

RDB 是快照持久化，会在某个时间点把内存数据保存成 `dump.rdb` 文件，优点是文件小、恢复快，缺点是可能丢失最近一次快照后的数据。

AOF 是追加日志持久化，会记录每次写命令，Redis 重启时通过重放 AOF 命令恢复数据。AOF 数据安全性更高，常用 `appendfsync everysec`，最多丢失 1 秒数据，但文件较大，恢复速度相对较慢。

实际生产中，如果 Redis 只是缓存，可以只开 RDB 或不开持久化；如果数据比较重要，推荐开启 AOF，并使用混合持久化。

一句话总结：

```text
RDB 是快照，恢复快但可能丢数据；
AOF 是写命令日志，数据更安全但文件更大；
生产重要数据推荐 AOF everysec + 混合持久化。
```
