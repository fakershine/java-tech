# Redis 中的复制总结

Redis 复制是指：**将主节点的数据同步到从节点**，常用于读写分离、数据备份和高可用。

核心结构：

```text
Master 主节点
  ↓
Replica 从节点
```

---

## 1. Redis 复制的作用

| 作用 | 说明 |
|---|---|
| 数据备份 | 从节点保存主节点数据副本 |
| 读写分离 | 主节点写，从节点读 |
| 高可用 | 主节点故障后，从节点可提升为主节点 |
| 扩展读能力 | 多个从节点分担读请求 |

---

## 2. 主从复制配置

Redis 5.0 以后推荐使用：

```bash
replicaof master_ip master_port
```

旧版本命令：

```bash
slaveof master_ip master_port
```

示例：

```bash
replicaof 192.168.1.10 6379
```

表示当前节点作为 `192.168.1.10:6379` 的从节点。

---

## 3. 复制流程

Redis 主从复制主要分为两种：

```text
全量复制
增量复制
```

整体流程：

```text
从节点连接主节点
  ↓
发送 PSYNC 命令
  ↓
判断是否可以增量复制
  ↓
如果不能，则全量复制
  ↓
如果可以，则增量复制
```

---

## 4. 全量复制

### 实现原理

当从节点第一次连接主节点，或者增量复制条件不满足时，会触发全量复制。

流程：

```text
1. 从节点连接主节点。
2. 从节点发送同步请求。
3. 主节点执行 bgsave 生成 RDB 文件。
4. 主节点将 RDB 文件发送给从节点。
5. 从节点清空旧数据，加载 RDB 文件。
6. 主节点将复制期间产生的新写命令发送给从节点。
7. 从节点执行这些写命令，最终追上主节点。
```

简化理解：

```text
全量复制 = RDB 快照 + 后续写命令同步
```

---

## 5. 增量复制

### 实现原理

如果主从之间只是短暂断开，重新连接后不需要重新全量同步。

Redis 会通过：

```text
runId
offset
复制积压缓冲区 replication backlog
```

判断能否增量复制。

流程：

```text
1. 从节点断线前记录复制偏移量 offset。
2. 重新连接主节点后发送 PSYNC。
3. 主节点判断 backlog 中是否还有从节点缺失的数据。
4. 如果有，则只发送缺失部分命令。
5. 从节点执行这些命令，完成增量同步。
```

简化理解：

```text
增量复制 = 只同步断线期间缺失的数据
```

---

## 6. PSYNC 机制

`PSYNC` 是 Redis 主从同步的核心命令。

它依赖两个关键值：

| 字段 | 说明 |
|---|---|
| `runId` | 主节点唯一运行 ID |
| `offset` | 主从复制偏移量 |

判断逻辑：

```text
runId 相同
并且
offset 还在 backlog 中
  ↓
执行增量复制

否则
  ↓
执行全量复制
```

---

## 7. 复制积压缓冲区

复制积压缓冲区是主节点维护的一块环形缓冲区。

作用：

```text
保存最近一段时间的写命令
用于从节点断线后增量同步
```

配置参数：

```bash
repl-backlog-size 1mb
```

如果从节点断线太久，缺失的数据已经被覆盖：

```text
无法增量复制
只能全量复制
```

---

## 8. Redis 复制特点

### 1. 异步复制

Redis 主从复制默认是异步的。

```text
客户端写入主节点成功
  ↓
主节点返回成功
  ↓
主节点异步同步给从节点
```

所以可能出现：

```text
主节点写成功
但还没同步给从节点
主节点宕机
这部分数据可能丢失
```

---

### 2. 主写从读

一般架构是：

```text
写请求 -> 主节点
读请求 -> 从节点
```

注意：

```text
从节点默认不允许写入
```

配置项：

```bash
replica-read-only yes
```

---

### 3. 一个主节点可以有多个从节点

```text
Master
 ├── Replica 1
 ├── Replica 2
 └── Replica 3
```

用于扩展读能力。

---

### 4. 支持链式复制

```text
Master
  ↓
Replica 1
  ↓
Replica 2
```

可以减轻主节点同步压力，但链路越长，延迟越大。

---

## 9. 复制中的问题

### 1. 主从延迟

由于复制是异步的，从节点可能落后主节点。

可能导致：

```text
刚写入的数据
马上从从库读取
可能读不到
```

解决方式：

```text
强一致读走主库
监控主从延迟
重要业务避免读从库
```

---

### 2. 数据丢失

如果主节点写入成功但还未同步给从节点就宕机，可能丢数据。

解决方式：

```text
使用 WAIT 命令增强同步确认
合理配置持久化
使用哨兵或集群提高可用性
业务接受最终一致
```

---

### 3. 全量复制开销大

全量复制会触发：

```text
bgsave
RDB 文件传输
从节点加载 RDB
```

可能带来：

```text
CPU 压力
磁盘 IO 压力
网络压力
从节点短暂不可用
```

优化：

```text
增大 repl-backlog-size
避免频繁断线
控制从节点数量
合理规划网络和机器资源
```

---

### 4. 复制风暴

如果大量从节点同时请求全量同步，主节点压力会很大。

解决方式：

```text
避免大量从节点同时重启
使用链式复制
合理扩容
控制全量同步并发
```

---

## 10. 和哨兵的关系

主从复制本身只负责：

```text
数据同步
```

不负责：

```text
自动故障转移
```

如果要主节点宕机后自动切换，需要 Redis Sentinel。

```text
主从复制：数据复制
Sentinel：监控 + 自动选主 + 故障转移
Cluster：分片 + 高可用
```

---

## 11. 总结

Redis 复制是通过主从结构实现的，主节点负责写入，从节点复制主节点数据，常用于读写分离、数据备份和高可用。

Redis 复制分为全量复制和增量复制。第一次同步或者无法增量同步时，会进行全量复制：主节点生成 RDB 文件发送给从节点，从节点加载 RDB 后，再接收复制期间产生的写命令。短暂断线重连时，如果主节点复制积压缓冲区中还保留从节点缺失的数据，则可以通过 `PSYNC` 进行增量复制。

Redis 主从复制默认是异步的，因此会存在主从延迟和极端情况下的数据丢失问题。如果要自动故障转移，需要配合 Sentinel 或 Redis Cluster。

一句话总结：

```text
Redis 复制 = 主节点写数据，从节点同步数据；
核心机制 = PSYNC + offset + runId + replication backlog；
复制方式 = 全量复制 + 增量复制。
```
