# 高可用系统设计总结

高可用系统的核心目标是：**系统出现部分故障时，仍然能够对外提供服务，避免单点故障导致整体不可用**。

核心思路：

```text
避免单点
  ↓
故障隔离
  ↓
自动切换
  ↓
限流熔断
  ↓
降级兜底
  ↓
监控告警
  ↓
故障恢复
```

---

## 1. 高可用系统核心目标

| 目标 | 说明 |
|---|---|
| 避免单点故障 | 任意单个节点故障不影响整体服务 |
| 故障自动转移 | 某个节点异常后自动切换到可用节点 |
| 服务隔离 | 防止局部故障扩散到整个系统 |
| 快速恢复 | 故障后可以快速恢复服务 |
| 降级兜底 | 核心功能优先可用，非核心功能可降级 |
| 可观测性 | 能及时发现问题、定位问题、处理问题 |

---

## 2. 整体架构设计

```text
用户请求
  ↓
DNS / CDN
  ↓
负载均衡 SLB / Nginx
  ↓
网关集群
  ↓
业务服务集群
  ↓
缓存集群 Redis
  ↓
消息队列集群 MQ
  ↓
数据库主从 / 集群
```

核心原则：

```text
所有核心组件都要集群部署
所有关键链路都要有降级方案
所有外部依赖都要有超时和熔断
```

---

## 3. 应用服务高可用

### 实现方式

业务服务必须多实例部署。

```text
order-service-1
order-service-2
order-service-3
```

通过注册中心和负载均衡进行调用。

```text
请求
  ↓
负载均衡
  ↓
健康实例
```

### 关键点

- 服务无状态化。
- 多实例部署。
- 注册中心服务发现。
- 健康检查。
- 故障实例自动摘除。
- 支持水平扩容。
- 支持优雅上下线。

---

## 4. 网关高可用

网关是系统入口，不能单点部署。

```text
Nginx / SLB
  ↓
Gateway-1
Gateway-2
Gateway-3
```

网关需要支持：

- 多实例部署。
- 动态路由。
- 限流。
- 熔断。
- 黑白名单。
- 认证鉴权。
- 灰度发布。
- 监控告警。

注意：

```text
网关要无状态，不能保存登录态和业务状态。
```

---

## 5. 注册中心高可用

注册中心负责服务发现。

常见方案：

```text
Nacos 集群
ZooKeeper 集群
Consul 集群
Eureka 集群
```

关键点：

- 多节点部署。
- 客户端本地缓存服务列表。
- 注册中心异常时，已有调用尽量不受影响。
- 服务上下线要能及时感知。
- 注册中心不能参与每次业务调用。

---

## 6. 配置中心高可用

配置中心用于动态管理配置。

设计要点：

- 配置中心集群部署。
- 客户端本地缓存配置快照。
- 配置发布支持版本管理。
- 配置错误支持快速回滚。
- 重要配置变更要灰度发布。
- 配置中心不可用时，应用能使用本地缓存启动或运行。

---

## 7. 缓存高可用

Redis 不能单节点部署。

常见方案：

| 方案 | 说明 |
|---|---|
| 主从复制 | 主节点写，从节点读 |
| Sentinel | 主节点故障后自动选主 |
| Redis Cluster | 分片集群，支持水平扩展 |
| 多级缓存 | 本地缓存 + Redis |

### 关键问题

- Redis 宕机怎么办。
- 热 Key 打爆怎么办。
- 缓存穿透怎么办。
- 缓存雪崩怎么办。
- 缓存和数据库不一致怎么办。

### 解决方式

```text
Redis 集群
本地缓存兜底
热点 Key 拆分
缓存空值
布隆过滤器
过期时间加随机值
限流降级
```

---

## 8. 数据库高可用

数据库是系统核心，必须重点设计。

### 常见方案

| 方案 | 说明 |
|---|---|
| 主从复制 | 主库写，从库读 |
| 读写分离 | 分担主库读压力 |
| 一主多从 | 提高读能力 |
| MHA / Keepalived | 主库故障切换 |
| 分库分表 | 解决单库单表瓶颈 |
| 数据备份 | 防止数据丢失 |
| 多机房容灾 | 应对机房级故障 |

### 注意点

- 主从延迟。
- 故障切换期间短暂不可用。
- 数据备份和恢复演练。
- 分库分表后的扩容和迁移。
- 核心交易数据要保证一致性。

---

## 9. MQ 高可用

消息队列用于异步解耦和削峰填谷，也要高可用。

常见方案：

```text
Kafka 多 Broker + 多副本
RocketMQ 多 Master / 主从
RabbitMQ 镜像队列 / Quorum Queue
```

关键点：

- Broker 集群部署。
- Topic / Queue 多副本。
- Producer 发送失败重试。
- Consumer 消费失败重试。
- 消费端幂等。
- 死信队列。
- 消息补偿。
- 消息积压监控。

---

## 10. 限流设计

限流用于防止突发流量打垮系统。

常见限流位置：

```text
网关限流
接口限流
用户限流
IP 限流
服务端限流
```

常见算法：

```text
固定窗口
滑动窗口
漏桶
令牌桶
并发数限制
```

常见实现：

```text
Redis + Lua
Sentinel
Resilience4j
Guava RateLimiter
网关限流
```

## 11. 熔断设计

当下游服务异常时，要快速失败，防止请求持续堆积。

流程：

```text
调用下游失败率升高
  ↓
达到阈值
  ↓
熔断器打开
  ↓
请求直接失败或返回兜底
  ↓
一段时间后半开探测
  ↓
恢复正常后关闭熔断
```

适用场景：

- 下游服务超时。
- 下游错误率过高。
- 第三方接口不稳定。
- 数据库或缓存压力过大。

---

## 12. 降级设计

降级是指在系统压力大或依赖异常时，关闭非核心功能，保证核心链路可用。

### 可降级功能

```text
推荐系统
排行榜
评论
非核心统计
短信通知
优惠券推荐
个性化展示
```

### 核心功能

```text
登录
下单
支付
退款
库存扣减
```

设计原则：

```text
保核心，降非核心。
```

---

## 13. 隔离设计

隔离用于防止一个模块拖垮整个系统。

常见隔离方式：

| 隔离方式 | 说明 |
|---|---|
| 线程池隔离 | 不同业务使用不同线程池 |
| 连接池隔离 | 不同下游使用不同连接池 |
| 服务隔离 | 核心服务和非核心服务拆开 |
| 数据库隔离 | 核心库和日志库分离 |
| 缓存隔离 | 核心缓存和非核心缓存分开 |
| 机房隔离 | 多机房容灾 |

示例：

```text
支付线程池
订单线程池
通知线程池
报表线程池
```

避免：

```text
报表慢查询拖垮支付链路
```

---

## 14. 超时和重试

所有远程调用必须设置超时。

```text
HTTP 超时
RPC 超时
Redis 超时
DB 超时
MQ 超时
第三方接口超时
```

### 重试注意点

- 查询接口可以适当重试。
- 写接口重试必须保证幂等。
- 不要无限重试。
- 避免重试风暴。
- 重试要配合退避策略。

推荐：

```text
超时 + 有限重试 + 幂等 + 熔断
```

---

## 15. 幂等设计

高可用系统中，失败重试和消息重复投递很常见，所以必须保证幂等。

常见方案：

```text
请求唯一 ID
数据库唯一索引
Redis SETNX
状态机
乐观锁
消费记录表
业务唯一键
```

示例：

```sql
UPDATE t_order
SET status = 'PAID'
WHERE order_no = ?
AND status = 'WAIT_PAY';
```

## 16. 多机房容灾

当单个机房故障时，系统仍能提供服务。

常见模式：

| 模式 | 说明 |
|---|---|
| 同城双活 | 两个机房同时提供服务 |
| 两地三中心 | 两个城市三个中心 |
| 异地灾备 | 主机房故障后切换到备机房 |
| 单元化架构 | 按用户或地域划分流量单元 |

### 关键点

- 流量切换。
- 数据同步。
- 数据一致性。
- 跨机房延迟。
- 故障演练。

---

## 17. 优雅上下线

服务发布或扩缩容时，要避免请求失败。

### 优雅上线

```text
服务启动
  ↓
完成初始化
  ↓
注册到注册中心
  ↓
开始接收流量
```

### 优雅下线

```text
从注册中心摘除实例
  ↓
停止接收新请求
  ↓
等待存量请求处理完成
  ↓
关闭线程池和连接
  ↓
停止服务
```

## 19. 故障演练

高可用不是设计出来就结束，必须演练验证。

常见演练：

```text
服务实例宕机

数据库主库切换

注册中心不可用
机房网络故障

```

目标：

```text
验证系统是否能自动恢复
验证告警是否及时
验证降级预案是否有效
```

---

## 20. 总结

设计高可用系统，核心是避免单点故障，并在故障发生时能够快速隔离、自动切换和降级兜底。

应用服务要无状态化、多实例部署，通过注册中心和负载均衡实现故障转移；网关、注册中心、配置中心、Redis、MQ、数据库等核心组件都要集群化部署。

同时要做好限流、熔断、降级、线程池隔离、超时重试和幂等设计，防止局部故障扩散成全局故障。

最后还要建设监控告警、日志追踪、故障演练和容灾恢复能力，保证问题能被及时发现、快速定位和有效恢复。

一句话总结：

```text
高可用系统设计 = 去单点 + 集群部署 + 故障转移 + 限流熔断 + 降级隔离 + 监控告警 + 容灾演练。
```
