# 接口加密和验签总结

接口加密和验签主要用于保证接口调用的：

```text
机密性：数据不能被别人看到
完整性：数据不能被篡改
身份可信：确认请求来自合法调用方
防重放：防止请求被抓包后重复提交
```

---

## 1. 加密和验签的区别

| 能力 | 作用 | 解决问题 |
|---|---|---|
| 加密 | 对请求或响应内容加密 | 防止数据泄露 |
| 签名 | 对请求参数生成摘要签名 | 防止参数被篡改 |
| 验签 | 服务端校验签名是否正确 | 确认请求合法 |
| 时间戳 + 随机数 | 防止重复请求 | 防重放攻击 |

简单理解：

```text
加密解决“别人看不懂”
签名解决“别人改不了”
时间戳和 nonce 解决“别人不能重复用”
```

---

## 2. 常见使用场景

- 开放平台接口。
- 支付回调接口。
- 第三方系统对接。
- App 和服务端通信。
- 内部敏感接口。
- 金融、交易、账户类接口。
- 防止请求参数被篡改。

---

## 3. 常见加密方式

## 3.1 对称加密

### 原理

加密和解密使用同一个密钥。

```text
明文 + secretKey -> 密文
密文 + secretKey -> 明文
```

常见算法：

```text
AES
DES
3DES
```

推荐：

```text
AES
```

### 优势

- 加解密速度快。
- 适合大数据量加密。
- 实现相对简单。

### 劣势

- 密钥分发困难。
- 双方都持有同一个密钥，泄露风险较高。

### 适用场景

```text
请求体加密
响应体加密
内部系统通信
```

---

## 3.2 非对称加密

### 原理

使用一对密钥：

```text
公钥加密，私钥解密
私钥签名，公钥验签
```

常见算法：

```text
RSA
ECC
```

### 优势

- 安全性更高。
- 私钥不需要传输。
- 适合身份认证和签名。

### 劣势

- 性能比对称加密差。
- 不适合加密大量数据。

### 适用场景

```text
签名验签
密钥交换
开放平台接口
支付接口
```

---

## 3.3 混合加密

实际项目中常用：

```text
AES 加密业务数据
RSA 加密 AES 密钥
RSA / HMAC 做签名
```

流程：

```text
1. 客户端生成 AES 密钥。
2. 使用 AES 加密请求体。
3. 使用服务端公钥加密 AES 密钥。
4. 使用私钥或 secret 生成签名。
5. 服务端解密 AES 密钥。
6. 服务端解密请求体。
7. 服务端验签。
```

优点：

```text
兼顾安全性和性能。
```

## 4. 常见签名方式

## 4.1 MD5 签名

### 原理

把参数拼接后加密钥，再做 MD5。

```text
sign = MD5(paramString + secret)
```

### 优势

- 简单。
- 性能高。

### 劣势

- 安全性较弱。
- 不推荐用于高安全场景。

---

## 4.2 HMAC-SHA256

### 原理

使用共享密钥对参数做 HMAC 摘要。

```text
sign = HMAC_SHA256(paramString, secret)
```

### 优势

- 安全性比 MD5 好。
- 性能较好。
- 开放 API 常用。

### 适用场景

```text
开放平台接口
内部系统接口
第三方接口验签
```

---

## 4.3 RSA 签名

### 原理

调用方使用私钥签名，服务端使用公钥验签。

```text
客户端：私钥签名
服务端：公钥验签
```

### 优势

- 安全性高。
- 不需要共享私钥。
- 适合开放平台和支付接口。

### 劣势

- 性能比 HMAC 差。
- 证书和密钥管理更复杂。

---

## 5. 签名参数设计

常见请求参数：

| 参数 | 说明 |
|---|---|
| `appId` | 调用方身份 |
| `timestamp` | 请求时间戳 |
| `nonce` | 随机字符串 |
| `sign` | 签名 |
| `data` | 加密后的业务数据 |
| `version` | 接口版本 |
| `signType` | 签名算法 |

示例：

```json
{
  "appId": "client_1001",
  "timestamp": 1710000000000,
  "nonce": "abc123xyz",
  "signType": "HMAC-SHA256",
  "data": "加密后的业务数据",
  "sign": "xxxxxx"
}
```

---

## 6. 签名生成流程

```text
1. 去除 sign 字段。
2. 过滤空值参数。
3. 按参数名 ASCII 升序排序。
4. 拼接成 key=value&key=value 格式。
5. 拼接 secret 或使用 secret 做 HMAC。
6. 生成 sign。
7. 将 sign 放入请求中。
```

示例：

```text
appId=client_1001&data=xxx&nonce=abc123&timestamp=1710000000000
```

生成签名：

```text
sign = HMAC_SHA256(待签名字符串, secret)
```

---

## 7. 服务端验签流程

```text
请求进入服务端
  ↓
校验 appId 是否存在
  ↓
根据 appId 获取 secret / publicKey
  ↓
校验 timestamp 是否过期
  ↓
校验 nonce 是否已使用
  ↓
按同样规则重新生成签名
  ↓
对比客户端传入 sign
  ↓
一致：验签通过
  ↓
不一致：拒绝请求
```

---

## 8. 防重放设计

攻击者可能抓包后重复请求。

解决方案：

```text
timestamp + nonce + Redis
```

### 校验时间戳

例如只允许 5 分钟内的请求：

```text
当前时间 - timestamp <= 5 分钟
```

超过时间直接拒绝。

---

### 校验 nonce

每个请求生成唯一随机字符串：

```text
nonce = UUID
```

服务端存 Redis：

```text
api:nonce:{appId}:{nonce} = 1
TTL = 5 分钟
```

使用 `SETNX` 判断是否重复：

```text
SET api:nonce:client_1001:abc123 1 NX EX 300
```

如果写入失败：

```text
说明 nonce 已使用，拒绝请求
```

---

## 9. 请求体加密设计

如果业务数据敏感，可以加密请求体。

流程：

```text
原始业务参数 JSON
  ↓
AES 加密
  ↓
得到 data
  ↓
对 appId、timestamp、nonce、data 签名
  ↓
发送请求
```

服务端：

```text
验签
  ↓
解密 data
  ↓
执行业务逻辑
```

注意：

```text
建议先验签，再解密。
```

避免无效请求消耗解密资源。

---

## 10. 响应加密和签名

如果响应数据也敏感，可以对响应加密并签名。

```json
{
  "code": 0,
  "timestamp": 1710000000000,
  "data": "加密后的响应数据",
  "sign": "响应签名"
}
```

客户端收到后：

```text
校验响应签名
  ↓
解密 data
  ↓
读取业务结果
```

## 11. 接口验签放在哪里

常见实现位置：

| 位置 | 说明 |
|---|---|
| 网关 | 统一处理外部接口验签 |
| Filter | 适合 Web 层统一校验 |
| Interceptor | 适合 Spring MVC 接口校验 |
| AOP | 适合注解式细粒度控制 |
| SDK | 调用方统一生成签名 |

推荐：

```text
开放接口：网关 / Filter 统一验签
内部特殊接口：AOP 注解控制
```

## 12. 安全设计要点

- 必须使用 HTTPS。
- 密钥不能硬编码在前端。
- `secret` 要定期轮换。
- `timestamp` 要限制有效期。
- `nonce` 要防重复。
- 签名字段不要参与签名。
- 参数排序规则必须统一。
- JSON 序列化顺序要稳定。
- 敏感数据不要明文传输。
- 加密不能替代验签。
- 验签不能替代权限校验。
- 签名失败要记录安全日志。

## 13. 常见问题

### 1. 有 HTTPS 还需要加密和验签吗？

看场景。

```text
HTTPS 解决传输安全
接口加密和验签解决应用层安全
```

如果是普通业务接口，HTTPS 通常够用。

如果是支付、开放平台、金融、第三方对接，通常还需要：

```text
签名 + 时间戳 + nonce + 必要的数据加密
```

---

### 2. 加密和签名哪个先做？

常见做法：

```text
先加密 data
再对 data 和公共参数做签名
```

服务端：

```text
先验签
再解密
```

---

### 3. MD5 能不能做签名？

可以做简单场景，但不推荐高安全场景。

推荐：

```text
HMAC-SHA256
RSA-SHA256
```

---

### 4. 如何防止参数被篡改？

```text
把所有关键参数都参与签名。
```

只要参数被改，服务端重新计算出的签名就会不一致。

---

## 14. 推荐方案

### 内部系统接口

```text
HTTPS + HMAC-SHA256 + timestamp + nonce
```

---

### 开放平台接口

```text
HTTPS + appId/appSecret + HMAC-SHA256 + timestamp + nonce + IP 白名单
```

---

### 支付 / 金融接口

```text
HTTPS + RSA 签名验签 + AES 加密报文 + timestamp + nonce + 证书管理
```

---

## 15. 总结

接口加密和验签主要是为了保证数据机密性、完整性、身份可信和防重放。

加密用于保护数据内容不被看到，常见方式有 AES、RSA，实际项目中常用 AES 加密业务数据，再用 RSA 加密 AES 密钥。签名用于防止参数被篡改，常见方式有 HMAC-SHA256 和 RSA-SHA256。

验签时，服务端会根据 `appId` 找到对应密钥，然后去掉 `sign` 字段，对参数排序拼接，重新计算签名并和客户端签名对比。同时通过 `timestamp` 控制请求有效期，通过 `nonce + Redis SETNX` 防止重放攻击。

一句话总结：

```text
接口安全 = HTTPS + 参数签名 + 请求体加密 + timestamp 防过期 + nonce 防重放 + 密钥管理。
```
