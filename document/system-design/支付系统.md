# 支付系统设计总结

支付系统的核心目标是：**安全、准确、稳定地完成支付，并保证订单、支付单、账户、渠道状态最终一致**。

核心原则：

```text
支付系统不能只关注支付成功
还要处理失败、超时、重复回调、退款、对账、补偿和风控
```

---

## 1. 支付系统核心功能

| 功能 | 说明 |
|---|---|
| 支付下单 | 创建支付单，发起支付 |
| 支付渠道 | 对接微信、支付宝、银行卡、余额等 |
| 支付回调 | 接收第三方支付结果通知 |
| 支付查询 | 主动查询渠道支付状态 |
| 支付关闭 | 超时未支付关闭支付单 |
| 退款 | 支持原路退款、部分退款 |
| 对账 | 和支付渠道账单核对 |
| 补偿 | 异常订单自动修复 |
| 幂等 | 防止重复支付、重复回调、重复退款 |
| 风控 | 防刷、防盗刷、限额、黑名单 |
| 账务 | 记录资金流水和账户变动 |

## 3. 支付下单流程

```text
用户提交支付请求
  ↓
校验订单是否存在
  ↓
校验订单是否待支付
  ↓
校验金额是否正确
  ↓
创建支付单 payment_order
  ↓
调用支付渠道预下单接口
  ↓
返回支付参数给前端
  ↓
用户完成支付
```

关键点：

```text
一个业务订单可以对应一个或多个支付单
但最终只能有一个支付单成功
```

例如用户第一次微信支付未完成，又切换支付宝支付，就可能生成新的支付单。

---

## 4. 支付回调流程

第三方支付成功后，会异步通知支付系统。

```text
支付渠道回调
  ↓
验签
  ↓
校验金额
  ↓
校验支付单状态
  ↓
更新支付单为 SUCCESS
  ↓
更新业务订单为 PAID
  ↓
记录支付流水
  ↓
发送支付成功消息
  ↓
返回渠道成功响应
```

注意：

```text
支付回调一定要幂等
不能因为重复回调导致重复改状态、重复发货、重复加积分
```

---

## 5. 支付回调幂等设计

支付渠道可能重复回调。

核心做法：

```sql
UPDATE payment_order
SET status = 'SUCCESS',
    pay_time = NOW(),
    channel_trade_no = ?
WHERE pay_no = ?
AND status IN ('INIT', 'PAYING');
```

如果影响行数为 `1`：

```text
第一次处理成功
继续更新订单、发送消息
```

如果影响行数为 `0`：

```text
说明已经处理过
直接返回成功给渠道
```

---

## 6. 订单和支付状态一致性

支付成功后，需要同时更新：

```text
支付单状态
业务订单状态
支付流水
后续业务消息
```

推荐使用：

```text
本地事务 + MQ 最终一致
```

流程：

```text
本地事务中：
1. 更新支付单成功
2. 更新订单成功
3. 写支付流水
4. 写本地消息表

事务提交后：
5. 异步发送支付成功 MQ
6. 下游处理发货、积分、通知等逻辑
```

---

## 7. 为什么不能只依赖支付回调

支付渠道回调可能出现：

```text
回调丢失
回调延迟
回调重复
回调验签失败
业务系统处理失败
```

所以必须补充：

```text
主动查询 + 定时补偿
```

---

## 8. 支付查询和补偿

### 主动查询流程

```text
定时扫描 PAYING 状态支付单
  ↓
调用渠道查询接口
  ↓
如果渠道已支付成功
  ↓
执行和回调一样的成功处理逻辑
```

注意：

```text
回调和主动查询必须共用同一套幂等更新逻辑
```

---

### 补偿任务

适合处理：

```text
支付回调失败
MQ 发送失败
订单状态未更新
支付单和订单状态不一致
```

补偿逻辑：

```text
扫描异常数据
  ↓
查询渠道真实状态
  ↓
根据真实状态修复本地数据
```

---

## 9. 超时关闭支付

如果用户长时间未支付，需要关闭支付单和订单。

```text
创建订单
  ↓
创建支付单
  ↓
发送延迟消息
  ↓
到期后检查支付状态
  ↓
如果仍未支付，则关闭支付单和订单
```

关闭时必须判断状态：

```sql
UPDATE payment_order
SET status = 'CLOSED'
WHERE pay_no = ?
AND status IN ('INIT', 'PAYING');
```

如果用户已支付成功，则不能关闭。

---

## 10. 支付和关闭并发问题

可能出现：

```text
支付回调成功
同时超时任务关闭支付单
```

解决方式：

```text
状态机 + 条件更新
```

支付成功：

```sql
UPDATE payment_order
SET status = 'SUCCESS'
WHERE pay_no = ?
AND status IN ('INIT', 'PAYING');
```

关闭支付：

```sql
UPDATE payment_order
SET status = 'CLOSED'
WHERE pay_no = ?
AND status IN ('INIT', 'PAYING');
```

谁先更新成功，谁生效。

## 11. 退款流程

```text
用户申请退款
  ↓
校验订单是否可退款
  ↓
创建退款单
  ↓
调用支付渠道退款接口
  ↓
渠道返回退款处理中
  ↓
等待退款回调或主动查询
  ↓
更新退款单状态
  ↓
更新订单退款状态
  ↓
记录退款流水
```

退款也必须幂等。

退款单唯一键：

```text
refund_no
```

或者：

```text
order_no + refund_request_no
```

防止重复发起退款。

## 12. 对账设计

支付系统必须做对账。

### 为什么需要对账

可能出现：

```text
渠道扣款成功，本地支付失败
本地支付成功，渠道实际失败
退款状态不一致
金额不一致
手续费不一致
```

### 对账流程

```text
下载渠道账单
  ↓
解析账单
  ↓
和本地支付流水比对
  ↓
生成差异记录
  ↓
自动补偿或人工处理
```

对账结果：

```text
平账
长款
短款
金额不一致
本地有渠道无
渠道有本地无
```

## 18. 支付系统完整流程

```text
支付前：
1. 用户创建订单。
2. 创建支付单。
3. 调用支付渠道预下单。
4. 返回支付参数。

支付中：
5. 用户完成支付。
6. 渠道异步回调。
7. 支付系统验签、校验金额。
8. 更新支付单和订单状态。
9. 发送支付成功 MQ。

支付后：
10. 下游处理发货、积分、通知。
11. 定时任务查询异常支付单。
12. 对账任务核对渠道账单。
13. 对异常数据进行补偿。
```

---

## 19. 总结

支付系统设计的核心是保证支付状态准确、安全和最终一致。

用户发起支付时，系统先创建业务订单和支付单，再调用支付渠道生成支付参数。支付成功后，第三方渠道会异步回调支付系统，支付系统必须先验签，再校验金额和订单状态，然后通过状态机条件更新保证幂等，最后更新支付单、业务订单并发送支付成功消息。

由于支付回调可能丢失、延迟或重复，所以不能只依赖回调，还需要主动查询、定时补偿和对账机制。退款、关闭支付、MQ 消费等场景也都必须保证幂等。

一句话总结：

```text
支付系统设计 = 支付单 + 状态机 + 渠道回调 + 幂等处理 + 主动查询 + MQ 最终一致 + 对账补偿 + 安全风控。
```
