# 一、下载中心是什么

下载中心是一个用于统一管理文件导出、文件生成、文件存储、下载记录和下载权限的系统模块。

用户发起导出请求后，系统不一定立即返回文件，而是先创建一个下载任务。

后台异步生成文件，生成完成后用户再到下载中心下载。

典型流程：

```text
用户发起导出
    |
    v
创建下载任务
    |
    v
后台异步生成文件
    |
    v
上传到文件服务器 / OSS
    |
    v
更新任务状态为已完成
    |
    v
用户到下载中心下载文件
```

---

# 二、为什么需要下载中心

## 1. 普通同步下载的问题

如果用户点击导出后，接口直接同步生成文件并返回，可能会有很多问题：

```text
1. 接口耗时长
2. 浏览器容易超时
3. Nginx 网关容易超时
4. 大数据量导出容易 OOM
5. 多个用户同时导出会拖垮数据库
6. 导出失败后无法追踪
7. 用户关闭页面后任务中断
8. 无法统一管理历史下载文件
9. 无法做权限、审计和清理
```

---

## 2. 下载中心解决什么问题

下载中心主要解决：

```text
1. 大文件异步导出
2. 下载任务统一管理
3. 用户可查看导出进度
4. 文件生成失败可重试
5. 文件下载权限可控制
6. 文件过期可自动清理
7. 避免接口长时间阻塞
8. 降低数据库和应用服务压力
9. 支持审计和操作追踪
```

---

## 3. 核心思想

下载中心的核心思想是：

```text
同步请求变异步任务；
实时生成变后台处理；
直接返回文件变返回任务编号；
文件临时生成变统一存储管理。
```

# 六、核心业务流程

## 1. 创建下载任务流程

```text
1. 用户点击导出
2. 前端提交导出条件
3. 后端校验用户权限
4. 后端校验导出参数
5. 判断是否重复提交
6. 创建下载任务，状态为 WAITING
7. 发送 MQ 消息
8. 返回 taskId 给前端
9. 前端展示任务处理中
```

---

## 2. 后台生成文件流程

```text
1. Worker 消费下载任务消息
2. 查询下载任务
3. 判断任务状态是否为 WAITING
4. 更新状态为 PROCESSING
5. 分页查询业务数据
6. 流式写入 Excel / CSV
7. 文件生成完成
8. 上传到 OSS / MinIO
9. 更新任务状态为 SUCCESS
10. 发送通知
```

---

## 3. 用户下载流程

```text
1. 用户进入下载中心
2. 查询自己的下载任务列表
3. 点击下载
4. 后端校验权限
5. 判断任务是否成功
6. 判断文件是否过期
7. 生成临时下载 URL
8. 返回给前端
9. 用户下载文件
```

---

## 4. 失败重试流程

```text
1. 任务执行失败
2. 记录失败原因
3. retry_count + 1
4. 如果未超过最大重试次数，重新投递 MQ
5. 如果超过最大重试次数，状态改为 FAILED
6. 用户可以手动重试或重新创建任务
```

```sql
CREATE TABLE download_task (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT DEFAULT NULL,
    task_no VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    task_type VARCHAR(64) NOT NULL,
    task_name VARCHAR(255) NOT NULL,
    request_param TEXT,
    file_name VARCHAR(255) DEFAULT NULL,
    file_path VARCHAR(512) DEFAULT NULL,
    file_size BIGINT DEFAULT NULL,
    file_md5 VARCHAR(64) DEFAULT NULL,
    status TINYINT NOT NULL,
    progress INT DEFAULT 0,
    total_count BIGINT DEFAULT 0,
    success_count BIGINT DEFAULT 0,
    fail_reason TEXT,
    retry_count INT DEFAULT 0,
    expire_time DATETIME DEFAULT NULL,
    start_time DATETIME DEFAULT NULL,
    finish_time DATETIME DEFAULT NULL,

    INDEX idx_user_status(user_id, status),
```

# 八、任务状态如何设计

## 1. 状态枚举

下载任务状态可以设计为：

```text
WAITING：等待处理
PROCESSING：处理中
SUCCESS：处理成功
FAILED：处理失败
CANCELLED：已取消
EXPIRED：已过期
DELETED：已删除
```

---

## 2. 状态流转

```text
WAITING -> PROCESSING
PROCESSING -> SUCCESS
PROCESSING -> FAILED
WAITING -> CANCELLED
PROCESSING -> CANCELLED
SUCCESS -> EXPIRED
SUCCESS -> DELETED
FAILED -> WAITING
```

---

## 3. 状态流转图

```text
创建任务
   |
   v
WAITING
   |
   v
PROCESSING
   |
   |----> SUCCESS ----> EXPIRED
   |
   |----> FAILED ----> WAITING
   |
   |----> CANCELLED
```

---

## 4. 状态更新要带条件

更新状态时要带旧状态，防止并发问题。

例如：

```sql
UPDATE download_task
SET status = 1,
    start_time = NOW()
WHERE id = ?
  AND status = 0;
```

含义：

```text
只有 WAITING 状态才能变成 PROCESSING。
```

# 十、大文件导出如何优化

## 1. 大文件导出风险

大文件导出常见风险：

```text
1. 一次性查询大量数据导致数据库压力大
2. 一次性放入内存导致 OOM
3. 接口响应超时
4. 文件生成时间长
5. 多任务并发导致 CPU 和磁盘 IO 高
6. 生成失败无法恢复
```

---

## 2. 分页查询

不要一次性查询全部数据。

错误方式：

```java
List<Order> list = orderMapper.selectAll();
```

正确方式：

```text
按分页查询；
每页查询 1000 条或 5000 条；
边查边写文件。
```

---

## 3. 游标分页

如果数据量很大，避免深分页。

可以使用游标分页：

```sql
SELECT *
FROM orders
WHERE id > #{lastId}
ORDER BY id
LIMIT 1000;
```

每次记录最后一条 ID。

---

## 4. 流式写入

生成文件时不要把全部数据放入内存。

正确方式：

```text
查询一页
写入一页
清理内存
继续下一页
```

---

## 5. 控制导出字段

不要导出不必要字段。

例如订单导出只需要：

```text
订单号
用户名称
订单金额
订单状态
创建时间
支付时间
```

不要直接导出整个订单对象。

---

## 6. 限制最大导出数量

必须限制单次导出最大数据量。

例如：

```text
普通用户最多导出 10 万条
管理员最多导出 100 万条
超过限制提示缩小筛选条件
```

---

## 7. 使用只读库

大批量导出可以走只读库，避免影响主库。

```text
普通查询 -> 主库或从库
大报表导出 -> 从库 / 报表库
```

---

## 8. 大文件压缩

对于大文件，可以压缩后下载：

```text
CSV -> ZIP
Excel -> ZIP
多个文件 -> ZIP
```

# 十一、如何防止重复提交

## 1. 重复提交场景

```text
用户连续点击导出按钮
前端请求超时重试
网关重试
页面刷新重复提交
同一个条件多次导出
```

---

## 2. 解决方案

```text
1. 前端按钮置灰
2. Redis SET NX 防重复
3. requestId 幂等
4. 相同用户 + 相同任务类型 + 相同参数去重
5. 数据库唯一约束
```

---

## 3. Redis 防重复

生成任务前，构造幂等 Key：

```text
download:submit:{tenantId}:{userId}:{taskType}:{paramMd5}
```

使用：

```bash
SET download:submit:1001:2001:ORDER_EXPORT:abc123 1 NX EX 60
```

如果设置成功，允许创建任务。

如果设置失败，说明短时间内重复提交。

---

## 4. 参数 MD5

将导出参数 JSON 排序后计算 MD5：

```text
paramMd5 = md5(taskType + userId + sortedRequestParam)
```

这样可以识别相同条件的重复导出。

# 十二、如何保证接口幂等

## 1. 创建任务接口幂等

前端提交时携带：

```text
requestId
```

后端基于 `requestId` 做幂等。

表中增加：

```sql
request_id VARCHAR(128)
```

唯一索引：

```sql
UNIQUE KEY uk_request_id(request_id)
```

重复请求时：

```text
如果任务已经存在，直接返回原 taskId。
```

---

## 2. MQ 消费幂等

Worker 消费任务消息时，不能重复执行同一个任务。

可以通过状态机控制：

```sql
UPDATE download_task
SET status = PROCESSING
WHERE id = ?
  AND status = WAITING;
```

如果更新行数为 1，说明抢占任务成功。

如果更新行数为 0，说明任务已经被其他 Worker 处理，不再重复执行。

---

## 3. 下载接口幂等

用户重复点击下载是允许的。

每次下载可以记录一条下载日志，但不能重复生成文件。

下载接口只负责：

```text
权限校验
状态校验
返回文件地址
记录下载行为
```

---

# 十三、如何保证任务可靠执行

## 1. 任务可靠性问题

可能出现：

```text
1. 任务创建成功，但 MQ 发送失败
2. MQ 消息发送成功，但 Worker 消费失败
3. Worker 执行过程中宕机
4. 文件生成成功，但上传 OSS 失败
5. 上传成功，但数据库状态更新失败
6. 任务一直卡在 PROCESSING
```

---

## 2. 解决方案

```text
1. 本地消息表
2. MQ 发送确认
3. 消费失败重试
4. 任务状态机
5. Worker 抢占任务
6. 超时任务补偿
7. 失败任务可重试
8. 文件上传后校验
```

---

## 3. 创建任务和发送消息一致性

推荐本地消息表方案：

```text
1. 创建 download_task
2. 插入 local_message
3. 本地事务提交
4. 后台任务扫描 local_message
5. 发送 MQ
6. 成功后更新消息状态
7. 失败继续重试
```

---

## 4. PROCESSING 超时补偿

如果任务长时间处于 `PROCESSING`，可能是 Worker 宕机。

定时任务扫描：

```sql
SELECT *
FROM download_task
WHERE status = PROCESSING
  AND update_time < NOW() - INTERVAL 30 MINUTE;
```

处理方式：

```text
1. retry_count 未超限，重置为 WAITING
2. 重新投递 MQ
3. 超过重试次数，标记 FAILED
```

---

# 十四、如何保证文件安全

## 1. 文件安全风险

```text
1. 用户越权下载别人的文件
2. 文件 URL 泄露后长期可访问
3. 敏感数据导出无审计
4. 文件未加密存储
5. 多租户文件路径串租户
6. 下载链接被盗用
```

---

## 2. 安全设计

```text
1. 下载前校验用户权限
2. 文件 URL 不直接暴露真实路径
3. 使用临时下载链接
4. 设置 URL 过期时间
5. 敏感文件可加密
6. 下载行为记录审计日志
7. 文件路径带 tenantId
8. OSS Bucket 设置私有读
```

---

## 3. 临时 URL

下载时后端生成短期有效 URL：

```text
有效期 5 分钟
只能当前用户访问
过期后重新申请
```

---

## 4. 后端流式转发

更安全的方式是后端校验权限后流式转发文件：


# 二十六、完整面试回答模板

如果让我设计一个下载中心，我会把它设计成异步任务模式。因为很多导出场景，比如订单导出、报表导出、对账单下载，数据量比较大，如果同步生成文件并返回，很容易出现接口超时、网关超时、内存溢出、数据库压力过大等问题。所以下载中心的核心思路是：用户提交导出请求后，系统先创建下载任务，然后通过 MQ 异步交给后台 Worker 生成文件，生成完成后上传到 OSS 或文件服务器，最后用户到下载中心下载。

整体流程是：用户点击导出，后端先校验权限和参数，然后创建一条 `download_task` 记录，状态为 `WAITING`，接着发送 MQ 消息并返回 `taskId`。Worker 消费消息后，通过状态机把任务从 `WAITING` 更新为 `PROCESSING`，抢占成功后开始执行导出。导出时分页查询业务数据，流式写入 Excel、CSV 或 PDF，文件生成完成后上传到 OSS，然后更新任务状态为 `SUCCESS`，记录文件名、文件路径、文件大小、过期时间等信息。用户进入下载中心后，可以看到任务状态，成功后点击下载。

数据库上，我会设计一张下载任务表，核心字段包括 `tenant_id`、`task_no`、`user_id`、`task_type`、`task_name`、`request_param`、`file_name`、`file_path`、`file_size`、`status`、`progress`、`retry_count`、`fail_reason`、`expire_time`、`start_time` 和 `finish_time`。任务状态可以设计为等待处理、处理中、成功、失败、取消、过期和删除。状态更新时要带旧状态条件，比如只有 `WAITING` 状态才能更新为 `PROCESSING`，这样可以防止多个 Worker 重复执行同一个任务。

大文件导出时，不能一次性查询所有数据，也不能把所有数据放到内存中。正确方式是分页查询、游标分页、流式写文件。比如每次查询 1000 条或 5000 条数据，写入文件后释放内存，再继续查询下一批。对于数据量特别大的导出，可以限制最大导出条数，提示用户缩小筛选条件，也可以使用 CSV 替代复杂 Excel，或者走只读库、报表库，避免影响主库。

为了防止重复提交，前端可以做按钮置灰，后端可以基于 `requestId` 做幂等，也可以使用 Redis `SET NX`。比如根据用户 ID、任务类型和导出参数 MD5 生成幂等 Key，短时间内相同条件的导出只允许提交一次。如果用户重复提交相同请求，可以直接返回已有任务的 `taskId`。

为了保证任务可靠执行，需要考虑任务创建成功但 MQ 发送失败、Worker 执行中宕机、文件上传失败、数据库状态更新失败等情况。比较可靠的做法是使用本地消息表，创建下载任务和插入消息记录放在同一个本地事务中，然后由后台任务扫描消息表发送 MQ。Worker 消费失败可以重试，长时间卡在 `PROCESSING` 的任务可以由定时任务扫描出来，如果未超过最大重试次数，就重置为 `WAITING` 并重新投递 MQ，否则标记为失败。

下载安全方面，不能直接暴露永久文件地址。文件最好存储在私有 OSS 或 MinIO 中，下载时先校验当前用户是否有权限访问该任务，再生成短期有效的临时 URL，或者由后端流式转发文件。下载行为要记录审计日志，包括用户 ID、租户 ID、任务 ID、文件名、IP、User-Agent 和下载时间。对于包含手机号、身份证、财务数据等敏感字段的导出，还要做字段权限控制，没有权限的用户只能导出脱敏后的数据。

如果是多租户系统，下载任务表、缓存 Key、文件路径、MQ 消息都要带 `tenant_id`。例如文件路径可以设计成 `tenant/1001/download/2026/04/order_export.xlsx`，Redis Key 可以设计成 `tenant:1001:download:task:123`。Worker 消费 MQ 时，要从消息体中取出 `tenantId` 并设置到租户上下文，处理完成后在 `finally` 中清理，避免串租户。

下载中心还需要做资源控制，因为导出任务会消耗数据库、CPU、内存、磁盘 IO 和网络带宽。可以限制单用户同时运行任务数、单租户同时运行任务数、单次最大导出数量和 Worker 并发数。比如单用户最多同时 3 个任务，单租户最多 20 个任务，单次最多导出 10 万条。对于大租户或大任务，可以放到低峰期执行。

最后，还要设计过期清理机制。下载文件不应该永久保存，可以根据任务类型设置不同保留时间，比如普通导出保留 7 天，敏感文件保留 1 天，财务报表保留 30 天。定时任务扫描过期文件，删除 OSS 文件并更新任务状态为 `EXPIRED`。如果删除失败，记录日志并下次继续重试。

总结来说，下载中心的核心设计是异步任务、状态机、分页流式导出、统一文件存储、权限校验、幂等控制、失败重试、过期清理和监控告警。这样可以避免同步导出带来的超时和 OOM 问题，也能统一管理用户的下载任务和文件安全。
