# 一、注册登录模块是什么

注册登录模块是系统的入口模块，主要负责用户身份识别和访问控制。

它解决的问题是：

```text
1. 用户是谁
2. 用户是否允许登录
3. 用户登录后如何维持登录状态
4. 用户能访问哪些资源
5. 如何保证账号和登录过程安全
```

在管理系统、SaaS 系统、电商系统、企业后台中，注册登录通常是基础能力。

---

# 二、注册登录核心功能

注册登录模块一般包括以下功能：

```text
1. 用户注册
2. 用户登录
3. 图形验证码
4. 短信验证码
5. 邮箱验证码
6. 密码加密
7. Token 生成
8. Token 校验
9. 登录状态缓存
10. 退出登录
11. 刷新 Token
12. 登录日志
13. 登录失败次数限制
14. 账号锁定
15. 密码重置
16. 第三方登录
17. 单点登录
18. 权限加载
```

# 五、注册流程设计

## 1. 注册方式

常见注册方式：

```text
1. 用户名 + 密码注册
2. 手机号 + 短信验证码注册
3. 邮箱 + 邮箱验证码注册
4. 第三方账号注册
5. 管理员后台创建账号
```

管理系统中常见方式：

```text
管理员创建账号
手机号注册
邮箱注册
```

C 端系统中常见方式：

```text
手机号验证码注册
第三方登录自动注册
```

---

## 2. 用户名密码注册流程

```text
1. 用户填写用户名、手机号、密码、验证码
2. 后端校验图形验证码或短信验证码
3. 校验用户名是否已存在
4. 校验手机号是否已存在
5. 校验密码强度
6. 使用 BCrypt 加密密码
7. 保存用户信息
8. 初始化默认角色
9. 记录注册日志
10. 返回注册成功
```

---

## 3. 注册流程图

```text
用户提交注册信息
        |
        v
参数校验
        |
        v
验证码校验
        |
        v
用户名 / 手机号唯一性校验
        |
        v
密码 BCrypt 加密
        |
        v
保存用户
        |
        v
绑定默认角色
        |
        v
返回注册成功
```

---

## 4. 注册接口示例

```http
POST /api/auth/register
Content-Type: application/json

{
  "username": "tom",
  "password": "123456",
  "phone": "13800138000",
  "captchaId": "abc",
  "captchaCode": "8x9p"
}
```

---

## 5. 注册注意事项

```text
1. 密码不能明文存储
2. 用户名、手机号、邮箱要做唯一校验
3. 验证码必须有过期时间
4. 注册接口要限流
5. 防止恶意批量注册
6. 敏感信息日志要脱敏
7. 注册成功后可自动登录，也可要求重新登录
8. 用户状态默认启用或待审核，根据业务决定
```

# 七、Token 认证设计

## 1. Token 是什么？

Token 是用户登录成功后，服务端签发给客户端的登录凭证。

前端后续请求时携带 Token：

```http
Authorization: Bearer access_token
```

后端根据 Token 识别当前用户身份。

---

## 2. Token 方案选择

常见方案：

```text
1. Session + Cookie
2. UUID Token + Redis
3. JWT
4. JWT + Redis
5. OAuth2
```

---

## 3. Session + Cookie

传统 Web 常用。

流程：

```text
1. 登录成功后服务端创建 Session
2. 返回 sessionId 到 Cookie
3. 浏览器后续请求自动携带 Cookie
4. 服务端根据 sessionId 获取用户信息
```

优点：

```text
服务端容易控制登录状态
退出登录方便
踢人方便
```

缺点：

```text
前后端分离和移动端不够灵活
分布式环境需要共享 Session
```

---

## 4. UUID Token + Redis

流程：

```text
1. 登录成功生成随机 Token
2. 用户信息存 Redis
3. Token 返回前端
4. 后续请求携带 Token
5. 后端从 Redis 查询用户状态
```

优点：

```text
服务端可控
退出登录方便
踢人方便
权限变更可及时生效
```

缺点：

```text
每次请求都要查 Redis
依赖 Redis
```

---

## 5. JWT

JWT 全称：

```text
JSON Web Token
```

JWT 由三部分组成：

```text
Header.Payload.Signature
```

优点：

```text
服务端可以无状态
适合微服务和开放 API
减少 Redis 查询
```

缺点：

```text
Token 签发后不容易主动失效
Payload 默认只是 Base64 编码，不是加密
Token 泄露后存在风险
权限变更不能立即生效，除非配合 Redis 黑名单或短过期时间
```

---

## 6. 推荐方案：JWT + Redis

实际项目中推荐：

```text
AccessToken：JWT，短过期时间
RefreshToken：随机字符串，存 Redis，长过期时间
Redis：保存登录状态、Token 黑名单、用户权限缓存
```

这样兼顾：

```text
性能
安全
可控性
分布式支持
```

---

## 7. Token 内容设计

JWT Payload 可以包含：

```json
{
  "userId": 1001,
  "tenantId": 2001,
  "username": "tom",
  "tokenId": "uuid",
  "loginTime": 1714380000000,
  "exp": 1714387200000
}
```

注意：

```text
不要把密码、手机号、身份证、密钥等敏感信息放进 JWT。
```

# 八、验证码设计

## 1. 为什么需要验证码？

验证码用于防止：

```text
暴力破解
恶意注册
撞库攻击
短信轰炸
接口刷请求
```

---

## 2. 图形验证码流程

```text
1. 前端请求验证码接口
2. 后端生成验证码图片和验证码文本
3. 验证码文本存 Redis
4. 返回 captchaId 和图片 Base64
5. 用户登录时提交 captchaId 和 captchaCode
6. 后端从 Redis 获取验证码文本并比对
7. 校验成功后删除验证码
```

---

## 3. Redis 存储验证码

```text
captcha:{captchaId} -> code
TTL：2 分钟
```

示例：

```bash
SET captcha:abc123 8x9p EX 120
```

---

## 4. 验证码接口示例

```http
GET /api/auth/captcha
```

响应：

```json
{
  "code": 0,
  "data": {
    "captchaId": "abc123",
    "imageBase64": "data:image/png;base64,..."
  }
}
```

---

## 5. 短信验证码流程

```text
1. 用户输入手机号
2. 后端校验手机号格式
3. 校验发送频率
4. 生成 6 位验证码
5. 验证码存 Redis
6. 调用短信服务发送
7. 登录或注册时校验验证码
8. 校验成功后删除验证码
```

---

## 6. 短信验证码 Redis Key

```text
sms:code:login:{phone}
sms:code:register:{phone}
sms:limit:{phone}
sms:limit:ip:{ip}
```

---

## 7. 验证码注意事项

```text
1. 验证码要设置过期时间
2. 校验成功后立即删除
3. 同一手机号发送频率要限制
4. 同一 IP 发送频率要限制
5. 错误次数要限制
6. 验证码日志要脱敏
7. 验证码不能返回明文给前端
```

# 九、密码加密设计

## 1. 密码为什么不能明文存储？

如果数据库泄露，明文密码会直接暴露用户账号安全。

所以密码必须加密存储。

---

## 2. 推荐使用 BCrypt

推荐：

```text
BCryptPasswordEncoder
```

BCrypt 特点：

```text
1. 自带随机盐
2. 计算成本可调
3. 同一个密码每次加密结果不同
4. 适合密码存储
```

---

## 3. Java 示例

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

public class PasswordDemo {

    public static void main(String[] args) {
        BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();

        String rawPassword = "123456";
        String encodedPassword = encoder.encode(rawPassword);

        boolean matches = encoder.matches(rawPassword, encodedPassword);

        System.out.println(encodedPassword);
        System.out.println(matches);
    }
}
```

---

## 4. 注册时加密

```java
String encodedPassword = passwordEncoder.encode(registerRequest.getPassword());

user.setPassword(encodedPassword);
```

---

## 5. 登录时校验

```java
boolean match = passwordEncoder.matches(
        loginRequest.getPassword(),
        user.getPassword()
);

if (!match) {
    throw new BusinessException("账号或密码错误");
}
```

---

## 6. 密码安全策略

```text
1. 密码不能明文存储
2. 密码不能打印日志
3. 密码传输必须走 HTTPS
4. 密码强度要校验
5. 修改密码后旧 Token 应失效
6. 登录失败多次要限制
7. 管理员重置密码后用户首次登录应修改密码
```

# 十、登录态存储设计

## 1. 为什么需要 Redis 存登录态？

如果只使用 JWT，服务端不保存状态，存在一些问题：

```text
1. 退出登录后 Token 仍可能有效
2. 无法主动踢用户下线
3. 权限变更不能立即生效
4. 无法限制单用户登录设备数
5. 无法统一管理在线用户
```

因此推荐把登录态存 Redis。

---

## 2. 登录态内容

Redis 中可以保存：

```json
{
  "userId": 1001,
  "tenantId": 2001,
  "username": "tom",
  "roles": ["admin"],
  "permissions": ["user:add", "user:update"],
  "loginIp": "192.168.1.1",
  "loginTime": "2026-04-30 10:00:00",
  "expireTime": "2026-04-30 12:00:00"
}
```

---

## 3. Redis Key

```text
login:token:{tokenId}
```

示例：

```text
login:token:9b3b0a8a-xxx
```

---

## 4. Token 校验流程

```text
1. 前端请求携带 Authorization
2. 后端解析 JWT
3. 获取 tokenId
4. 查询 Redis login:token:{tokenId}
5. Redis 存在，说明登录有效
6. Redis 不存在，说明 Token 已失效
7. 将用户信息放入上下文
```

---

## 5. 用户上下文

```java
public class LoginUserContextHolder {

    private static final ThreadLocal<LoginUser> CONTEXT = new ThreadLocal<>();

    public static void set(LoginUser loginUser) {
        CONTEXT.set(loginUser);
    }

    public static LoginUser get() {
        return CONTEXT.get();
    }

    public static void clear() {
        CONTEXT.remove();
    }
}
```

请求结束后必须：

```java
LoginUserContextHolder.clear();
```

防止线程复用导致用户信息串号。

# 十一、权限加载设计

## 1. 登录时加载权限

登录成功后可以查询：

```text
用户信息
角色列表
菜单列表
按钮权限
数据权限
租户信息
```

---

## 2. 权限缓存

权限可以缓存到 Redis：

```text
user:permission:{userId}
user:menu:{userId}
```

多租户场景：

```text
tenant:{tenantId}:user:permission:{userId}
tenant:{tenantId}:user:menu:{userId}
```

---

## 3. 权限变更后如何处理？

当管理员修改用户角色或权限后：

```text
1. 删除用户权限缓存
```

# 十三、刷新 Token 设计

## 1. 为什么需要刷新 Token？

AccessToken 不建议设置太长时间。

原因：

```text
Token 泄露后风险较大
权限变更不容易立即生效
```

推荐：

```text
AccessToken 短有效期
RefreshToken 长有效期
```

---

## 2. 双 Token 模式

```text
AccessToken：短期，比如 2 小时
RefreshToken：长期，比如 7 天或 30 天
```

---

## 3. 刷新流程

```text
1. AccessToken 过期
2. 前端携带 RefreshToken 请求刷新接口
3. 后端校验 RefreshToken 是否有效
4. 生成新的 AccessToken
5. 可选择轮换 RefreshToken
6. 返回新的 Token
```

---

## 4. RefreshToken Redis Key

```text
refresh:token:{refreshToken}
```

value：

```text
userId、tenantId、tokenId、expireTime
```

---

## 5. 安全建议

```text
1. RefreshToken 要存 Redis
2. RefreshToken 泄露风险更高，要妥善保存
3. 刷新 Token 要限制频率
4. 可以启用 RefreshToken 轮换
5. 修改密码后清理所有 RefreshToken
```

## 3. 不同存储方式对比

| 存储方式 | 优点 | 缺点 |
|---|---|---|
| LocalStorage | 使用简单，刷新不丢 | 容易受 XSS 影响 |
| SessionStorage | 浏览器关闭即清理 | 刷新保留，但新窗口不共享 |

```text
AccessToken 存内存或 SessionStorage
RefreshToken 放 HttpOnly Cookie，安全要求高时使用
```

普通后台也常用：

```text
LocalStorage + HTTPS + XSS 防护
```

具体要根据安全要求决定。

# 二十五、完整面试回答模板

注册登录模块是系统的入口模块，主要负责用户身份认证、登录态维护和权限加载。设计时我会重点考虑安全性、可扩展性、登录状态管理、权限控制和防刷能力。

技术选型上，后端可以使用 Spring Boot 作为基础框架，安全认证使用 Spring Security，数据库使用 MySQL，ORM 使用 MyBatis-Plus，缓存使用 Redis，密码加密使用 BCrypt，Token 可以使用 JWT，验证码可以使用 EasyCaptcha 或短信服务。如果是微服务架构，可以使用 Spring Cloud Gateway 做统一鉴权和路由，Nacos 做注册配置中心，Sentinel 做登录、注册、验证码等接口限流。

注册流程一般是用户提交用户名、手机号、密码和验证码，后端先做参数校验，然后校验图形验证码或短信验证码。接着校验用户名、手机号、邮箱是否已存在，密码强度是否满足要求。密码不能明文保存，要使用 BCrypt 加密后再入库。注册成功后可以绑定默认角色，并记录注册日志。为了防止重复注册，需要前端按钮置灰，后端使用 Redis 锁或 requestId 做幂等，同时数据库对用户名、手机号或邮箱建立唯一索引兜底。

登录流程一般是用户提交账号、密码和验证码，后端先校验验证码，再根据用户名、手机号或邮箱查询用户。查询到用户后，需要判断用户状态是否正常，例如是否禁用、锁定或过期。然后使用 BCrypt 校验密码，如果密码正确，就加载用户角色、菜单权限、按钮权限和数据权限，生成 AccessToken 和 RefreshToken，并把登录态保存到 Redis，最后记录登录日志并返回 Token 和用户信息。

Token 设计上，我比较推荐 AccessToken + RefreshToken 的方式。AccessToken 可以使用 JWT，过期时间较短，例如 2 小时；RefreshToken 使用随机字符串，过期时间较长，例如 7 天或 30 天，并保存在 Redis 中。这样 AccessToken 用于日常接口认证，RefreshToken 用于刷新登录状态。Redis 中保存登录态可以支持退出登录、踢人下线、Token 续期、在线用户管理和权限变更即时生效。

每次请求时，前端在请求头中携带 `Authorization: Bearer token`。后端或网关解析 Token，获取 userId、tenantId、tokenId 等信息，然后到 Redis 查询登录态。如果 Redis 中存在，说明登录有效，再把用户信息放入用户上下文中；如果不存在，说明用户已退出、Token 过期或被踢下线。请求结束后，要清理 ThreadLocal，防止线程复用导致用户信息串号。

密码安全方面，密码不能明文存储，也不建议使用普通 MD5。推荐使用 BCrypt，因为它自带随机盐，并且计算成本可调。同一个密码每次加密结果都不同，更适合密码存储。登录时使用 `matches` 方法比对原始密码和加密后的密码。密码传输必须走 HTTPS，日志中不能打印密码、短信验证码、完整 Token 等敏感信息。

验证码方面，登录可以使用图形验证码，注册或找回密码可以使用短信验证码或邮箱验证码。验证码文本保存在 Redis 中，并设置较短过期时间，例如 2 分钟或 5 分钟。用户校验成功后要立即删除验证码，防止重复使用。短信验证码还要限制发送频率，例如同一手机号 1 分钟只能发送一次，一天最多发送固定次数，同一 IP 也要限制请求频率，防止短信轰炸。

登录安全方面，要防止暴力破解和撞库攻击。可以记录登录失败次数，比如同一账号 5 分钟内失败 5 次，就临时锁定 15 分钟；同一 IP 请求登录接口过多，也要限流。登录接口、注册接口、验证码接口、短信发送接口都要做限流，可以使用 Redis + Lua、Sentinel 或网关限流实现。每次登录都要记录登录日志，包括用户名、用户 ID、登录 IP、User-Agent、登录时间、登录结果和失败原因。

退出登录时，前端调用退出接口，后端解析 Token，获取 tokenId，然后删除 Redis 中的登录态。如果使用 JWT，也可以把 Token 加入黑名单直到自然过期。退出成功后前端清理本地 Token。退出接口本身要设计成幂等，即使重复退出也应该返回成功。

如果系统需要单端登录，可以在用户登录时维护 `login:user:{userId}` 到 tokenId 的映射，新登录成功后删除旧 tokenId 对应的登录态，旧设备下次请求时就会提示已在其他设备登录。如果支持多端登录，可以按设备类型维护 Token，例如 PC、APP、小程序分别保存不同登录态。管理员踢人下线，本质上就是删除指定用户或指定设备的 Redis 登录态。

如果是多租户系统，注册登录还要考虑租户识别。可以通过域名、租户编码、请求头或登录页面选择租户来确定 tenantId。登录时根据 tenantId 查询用户，Token 中也要携带 tenantId，Redis Key、权限缓存、登录日志都要带 tenantId，避免租户之间数据串用。

第三方登录可以基于 OAuth2 思路实现。用户点击第三方登录后跳转到第三方授权页面，授权完成后第三方回调 code，后端用 code 换取 access_token，再获取 openId。然后根据 openId 查询是否已经绑定系统用户，已绑定则直接登录，未绑定则引导绑定手机号或创建新用户。第三方账号和系统用户之间的关系保存在第三方账号绑定表中。

总体来说，注册登录设计的核心不是简单校验账号密码，而是要完整考虑密码安全、验证码、防刷限流、Token 管理、登录态存储、权限加载、退出登录、刷新 Token、登录日志、单点登录、多端登录和多租户隔离。技术选型上要优先选择成熟稳定的方案，例如 Spring Security、Redis、JWT、BCrypt 和 MySQL，并根据系统规模决定是否引入网关、认证中心和 OAuth2。
