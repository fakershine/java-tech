# 微服务网关设计总结

微服务网关是系统的统一入口，负责将外部请求转发到内部微服务，并统一处理 **路由、鉴权、限流、熔断、日志、监控、灰度发布** 等通用能力。

---

## 1. 网关的作用

微服务系统中，如果客户端直接调用各个服务，会出现：

```text
服务地址暴露
认证逻辑重复
接口管理混乱
跨域处理分散
限流熔断难统一
客户端调用复杂
```

所以需要网关作为统一入口：

```text
客户端
  ↓
API Gateway
  ↓
用户服务 / 订单服务 / 支付服务 / 商品服务
```

---

## 2. 网关核心功能

| 功能 | 说明 |
|---|---|
| 统一入口 | 所有外部请求先进入网关 |
| 路由转发 | 根据路径、域名、Header 转发到不同服务 |
| 认证鉴权 | 校验 Token、权限、租户信息 |
| 限流 | 控制接口访问频率，防止流量打爆服务 |
| 熔断降级 | 下游服务异常时快速失败或返回兜底结果 |
| 负载均衡 | 从多个服务实例中选择一个调用 |
| 灰度发布 | 按用户、Header、版本、权重转发流量 |
| 日志监控 | 记录请求日志、耗时、状态码、异常 |
| 跨域处理 | 统一处理 CORS |
| 协议转换 | HTTP 转 RPC、HTTP 转 WebSocket 等 |
| 黑白名单 | 控制 IP、用户、应用访问 |
| 请求改写 | 修改 Path、Header、参数等 |

---

## 3. 网关整体架构

```text
客户端
  ↓
负载均衡器 Nginx / SLB
  ↓
网关集群
  ↓
注册中心
  ↓
微服务集群
```

网关本身也要集群部署：

```text
Gateway-1
Gateway-2
Gateway-3
```

避免单点故障。

## 4. 请求处理流程

```text
请求进入网关
  ↓
全局过滤器
  ↓
认证 Token
  ↓
权限校验
  ↓
限流判断
  ↓
匹配路由规则
  ↓
服务发现
  ↓
负载均衡选择实例
  ↓
转发请求到后端服务
  ↓
接收响应
  ↓
记录日志和监控
  ↓
返回客户端
```

## 5. 路由设计

### 实现原理

网关根据请求特征匹配路由规则。

常见匹配条件：

```text
Path
Host
Method
Header
Query
Cookie
```

示例：

```text
/user/**  -> user-service
/order/** -> order-service
/pay/**   -> pay-service
```

### 配置示例

```yaml
routes:
  - id: user-service
    uri: lb://user-service
    predicates:
      - Path=/user/**
```

含义：

```text
访问 /user/** 的请求转发到 user-service
```

---

## 6. 服务发现与负载均衡

网关不应该写死服务地址，而是从注册中心获取服务实例。

```text
网关
  ↓
注册中心 Nacos / Eureka / Consul
  ↓
获取 user-service 实例列表
  ↓
负载均衡选择一个实例
```

负载均衡算法：

```text
轮询
随机
权重
最少连接
一致性 Hash
```

---

## 7. 认证鉴权设计

### 认证

认证解决：

```text
用户是谁
```

常见方式：

```text
JWT
Session
OAuth2
Token + Redis
```

流程：

```text
请求携带 Token
  ↓
网关解析 Token
  ↓
校验 Token 是否有效
  ↓
提取 userId、tenantId、roles
  ↓
写入请求 Header 转发给下游服务
```

---

### 鉴权

鉴权解决：

```text
用户能不能访问这个接口
```

流程：

```text
获取用户权限
  ↓
匹配当前接口所需权限
  ↓
有权限：放行
  ↓
无权限：返回 403
```

注意：

```text
网关适合做粗粒度鉴权
业务服务仍要做细粒度权限校验
```

---

## 8. 限流设计

限流用于防止流量过大打垮系统。

常见限流维度：

```text
IP
用户
接口
应用
租户
服务
```

常见限流算法：

| 算法 | 说明 |
|---|---|
| 固定窗口 | 固定时间窗口内限制请求数 |
| 滑动窗口 | 统计最近一段时间内请求数 |
| 漏桶 | 请求匀速流出 |
| 令牌桶 | 按固定速率生成令牌，请求获取令牌后放行 |
| 并发数限制 | 限制同时处理的请求数量 |

常见实现：

```text
Redis + Lua
Sentinel
Resilience4j
本地限流
```

---

## 9. 熔断降级设计

当下游服务异常时，网关可以快速失败，避免请求大量阻塞。

触发条件：

```text
超时率过高
异常率过高
并发数过高
响应时间过长
```

流程：

```text
调用下游服务失败率升高
  ↓
达到阈值
  ↓
打开熔断
  ↓
请求直接返回降级结果
  ↓
一段时间后半开探测
  ↓
恢复正常则关闭熔断
```

---

## 10. 灰度发布设计

灰度发布用于将部分流量转发到新版本服务。

常见灰度规则：

```text
按用户 ID
按 Header
按 Cookie
按 IP
按版本号
按权重
按租户
```

示例：

```text
Header version = v2
  ↓
转发到 order-service-v2
```

或者：

```text
10% 流量 -> 新版本
90% 流量 -> 老版本
```

## 12. 链路追踪

网关是请求入口，应该生成或透传 `traceId`。

流程：

```text
请求进入网关
  ↓
生成 traceId
  ↓
写入 Header
  ↓
转发给下游服务
  ↓
整个调用链共享 traceId
```

常见组件：

```text
SkyWalking
Zipkin
Jaeger
OpenTelemetry
```

## 13. 高可用设计

网关是流量入口，必须高可用。

常见设计：

```text
多实例部署
前置 Nginx / SLB
无状态设计
配置中心动态路由
注册中心服务发现
限流熔断保护
监控告警
优雅上下线
```

网关不要保存强状态，登录态、权限、限流计数等可以放到：

```text
Redis
配置中心
认证中心
```

---

## 14. 性能优化

优化方向：

```text
使用异步非阻塞模型
避免在网关做复杂业务逻辑
连接池复用
合理设置超时时间
开启压缩
热点接口限流
日志异步写入
大请求体限制
```

注意：

```text
网关只做通用能力，不要承载复杂业务逻辑。
```

## 16. Spring Cloud Gateway 实现思路

核心组件：

| 组件 | 作用 |
|---|---|
| Route | 路由规则 |
| Predicate | 路由匹配条件 |
| Filter | 请求过滤和增强 |
| GlobalFilter | 全局过滤器 |
| GatewayFilter | 路由级过滤器 |
| LoadBalancer | 负载均衡 |
| Reactor Netty | 网络通信 |

调用流程：

```text
请求进入 Gateway
  ↓
Predicate 匹配路由
  ↓
执行 GlobalFilter
  ↓
执行 GatewayFilter
  ↓
LoadBalancer 选择服务实例
  ↓
Netty 转发请求
  ↓
返回响应
```

## 17. 网关和业务服务职责边界

网关适合做：

```text
认证
限流
路由
灰度
日志
监控
跨域
协议转换
黑白名单
```

业务服务适合做：

```text
业务参数校验
业务权限校验
数据权限控制
业务规则处理
事务处理
领域逻辑
```

不要把业务逻辑大量写在网关中，否则网关会变成新的单体系统。

---

## 18. 总结

微服务网关是系统统一入口，主要负责路由转发、认证鉴权、限流、熔断降级、负载均衡、灰度发布、跨域处理、日志监控和链路追踪。

设计网关时，首先要保证高可用和高性能，网关本身应无状态、多实例部署，前面可以挂 Nginx 或云负载均衡。网关通过注册中心发现后端服务，通过路由规则匹配请求，再通过负载均衡选择具体实例进行转发。

网关适合处理通用横切逻辑，例如 Token 校验、接口限流、黑白名单、日志监控等；业务相关的细粒度权限和数据权限仍然应该放在业务服务中。

一句话总结：

```text
微服务网关 = 统一入口 + 路由转发 + 认证鉴权 + 限流熔断 + 灰度发布 + 日志监控。
```
