# 权限系统设计总结

权限系统的核心目标是：**控制谁能访问什么资源，以及能做什么操作**。

常见权限模型：

```text
用户 -> 角色 -> 权限 -> 资源
```

---

## 1. 权限系统核心能力

| 能力 | 说明 |
|---|---|
| 用户管理 | 管理用户账号、状态、组织关系 |
| 角色管理 | 按职责划分权限集合 |
| 权限管理 | 控制菜单、按钮、接口、数据访问 |
| 资源管理 | 菜单、接口、页面、按钮等资源 |
| 组织架构 | 部门、岗位、上下级关系 |
| 数据权限 | 控制用户能看哪些数据 |
| 登录认证 | 判断用户是谁 |
| 访问授权 | 判断用户能不能访问 |
| 操作审计 | 记录用户操作日志 |

---

## 2. 认证和授权区别

| 概念 | 说明 | 示例 |
|---|---|---|
| 认证 | 判断用户是谁 | 登录、Token 校验 |
| 授权 | 判断用户能做什么 | 是否能删除订单 |

简单理解：

```text
认证：你是谁
授权：你能干什么
```

---

## 3. 常见权限模型

## 3.1 RBAC 模型

RBAC 是最常见的权限模型。

```text
User -> Role -> Permission
```

即：

```text
用户绑定角色
角色绑定权限
用户通过角色获得权限
```

示例：

```text
张三 -> 运营角色 -> 订单查询、订单导出
李四 -> 管理员角色 -> 用户管理、角色管理、订单管理
```

### 优势

- 模型简单。
- 易理解。
- 易维护。
- 适合大多数后台系统。

### 劣势

- 权限粒度复杂时角色容易膨胀。
- 动态条件权限支持较弱。

---

## 3.2 RBAC 扩展模型

实际项目中一般会扩展为：

```text
用户 -> 角色 -> 菜单权限
              -> 按钮权限
              -> 接口权限
              -> 数据权限
```

常见权限类型：

| 权限类型 | 说明 |
|---|---|
| 菜单权限 | 控制用户能看到哪些菜单 |
| 按钮权限 | 控制新增、删除、导出等按钮 |
| 接口权限 | 控制后端接口是否允许访问 |
| 数据权限 | 控制能查看哪些数据 |

---

## 3.3 ABAC 模型

ABAC 是基于属性的权限控制。

它会根据用户、资源、环境等属性动态判断权限。

示例：

```text
用户部门 = 订单所属部门
并且
订单状态 = 待审核
则允许审核订单
```

### 适用场景

- 权限规则复杂。
- 需要动态条件判断。
- 金融、审批、风控等系统。

## 5. 登录认证流程

```text
用户输入账号密码
  ↓
后端校验用户名和密码
  ↓
校验用户状态
  ↓
查询用户角色和权限
  ↓
生成 Token
  ↓
返回给前端
  ↓
前端后续请求携带 Token
```

常见 Token 方式：

```text
JWT
Redis Token
Session
OAuth2 Token
```

---

## 6. 接口鉴权流程

```text
请求进入网关或后端服务
  ↓
解析 Token
  ↓
获取用户信息
  ↓
获取用户权限列表
  ↓
匹配当前接口所需权限
  ↓
有权限：放行
  ↓
无权限：返回 403
```

示例：

```java
@PreAuthorize("hasAuthority('order:delete')")
@DeleteMapping("/order/{id}")
public void deleteOrder(@PathVariable Long id) {
}
```

## 7. 前端权限控制

前端主要控制：

```text
菜单显示
按钮显示
路由访问
```

流程：

```text
登录成功
  ↓
后端返回用户菜单和权限码
  ↓
前端动态生成路由
  ↓
根据权限码控制按钮显示
```

示例权限码：

```text
order:list
order:create
order:update
order:delete
order:export
```

注意：

```text
前端权限只能提升体验，不能作为真正安全控制。
真正权限必须由后端校验。
```

---

## 8. 后端权限控制

后端主要控制：

```text
接口权限
数据权限
操作权限
```

常见方式：

```text
Spring Security
Shiro
自定义拦截器
网关鉴权
AOP 注解鉴权
```

推荐：

```text
粗粒度权限放网关
细粒度权限放业务服务
```

---

## 9. 数据权限设计

数据权限用于控制用户能看到哪些数据。

常见数据范围：

| 类型 | 说明 |
|---|---|
| 全部数据 | 管理员可看所有数据 |
| 本部门数据 | 只能看当前部门数据 |
| 本部门及子部门数据 | 能看当前部门及下级部门 |
| 本人数据 | 只能看自己创建的数据 |
| 自定义部门数据 | 指定可访问部门范围 |

---

## 10. 数据权限实现方式

### 方式一：SQL 拼接条件

根据用户数据权限动态拼接 SQL。

```sql
SELECT *
FROM order_info
WHERE dept_id IN (...)
```

### 方式二：MyBatis 插件

通过 MyBatis 拦截器统一改写 SQL。

```text
拦截查询 SQL
  ↓
判断是否需要数据权限
  ↓
拼接 dept_id / user_id 条件
  ↓
执行 SQL
```

### 方式三：AOP 注解

```java
@DataScope
public List<Order> listOrders() {
}
```

切面中根据当前用户权限拼接查询条件。

## 11. 权限缓存设计

权限数据不能每次请求都查数据库。

常见缓存方式：

```text
Redis 缓存用户权限
本地缓存权限配置
Token 中保存少量用户信息
```

缓存 Key 示例：

```text
user:permission:{userId}
user:roles:{userId}
```

缓存内容：

```text
角色列表
权限码列表
菜单列表
数据权限范围
```

权限变更后需要：

```text
删除用户权限缓存
或
更新权限版本号
```

---

## 12. 权限变更如何生效

常见方案：

### 1. 删除缓存

```text
角色权限变更
  ↓
删除相关用户权限缓存
  ↓
下次请求重新加载权限
```

### 2. Token 版本号

用户表维护权限版本：

```text
permission_version
```

Token 中也存版本号。

```text
请求时比较 Token 版本和 Redis / DB 版本
不一致则要求重新登录或刷新权限
```

### 3. 短 Token 过期时间

让 Token 较快过期，降低权限变更延迟。

---

## 13. 多租户权限设计

如果系统支持多租户，需要在权限模型中加入：

```text
tenant_id
```

常见表：

```text
sys_user
sys_role
sys_permission
sys_user_role
sys_role_permission
```

都需要带：

```text
tenant_id
```

查询时必须隔离：

```sql
WHERE tenant_id = ?
```

避免租户之间数据串读。

## 15. 安全设计要点

- 密码必须加密存储，例如 BCrypt。
- 接口必须做后端鉴权。
- Token 要设置过期时间。
- 敏感接口需要二次校验。
- 删除、导出、审批等操作要记录日志。
- 防止越权访问。
- 防止水平越权和垂直越权。
- 权限变更后要及时清理缓存。
- 前端隐藏按钮不等于安全。
- 管理员权限要谨慎分配。

---

## 16. 常见越权问题

### 1. 水平越权

用户 A 访问用户 B 的数据。

示例：

```text
/order/detail?id=1001
```

如果后端只根据订单 ID 查询，不校验订单归属，就会出现水平越权。

解决：

```text
查询时加 user_id / dept_id / tenant_id 条件
```

---

### 2. 垂直越权

普通用户访问管理员接口。

示例：

```text
普通用户调用 /admin/deleteUser
```

解决：

```text
接口权限校验
角色权限校验
后端注解鉴权
```

## 17. 推荐架构

```text
前端
  ↓
网关：Token 校验、粗粒度权限、限流
  ↓
业务服务：接口权限、数据权限、业务规则校验
  ↓
数据库：租户隔离、数据范围过滤
```

权限数据流：

```text
用户登录
  ↓
查询角色和权限
  ↓
缓存到 Redis
  ↓
返回 Token 和菜单权限
  ↓
请求接口时校验 Token 和权限码
  ↓
查询数据时拼接数据权限条件
```

---

## 18. 总结

权限系统一般采用 RBAC 模型设计，即用户关联角色，角色关联权限，用户通过角色获得权限。实际项目中会扩展菜单权限、按钮权限、接口权限和数据权限。

登录时完成认证，生成 Token，并缓存用户角色和权限；请求接口时通过 Token 识别用户，再判断用户是否拥有当前接口所需权限；查询数据时根据用户的数据权限范围拼接查询条件，防止越权访问。

权限系统要特别关注缓存一致性、数据权限、多租户隔离、操作审计和越权问题。前端权限只能控制显示，真正的权限控制必须放在后端。

一句话总结：

```text
权限系统设计 = RBAC 模型 + Token 认证 + 接口鉴权 + 数据权限 + 权限缓存 + 操作审计。
```
