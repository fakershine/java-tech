# 高并发系统设计总结

高并发系统的核心目标是：**在大量请求同时到来时，系统仍然能保持高吞吐、低延迟、高可用和数据一致性**。

设计思路：

```text
流量入口削峰
  ↓
应用层水平扩展
  ↓
缓存抗读
  ↓
消息队列削峰
  ↓
数据库抗写
  ↓
限流熔断保护
  ↓
监控告警兜底
```

---

## 1. 高并发系统核心问题

| 问题 | 说明 |
|---|---|
| 请求量大 | QPS 高，接口压力大 |
| 瞬时流量高 | 秒杀、抢购、活动流量突增 |
| 数据库压力大 | 慢 SQL、锁竞争、连接数打满 |
| 缓存压力大 | 热 Key、缓存穿透、缓存击穿 |
| 下游服务压力大 | RPC 超时、线程池打满 |
| 数据一致性 | 库存、订单、支付等状态一致 |
| 系统可用性 | 局部故障不能拖垮整体 |

---

## 2. 整体架构设计

```text
用户请求
  ↓
CDN
  ↓
负载均衡 Nginx / SLB
  ↓
API 网关
  ↓
应用服务集群
  ↓
缓存 Redis
  ↓
消息队列 MQ
  ↓
数据库集群
  ↓
异步任务 / 统计系统
```

核心思想：

```text
能缓存就缓存
能异步就异步
能拆分就拆分
能限流就限流
能水平扩展就水平扩展
```

---

## 3. 流量入口优化

### 3.1 CDN 加速

适合缓存静态资源：

```text
图片
JS
CSS
视频
静态页面
```

作用：

```text
减少源站压力
降低访问延迟
提升用户体验
```

---

### 3.2 负载均衡

使用 Nginx、SLB、LVS 等做流量分发。

```text
请求
  ↓
负载均衡
  ↓
应用实例 1 / 2 / 3
```

常见算法：

```text
轮询
随机
加权轮询
最少连接
一致性 Hash
```

---

### 3.3 网关限流

在网关层做统一限流：

```text
按 IP 限流
按用户限流
按接口限流
按租户限流
按应用限流
```

常见算法：

```text
令牌桶
漏桶
滑动窗口
固定窗口
```

## 4. 应用层设计

### 4.1 无状态化

应用服务尽量无状态。

```text
Session 不存本机
登录态放 Redis / Token
文件上传放对象存储
```

好处：

```text
方便水平扩容
方便故障迁移
方便滚动发布
```

---

### 4.2 水平扩展

当单机扛不住时，通过增加实例提升吞吐。

```text
应用服务 1
应用服务 2
应用服务 3
```

前提：

```text
服务无状态
配置统一
注册中心可发现
负载均衡可分发
```

---

### 4.3 线程池隔离

不同业务使用不同线程池，避免互相影响。

```text
核心接口线程池
普通接口线程池
异步任务线程池
第三方调用线程池
```

避免：

```text
非核心接口拖垮核心接口
慢接口占满所有线程
```

---

### 4.4 超时控制

所有外部调用都必须设置超时。

```text
HTTP 调用超时
RPC 调用超时
Redis 超时
数据库超时
MQ 超时
```

原则：

```text
不能无限等待下游响应
```

---

## 5. 缓存设计

### 5.1 多级缓存

```text
本地缓存 Caffeine
  ↓
分布式缓存 Redis
  ↓
数据库
```

适合：

```text
热点商品
系统配置
用户权限
字典数据
首页数据
```

---

### 5.2 缓存穿透

问题：

```text
查询不存在的数据，大量请求直接打到数据库
```

解决：

```text
缓存空值
布隆过滤器
参数校验
接口限流
```

---

### 5.3 缓存击穿

问题：

```text
热点 Key 过期瞬间，大量请求同时打到数据库
```

解决：

```text
互斥锁重建缓存
逻辑过期
热点 Key 永不过期
异步刷新缓存
```

---

### 5.4 缓存雪崩

问题：

```text
大量 Key 同时过期，数据库压力暴增
```

解决：

```text
过期时间加随机值
热点数据预热
多级缓存
Redis 高可用
限流降级
```

---

### 5.5 热 Key

问题：

```text
某个 Key 访问量极高，打爆单个 Redis 节点
```

解决：

```text
本地缓存
热点 Key 拆分
读副本扩展
请求合并
限流保护
```

## 6. 异步削峰

### 6.1 使用 MQ 削峰填谷

高并发写请求不要全部同步打到数据库。

```text
请求进入
  ↓
快速校验
  ↓
写入 MQ
  ↓
立即返回排队中
  ↓
消费者异步处理
  ↓
落库
```

适合：

```text
秒杀下单
订单创建
日志采集
积分发放
通知发送
数据同步
```

---

### 6.2 异步化处理

非核心逻辑异步执行：

```text
发送短信
发送邮件
写操作日志
发优惠券
积分变更
统计分析
```

主链路只做核心操作：

```text
校验
扣减
创建核心数据
返回结果
```

## 7. 数据库设计

### 7.1 SQL 优化

重点优化：

```text
索引设计
慢 SQL
分页查询
避免全表扫描
避免大事务
避免一次查询大量数据
```

常见手段：

```text
EXPLAIN 分析执行计划
加合适索引
覆盖索引
减少回表
拆分复杂 SQL
```

---

### 7.2 读写分离

读多写少场景可以使用主从架构。

```text
写请求 -> 主库
读请求 -> 从库
```

作用：

```text
降低主库读压力
提升读吞吐
```

注意：

```text
主从延迟会导致短时间读不到最新数据
```

---

### 7.3 分库分表

当单库单表数据量过大时，进行水平拆分。

```text
user_id % 16
  ↓
分到不同表或不同库
```

适合：

```text
订单表
流水表
日志表
用户行为表
```

注意：

```text
分库分表会带来跨库查询、分布式事务、分页排序、扩容迁移问题
```

---

### 7.4 冷热数据分离

把历史数据迁移到冷库。

```text
近 3 个月订单 -> 热库
3 个月前订单 -> 冷库 / 归档库
```

好处：

```text
降低主表数据量
提升核心查询性能
减少索引维护成本
```

---

## 8. 秒杀场景设计

秒杀是典型高并发场景。

核心设计：

```text
前端限流
  ↓
网关限流
  ↓
活动校验
  ↓
库存预热到 Redis
  ↓
Redis 原子扣减库存
  ↓
成功请求进入 MQ
  ↓
异步创建订单
  ↓
数据库最终落库
```

关键点：

```text
库存不能直接打数据库
必须防止超卖
必须限制重复下单
必须异步削峰
必须做好失败补偿
```

## 9. 限流、熔断、降级

### 9.1 限流

限制入口流量，保护系统。

```text
超过阈值直接拒绝
返回稍后重试
```

---

### 9.2 熔断

下游异常时快速失败。

```text
失败率过高
  ↓
打开熔断
  ↓
直接返回兜底结果
  ↓
半开探测恢复
```

---

### 9.3 降级

非核心功能暂时关闭。

例如：

```text
关闭推荐
关闭排行榜
关闭评论
关闭非核心统计
只保留下单和支付主链路
```

## 10. 数据一致性设计

高并发下常见一致性问题：

```text
库存超卖
重复下单
重复支付
缓存和数据库不一致
MQ 消息重复消费
分布式事务不一致
```

常见方案：

| 问题 | 解决方案 |
|---|---|
| 超卖 | Redis 原子扣减、数据库乐观锁 |
| 重复提交 | 幂等 Token、唯一索引 |
| 重复消费 | 消费记录表、业务唯一键 |
| 缓存不一致 | 先更新 DB 再删缓存、延迟双删 |
| 分布式事务 | 本地消息表、事务消息、Seata |
| 状态错乱 | 状态机 + 条件更新 |

## 17. 总结

设计高并发系统时，要从入口流量、应用服务、缓存、消息队列、数据库和稳定性治理几个方面考虑。

入口层通过 CDN、负载均衡、网关限流减少系统压力；应用层要无状态化，支持水平扩容，并做好线程池隔离和超时控制；读多场景用 Redis 和本地缓存抗住访问压力；写多或瞬时流量高的场景用 MQ 削峰填谷；数据库层通过索引优化、读写分离、分库分表和冷热分离提升承载能力；同时要通过限流、熔断、降级、幂等、监控告警保证系统稳定性。

一句话总结：

```text
高并发系统设计 = 前端削峰 + 网关限流 + 服务扩容 + 缓存抗读 + MQ 削峰 + 数据库拆分 + 熔断降级 + 监控压测。
```
