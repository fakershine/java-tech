# 秒杀系统设计总结

秒杀系统的核心目标是：**在瞬时高并发下，保证系统不被打垮、不超卖、不重复下单，并尽快返回结果**。

核心思路：

```text
前端限流
  ↓
网关限流
  ↓
Redis 预扣库存
  ↓
MQ 异步削峰
  ↓
消费者创建订单
  ↓
数据库最终落库
```

---

## 1. 秒杀系统核心问题

| 问题 | 说明 |
|---|---|
| 瞬时高并发 | 大量用户同时抢购 |
| 库存超卖 | 实际卖出数量超过库存 |
| 重复下单 | 同一用户多次提交 |
| 数据库压力大 | 请求直接打 DB 容易崩 |
| MQ 积压 | 下单请求过多，消费跟不上 |
| 恶意刷接口 | 机器人、脚本大量请求 |
| 用户体验 | 秒杀结果要尽快返回 |

---

## 2. 整体架构

```text
用户
  ↓
前端页面静态化 / CDN
  ↓
网关限流 / 鉴权
  ↓
秒杀服务
  ↓
Redis 扣减库存
  ↓
MQ 异步下单
  ↓
订单服务消费消息
  ↓
数据库落库
```

核心原则：

```text
读走缓存
写走队列
库存先 Redis 预扣
订单异步落库
数据库不承接瞬时流量
```

---

## 3. 秒杀流程

```text
1. 活动开始前，将商品库存预热到 Redis。
2. 用户进入秒杀页面，请求秒杀接口。
3. 网关进行限流、鉴权、黑名单校验。
4. 秒杀服务校验活动时间、用户资格、是否重复下单。
5. Redis 原子扣减库存。
6. 扣减成功后，发送下单消息到 MQ。
7. 立即返回用户“排队中”或“秒杀成功待确认”。
8. 订单服务异步消费 MQ，创建订单并扣减数据库库存。
9. 用户轮询查询秒杀结果。
```

---

## 4. 库存设计

### 4.1 Redis 预扣库存

活动开始前：

```text
seckill:stock:{skuId} = 100
```

秒杀时通过 Redis 原子操作扣减库存。

```lua
local stock = redis.call('GET', KEYS[1])

if tonumber(stock) <= 0 then
    return -1
end

redis.call('DECR', KEYS[1])
return 1
```

作用：

```text
避免所有请求直接打数据库
利用 Redis 单线程原子性防止超卖
```

---

### 4.2 数据库库存兜底

数据库更新时仍要加条件，防止异常情况超卖。

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE sku_id = ?
AND stock > 0;
```

如果影响行数为 `0`，说明库存不足。

---

## 5. 防止重复下单

### Redis 防重

用户秒杀成功后，写入 Redis 标记：

```text
seckill:user:{activityId}:{userId} = 1
```

使用 `SETNX`：

```bash
SET seckill:user:1001:2001 1 NX EX 3600
```

流程：

```text
先判断用户是否抢过
  ↓
没抢过才允许扣库存
  ↓
抢过则直接返回重复下单
```

---

### 数据库唯一索引兜底

订单表增加唯一索引：

```sql
UNIQUE KEY uk_activity_user(activity_id, user_id)
```

即使 Redis 防重失效，数据库也能防止重复订单。

---

## 6. MQ 异步削峰

秒杀请求不能同步创建订单，否则数据库压力过大。

推荐流程：

```text
Redis 扣库存成功
  ↓
发送下单消息到 MQ
  ↓
立即返回排队中
  ↓
消费者异步创建订单
```

消息内容：

```text
activityId
skuId
userId
requestId
createTime
```

优势：

- 削峰填谷。
- 保护数据库。
- 提高接口响应速度。
- 支持失败重试和补偿。

---

## 7. 秒杀结果查询

由于下单是异步的，用户需要查询结果。

结果状态可以放 Redis：

```text
seckill:result:{activityId}:{userId}
```

状态：

```text
PROCESSING：排队中
SUCCESS：秒杀成功
FAIL：秒杀失败
SOLD_OUT：库存不足
```

用户下单后：

```text
前端轮询查询秒杀结果
```

## 8. 限流设计

秒杀系统必须限流。

常见限流位置：

```text
前端按钮防重复点击
网关限流
用户维度限流
IP 维度限流
接口维度限流
服务端令牌桶限流
```

常见算法：

```text
令牌桶
漏桶
滑动窗口
固定窗口
```

推荐：

```text
网关 Redis + Lua 限流
服务端本地限流兜底
```

## 9. 防刷设计

常见防刷手段：

- 秒杀链接动态化。
- 秒杀开始前隐藏真实接口。
- 用户登录校验。
- 图形验证码 / 滑块验证码。
- IP 限流。
- 用户限流。
- 黑名单。
- 风控评分。
- 请求签名。
- 时间戳防重放。

秒杀地址动态化：

```text
活动开始前，用户先请求秒杀地址
服务端校验资格后返回临时 path
用户使用临时 path 发起秒杀
```

## 10. 缓存预热

活动开始前提前加载数据到 Redis。

预热内容：

```text
商品信息
活动信息
库存数量
用户资格
限购规则
秒杀开始时间
```

好处：

```text
避免活动开始瞬间大量请求打数据库
```

---

## 11. 热点隔离

秒杀属于热点业务，建议和普通业务隔离。

隔离方式：

```text
独立秒杀服务
独立 Redis 集群
独立 MQ Topic
独立数据库表
独立线程池
独立限流规则
```

避免：

```text
秒杀流量拖垮正常下单、支付、用户服务
```

---

## 12. 数据一致性设计

秒杀系统一般采用最终一致性。

常见问题和解决方案：

| 问题 | 解决方案 |
|---|---|
| Redis 扣库存成功，MQ 发送失败 | 本地消息表 / 事务消息 / 补偿任务 |
| MQ 消息重复消费 | 消费端幂等、订单唯一索引 |
| 数据库下单失败 | 回补 Redis 库存、记录失败日志 |
| Redis 库存和 DB 库存不一致 | 定时校准、活动结束后对账 |
| 用户重复请求 | Redis SETNX + DB 唯一索引 |

---

## 13. 消费端幂等

消费者创建订单时必须幂等。

方案：

```text
订单表唯一索引 activity_id + user_id
消费记录表 message_id
状态机判断
```

示例：

```sql
INSERT INTO seckill_order(activity_id, user_id, sku_id)
VALUES (?, ?, ?);
```

如果重复插入触发唯一索引冲突，说明已经下单，直接忽略。

## 16. 秒杀系统完整流程

```text
活动前：
1. 配置秒杀活动。
2. 预热商品、活动、库存到 Redis。
3. 静态资源推送到 CDN。
4. 做压测和限流配置。

活动中：
1. 用户请求秒杀接口。
2. 网关限流、防刷、鉴权。
3. 秒杀服务校验资格。
4. Redis 判断是否重复下单。
5. Redis 原子扣减库存。
6. 扣减成功后发送 MQ。
7. 返回排队中。
8. 消费者异步创建订单。
9. 用户查询秒杀结果。

活动后：
1. 对账 Redis、MQ、数据库。
2. 处理失败消息。
3. 回补异常库存。
4. 生成统计报表。
```

---

## 17. 总结

秒杀系统的核心是抗住瞬时高并发，并保证不超卖、不重复下单。

设计上，活动开始前要把库存和活动信息预热到 Redis；秒杀请求进入后，先经过网关限流、防刷和鉴权，然后在 Redis 中通过 Lua 脚本原子扣减库存，并用 `SETNX` 防止用户重复下单。扣减成功后不直接写数据库，而是发送 MQ 异步创建订单，从而削峰填谷保护数据库。

数据库层面仍要通过库存条件更新和唯一索引兜底，防止极端情况下超卖和重复下单。消费端要保证幂等，异常场景要通过补偿任务、死信队列和对账机制保证最终一致。

一句话总结：

```text
秒杀系统 = CDN 静态化 + 网关限流防刷 + Redis 原子扣库存 + MQ 异步下单 + DB 唯一索引兜底 + 幂等补偿。
```
