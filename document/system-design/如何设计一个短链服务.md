# 短链服务设计总结

短链服务用于将长 URL 转换成短 URL，用户访问短 URL 时，再跳转到原始长 URL。

示例：

```text
长链接：https://www.example.com/activity/detail?id=1001&source=wechat
短链接：https://s.cn/aB12xY
```

---

## 1. 核心功能

| 功能 | 说明 |
|---|---|
| 生成短链 | 长链接转换成短码 |
| 短链跳转 | 根据短码查询长链接并重定向 |
| 防重复生成 | 相同长链接可返回相同短链 |
| 过期时间 | 支持短链自动失效 |
| 访问统计 | 统计 PV、UV、来源、地域等 |
| 风控校验 | 防止恶意链接、刷接口 |
| 后台管理 | 查询、禁用、删除短链 |

---

## 2. 核心流程

### 生成短链

```text
用户提交长链接
  ↓
参数校验
  ↓
判断长链接是否合法
  ↓
生成短码
  ↓
保存短码和长链接映射关系
  ↓
返回短链接
```

---

### 访问短链

```text
用户访问短链接
  ↓
解析短码
  ↓
先查缓存
  ↓
缓存没有查数据库
  ↓
判断是否过期 / 禁用
  ↓
记录访问日志
  ↓
302 重定向到原始长链接
```

---

## 3. 短码生成方案

## 3.1 自增 ID + Base62

### 实现原理

先生成一个全局唯一 ID，再转成 Base62 字符串。

```text
id = 10000001
  ↓
Base62 编码
  ↓
短码 = aZ3x9
```

Base62 字符集：

```text
0-9
a-z
A-Z
```

### 优势

- 实现简单。
- 不容易冲突。
- 短码长度较短。
- 性能好。

### 劣势

- 自增 ID 容易暴露数据量。
- 需要全局 ID 生成器。
- 可预测，安全性一般。

### 优化

可以对 ID 做扰动：

```text
id 加盐
id 打乱
号段随机偏移
```

---

## 3.2 哈希算法

### 实现原理

对长链接做 Hash，再取部分字符作为短码。

```text
longUrl
  ↓
MD5 / MurmurHash
  ↓
取前 6~8 位
  ↓
生成短码
```

### 优势

- 相同长链接可以生成相同短码。
- 不依赖自增 ID。
- 实现简单。

### 劣势

- 可能发生 Hash 冲突。
- 需要冲突检测和重试。
- 截断越短，冲突概率越高。

### 冲突处理

```text
生成短码
  ↓
查询短码是否存在
  ↓
不存在：保存
  ↓
存在且长链接相同：直接返回
  ↓
存在但长链接不同：加盐重新生成
```

---

## 3.3 分布式 ID + Base62

### 实现原理

使用 Snowflake、Redis 自增、号段模式等生成分布式唯一 ID，再转 Base62。

```text
Snowflake ID
  ↓
Base62
  ↓
短码
```

### 优势

- 支持分布式高并发。
- 不容易冲突。
- 性能高。
- 可扩展性好。

### 劣势

- ID 可能较长，短码也会变长。
- Snowflake 依赖机器号和时钟。
- 需要 ID 生成服务稳定。

### 推荐

实际项目中常用：

```text
分布式 ID + Base62
```

## 4. 数据库设计

### 短链映射表

```sql
CREATE TABLE short_url (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    short_code VARCHAR(32) NOT NULL,
    long_url TEXT NOT NULL,
    url_hash VARCHAR(64),
    status TINYINT NOT NULL DEFAULT 1,
    expire_time DATETIME,
    create_time DATETIME,
    update_time DATETIME,
    UNIQUE KEY uk_short_code(short_code),
    KEY idx_url_hash(url_hash)
);
```

### 字段说明

| 字段 | 说明 |
|---|---|
| id | 主键 ID |
| short_code | 短码 |
| long_url | 原始长链接 |
| url_hash | 长链接 Hash，用于防重复 |
| status | 状态：正常、禁用、删除 |
| expire_time | 过期时间 |
| create_time | 创建时间 |
| update_time | 更新时间 |

## 5. 缓存设计

短链跳转是高频读场景，需要使用 Redis 缓存。

### 缓存 Key

```text
short:url:{shortCode}
```

### 缓存 Value

```text
longUrl
expireTime
status
```

### 查询流程

```text
访问短链
  ↓
查 Redis
  ↓
命中：直接跳转
  ↓
未命中：查 DB
  ↓
DB 存在：写入 Redis
  ↓
DB 不存在：缓存空值，防止穿透
```

---

## 6. 重定向选择

短链跳转一般使用：

```text
302 临时重定向
```

原因：

```text
302 每次都会请求短链服务，方便做访问统计。
```

如果使用：

```text
301 永久重定向
```

浏览器可能缓存跳转结果，后续不再请求短链服务，不利于统计和变更。

---

## 7. 高并发优化

### 读多写少

短链服务典型特点：

```text
生成短链少
访问短链多
```

优化重点在跳转链路。

### 优化方式

- Redis 缓存短码映射。
- 热点短链本地缓存。
- 数据库读写分离。
- 短链表分库分表。
- 访问日志异步写入 MQ。
- 跳转接口尽量轻量。
- 使用 CDN / 边缘节点加速。

---

## 8. 防止缓存穿透

如果用户大量访问不存在的短码，会打到数据库。

解决方案：

```text
缓存空值
布隆过滤器
接口限流
黑名单
```

空值缓存：

```text
short:url:xxx = NULL
TTL = 1~5 分钟
```

---

## 9. 访问统计设计

短链访问时可以记录：

| 指标 | 说明 |
|---|---|
| PV | 总访问次数 |
| UV | 独立用户数 |
| IP | 访问 IP |
| User-Agent | 浏览器、设备信息 |
| Referer | 来源页面 |
| 地域 | 根据 IP 解析 |
| 时间 | 访问时间 |
| shortCode | 短码 |

### 推荐方式

不要在跳转链路同步写数据库。

推荐：

```text
访问短链
  ↓
快速重定向
  ↓
异步发送访问日志到 MQ
  ↓
消费端统计 PV、UV、来源、地域
```

---

## 10. 安全和风控

需要防止短链被用于恶意跳转。

常见措施：

- 长链接域名白名单 / 黑名单。
- 校验 URL 格式。
- 禁止跳转钓鱼、违法、恶意域名。
- 生成接口限流。
- 同一用户生成数量限制。
- 短链访问频率限制。
- 后台支持禁用短链。
- 接入安全扫描。

## 11. 分库分表设计

如果短链数据量很大，可以按 `short_code` 或 `id` 分片。

### 按 short_code Hash 分库分表

```text
hash(short_code) % 分片数
```

### 按 id 分片

```text
id % 分片数
```

### 注意

短链跳转时只有 `short_code`，所以推荐：

```text
按 short_code 分片
```

这样查询时可以直接定位分片。

## 13. 常见问题

### 1. 短码冲突怎么办？

```text
唯一索引兜底
冲突后重新生成
加盐重试
限制最大重试次数
```

---

### 2. 相同长链接是否生成同一个短链？

看业务。

如果希望节省存储：

```text
根据 long_url_hash 查询，已存在则返回旧短链
```

如果需要区分渠道、用户、活动：

```text
即使长链接相同，也生成不同短链
```

---

### 3. 为什么用 302？

```text
302 可以让每次访问都经过短链服务，方便统计和风控。
```

---

### 4. 短链过期如何处理？

访问时判断：

```text
expire_time < now()
  ↓
返回 404 或过期页面
```

也可以定时清理过期数据。

## 14. 推荐架构

```text
客户端
  ↓
短链服务
  ↓
Redis 缓存
  ↓
数据库
  ↓
MQ
  ↓
统计服务
```

生成链路：

```text
长链接
  ↓
生成 shortCode
  ↓
写 DB
  ↓
写 Redis
  ↓
返回短链
```

访问链路：

```text
短链访问
  ↓
查 Redis
  ↓
查 DB
  ↓
异步记录访问日志
  ↓
302 跳转长链接
```

## 15. 总结

短链服务核心是长链接和短码之间的映射。生成短链时，可以使用分布式 ID 加 Base62 编码生成短码，也可以使用 Hash 算法生成短码，但 Hash 方案需要处理冲突。

访问短链时，根据短码查询长链接，优先查 Redis，缓存未命中再查数据库，然后通过 302 重定向到原始长链接。之所以使用 302，是为了让每次访问都经过短链服务，方便做访问统计和风控。

系统设计上，要考虑短码唯一性、缓存穿透、热点短链、高并发跳转、访问统计、短链过期、恶意链接风控、分库分表和高可用。

一句话总结：

```text
短链服务 = 短码生成 + 长短链映射 + Redis 缓存 + 302 跳转 + 访问统计 + 风控限流。
```
