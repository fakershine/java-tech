# 一、什么是多租户系统

## 1. 多租户是什么？

多租户英文是：

```text
Multi-Tenant
```

多租户系统是指：

> 一套系统同时服务多个客户或组织，每个客户叫一个租户，不同租户之间共享系统能力，但数据和权限相互隔离。

例如一个 SaaS 系统：

```text
A 公司使用这套系统
B 公司也使用这套系统
C 公司也使用这套系统
```

它们访问的是同一套应用，但各自只能看到自己的数据。

---

## 2. 租户是什么？

租户可以理解为：

```text
一个公司
一个学校
一个门店
一个机构
一个组织
一个客户
一个业务方
```

例如：

```text
tenant_id = 1001 代表 A 公司
tenant_id = 1002 代表 B 公司
tenant_id = 1003 代表 C 公司
```

---

## 3. 多租户系统例子

常见多租户系统：

```text
SaaS CRM 系统
企业培训系统
智慧零售系统
连锁门店系统
低代码平台
在线教育平台
OA 系统
ERP 系统
权限管理平台
```

---

## 4. 多租户系统核心特点

```text
1. 多个租户共用一套系统
2. 租户之间数据隔离
3. 租户之间权限隔离
4. 租户可以有独立配置
5. 租户可以有独立套餐
6. 租户可以有独立资源限制
7. 系统需要支持租户扩容和迁移
```

---

# 二、多租户系统适用场景

## 1. 适合多租户的场景

多租户适合：

```text
1. SaaS 平台
2. 多企业共用系统
3. 多门店共用系统
4. 多机构共用系统
5. 多客户共用后台
6. 业务模型相似但数据要隔离的系统
```

---

## 2. 不适合多租户的场景

不适合多租户的场景：

```text
1. 每个客户业务差异极大
2. 每个客户都要求完全独立部署
3. 数据安全隔离要求极高
4. 客户之间完全不能共享基础设施
5. 单个客户数据量特别大，适合独立系统
```

---

## 3. 多租户带来的价值

```text
1. 降低部署成本
2. 降低运维成本
3. 方便统一升级
4. 方便统一监控
5. 提升资源利用率
6. 支持标准化 SaaS 交付
```

---

## 4. 多租户带来的复杂度

```text
1. 数据隔离复杂
2. 权限控制复杂
3. 缓存隔离复杂
4. 配置隔离复杂
5. 定制化需求复杂

7. 大租户和小租户资源隔离复杂
```

# 三、多租户系统核心目标

设计多租户系统，核心目标包括：

```text
1. 数据隔离
2. 权限隔离
3. 配置隔离
4. 缓存隔离
5. 文件隔离
6. 消息隔离
7. 资源隔离
8. 可扩展
9. 可迁移
10. 可运维
```

---

## 1. 数据隔离

不同租户之间不能查询、修改、删除彼此的数据。

例如：

```text
A 公司用户不能看到 B 公司订单
A 门店不能操作 B 门店库存
```

---

## 2. 权限隔离

不同租户有自己的用户、角色、菜单、按钮、数据权限。

例如：

```text
A 公司管理员只能管理 A 公司用户
B 公司管理员只能管理 B 公司用户
```

---

## 3. 配置隔离

不同租户可以有不同配置：

```text
系统名称
Logo
主题色
短信模板
审批流程
功能开关
套餐能力
数据保留时间
```

---

## 4. 资源隔离

不同租户可以有不同资源限制：

```text
用户数量限制
存储空间限制
接口 QPS 限制
订单数量限制
文件上传大小限制
并发任务限制
```

# 四、多租户系统常见架构模式

多租户数据库隔离通常有三种模式：

```text
1. 共享库共享表
2. 共享库独立表
3. 独立库
```

也可以组合使用：

```text
普通租户使用共享库共享表
大客户使用独立库
敏感客户使用独立部署
```

---

# 五、共享库共享表模式

## 1. 什么是共享库共享表？

所有租户共用同一个数据库、同一套表，通过 `tenant_id` 区分数据。

例如订单表：

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    order_no VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    status TINYINT NOT NULL,
    create_time DATETIME NOT NULL,
    INDEX idx_tenant_order_no(tenant_id, order_no),
    INDEX idx_tenant_user(tenant_id, user_id)
);
```

数据示例：

| id | tenant_id | order_no | amount |
|---|---|---|---|
| 1 | 1001 | O001 | 99.00 |
| 2 | 1002 | O002 | 188.00 |
| 3 | 1001 | O003 | 66.00 |

---

## 2. 查询方式

所有业务查询都要带上 `tenant_id`：

```sql
SELECT *
FROM orders
WHERE tenant_id = 1001
  AND order_no = 'O001';
```

---

## 3. 优点

```text
1. 成本最低
2. 资源利用率高
3. 开发和部署相对简单
4. 租户开通快
5. 统一升级方便
6. 适合中小租户数量多的 SaaS 系统
```

---

## 4. 缺点

```text
1. 数据隔离弱，依赖 tenant_id
2. SQL 漏加 tenant_id 风险大
3. 大租户可能影响小租户
4. 单表数据量增长快
5. 后期迁移独立库有成本
6. 安全合规要求高的客户可能不接受
```

---

## 5. 适用场景

```text
中小 SaaS 系统
租户数量多
单租户数据量不大
客户隔离要求不是极端严格
希望降低成本和运维复杂度
```

---

# 六、共享库独立表模式

## 1. 什么是共享库独立表？

所有租户共用一个数据库，但每个租户有独立的数据表。

例如：

```text
orders_1001
orders_1002
orders_1003
```

或者：

```text
tenant_1001_orders
tenant_1002_orders
```

---

## 2. 示例

租户 1001 的订单表：

```sql
CREATE TABLE orders_1001 (
    id BIGINT PRIMARY KEY,
    order_no VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    status TINYINT NOT NULL,
    create_time DATETIME NOT NULL
);
```

租户 1002 的订单表：

```sql
CREATE TABLE orders_1002 (
    id BIGINT PRIMARY KEY,
    order_no VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    status TINYINT NOT NULL,
    create_time DATETIME NOT NULL
);
```

---

## 3. 优点

```text
1. 数据隔离比共享表更强
2. 单表数据量相对可控
3. 某个租户表可以单独维护
4. 大租户可以单独优化表结构或索引
```

---

## 4. 缺点

```text
1. 表数量会快速膨胀
2. DDL 变更复杂
3. SQL 动态表名复杂
4. 维护成本高
5. 跨租户统计复杂
6. 不适合租户数量特别多的系统
```

---

## 5. 适用场景

```text
租户数量有限
单租户数据量较大
希望比共享表更强隔离
但又不想每个租户单独建库
```

---

# 七、独立库模式

## 1. 什么是独立库？

每个租户使用独立数据库。

例如：

```text
tenant_1001_db
tenant_1002_db
tenant_1003_db
```

---

## 2. 示例

租户路由表：

```sql
CREATE TABLE tenant_datasource (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    db_name VARCHAR(128) NOT NULL,
    jdbc_url VARCHAR(512) NOT NULL,
    username VARCHAR(128) NOT NULL,
    password VARCHAR(256) NOT NULL,
    status TINYINT NOT NULL,
    create_time DATETIME NOT NULL,
    UNIQUE KEY uk_tenant_id(tenant_id)
);
```

---

## 3. 优点

```text
1. 数据隔离最强
2. 单租户数据备份恢复方便
3. 单租户迁移方便
4. 大客户可以独立扩容
5. 满足更高安全合规要求
6. 某个租户故障影响面更小
```

---

## 4. 缺点

```text
1. 成本最高
2. 数据源管理复杂
3. 租户开通复杂
4. 连接池数量多
5. 运维复杂度高
6. 统一升级和 DDL 管理复杂
7. 跨租户统计困难
```

---

## 5. 适用场景

```text
大客户
数据量大
安全隔离要求高
客户要求独立备份恢复
金融、政企、医疗等合规要求较高场景
```

---

# 八、三种模式对比

| 模式 | 隔离级别 | 成本 | 扩展性 | 运维复杂度 | 适合场景 |
|---|---|---|---|---|---|
| 共享库共享表 | 低 | 低 | 一般 | 低 | 中小租户 SaaS |
| 共享库独立表 | 中 | 中 | 一般 | 中高 | 租户数量有限，单租户数据较大 |
| 独立库 | 高 | 高 | 好 | 高 | 大客户、高安全、高隔离要求 |

---

## 1. 推荐选择

常见推荐：

```text
初期或中小租户：共享库共享表
租户数量不多但数据较大：共享库独立表
大客户或高安全要求：独立库
```

---

## 2. 混合模式

实际项目中经常使用混合模式：

```text
普通租户：共享库共享表
大租户：独立库
政企客户：独立部署
历史大数据：归档库
```

这种方式兼顾：

```text
成本
性能
隔离性
可扩展性
```

# 九、租户识别怎么做

## 1. 常见租户识别方式

租户识别可以通过：

```text
1. 域名识别
2. 请求头识别
3. Token 识别
4. URL 路径识别
5. 登录用户识别
6. API Key 识别
```

---

## 2. 域名识别

不同租户使用不同子域名：

```text
a.example.com -> tenant_id = 1001
b.example.com -> tenant_id = 1002
```

优点：

```text
用户体验好
品牌隔离强
适合 SaaS
```

缺点：

```text
域名和证书管理复杂
```

---

## 3. 请求头识别

前端在请求头中携带租户标识：

```http
X-Tenant-Id: 1001
```

优点：

```text
实现简单
适合内部系统和微服务调用
```

缺点：

```text
不能完全信任前端传入，后端必须校验权限
```

---

## 4. Token 识别

登录成功后，Token 中包含租户信息：

```json
{
  "userId": 1,
  "tenantId": 1001,
  "roles": ["admin"]
}
```

后端解析 Token 获取 `tenant_id`。

优点：

```text
安全性更好
适合前后端分离系统
```

---

## 5. URL 路径识别

请求路径中包含租户：

```text
/api/{tenantCode}/orders
```

例如：

```text
/api/company-a/orders
```

优点：

```text
直观
便于路由
```

缺点：

```text
URL 设计稍复杂
```

---

## 6. 推荐方案

推荐组合：

```text
登录阶段：根据域名、租户编码或账号识别租户
登录成功：Token 中写入 tenantId
请求阶段：网关解析 Token，生成租户上下文
服务内部：从租户上下文中获取 tenantId
```

# 十、租户上下文如何传递

## 1. 什么是租户上下文？

租户上下文用于保存当前请求所属租户。

例如：

```text
tenantId
tenantCode
userId
roleIds
dataScope
```

---

## 2. 使用 ThreadLocal 保存租户上下文

```java
public class TenantContextHolder {

    private static final ThreadLocal<Long> TENANT_CONTEXT = new ThreadLocal<>();

    public static void setTenantId(Long tenantId) {
        TENANT_CONTEXT.set(tenantId);
    }

    public static Long getTenantId() {
        return TENANT_CONTEXT.get();
    }

    public static void clear() {
        TENANT_CONTEXT.remove();
    }
}
```

---

## 3. 在过滤器中设置租户上下文

```java
public class TenantFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request,
                         ServletResponse response,
                         FilterChain chain) {
        try {
            HttpServletRequest httpRequest = (HttpServletRequest) request;
            String tenantId = httpRequest.getHeader("X-Tenant-Id");

            if (tenantId != null) {
                TenantContextHolder.setTenantId(Long.valueOf(tenantId));
            }

            chain.doFilter(request, response);
        } finally {
            TenantContextHolder.clear();
        }
    }
}
```

---

## 4. 为什么必须 clear？

如果使用线程池处理请求，线程会被复用。

如果不清理 ThreadLocal，可能导致：

```text
租户上下文串租户
A 租户请求结束后，线程被 B 租户复用
B 租户可能拿到 A 租户 tenantId
```

所以必须在 `finally` 中清理。

---

## 5. 微服务调用如何传递租户？

服务间调用时，需要把租户信息透传。

例如 Feign 拦截器：

```java
@Component
public class TenantFeignInterceptor implements RequestInterceptor {

    @Override
    public void apply(RequestTemplate template) {
        Long tenantId = TenantContextHolder.getTenantId();
        if (tenantId != null) {
            template.header("X-Tenant-Id", String.valueOf(tenantId));
        }
    }
}
```

---

## 6. 异步线程如何传递租户？

异步线程不会自动继承 ThreadLocal。

需要：

```text
1. 手动传递 tenantId
2. 使用任务包装器 TaskDecorator
3. 使用 TransmittableThreadLocal
```

示例：

```java
public class TenantTaskDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable runnable) {
        Long tenantId = TenantContextHolder.getTenantId();

        return () -> {
            try {
                TenantContextHolder.setTenantId(tenantId);
                runnable.run();
            } finally {
                TenantContextHolder.clear();
            }
        };
    }
}
```

# 十一、数据库表如何设计

## 1. 租户主表

```sql
CREATE TABLE tenant (
    id BIGINT PRIMARY KEY,
    tenant_code VARCHAR(64) NOT NULL,
    tenant_name VARCHAR(128) NOT NULL,
    status TINYINT NOT NULL,
    expire_time DATETIME DEFAULT NULL,
    create_time DATETIME NOT NULL,
    update_time DATETIME NOT NULL,
    UNIQUE KEY uk_tenant_code(tenant_code)
);
```

---

## 2. 业务表增加 tenant_id

例如订单表：

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    order_no VARCHAR(64) NOT NULL,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2) NOT NULL,
    status TINYINT NOT NULL,
    create_time DATETIME NOT NULL,
    update_time DATETIME NOT NULL,
    UNIQUE KEY uk_tenant_order_no(tenant_id, order_no),
    INDEX idx_tenant_user_time(tenant_id, user_id, create_time)
);
```

---

## 3. 为什么唯一索引要带 tenant_id？

如果订单号只在租户内唯一，那么唯一索引应该是：

```sql
UNIQUE KEY uk_tenant_order_no(tenant_id, order_no)
```

而不是：

```sql
UNIQUE KEY uk_order_no(order_no)
```

否则不同租户不能使用相同业务编号。

---

## 4. 索引设计原则

多租户共享表下，索引通常要把 `tenant_id` 放在前面：

```sql
INDEX idx_tenant_status_time(tenant_id, status, create_time)
INDEX idx_tenant_user_time(tenant_id, user_id, create_time)
INDEX idx_tenant_order_no(tenant_id, order_no)
```

原因：

```text
几乎所有查询都要按 tenant_id 过滤。
```

---

## 5. 公共表是否需要 tenant_id？

不一定。

例如：

```text
省市区字典
国家编码
系统枚举
公共配置
行业分类
```

这些全局共享表可以不加 `tenant_id`。

但租户私有数据必须加。

---

## 6. 字段设计建议

```text
1. 所有租户数据表必须有 tenant_id
2. tenant_id 建议 NOT NULL
3. 查询索引尽量包含 tenant_id
4. 唯一约束要考虑租户维度
5. 禁止直接根据 id 更新敏感数据，最好带 tenant_id
6. 公共表需要明确标识为全局表
```

# 十二、MyBatis / MyBatis-Plus 如何实现租户隔离

## 1. 核心思路

在 SQL 执行前，自动追加租户条件：

```sql
WHERE tenant_id = 当前租户ID
```

例如原 SQL：

```sql
SELECT * FROM orders WHERE status = 1;
```

自动改写为：

```sql
SELECT *
FROM orders
WHERE status = 1
  AND tenant_id = 1001;
```

---

## 2. MyBatis-Plus 多租户插件

MyBatis-Plus 提供租户插件，可以自动拼接 `tenant_id` 条件。

示例：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();

    TenantLineInnerInterceptor tenantInterceptor =
            new TenantLineInnerInterceptor(new TenantLineHandler() {

                @Override
                public Expression getTenantId() {
                    Long tenantId = TenantContextHolder.getTenantId();
                    return new LongValue(tenantId);
                }

                @Override
                public String getTenantIdColumn() {
                    return "tenant_id";
                }

                @Override
                public boolean ignoreTable(String tableName) {
                    return "tenant".equals(tableName)
                            || "sys_dict".equals(tableName);
                }
            });

    interceptor.addInnerInterceptor(tenantInterceptor);
    return interceptor;
}
```

---

## 3. 忽略公共表

公共表不需要拼接租户条件：

```java
@Override
public boolean ignoreTable(String tableName) {
    return "sys_dict".equals(tableName)
            || "area_code".equals(tableName)
            || "tenant".equals(tableName);
}
```

---

## 4. 更新和删除也要隔离

不仅查询需要租户隔离，更新和删除也必须隔离。

例如：

```sql
UPDATE orders
SET status = 2
WHERE id = 1
  AND tenant_id = 1001;
```

否则可能误更新其他租户数据。

---

## 5. 手写 SQL 注意事项

手写复杂 SQL 时要注意：

```text
1. 是否被租户插件正确处理
2. 子查询是否加了 tenant_id
3. JOIN 表是否加了 tenant_id
4. 批量更新是否带 tenant_id
5. 公共表是否被误加 tenant_id
```

# 十四、缓存如何做租户隔离

## 1. 为什么缓存也要租户隔离？

如果缓存 key 没有租户维度，可能出现串数据。

错误示例：

```text
user:1
```

如果 A 租户和 B 租户都有 userId = 1，就会冲突。

---

## 2. 正确缓存 key 设计

缓存 key 必须带 `tenant_id`：

```text
tenant:{tenantId}:user:{userId}
tenant:{tenantId}:order:{orderId}
tenant:{tenantId}:config:{configKey}
```

示例：

```text
tenant:1001:user:1
tenant:1002:user:1
```

---

## 3. 缓存工具类统一封装

建议统一封装 key 生成工具：

```java
public class CacheKeyBuilder {

    public static String tenantKey(String bizKey) {
        Long tenantId = TenantContextHolder.getTenantId();
        return "tenant:" + tenantId + ":" + bizKey;
    }

    public static String userKey(Long userId) {
        return tenantKey("user:" + userId);
    }

    public static String orderKey(Long orderId) {
        return tenantKey("order:" + orderId);
    }
}
```

---

## 4. Redis 数据结构设计

```text
tenant:1001:user:1
tenant:1001:order:10001
tenant:1001:permission:user:1
tenant:1001:config:theme
tenant:1001:rate-limit:/order/create
```

---

## 5. 注意事项

```text
1. 缓存 key 必须带 tenant_id
2. 分布式锁 key 也必须带 tenant_id
3. 限流 key 也要带 tenant_id
4. 幂等 key 也要带 tenant_id
5. 公共缓存要明确标记 global
```

公共缓存示例：

```text
global:dict:gender
global:area:china
```

# 十七、消息队列如何做租户隔离

## 1. MQ 为什么要考虑租户？

消息中如果没有租户信息，消费者处理时可能不知道数据属于哪个租户。

可能导致：

```text
消费时 tenant_id 丢失
写入错误租户数据
缓存 key 错误
权限上下文丢失
```

---

## 2. 消息体携带 tenant_id

消息体中必须包含：

```json
{
  "tenantId": 1001,
  "messageId": "xxx",
  "bizType": "ORDER_CREATED",
  "data": {
    "orderId": 123
  }
}
```

---

## 3. 消费时设置租户上下文

```java
public void consume(OrderMessage message) {
    try {
        TenantContextHolder.setTenantId(message.getTenantId());

        // 执行业务逻辑
        orderService.handle(message);
    } finally {
        TenantContextHolder.clear();
    }
}
```

---

## 4. Topic 是否按租户拆分？

一般不建议每个租户一个 Topic。

推荐：

```text
按业务拆 Topic，消息体携带 tenant_id
```

例如：

```text
order-created-topic
payment-success-topic
```

只有大租户或强隔离场景才考虑：

```text
tenant-1001-order-topic
```

---

## 5. 消费幂等

消费记录也要带租户：

```sql
CREATE TABLE mq_consume_log (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    message_id VARCHAR(128) NOT NULL,

    create_time DATETIME NOT NULL,

```

# 十八、定时任务如何做租户隔离

## 1. 定时任务问题

多租户系统中，定时任务可能需要处理所有租户数据。

例如：

```text
订单超时关闭
套餐到期提醒
账单生成
数据归档
报表统计
```

---

## 2. 推荐处理方式

```text
1. 查询有效租户列表
2. 逐个租户设置上下文
3. 按租户执行任务
4. 每个租户独立记录执行结果
5. 失败不影响其他租户
```

---

## 3. 示例代码

```java
public void executeTask() {
    List<Tenant> tenants = tenantService.listActiveTenants();

    for (Tenant tenant : tenants) {
        try {
            TenantContextHolder.setTenantId(tenant.getId());

            // 执行当前租户任务
            orderService.closeTimeoutOrders();
        } catch (Exception e) {
            log.error("租户任务执行失败，tenantId={}", tenant.getId(), e);
        } finally {
            TenantContextHolder.clear();
        }
    }
}
```

---

## 4. 注意事项

```text
1. 一个租户失败不能影响其他租户
2. 任务日志要记录 tenant_id
3. 大租户可以单独拆任务
4. 避免单次任务扫描所有租户大数据
5. 支持分片执行
6. 支持任务重试
```

# 二十、租户数据安全如何保证

## 1. 数据安全风险

多租户系统最大风险是：

```text
串租户
越权访问
缓存串数据
消息消费丢失租户上下文
SQL 漏加 tenant_id
导出数据越权
文件访问越权
```

---

## 2. 防护措施

```text
1. 所有租户数据表增加 tenant_id
2. SQL 自动拼接 tenant_id
3. 更新和删除必须带 tenant_id
4. 缓存 key 必须带 tenant_id
5. 文件路径必须带 tenant_id
6. 消息体必须带 tenant_id
7. 租户上下文必须 finally 清理
8. 权限校验必须包含租户校验
9. 数据导出必须限制租户范围
10. 关键操作记录审计日志
```

---

## 3. 防止 SQL 漏租户

措施：

```text
1. 使用 MyBatis-Plus 多租户插件
2. 代码 Review 检查 tenant_id
3. SQL 审计
4. 单元测试覆盖
5. 禁止绕过租户插件直接查库
6. 敏感接口强制校验 tenant_id
```

---

## 4. 防止缓存串租户

错误：

```text
user:1
```

正确：

```text
tenant:1001:user:1
```

---

## 5. 防止 ThreadLocal 串租户

必须：

```java
try {
    TenantContextHolder.setTenantId(tenantId);
    // business
} finally {
    TenantContextHolder.clear();
}
```

# 二十四、完整面试回答模板

多租户系统是指一套系统同时服务多个客户或组织，每个客户就是一个租户。不同租户之间共享系统能力，但数据、权限、配置和资源要相互隔离。常见场景包括 SaaS 系统、企业培训平台、智慧零售系统、连锁门店系统和 OA/ERP 系统。

多租户系统最核心的是租户隔离，包括数据隔离、权限隔离、缓存隔离、配置隔离、文件隔离和消息隔离。数据库层面常见有三种设计模式：第一种是共享库共享表，所有租户共用同一套表，通过 `tenant_id` 区分数据，成本低、扩展快，但隔离性相对弱；第二种是共享库独立表，每个租户一套表，隔离性更好，但表数量多，DDL 和运维复杂；第三种是独立库，每个租户一个数据库，隔离性最强，适合大客户或高安全要求客户，但成本和运维复杂度最高。

实际项目中我更推荐混合模式。普通中小租户使用共享库共享表，大租户或数据量特别大的租户可以迁移到独立库，高安全要求客户可以独立部署。这样可以在成本、性能和隔离性之间取得平衡。

在共享库共享表模式下，所有租户私有业务表都需要增加 `tenant_id` 字段。查询、更新、删除时都必须带上 `tenant_id`。唯一索引也要考虑租户维度，例如订单号如果只要求租户内唯一，就应该建立 `(tenant_id, order_no)` 唯一索引。查询索引通常也会把 `tenant_id` 放在前面，例如 `(tenant_id, user_id, create_time)`。

租户识别可以通过域名、请求头、Token、URL 路径或 API Key 实现。比较常见的做法是登录时识别租户，登录成功后在 Token 中写入 `tenantId`。后续请求进入网关后，网关解析 Token，获取 `tenantId`，并通过请求头传递给下游服务。服务内部使用 ThreadLocal 保存租户上下文，但请求结束后必须在 `finally` 中清理，防止线程复用导致串租户。

SQL 层面可以通过 MyBatis 或 MyBatis-Plus 多租户插件实现自动隔离。插件会在执行 SQL 前自动追加 `tenant_id = 当前租户ID` 条件，避免开发人员手写 SQL 时遗漏租户条件。公共表，比如字典表、省市区表，可以配置为忽略租户插件。需要注意的是，不仅查询要做租户隔离，更新和删除也必须带租户条件。

缓存层面也必须做租户隔离。Redis key 不能只写 `user:1`，因为不同租户可能都有相同的 userId。正确做法是统一封装缓存 key，例如 `tenant:1001:user:1`、`tenant:1001:order:10001`。分布式锁、接口限流、幂等 key 也都要带租户维度。

消息队列也要携带租户信息。生产者发送消息时，消息体中必须包含 `tenantId`。消费者消费消息时，先把消息中的 `tenantId` 设置到租户上下文中，再执行业务逻辑，最后在 `finally` 中清理上下文。消费幂等表也要带 `tenant_id`，例如对 `(tenant_id, message_id, consumer_group)` 建唯一索引。

权限方面，一般采用 RBAC 模型，也就是租户、用户、角色、权限。平台管理员可以管理所有租户，租户管理员只能管理自己租户内的用户、角色和业务数据。接口权限、菜单权限、按钮权限和数据权限都要结合 `tenant_id` 判断，不能只判断用户角色。

配置方面，不同租户可以有不同的系统名称、Logo、主题色、短信模板、套餐能力、限流阈值和功能开关。配置读取时可以先查租户级配置，如果没有则读取系统默认配置。租户配置可以缓存到 Redis，缓存 key 中也要包含 `tenant_id`。

文件存储方面，文件路径要按租户隔离，例如 `tenant/1001/avatar/xxx.png`、`tenant/1001/order/xxx.pdf`。下载文件时必须校验当前用户所属租户和文件所属租户是否一致，避免越权访问。

多租户系统最容易出问题的是串租户。常见原因包括 SQL 漏加 `tenant_id`、缓存 key 没带租户、ThreadLocal 没清理、MQ 消费没有设置租户上下文、文件下载没有校验租户。解决办法是统一租户上下文、统一 SQL 拦截、统一缓存 key 规范、统一消息格式，并通过代码 Review、测试用例和监控审计来兜底。

如果某个租户数据量变大或者访问量过高，可以考虑把该租户从共享表迁移到独立库。迁移流程一般是创建独立库、初始化表结构、全量同步租户历史数据、增量同步迁移期间变更数据、校验一致性、灰度切流、更新租户路由配置，最后观察稳定后清理旧数据。

总体来说，多租户系统设计的关键是：租户识别准确、租户上下文传递完整、数据隔离可靠、缓存和消息不串租户、权限控制到位，并且预留大租户迁移和独立部署能力。
